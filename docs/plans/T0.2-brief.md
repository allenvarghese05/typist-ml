## 2. Why it matters

What T0.2 enables later:
- Every frontend task builds on this scaffold: T1.3 TextCursor, T1.4 KeystrokeRecorder, T1.5
  TypingSurface, T1.6 EventBuffer, T1.10 bigram matrix page, T2.9 admin page, T4.2 dashboard,
  T4.5 debrief page.
- T1.3's acceptance ("All fixture outcomes match") runs in Vitest against
  `services/api/tests/fixtures/golden_session.json`, a file outside `apps/web`. The Vitest and
  TypeScript setup chosen here decides how easily that file can be read.
- T1.4 needs "Tests with synthetic KeyboardEvents cover repeat, modifiers, overlapping keys".
  That requires a DOM-capable test environment in Vitest.
- T0.4 (CI) needs a web app that installs from a committed lockfile and passes lint, format, types
  and tests on Linux. `main`'s ruleset requires a status check named exactly `web`.
- M0 done-when ("just dev runs web, API and worker") needs `pnpm run dev` to work in `apps/web`.
- D21 (`just check`) starts checking real web code for the first time. From now on every PR's
  gate includes Biome lint, Biome format, `tsc -b` and Vitest for `apps/web`.

What breaks if it is wrong:
- If the scaffold does not meet the justfile contracts (section 4), `just lint`, `format-check`,
  `types`, `test`, `check` and `dev` fail for every later task, and the acceptance criterion fails.
- If TypeScript strictness is weaker than section 17.1 requires, it is expensive to tighten later
  (every file then needs fixes), and telemetry code (section 12, "the most correctness-sensitive
  part of the project") gets written without those checks.
- If `just check` (Biome lint + format) and the pre-commit hook (`biome check --write`) disagree,
  code that passes the local hook fails the gate, or the reverse (see Risks).
- If the scaffold only works on macOS (for example native binaries or path-case issues), T0.4 CI
  on Linux fails.
- If versions are not pinned in the lockfile, section 18's "Library changes mid-project /
  Behaviour drift" risk applies to the frontend telemetry during the pilot.

## 6. Constraints

- **Acceptance is literal:** `just test` runs one passing web test. It runs
  `cd apps/web && pnpm exec vitest run`. `vitest run` exits non-zero when it finds no test files
  (verify for the installed version), so at least one test must be picked up by the default or
  configured include pattern.
- **D21 gate must stay green:** `just check` must pass after T0.2 with services/api skipped. That
  means the whole scaffold (template files, configs, JSON) must pass `biome lint .`,
  `biome format .` (check mode) and `tsc -b` as well as Vitest.
- **Justfile contracts:** `@biomejs/biome`, `typescript`, `vitest` as dev dependencies (so
  `pnpm exec` finds `biome`, `tsc`, `vitest`); a `dev` script; `noEmit` in the tsconfig files.
- **Lockfile location:** `apps/web/pnpm-lock.yaml` (README, pre-commit config comment,
  cloud-setup.sh `cd apps/web && pnpm install`). A root-level pnpm workspace would move the
  lockfile to the repo root and contradict all three.
- **Versions:** Node v22.22.2 and pnpm 12.6.0 are the recorded versions. Vite 8 requires a recent
  Node 20 or 22 minor (Node 20.19+ or 22.12+, verify); v22.22.2 is above that. Section 19.1:
  "Vite 8 (March 2026) replaced esbuild and Rollup with the Rust-based Rolldown bundler;
  @vitejs/plugin-react v6 no longer needs Babel." Section 5.1: "Tailwind CSS v4".
- **Platforms:** Development on macOS arm64 (M1 Pro). CI (T0.4) and cloud sessions run on Linux
  x64. Rolldown, Biome, Tailwind v4's engine and Lightning CSS ship platform-specific native
  binaries as optional dependencies (verify). One lockfile must install on both platforms.
- **No mlx involvement:** the web app never talks to the model (section 6.1: the typing surface
  must not "talk to the model"). No platform marker is needed on the web side.
- **Local only:** no CDN assets, remote fonts, analytics or telemetry (D19, CLAUDE.md). Dev
  server for one machine (D06). API origin `http://127.0.0.1:8000/api/v1` (section 14).
- **No GPL or Monkeytype code** (CLAUDE.md).
- **TypeScript:** section 17.1 "strict: true, no any without a comment explaining why". TypeScript
  `strict` does not forbid an explicit `any`; only a lint rule can enforce the "comment" part.
- **Workflow:** branch `t0-2-web-scaffold` (dash form, T0.1 owner answer 15). Conventional commits.
  One task per PR. `just check` before pushing. Owner merges T0.1 to T0.3 as admin because the
  `web` and `api` required checks do not exist until T0.4 (T0.1 owner answer 14).
- **Golden fixture:** `services/api/tests/fixtures/golden_session.json` must never be rewritten by
  any tool (T0.1 owner answer 10; `.pre-commit-config.yaml` global `exclude`).
- **Frontend rules that later tasks must be able to meet (section 12):** "no React state updates
  inside [the handler], no allocation-heavy work, no network calls. Rendering happens through the
  external store." Section 9.2: "React subscribes to it with useSyncExternalStore". Section 6.1:
  KeystrokeRecorder must not "Depend on React; it is a plain class so it can be unit tested".
- **Typing surface rules (11.3), later:** "monospace font, the whole block visible, one character
  per keystroke, wrong characters shown in red ..., no autocorrect or spellcheck, and the block
  pauses if the window loses focus."
- **Sandbox:** the orchestrator's hard rule is that sandbox restrictions are never disabled. If
  `pnpm install` is blocked, the builder must stop and report.

## 7. Edge cases

1. **Registry access blocked in the sandbox.** `pnpm install` needs the npm registry. Example: the
   builder runs `pnpm install` and gets a network error such as `ERR_PNPM_META_FETCH_FAIL`.
   Without network the scaffold cannot be created, and the lockfile cannot be generated.
2. **pnpm store outside the worktree.** pnpm keeps a global content-addressable store (on macOS
   usually under `~/Library/pnpm/store`, verify) and hard-links from it. A sandbox that only
   allows writes inside the worktree may block the store write, or pnpm may fall back to copying.
3. **Dependency build scripts blocked.** pnpm 10 and later do not run dependency lifecycle scripts
   unless they are explicitly allowed (verify for pnpm 12.6.0). Example: a package that needs a
   postinstall step installs "successfully" but fails at runtime, or pnpm prints an "ignored build
   scripts" warning (or error) that the builder must answer.
4. **pnpm version drift.** The Mac has pnpm 12.6.0. `scripts/cloud-setup.sh` runs
   `npm install -g pnpm` with no version, and CI (T0.4) will pick its own. A different pnpm major
   can rewrite `pnpm-lock.yaml` (different `lockfileVersion`) or refuse a frozen install. If a
   `packageManager` field is present in `package.json`, recent pnpm versions may switch themselves
   to that version (verify).
5. **Native optional dependencies across platforms.** The lockfile created on macOS arm64 must
   also install the Linux x64 binaries for Rolldown, Biome, Tailwind's engine and Lightning CSS.
   Example: CI fails with "Cannot find native binding" or "Cannot find module
   '@rolldown/binding-linux-x64-gnu'" if the lockfile or install settings leave them out.
6. **Case-sensitive file systems.** macOS is case-insensitive by default; Linux is not. Example:
   `import App from "./app"` works on the Mac against `App.tsx` and fails in CI.
7. **Biome defaults vs template style.** Biome's default formatter uses tab indentation and double
   quotes (verify for the installed version). Vite's React template files are written in another
   style (single quotes and no semicolons in recent templates, verify). Unchanged template files
   will fail `biome format .`, and so `just check`, until they are reformatted or the Biome
   formatter is configured to match. Which style the repo uses is not decided.
8. **Biome lint/format vs check/ci.** `biome lint .` runs linter rules. `biome format .` checks
   formatting only. Import sorting is an "assist" action in Biome 2 (verify), which `biome check`
   and `biome ci` apply but `lint` and `format` do not. Example: a file with unsorted imports
   passes `just check`, then the pre-commit hook (`biome check --write`) reorders it on the next
   commit, producing an unrelated diff. The reverse also happens: a Biome rule configured only
   as an assist is never enforced by `just check` or CI.
9. **TypeScript build-info files.** `tsc -b` writes `.tsbuildinfo` files even with `noEmit`
   (TypeScript 5.6 and later, verify). Their location is set by `tsBuildInfoFile`. If they land
   under `node_modules/`, `.gitignore` covers them. If they land elsewhere (for example
   `apps/web/tsconfig.app.tsbuildinfo`), they show up as untracked files; `.gitignore` has no
   `*.tsbuildinfo` entry.
10. **`noEmit` in every tsconfig.** `tsc -b` follows project references. The justfile contract
    says "tsconfig files set 'noEmit'" (plural). Example: a referenced `tsconfig.node.json`
    without `noEmit` makes `just types` write `vite.config.js` next to `vite.config.ts`.
11. **TypeScript major version.** TypeScript 6.0 and the native TypeScript 7 preview exist in 2026
    (verify). TypeScript 6 changes some defaults and deprecates options (verify). The justfile
    calls `tsc`; if the chosen package ships a differently named binary (for example the native
    preview's `tsgo`), `pnpm exec tsc -b` breaks.
12. **Strictness beyond `strict`.** `strict: true` does not include `noUncheckedIndexedAccess` or
    `exactOptionalPropertyTypes`. Example relevant to T1.3: with `noUncheckedIndexedAccess`,
    `target[index]` has type `string | undefined`, which forces the TextCursor to handle
    out-of-range positions explicitly. Without it, the compiler assumes `string`.
13. **"No any without a comment."** `tsc` allows `let x: any` under `strict`. `noImplicitAny` only
    catches implicit `any`. Biome has a rule against explicit `any` (`noExplicitAny`, verify its
    default severity), and Biome suppression comments require an explanation text (verify). The
    design doc does not say how the rule is enforced.
14. **Zero tests or tests in the wrong place.** Vitest's default include is
    `**/*.{test,spec}.?(c|m)[jt]s?(x)` (verify). Section 7 puts tests in
    `src/telemetry/__tests__/`. A later Playwright file such as `e2e/smoke.spec.ts` would match
    Vitest's default include and be run by `vitest run`, failing because Playwright's `test` is
    not Vitest's.
15. **DOM environment.** Vitest's default environment is `node`. A test that renders a React
    component or constructs a `KeyboardEvent` (T1.4) fails with "document is not defined" or
    "KeyboardEvent is not defined" unless a DOM environment (jsdom or happy-dom) is installed
    and selected.
16. **Reading the golden fixture from Vitest (T1.3).** The file lives at
    `services/api/tests/fixtures/golden_session.json`, i.e. `../../services/api/...` from
    `apps/web`. TypeScript `include`/`rootDir`, JSON module imports and Vite's file-system
    restrictions all have rules about files outside the project root (verify). The fixture does
    not exist until T1.2, and `services/api` does not exist until T0.3.
17. **Golden fixture and Biome.** `just lint` and `format-check` run `biome ... .` inside
    `apps/web`, so they do not reach `services/`. A Biome config placed at the repo root, or an
    `includes` pattern reaching outside `apps/web`, could bring the fixture into scope. The
    pre-commit hook only receives `^apps/web/` files and excludes the fixture globally.
18. **Biome and ignore files.** Whether Biome reads `.gitignore` depends on its VCS settings. The
    repo `.gitignore` lives at the root, while Biome runs from `apps/web`. Example: without VCS
    integration, `biome lint .` may walk into `dist/` after a `vite build`, or into generated
    `src/api/schema.d.ts` later (Biome ignores `node_modules` by default, verify).
19. **Biome and Tailwind CSS syntax.** Tailwind v4 uses CSS at-rules such as `@import
    "tailwindcss"`, `@theme`, `@apply`, `@utility`. Biome's CSS parser may report parse errors
    on Tailwind-specific directives unless a parser option for them is enabled (verify for the
    installed Biome version). Example: `biome lint .` fails on `src/index.css`.
20. **Biome on non-code files in the hook.** The pre-commit hook passes `pnpm-lock.yaml`,
    `.svg`, `.html` files to Biome with `--files-ignore-unknown=true`. JSON files such as
    `package.json` and `tsconfig.json` are formatted by Biome. `tsconfig.json` often contains
    comments (JSONC); Biome treats known tsconfig names as JSONC (verify).
21. **Tailwind wiring not checked by any gate.** `just check` runs lint, format, types and tests.
    None of them builds the app or produces CSS. Example: a broken Tailwind plugin setup passes
    `just check` and fails only when someone runs `vite build` or opens the dev server.
22. **`vite build` not in any gate.** The template's `build` script is usually `tsc -b && vite
    build` (verify). Neither the justfile nor D21 runs a production build. Section 6.2 says the
    built version is served by FastAPI.
23. **`just dev` with the real Vite (reviewer follow-up 2).** The recipe starts `pnpm run dev` in a
    background subshell and later runs `kill $pids` (SIGTERM to the pnpm process). Facts to
    check: whether pnpm forwards SIGTERM to its `vite` child, or leaves Vite running on its port
    (default 5173); in a non-interactive bash, background jobs start with SIGINT ignored, and an
    ignored disposition survives `exec` (verify how Node and Vite react); Vite's keyboard
    shortcuts read from stdin when it is a TTY, while the API and the recipe share the same
    terminal. Example: after Ctrl-C, `lsof -i :5173` still shows a node process.
24. **Dev host and CORS origin.** Vite's default host is `localhost`, which may resolve to `::1`
    on macOS, while the API binds to `127.0.0.1`. The API "allows the Vite dev origin through
    CORS" (6.2). Example: the browser origin is `http://localhost:5173` but T0.3 allows
    `http://127.0.0.1:5173`, so requests are blocked. If port 5173 is busy, Vite picks another
    port unless told not to, which changes the origin.
25. **React StrictMode in development.** The template wraps the app in `StrictMode`, which mounts,
    unmounts and remounts components and runs effects twice in development. Later (T1.4/T1.5)
    this can double-register `keydown`/`keyup` listeners on `window` or create two recorders if
    cleanup is wrong. It does not affect production builds.
26. **Dev vs built timing.** React's development build is slower than the production build.
    Section 12.5 measures handler time per keystroke. Section 6.2 says the pilot can use the
    built version served by FastAPI. Which one participants use is not stated in the design doc.
27. **Timer precision and headers.** Section 12.2: "Browsers coarsen timers slightly for security".
    The coarsening depends on cross-origin isolation headers (COOP/COEP) (verify). If the Vite dev
    server and FastAPI send different headers, timer resolution can differ between dev and built
    versions.
28. **Template boilerplate.** The Vite template includes demo assets (logos, counter demo) and may
    reference remote URLs in links (vite.dev, react.dev). Links are not network requests, but
    any remote image, font or script would be (D19).
29. **Worktree nested inside the main checkout.** This worktree is at
    `/Users/allen/Downloads/typist-ml/.claude/worktrees/typist-ml-overview-3379c6`, inside the main
    repo directory. Tools that search parent directories for configuration (Biome config
    discovery, pnpm workspace detection via `pnpm-workspace.yaml`, TypeScript `extends` lookups)
    could find files in `/Users/allen/Downloads/typist-ml/` if such files exist there. Currently
    none exist in this worktree's tree; the main checkout's working tree was not inspected.
30. **`.git` is a file in a worktree.** In a git worktree `.git` is a file pointing to the common
    git dir, not a directory. Tools with git integration (Biome VCS, Vitest `--changed`) may
    detect the repository root differently (verify).
31. **`apps/.gitkeep` remains.** After `apps/web/` exists, `apps/.gitkeep` is redundant. T0.1 owner
    answer 6 said to leave filling directories to their own tasks; it did not say whether the
    placeholder is removed.
32. **Existing `.gitignore` covers `dist/`, `coverage/`, `.vite/` unanchored.** A source folder
    named `dist` or `coverage` anywhere under `apps/web/src` would be silently ignored.
33. **`.env` files.** `.env` and `.env.*` are ignored (except `.env.example`). Vite loads
    `.env*` files from its root and exposes `VITE_*` variables to client code (verify). Nothing
    in the design doc uses frontend env files.

## 8. Risks

1. **Sandbox blocks `pnpm install`** (network or writes outside the worktree). The builder cannot
   produce the lockfile. The hard rule forbids bypassing the sandbox, so the task stalls until
   the owner runs the install or grants access.
2. **`just check` red on the scaffold itself.** Unformatted template files, Tailwind CSS syntax
   that Biome cannot parse, or a tsconfig without `noEmit` make D21's gate fail even though
   `just test` passes. The acceptance criterion would be met while the PR gate is not.
3. **Hook and gate disagree** (reviewer follow-up 1). `just check` uses `biome lint` + `biome
   format`; the hook uses `biome check --write`. Import ordering and other assist actions are
   enforced only by the hook. Changing the justfile to `biome ci .` would change what D21 says
   ("Biome lint, Biome format check"), which by section 2 and 17.3 needs a new decision row/ADR.
4. **Lockfile does not install on Linux CI** (native optional dependencies, pnpm version
   mismatch). This surfaces only in T0.4 and blocks "CI green on main".
5. **Weak strictness baked in.** If only `strict: true` is set, T1.3/T1.4 telemetry code is
   written without `noUncheckedIndexedAccess`-style checks, and the "no any without a comment"
   rule is unenforced. Tightening later touches every file.
6. **Test environment chosen too narrowly.** A `node`-only Vitest setup passes T0.2's single test
   but blocks T1.4's synthetic `KeyboardEvent` tests and component tests.
7. **`just dev` leaves Vite running after Ctrl-C** (reviewer follow-up 2). A stale dev server
   holds port 5173; the next `just dev` starts Vite on another port, which changes the dev origin
   the API allows through CORS.
8. **Scope creep.** Adding TanStack Query, Recharts, Playwright, openapi-typescript, a router or the
   section-7 feature folders turns T0.2 into several tasks ("One task per PR"). Leaving them out
   means later tasks must add them, and no section-16 task currently names them.
9. **Version churn.** "Current as of September 2026" versions (Vite 8, TypeScript 6/7, Biome 2.x,
   Vitest, Tailwind 4) change often. Unpinned ranges plus no committed lockfile would let CI and
   the Mac resolve different versions (section 18 risk "Library changes mid-project").
10. **Third-party scanners.** `codacy.yml` uploads analysis to Codacy (a third-party service) and
    to GitHub code scanning; it may fail on the T0.2 PR if the secret or code scanning is not
    set up, producing a red check that is not required but is visible. `codeql.yml` does not scan
    TypeScript, so reviewers may assume coverage that does not exist.
