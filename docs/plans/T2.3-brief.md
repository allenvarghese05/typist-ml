# T2.3 brief — generation/base.py and validator.py with tests

*Analyst brief. Facts only; no design or implementation.*

## 1. Task

- **ID:** T2.3 (milestone **M2 "Loop with heuristic and control"**, design doc §16; M2 "Done
  when": "A test participant goes baseline, assign, practice, retest end to end").
- **Title (verbatim, §16):** "generation/base.py and validator.py with tests".
- **Acceptance criteria (verbatim, §16):** "Each rejection reason has a test".
- **Test-type mandate (§17.2 verbatim):** "Validator and generators | Each rule, determinism,
  density range | pytest unit".

## 2. Why it matters

`base.py` and `validator.py` are the two shared spines of the entire generation subsystem.

- **`base.py` defines the contracts every arm implements.** §7 lists its contents as
  "`Arm, DrillSpec, DrillCandidate, DrillGenerator`". §9.1: "Every generator implements the same
  `DrillGenerator` protocol." If the `DrillSpec`/`DrillCandidate`/`DrillGenerator` shapes are
  wrong, T2.4 (control + heuristic), T3.1 (Markov) and T3.2 (LLM) all build on a broken interface
  and `service.py` (GenerationService, T2.5) cannot drive them uniformly.
- **`validator.py` is the one fairness gate (D16).** §9.1: "the `DrillValidator` is the single
  fairness gate for all arms." §13.1 "Why the gate matters": "the question is whether the *method*
  of choosing text matters. If one arm's text were much denser or longer, that alone could explain
  a difference. The validator forces all targeted arms into the same range, and the density, word
  length and real-word ratio of every drill are stored so the write-up can show the arms were
  comparable." If the validator is wrong, the experiment's core comparability claim (arms differ
  only in method) is unsupported, and the §15.2/§15.3 "Drill quality" fairness evidence is wrong.
- **The rejection reasons feed the acceptance-rate measurement.** `generation_attempts.density,
  accepted, reject_reasons` (§8.1) exist "For the rejection rate" (§8.1), reported as an
  engineering claim (§3.5 "LLM generation… acceptance rate, attempts per accepted drill";
  §15.2 Generation view). Each reason must be nameable and testable, which is exactly the
  acceptance criterion.

What breaks if it is wrong: a too-loose validator lets arms diverge in density/length (confound
D16 is designed to remove); a too-strict one starves the LLM arm (risk §18 "1B model writes poor
drills"); a wrong reason taxonomy makes the acceptance-rate / rejection-rate numbers meaningless;
a non-deterministic validator breaks §13.1 "Determinism" and §17.2 "determinism".

## 3. Governing decisions (each D-number and what it forces here)

- **D03 (Arms = `control, heuristic, markov, llm`):** `Arm` StrEnum in `base.py` has exactly these
  four members (already mirrored by `DRILL_ARMS` in `models/drills.py`). The validator must handle
  `control` (no targets) as well as the three targeted arms.
- **D09 / D10 (model runtime / model):** `base.py` carries `DrillSpec.seed` and determinism; the
  LLM-specific `model_id`, `prompt_version` live on `drills`/attempts, not in the shared base.
  `base.py` and `validator.py` are pure Python and must not import `mlx-lm` (CLAUDE.md: mlx-lm is
  Apple-Silicon-only; `base.py`/`validator.py` run in Linux CI).
- **D11 (batch generation):** the validator is called inside the worker retry loop (§10.2);
  `accepted` + `reject_reasons` are what the loop logs per attempt (§13.5 "every attempt is logged
  in `generation_attempts`").
- **D13 (text scope — a–z + space, letter-letter bigrams only):** the charset rule and the bigram
  definition. The project's single bigram definition is
  `typist.corpus.word_index.count_bigrams` (letter-letter, never across a space); the validator's
  density/coverage/repetition logic must use the same definition (CLAUDE.md "one source of truth").
- **D16 (fairness gate — the whole task):** "All targeted arms pass one shared validator: length,
  charset, density range, per-bigram coverage, repetition limits." This is the exact rule list the
  validator enforces; §13.1 adds real-word ratio as a recorded metric (LLM-only gate).
- **D19 (no cloud, no WASM):** validator is local pure Python.
- **D20 / freeze:** `d_min`/`d_max` are "calibrated in M3, then frozen" (§13.1, §13.5 "Frozen for
  the pilot: … d_min and d_max"; T3.4/T3.5). **T2.3 runs in M2, before M3**, so it must read the
  range from config/spec, never hard-code it; current seeded values are `d_min=0.15`, `d_max=0.40`
  (migration `0001`).

### 4.2 The §9.1 contracts T2.3 must implement (verbatim from the PDF)

```python
class Arm(StrEnum):
    CONTROL = "control"; HEURISTIC = "heuristic"; MARKOV = "markov"; LLM = "llm"

@dataclass(frozen=True)
class DrillSpec:
    participant_id: str
    arm: Arm
    target_bigrams: tuple[str, ...]   # empty for CONTROL
    length_chars: int = 300
    min_density: float = 0.15
    max_density: float = 0.40
    seed: int = 0

class DrillGenerator(Protocol):
    arm: Arm
    version: str
    def generate(self, spec: DrillSpec) -> DrillCandidate: ...
```

`GenerationService` is the only class that talks to the database during generation, and the
`DrillValidator` is the single fairness gate for all arms." **`DrillCandidate`'s fields and
`DrillValidator`'s method signature are named in §7/§9.1 but their shapes are not given in the

### 4.3 The §13.1 shared-rules table (verbatim)

| Rule | Default | Applies to |
|---|---|---|
| Length | 300 characters, cut at a word boundary; reject if under 270 | All arms |
| Charset | Lowercase a to z and single spaces only | All arms |
| Target density | Target bigram occurrences divided by all letter-letter bigrams, between d_min 0.15 and d_max 0.40 (calibrated in M3, then frozen) | Heuristic, Markov, LLM |
| Coverage | Each target bigram appears at least 3 times | Heuristic, Markov, LLM |
| Repetition | No word more than 3 times; no bigram repeated 3 times in a row (for example thth th) | All arms |
| Real-word ratio | Share of tokens found in the word list, measured before cleaning; recorded, and LLM output under 0.8 is rejected | Recorded for all; gate for LLM |
| Determinism | Same spec and seed gives the same text (LLM: same seed and pinned versions) | All arms |

## 5. Inputs and outputs

**Inputs to `validator.py`:**
- A candidate drill text (lowercase a–z + spaces) and its `DrillSpec` (carries `target_bigrams`,
  `length_chars`, `min_density`, `max_density`, `arm`, `seed`).
- For the real-word-ratio metric: a word-membership source (the corpus `WordIndex` / `words.json`,
  or a separate 50,000-word list — unresolved, Open Q 3).
- `d_min`/`d_max` ultimately originate from `experiment_config` but reach the validator via
  `DrillSpec.min_density`/`max_density` (the §9.1 dataclass already carries them).

**Outputs of `validator.py`:** a validation result containing (a) `accepted: bool`,
(b) `reject_reasons: list[str]` (the strings persisted to `generation_attempts.reject_reasons`),
(c) the three recorded fairness metrics `target_density`, `mean_word_len`, `real_word_ratio`
(persisted to `drills` and `density` to the attempt). Exact result type/name undefined (Open Q 2).

**Outputs of `base.py`:** the `Arm` enum, `DrillSpec`, `DrillCandidate`, and the `DrillGenerator`
protocol (and possibly the `DrillValidator` interface) — the types every generator and the worker
import.

**Where each lives:** `src/typist/generation/base.py`, `src/typist/generation/validator.py`;
tests in `tests/unit/` (pure, no DB). Persisted downstream by T2.5's `service.py` into `drills` /
`generation_attempts`.

## 6. Constraints

- **Platform:** `base.py`/`validator.py` must be pure Python importable on Linux CI — **no
  `mlx-lm` import** (mlx-lm is Apple-Silicon-only, CLAUDE.md). LLM-specific code stays in
  `generation/llm/`.
- **Determinism (§13.1, §17.1, §17.2):** "Same spec and seed gives the same text." Randomness
  "always goes through a seeded generator passed in from the caller" (§17.1; CLAUDE.md). The
  validator itself is deterministic (pure function of text + spec).
- **No experiment literals in logic (§17.1):** "Every experiment parameter lives in config, never
  as a literal inside logic." `d_min`/`d_max`/`block_chars` come from config/spec. (The composer
  precedent keeps pure-algorithm constants like softmax temperature as module literals — Open Q 5
  for the `270` floor.)
- **Single bigram definition:** use `count_bigrams`/`word_bigrams`; do not re-implement bigram
  counting (CLAUDE.md, D13).
- **Frozen keys:** `d_min`/`d_max` are frozen in M3; T2.3 must not write or hard-code them.
- **Performance:** none stated for the validator itself; generation is batch/off-path (D11) so the
  validator is not latency-critical.

## 7. Edge cases (concrete examples)

The rejection reasons D16 + §13.1 imply, each needing a test ("Each rejection reason has a test"):

1. **Length under floor** — text ≥1 word but <270 chars after word-boundary cut.
   Example: a 260-char drill → reject (length). *Applies to all arms.*
2. **Charset violation** — any character outside `a–z`/single-space.
   Examples: `"the qu1ck"` (digit), `"hello,world"` (punctuation), `"a  b"` (double space),
   `" abc"` / `"abc "` (leading/trailing space). *All arms.* (Whether the validator rejects or is
   an invariant for already-clean non-LLM arms: Open Q 6.)
3. **Density below `d_min`** — (summed target-bigram occurrences)/(all letter-letter bigrams)
   < 0.15. Example: targets `("ck","ow")`, 2 target occurrences in 200 letter-letter bigrams →
   density 0.01 → reject. *Heuristic/Markov/LLM only; never for control.*
4. **Density above `d_max`** — same ratio > 0.40. Example: `"thth thth thth …"` → reject.
   *Targeted arms only.*
5. **Coverage shortfall** — a target bigram appears <3 times. Example: targets `("ck","ow")`,
   `"ck"` appears 5×, `"ow"` appears 2× → reject (coverage). *Targeted arms only.*
6. **Word repetition** — a word used **more than 3** times. Example: `"the the the the …"`
   (4× "the") → reject. *All arms.* (Boundary: exactly 3 is allowed; >3 rejects.)
7. **Bigram repeated 3 times in a row** — §13.1 example "thth th" (the doc's own example string).
   Example to reject: a run like `"thththth"` where a bigram repeats back-to-back. *All arms.*
   (Exact meaning of "3 times in a row" and whether it spans spaces: Open Q 7.)
8. **Real-word ratio below 0.8** — share of tokens in the word list <0.8. Example: mostly
   pseudo-words → reject. *LLM only (gate); recorded for all arms.*

Other edge cases:
- **Control drill** (`target_bigrams = ()`): density and coverage rules do **not** apply (§13.1
  "Heuristic, Markov, LLM"); the validator must not emit density/coverage reasons for it. Needs a
  test that control passes with empty targets (Open Q 8).
- **Empty / whitespace-only text:** zero letter-letter bigrams → density is 0/0 (division by
  zero). Behaviour undefined by the doc (Open Q 9).
- **Multiple simultaneous violations:** does `reject_reasons` collect all of them, or stop at the
  first? "For the rejection rate" (§8.1) suggests collecting all (Open Q 2/4).
- **Word-boundary cut vs length:** §13.1 says cut at a word boundary then reject if <270 — order
  matters (cut first, measure after).
- **`mean_word_len`** is a **recorded metric, not a gate** — it has no reject reason; it must still
  be computed for the `drills` column.
- **Markov pseudo-words** legitimately have low real-word ratio but are **not** gated (only LLM is)
  — the validator must record it without rejecting Markov.

## 8. Risks

- **Reason taxonomy drift:** if the `reject_reasons` string names here differ from what T2.4/T2.5
  and the §15.2 dashboard expect, the acceptance-rate breakdown is inconsistent. The doc never
  fixes the string tokens (Open Q 2).
- **Density semantics wrong:** reading "Target bigram occurrences" as per-bigram vs summed changes
  every acceptance decision and the M3 `d_min`/`d_max` calibration (T3.4) built on top (Open Q 4).
- **Real-word-ratio source ambiguity:** using the 20,000 corpus vs an (unbuilt) 50,000 list shifts
  the ratio and could wrongly gate the LLM arm (Open Q 3).
- **Hidden hard-coded `270`/`0.8`/`3`:** violating §17.1 "no experiment literals in logic" and
  making M3 freeze (`d_min`/`d_max`) or any tuning impossible without code change (Open Q 5).
- **Over-/under-strict validator** feeding the "1B model writes poor drills" risk (§18): too strict
  starves the LLM arm's pool; too loose breaks D16 comparability.
- **Accidental mlx-lm coupling** in `base.py` would break Linux CI import.
- **Bigram-definition duplication** (not reusing `count_bigrams`) would silently diverge from
  attribution/corpus and violate CLAUDE.md.

## 9. Open questions (numbered; design doc does not settle these)

1. **`DrillCandidate` shape.** §7/§9.1 name `DrillCandidate` as `DrillGenerator.generate`'s return
   type but give no fields. What does it carry — `text`, the three metrics, `seed`/`version`, and
   does it embed validation result or is validation separate? (Needed before T2.4/T3.x build on it.)
2. **Validator result type and reject-reason tokens.** §9.1 names `DrillValidator` but gives no
   method signature; §8.1 only says `reject_reasons` is a JSON list. What is the result type's
   name/shape, what exact string tokens are stored per reason (e.g. `"length"`, `"density_low"`,
   `"coverage"`, `"repeat_word"`, `"repeat_bigram"`, `"real_word_ratio"`, `"charset"`), and does it
   collect **all** failing reasons or stop at the first?
3. **Real-word-ratio word source.** §13.1 says "found in the word list"; §13.5 post-processing says
   "drop words not in the **50,000**-word list". The built corpus is **20,000** words
   (`words.json`); no 50,000-word artifact exists. Which list backs the validator's real-word
   ratio, and must T2.3 build/load a 50,000-word list (expanding corpus/build.py) or reuse the
   existing 20,000-word `WordIndex`?
4. **Definition of "density" — summed or per-bigram.** §13.1: "Target bigram occurrences divided by
   all letter-letter bigrams." Is the numerator the **sum** of occurrences across all target
   bigrams (one density per drill), or is density computed per target bigram with every one
   required to fall in `[d_min, d_max]`? (The plural phrasing and the single `drills.target_density`
   column suggest summed, but it is not stated outright.)
5. **The `270` length floor and the `0.8` ratio / `3`-count limits — config or literal?** §13.1
   gives `270` as a literal (= 0.9 × 300). Should the floor be a config key, derived from
   `DrillSpec.length_chars` (× 0.9), or a module constant (like the composer's pure-algorithm
   literals)? Same question for the `0.8` real-word threshold and the `3`-count coverage/repetition
   limits (§17.1 "every experiment parameter lives in config").
6. **Charset: reject vs invariant.** Non-LLM arms produce already-clean a–z+space text, so a
   charset failure can only come from the LLM path (which cleans in T3.2 post-processing). Is
   charset a real rejection reason the validator emits, or an asserted invariant for non-LLM arms?
   And does charset also reject double/leading/trailing spaces, or only non-`[a-z ]` characters?
7. **"No bigram repeated 3 times in a row (for example thth th)."** What exactly counts: a bigram
   appearing in 3 consecutive adjacent positions (`xyxyxy`), or 3 immediate repetitions of the same
   two-character pattern? Does the run respect word boundaries (the example "thth th" contains a
   space), and is the limit "3 in a row rejects" (so 2 is allowed)?
8. **Control drill validation.** With `target_bigrams = ()`, density and coverage are N/A (§13.1
   "Heuristic, Markov, LLM"). Does the validator short-circuit those rules for `control` and still
   apply length/charset/repetition/real-word-ratio-recording? Is there an explicit "control passes"
   test expected under "each rejection reason has a test"?
9. **Degenerate inputs.** How should the validator treat empty or whitespace-only text, or text
   with **zero** letter-letter bigrams (density numerator and denominator both 0 → 0/0)? Reject as
   length/charset, define density as 0, or raise? The doc is silent.

## Owner answers

2026-10-21 — answered by the orchestrator under the autonomous pipeline rule. Sources: (a) design
doc, (c) earlier plans, (d) code conventions, (e) industry practice.

1. **`DrillCandidate` is a frozen dataclass: `text: str`, `raw_output: str` (equal to `text`
   for non-LLM arms), `generator_version: str`, `seed: int`, `model_id: str | None = None`,
   `prompt_version: str | None = None`, plus LLM timing `gen_ms`, `gen_tokens`,
   `tokens_per_sec`, `peak_memory_mb` all `float | int | None = None`.** No metrics inside it —
   the validator computes metrics, so a candidate cannot carry stale or self-reported numbers.
   Source: (a) 8.1 `drills`/`generation_attempts` columns are exactly these fields; (d) frozen
   dataclass convention.

2. **`validate(candidate_text, spec, index) -> ValidationResult`** with `ValidationResult(
   accepted: bool, reasons: tuple[str, ...], metrics: DrillMetrics)` and `DrillMetrics(
   length_chars, target_density, mean_word_len, real_word_ratio, coverage: dict[str, int],
   max_word_count, bigram_run)`. **Collect all failing reasons, never stop at the first** — the
   rejection-rate report needs the full taxonomy per attempt. Reason tokens (a `StrEnum
   RejectReason`): `too_short`, `bad_charset`, `density_low`, `density_high`, `coverage`,
   `word_repeat`, `bigram_repeat`, `real_word_ratio`. Source: (a) 8.1 `reject_reasons JSON`;
   (e) stable tokens for aggregation.

3. **The 20,000-word `words.json` list via `WordIndex`.** Source: (c) T1.8 answer 4 built this
   as "the" corpus word list; 13.5's "50,000" is the LLM prompt's vocabulary hint, not a gate
   artifact. Record in the plan that if M3's LLM arm is starved by a too-small list, the list
   size (`corpus_word_count`) is the knob — a config key, not a code change.

4. **One density per drill: Σ occurrences of all target bigrams ÷ all letter-letter bigrams.**
   Source: (a) 13.1 wording "Target bigram occurrences divided by all letter-letter bigrams" is
   a single ratio; per-bigram balance is what the coverage rule handles. Occurrences counted with
   `count_bigrams` (never across spaces). For control (no targets) density is recorded as 0.0 and
   the density/coverage rules are skipped.

5. **Config keys, read from `experiment_config`, via data-only migration
   `0006_validator_config`:** `drill_length_chars: 300`, `drill_min_length_chars: 270`,
   `drill_min_coverage: 3`, `drill_max_word_repeats: 3`, `drill_max_bigram_run: 3`,
   `drill_min_real_word_ratio: 0.8`. `d_min`/`d_max` already exist. `DrillSpec.length_chars`
   and `min/max_density` default from these keys when built by the service; the validator takes
   a `ValidatorConfig` dataclass (built from config by a `load_validator_config(session)`
   helper following `assignment.py`'s pattern) so unit tests pass plain values. Source: (a) 17.1
   "every experiment parameter lives in config"; (d) 0002/0005 precedent. Update
   `SEEDED_CONFIG_ROWS` (16 → 22) and head pins.

6. **Charset is a real rejection for every arm, and single-space strictness is part of it.**
   Reject if `text` contains anything outside `[a-z ]`, or has leading/trailing space, or two
   consecutive spaces, or is empty. Source: (a) 13.1 "Lowercase a to z and single spaces only";
   (e) the LLM arm will produce exactly these faults, and the gate must be the same for all arms.
   Cleaning (lower-casing, stripping punctuation) is the generator's job before it hands text
   over; the validator never mutates text.

7. **"No bigram repeated 3 times in a row" = the same two-letter bigram occurring at three
   consecutive letter positions within one word** (`thth` already contains `th` at positions 0
   and 2 — a run of 2; `ththth` is a run of 3 → reject). Counting is within words only (never
   across spaces); two in a row is allowed. Implementation: for each word, slide over
   `word_bigrams(word)` and count the longest run where `bigrams[i] == bigrams[i+2] ==
   bigrams[i+4]` — i.e. the same bigram starting at every other position. Record `bigram_run`
   as the longest such run. Source: (a) the 13.1 example "thth th"; (e) the only reading that
   makes "3 times in a row" well-defined.

8. **Control: density and coverage skipped, every other rule applied, metrics recorded; an
   explicit "control passes with empty targets" test and a "control rejected for word_repeat"
   test.** Source: (a) 13.1 "Applies to" column.

9. **Empty or whitespace-only text is rejected with `too_short` and `bad_charset`; density with
   zero letter-letter bigrams is 0.0 (never raises).** Source: (e) a validator must never raise
   on generator output; the worker logs reasons.
