## 2. Why it matters

T2.10 provides the end-to-end integration proof that the full Typist-ML experiment loop functions cohesively from start to finish:

- **Proves Milestone 2 completion (§16):** Milestone 2 is done when *"A test participant goes baseline, assign, practice, retest end to end"*. Prior tasks built each component in isolation (tables, assignment, validator, generators, worker loop, session planner, retest composer, participant state transitions, and admin UI). T2.10 is the milestone capstone that runs all pieces together in an unbroken end-to-end sequence.
- **Validates the full participant lifecycle DAG (§3.2, §9.3 Figure 6, §10.1, §14):**
  1. Enrolment: create participant with status `enrolled` (`POST /api/v1/participants`).
  2. Consent: record consent, moving status from `enrolled` to `baseline` (`POST /api/v1/participants/{pid}/consent`).
  3. Baseline sessions: start, type, and complete two baseline sessions covering Form A parts 0 and 1 (`POST /api/v1/participants/{pid}/sessions`, `POST /api/v1/blocks/{bid}/start`, `POST /api/v1/blocks/{bid}/events`, `POST /api/v1/blocks/{bid}/complete`, `POST /api/v1/sessions/{sid}/complete`), generating keystroke telemetry, running attribution, and computing session and bigram metrics.
  4. Assignment and freeze: rank weak bigrams, deal into sets in snake order, map sets to enabled arms with a seeded shuffle, freeze `bigram_assignment` rows, compose Form B retest passages, and transition participant to `assigned` (`POST /api/v1/admin/participants/{pid}/assign`).
  5. Drill pool generation: enqueue replenishment jobs and run the generation service / worker loop to produce ready drills for each assigned arm (`replenish_drill_pool`, `GenerationService`, `worker.run_worker_once`).
  6. Practice sessions: plan and type $N$ practice sessions across Latin-square rotated arms (`POST /api/v1/participants/{pid}/sessions`), consuming drills from the pool, marking drills `used`, transitioning participant to `practice` on session 1, and advancing to `retest` upon completing session $N$.
  7. Retest sessions: plan and type two retest sessions covering Form B parts 0 and 1, advancing participant to `done` upon completing the final retest session.
  8. Post-study analysis and verification: run participant data checks (`GET /api/v1/admin/checks/{pid}`), query outcome analysis (`GET /api/v1/analysis/participants/{pid}`), and confirm stats recomputation idempotence (`typist stats recompute`).
- **Enforces the scientific boundary ("Never used as evidence"):** The Project Guide explicitly dropped simulated typists as empirical evidence. Simulated or scripted keystrokes are strictly a developer diagnostic and continuous-integration gate; they must never be stored in persistent pilot database files (`data/typist.db`) or cited as experimental results.
- **Unblocks Milestone 3 (Markov, LLM, bake-off, freeze):** M3 introduces Markov and LLM drill generators and freezes `experiment_config`. Having a verified pipeline test in CI ensures that adding new generators does not break the session planner, drill pool, or participant lifecycle.

What breaks if it is wrong:
- **Acceptance criteria failure:** If the full flow fails or is skipped in CI, regressions in database constraints, API request/response schemas, state transitions, or drill consumption will go undetected until a real human typist encounters them.
- **Protocol breakage:** If state transitions, Latin square rotation, drill marking, or session completion misbehave, participants could get trapped in `practice`, drills could be reused, or retest sessions could fail to load Form B passages.
- **Evidence pollution:** If scripted keystroke test runs write to `data/` or contaminate pilot data, real pilot analyses and README claims will be invalidated (violating D19, CLAUDE.md, and the Project Guide).
- **CI performance bottleneck:** If the pipeline test is inefficient or issues excessive synchronous overhead, CI runners could exceed job timeouts (10 minutes) or slow down PR feedback loops.

## 3. Governing decisions

- **D01 (Experiment unit — within-person):** Comparisons are within-person; each participant has their own weak bigram ranking, snake split, and arm mapping. The pipeline test must verify this complete within-person flow.
- **D02 (Control arm):** Control block uses frequency-weighted random words without targeting, equal exposure.
- **D03 (Arms: control, heuristic, markov, llm):** In M2, only `control` and `heuristic` exist (built in T2.4). The M2 cut-line (§16) specifies 2-set mode (`arms_enabled = ["control", "heuristic"]`, 8 bigrams each).
- **D04 (Assignment freeze before practice):** "Rank weak bigrams, deal into sets in snake order, map sets to arms with a seeded shuffle, freeze before practice. Balances weakness across sets and removes builder choice. Never mid-pilot." Assignment runs strictly in `baseline` status after baseline sessions complete, inserting immutable frozen rows.
- **D06 (Deployment — local-only on MacBook Pro):** Single local SQLite database; no remote cloud hosting, model serving, or authentication.
- **D08 (Backend stack):** Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite in WAL mode, Typer CLI, ruff, pyright, pytest.
- **D11 (Generation timing — batch via worker):** Drills are pre-generated. The pipeline test must exercise drill generation via `GenerationService` / `worker.run_worker_once` to populate ready drills before practice blocks can be planned.
- **D13 (Text scope):** English, QWERTY, lowercase a to z and space. Tracked bigrams are letter-letter only. Scripted keystrokes must strictly produce characters in this alphabet.
- **D14 (Error definition):** First-attempt substitution at position $j$, counted only when position $j-1$ was correct on first attempt. Scripted keystrokes must produce clean keystroke sequences with realistic correct and error outcomes to yield attributed bigram samples.
- **D15 (Timing — timestamps from event.timeStamp):** IKI = press-to-press; dwell = release minus press. Scripted keystroke rows must carry monotonic, non-negative timestamps (`t_down_ms`, `t_up_ms`, `dwell_ms`, `iki_ms`).
- **D16 (Fairness gate):** All drills generated by targeted arms must pass the shared `DrillValidator`.
- **D17 (Word list):** `wordfreq` English list, filtered to a to z. Used by generators, baseline composer, retest composer, and assignment.
- **D18 (Blinding):** Blocks are labelled Block 1 to Block 4. The participant is blinded unless `is_builder = True`.
- **D19 (No cloud, no WASM):** All local, standard JSON endpoints; no telemetry or analytics services.
- **D21 (`just check` runs lint, format-check, types, test, build):** CI runs `pytest` in `api` job and `vitest` in `web` job. Any automated test in CI must execute within these established jobs without altering the protect-main ruleset (`scripts/github-ruleset.json`).
- **D24 (`after_pause` flag on keystroke events):** Keystroke rows must supply boolean `after_pause`.
- **D25 (Backspace target index):** Backspace rows record post-move cursor position `target_index = max(index - 1, 0)`.
- **D26 (Session WPM time base, and idle limit):** Session WPM uses elapsed time from first keypress to last keypress. Keystrokes must not exceed idle timeouts.
- **D27 (Where `iki_ms` and `dwell_ms` are computed):** The browser computes `iki_ms` and `dwell_ms` in the row. Scripted keystroke payloads sent to `POST /events` must supply valid `t_down_ms`, `t_up_ms`, `dwell_ms`, and `iki_ms`.
- **D28 (Candidate observation threshold is 15):** A tracked bigram qualifies for assignment when pooled first-attempt attempts over baseline sessions are $\ge 15$. Scripted keystrokes in baseline sessions must generate at least 15 observations across enough tracked bigrams so assignment does not fail with `TooFewCandidatesError`.

## 5. Inputs and outputs

### Inputs
- **Participant parameters:** alias (e.g. `"test-dev"`), `is_builder` flag, `is_blinded` flag.
- **Corpus / Word Index:** `WordIndex` with vocabulary and tracked bigrams (either seeded in temporary test fixtures or loaded via `WordIndex.load(corpus_dir)`).
- **Passages:**
  - Baseline Form A parts 0 and 1 (from `compose_baseline` and `persist_baseline`).
  - Retest Form B parts 0 and 1 (from `compose_and_persist_retest`).
  - Practice block targets (assembled from pre-generated drills in the pool).
- **Scripted keystroke stream:** generated sequence of keystroke events for each block matching `block.target_text`, containing keys, codes, timestamps, dwell, IKI, and cursor comparison steps (correct, error, backspace).
- **Experiment configuration:** values in `experiment_config` (such as `arms_enabled`, `practice_days`, `block_chars`, `baseline_parts`, `retest_parts`, `assignment_min_observations`).

### Outputs
- **Database state (in an isolated temporary SQLite database):**
  - `participants` row progressing through: `enrolled` $\to$ `baseline` $\to$ `assigned` $\to$ `practice` $\to$ `retest` $\to$ `done`.
  - `sessions` rows for 2 baseline sessions, $N$ practice sessions, and 2 retest sessions, all marked `status = "completed"`.
  - `session_blocks` rows for all session blocks with `started_at` and `completed_at` timestamps.
  - `keystroke_events` rows for every scripted keystroke event.
  - `bigram_assignment` rows frozen with `frozen_at`.
  - `text_passages` rows for Form A and Form B.
  - `drills` rows generated by worker and consumed by practice sessions (`status = "used"` with `used_in_block_id`).
  - `generation_jobs` and `generation_attempts` rows tracking drill generation and fairness validation.
  - `bigram_stats` rows computed and stored for every session.
- **Verification assertions:**
  - Participant reaches `status == "done"`.
  - All sessions and blocks completed.
  - `run_participant_checks` returns clean checks (`missing_keyups` within tolerance, valid dwells, monotonic trends).
  - `GET /api/v1/analysis/participants/{pid}` returns valid set statistics.
  - `recompute_stats` produces identical stats confirming idempotence.

## 6. Constraints

- **Platform independence (CI on Linux):** CI runs on Ubuntu Linux (`ubuntu-latest`). Apple Silicon MLX models (`mlx-lm`) cannot run on Linux (CLAUDE.md: `"Cloud sessions and CI run on Linux. The model runtime (mlx-lm) only runs on Apple Silicon."`). The pipeline test must run in CI using only generators supported off-Mac: in M2, `ControlGenerator` and `HeuristicGenerator` (which are pure Python using `wordfreq`).
- **CI time limits:** GitHub Actions job timeout is 10 minutes; `pytest` currently completes in ~23 seconds. The pipeline test must not cause test suite execution to balloon. Keystrokes must be generated and ingested efficiently (e.g. batched via `POST /events` in realistic batch chunks, or optimized for test performance).
- **No data pollution (CLAUDE.md / D19):** `"Never commit anything under data/ (database, corpus artifacts)."`, `"Never used as evidence"`. The test must run against an isolated temporary SQLite database (`tmp_path`) and never write to or inspect `data/typist.db`.
- **Status check names fixed (protect-main ruleset):** CI job names `web` and `api` are immutable per `scripts/github-ruleset.json` and D21. Any CI test must execute within the existing `api` job (via `pytest`) or `web` job (via `vitest`).
- **Deterministic randomness:** Any pseudo-random typing or error generation must use an explicitly seeded `random.Random` instance (CLAUDE.md correctness rule: `"Randomness always comes from a seeded generator passed in by the caller."`).

## 7. Edge cases

1. **Insufficient qualifying bigrams for assignment (`TooFewCandidatesError`):**
   - *Case:* If baseline scripted typing is too brief or errors are distributed across untracked bigrams, fewer than `config.per_set_fallback * sets` (e.g. $3 \times 2 = 6$ in 2-set mode, or $3 \times 4 = 12$ in 4-set mode) tracked bigrams reach the `assignment_min_observations = 15` threshold (D28).
   - *Concrete example:* A scripted keystroke generator that only types a 100-character snippet results in at most 1-2 occurrences per bigram. When `assign_participant` executes, `candidates` is empty, raising `TooFewCandidatesError`. The baseline text and scripted typing must type enough text (or standard Form A passages) so that all required candidate bigrams have $\ge 15$ observations.
2. **Context error invalidation in attribution (D14):**
   - *Case:* Section 12.3 attribution skips position $j$ if position $j-1$ was not correct on first attempt.
   - *Concrete example:* Target is `"the quick"`. Scripted typist types `'t'`, then mistakenly types `'x'` instead of `'h'`, then `'e'`. Position 1 (`'h'`) is an error. Position 2 (`'e'`) is correct, but because position 1 failed, bigram `"he"` is skipped during attribution. If scripted errors are injected on adjacent characters, downstream bigram observations are dropped.
3. **Drill pool starvation on practice planning:**
   - *Case:* Starting a practice session requires $K$ ready drills per arm (default $K=2$, `drills_per_block`).
   - *Concrete example:* Participant transitions to `assigned`. If `plan_session(session, pid, "practice")` is called before running the generation worker, ready drills count is 0, raising `DrillPoolExhaustedError: participant 'p1' arm 'control' has 0 ready drill(s), need 2`. The test must ensure `replenish_drill_pool` and worker generation run to produce sufficient ready drills prior to each practice session.
4. **Arm generator availability in M2 (2-set mode):**
   - *Case:* In M2, only Control and Heuristic generators exist (T2.4). If `arms_enabled` in `experiment_config` contains `"markov"` or `"llm"` (the default 4-arm list from migration 0001), `GenerationService` will raise `UnregisteredArmError: no generator registered for arm 'markov'`.
   - *Concrete example:* Calling `replenish_drill_pool` with default config enqueues jobs for `control`, `heuristic`, `markov`, and `llm`. When `worker.run_worker_once` claims the `markov` job, `build_default_generators` only returns `{Arm.CONTROL: ..., Arm.HEURISTIC: ...}`, causing the job to fail with `UnregisteredArmError`. In M2, the pipeline must either run in 2-set mode (`arms_enabled = ["control", "heuristic"]`, per M2 cut-line §16) or supply test mock generators for markov/llm.
5. **Retest passage composition dependency on Form A:**
   - *Case:* Retest Form B passages are composed during assignment via `compose_and_persist_retest(session, participant_id, index)`. This requires `load_form_a_words` to inspect Form A passages in `text_passages`.
   - *Concrete example:* If Form A passages are not persisted before assignment, `compose_and_persist_retest` catches `BaselinePassagesNotFoundError`, and `form_b_composed` is False. Subsequent planning of retest sessions will raise `PassageNotFoundError: no retest (form B) passage for part 0`.
6. **Key-up pairing invariant validation:**
   - *Case:* `KeystrokeEventIn._check_invariants` requires `(self.t_up_ms is None) != (self.dwell_ms is None)` to be False (both null or both set).
   - *Concrete example:* If scripted keystrokes set `t_up_ms = 150.0` but leave `dwell_ms = None`, FastAPI returns HTTP 422 Unprocessable Content, failing the batch.
7. **Session abandonment on 30-minute staleness:**
   - *Case:* `plan_session` checks if an open session's age exceeds `STALE_SESSION_TIMEOUT = 30 minutes`.
   - *Concrete example:* If simulated timestamps jump ahead by > 30 minutes between sessions, an open in-progress session is marked `abandoned` upon calling `plan_session`, which would require restarting that session.
8. **Checks service tolerance thresholds:**
   - *Case:* `checks.run_participant_checks` validates:
     - Missing keyups: $\le 2\%$ missing keyup rows (`MISSING_KEYUP_TOLERANCE_SHARE = 0.02`).
     - Dwell: p50 and p95 between 20ms and 300ms.
     - Event sequence: non-decreasing `t_down_ms`.
   - *Concrete example:* If scripted keystrokes omit keyups (all `t_up_ms = None`), `checks.run_participant_checks` flags `missing_keyups` as failed (`severity = "error"`).
9. **Idle timeout within block (D26):**
   - *Case:* In real typing, 5s without keypress warns, 10s abandons the block.
   - *Concrete example:* Scripted keystroke intervals between successive keys must remain within reasonable typing speed (e.g. 50ms–250ms), avoiding simulated pauses $\ge 10,000$ms.

## 8. Risks

- **Execution time and CI slowdown:** Simulating 2 baseline sessions (2 $\times$ 2,700 chars), 10 practice sessions (10 $\times$ 4 $\times$ 300 chars), and 2 retest sessions (2 $\times$ 2,000 chars) amounts to over 20,000 keystroke events. Ingesting this volume through HTTP endpoints could take tens of seconds or minutes if not batched or scaled appropriately.
- **Corpus availability in isolated CI test environments:** Building the full corpus from `wordfreq` during test execution can take several seconds and depends on `data/corpus/`. The pipeline test must either operate with a self-contained, lightweight `WordIndex` fixture (as in `test_assignment_service.py` and `test_retest_persist.py`) or use the committed corpus if available.
- **Coupling between M2 cut-line (2-set mode) and M3 defaults:** Migration 0001 seeds `arms_enabled` with all 4 arms, but M2 only has 2 generators implemented. If the pipeline test does not explicitly configure or test 2-set mode (`arms_enabled = ["control", "heuristic"]`), it will fail when attempting to generate Markov or LLM drills.
- **Drift between browser telemetry schemas and Python ingestion:** Any field mismatch between TypeScript `KeystrokeRow` / `types.ts` and Python `KeystrokeEventIn` will fail validation with 422.
