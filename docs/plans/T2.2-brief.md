  "A test participant goes baseline, assign, practice, retest end to end").
- **Title (verbatim, §16):** "assignment.py: smoothing, ranking, snake split, seeded mapping,
  freeze".
- **Acceptance criteria (verbatim, §16):** "Same seed gives same mapping; frozen rows cannot be
  updated".
- **Mandated extra deliverable (owner-decisions.md #6):** T2.2 must also write an ADR reconciling

## 2. Why it matters

Assignment is the hinge of the whole within-person experiment (D01/D04). It turns two baseline
sessions into the frozen `bigram_assignment` rows that every downstream task reads:

- **Everything after it depends on the frozen map.** T2.4/T2.6 generate and schedule drills *per
  arm per set*; T2.7 (retest composer) must cover exactly the tracked bigrams this task selects;
  T4.1 (`analysis.py`) computes the primary outcome (set error-rate change minus control's, §3.5)
  and the key secondary (set IKI change) *by set membership stored here*. If the wrong bigrams are
  chosen, or the set→arm map is wrong, or rows are mutated after freeze, the primary comparison is
  meaningless and no later task can detect it.
- **Freeze is irreversible and pre-registration-like (D04 "freeze before practice", "Never
  mid-pilot"; D20; pilot runbook "Do not change code that affects … text composition during the
  pilot").** A bug found after `frozen_at` is set cannot be corrected without discarding the
  participant's baseline (§3.2 rule). The worker pre-generates 3 days of drills immediately after
  freeze (§3.2 "Worker pre-generates 3 days of drills"), so the sets must be final before practice.
- **Determinism is the acceptance.** "Same seed gives same mapping" means the ranking tie-breaks,
  the snake deal and the arm shuffle must be fully reproducible from a stored seed; this removes
  builder choice (D04 "removes builder choice") and lets the mapping be re-derived for audit.

What breaks if it is wrong: a mis-ranked or non-deterministic selection silently biases which
bigrams each arm drills; a mutable "frozen" row lets later code (or a re-run of assign) change the
unit of analysis after data exists; a wrong set→arm shuffle confounds arm with set weakness, which
is the exact confound D04 exists to prevent.

## 3. Governing decisions

- **D01 (Experiment unit — within-person):** "Each participant's weak bigrams are split into 4
  sets; each set is assigned one arm." Forces: output is per-(participant, bigram) rows grouped
  into 4 sets, one arm per set.
- **D02 (Control):** control is the held-out set (no targeted drills) and is one of the arms the
  shuffle maps a set onto. Forces: `control` participates in the seeded arm shuffle like any arm.
- **D03 (Arms):** `control, heuristic, markov, llm`. Forces: the arm list that is shuffled and
  mapped A→D is exactly these four (the `DRILL_ARMS` constant, see §4.3). **Note the M2 cut-line
  (§16): "run the pilot in 2-set mode (control and heuristic, 8 bigrams each), which the config
  supports with `arms_enabled`"** — so the number of sets may be 2, not 4 (Open Q 1).
- **D04 (Assignment — the whole task):** "Rank weak bigrams, deal into sets in snake order, map
  sets to arms with a seeded shuffle, freeze before practice." "Balances weakness across sets and
  removes builder choice." "Revisit if: Never mid-pilot."
- **D05 (Outcomes):** primary = per-set pooled error-rate change minus control's; key secondary =
  per-set median-IKI change minus control's. Forces: set membership and the baseline snapshot
  (`baseline_attempts`, `baseline_errors`, and the IKI used at analysis) must be stored so T4.1 can
  compute "retest minus baseline" over the same bigrams.
- **D13 (Text scope):** letter-letter bigrams only, two lowercase letters. Forces: candidates and
  stored `bigram` are two a–z letters; matches the existing `length(bigram) = 2` CHECK.
- **D18 (Blinding):** blocks are labelled 1–4; the mapping is hidden from the (second) participant.
  Forces: assign writes the map but the UI never names arms; the builder is flagged unblinded.
- **D20 (Pre-registration spirit):** the map is frozen before practice; §3.4 is the algorithm of
  record.
- **§17.1 standards (binding):** "Every experiment parameter lives in config, never as a literal
  inside logic" (the strength 20, the "150", the "16/12" cutoffs, the `assignment_seed`); "Routers
  are thin. Business logic lives in services"; "Randomness always goes through a seeded generator
  passed in from the caller" (the acceptance depends on this).
- **owner-decisions.md #6 (copied in full under "## Owner answers"):** T2.2 must reconcile §3.4's
  "at least 20 first-attempt observations" with `baseline_min_occurrences = 15` through an ADR,
  because T1.8 option A makes each baseline session type only one part (≈15 observations per
  bigram, below 20).

## 4. Current state (what exists, with signatures quoted)

### 4.1 The §3.4 algorithm (verbatim)

> 1. Candidates are letter-letter bigrams from the ~150 most common in English that have at least
> 20 first-attempt observations in the two baseline sessions.
> 2. For each candidate, compute a smoothed error rate: posterior mean of a Beta prior updated with
> the bigram's errors and attempts. The prior is centred on the participant's overall bigram error
> rate with strength 20 (empirical Bayes). This stops a bigram with 1 error in 3 attempts from
> ranking first.
> 3. Rank by smoothed error rate. Break ties with the bigram's median inter-key interval z-score
> within the participant (slower ranks weaker).
> 4. Take the top 16 (4 per set). If fewer than 16 qualify, take 12 (3 per set) and log it.
> 5. Deal them into sets A, B, C, D in snake order: rank 1 to A, 2 to B, 3 to C, 4 to D, 5 to D, 6
> to C, 7 to B, 8 to A, and so on. This balances weakness across sets.
> 6. Shuffle the arm list with a seed stored in experiment_config and map A to D onto the shuffled
> arms. Freeze by writing frozen_at. Frozen rows are never updated.

§3.5 columns T2.2's snapshot must support: "Set error rate change … pooled errors divided by pooled
attempts over its bigrams, retest minus baseline" (primary); "Set IKI change: median inter-key
interval over the set's bigrams, retest minus baseline" (key secondary).

- One row per (session_id, bigram). The index `(participant_id, bigram)` exists specifically for
  "T2.2's ranking" (docstring: "the (participant_id, bigram) index serves T2.2's ranking (8.2)").
- `attempts`/`errors` follow §12.3 / D23(a): a bigram "attempt" is a position j where j-1 was a
  first-attempt correct keystroke and b is a first-attempt keystroke; this is exactly §3.4's
  "first-attempt observations." So **"≥20 first-attempt observations in the two baseline sessions" =

- `iki_median_ms` is `statistics.median` over pooled **clean, correct, unpaused** samples; NULL
  exactly when `iki_n == 0`. It is a **per-session** median; the §3.4 tie-break needs a per-bigram
  median across the two baseline sessions (see §7, Open Q 4).

### 4.5 How a session's stats are produced (`services/session_stats.py`)

Baseline rows are written at session completion. Key authoritative facts (docstring/functions,
verbatim intent):

- Pooling across blocks is "sum attempts/errors, concat raw IKI samples, then one
  `statistics.median` — NOT a median of medians" (`merge_bigram_samples`). This is per-session only.
- `recompute_stats(session, participant_id=None)` rebuilds every completed session's rows
  deterministically. T2.2 reads the rows these functions write; it does **not** recompute from raw
  keystrokes itself.
- There is **no existing function that pools `bigram_stats` across the two baseline sessions** into a
  participant-level per-bigram attempts/errors/median. T2.2 (or a helper it adds) must do that.

## 6. Constraints

- **Determinism (acceptance; §17.1):** the seed must come from a seeded generator passed in by the
  caller; the same seed + same baseline data must yield byte-identical rows (ranks, sets, arms).
  Note T1.1 answer 17: per-participant determinism combines the global seed with `participant_id`.
  Python's `random.Random(seed)` sequence and `random.shuffle` are stable across platforms for a
  fixed CPython; the generator must be the only randomness source (no set/dict iteration order, no
  unordered DB reads feeding the shuffle).
- **Immutability (acceptance; D04):** once `frozen_at` is set, the service must refuse to update
  those rows; the DB has no trigger (§4.2). Define the error path (409/raised exception) for a
  re-assign of a frozen participant.
- **Config, not literals (§17.1):** strength 20, the 150, the observation threshold, the 16/12
  cutoffs, and `assignment_seed` must be config/constants, not inline numbers.
- **Charset / key shape (D13):** bigrams are two a–z letters; `length(bigram)=2` CHECK and the
  `set_label`/`arm` CHECKs will reject bad values at insert.
- **State precondition (§14):** assign is allowed "only in baseline-done state" and returns 409
  otherwise (coordination with T2.8 — Open Q 6).
- **Platform:** pure Python; runs on **Linux/CI** and macOS; **no mlx-lm**, no `@pytest.mark.mlx`.
- **Schema/frozen keys:** must not alter existing `experiment_config` keys or existing tables; only
  add `assignment_seed`. Migration up/down must both work (§8).
- **Workflow (CLAUDE.md):** branch `t2-2-assignment` (or similar), conventional commits, one task
  per PR, `just check` green, CI green. Never edit golden/expected values to pass a test.

## 7. Edge cases (concrete)

1. **Fewer than 16 qualify → take 12 (§3.4 step 4).** If, say, only 14 candidate bigrams clear the
   observation threshold, take 12 (3 per set) and **log it**. If fewer than 12 qualify, §3.4 is
   silent (Open Q 1). Concrete: 11 qualifying bigrams → undefined behaviour in the doc. 2-set mode
   (§16 cut-line, 8 bigrams each) changes "16/12" entirely (Open Q 1).
2. **The 20-vs-15 observation gap (the ADR).** Under option A each bigram has ≈15 observations, so a
   literal "≥20" threshold could disqualify nearly every bigram, yielding a near-empty candidate
   pool. Concrete: top bigram `th` with 15 observations fails "≥20" and is dropped. The ADR must
   settle the threshold (lower to 15 / `baseline_min_occurrences`, or accept a smaller pool).
3. **Beta posterior-mean arithmetic (§3.4 step 2).** Prior centred on the participant's overall
   bigram error rate `p0` with strength `s = 20`: `α0 = s·p0`, `β0 = s·(1−p0)`; posterior mean for a
   bigram with `e` errors in `n` attempts = `(s·p0 + e) / (s + n)`. Subtleties the plan must pin:
   (a) what `p0` is — pooled `Σerrors / Σattempts` over *which* bigrams (all tracked candidates? all
   the participant's baseline bigrams? only qualifying ones?) (Open Q 3); (b) `e`/`n` are the
   two-session **pooled** counts, not per-session; (c) division-by-zero when `Σattempts = 0` (no
   baseline data) must be handled. Worked example from the doc's own rationale: 1 error in 3
   attempts with `p0 = 0.05` → `(20·0.05 + 1)/(20 + 3) = 2/23 ≈ 0.087`, close to `p0`, so it does
   not rank first — exactly the intent.
4. **Tie-break by "median IKI z-score within the participant" (§3.4 step 3).** The median IKI is the
   bigram's across-session value, but `bigram_stats.iki_median_ms` is **per session** and must NOT
   be averaged as a median-of-medians (CLAUDE.md pattern; §4.5). The "z-score within the
   participant" standardizes a bigram's median against the distribution of per-bigram medians across
   that participant: `z = (m_bigram − mean(m)) / std(m)`; "slower ranks weaker" → larger IKI → used
   only to order bigrams with equal smoothed error rate. Subtleties (Open Q 4): how to get a bigram's
   single across-session median (re-pool raw samples vs combine the two session medians); `iki_n = 0`
   bigrams have `iki_median_ms = NULL`; `std = 0` (all equal) makes z undefined; exact float ties in
   smoothed rate are the only time the tie-break fires, so a *total* deterministic order still needs
   a final tiebreak (e.g. the bigram string) for reproducibility.
5. **Snake deal into 4 sets (§3.4 step 5).** Order A B C D D C B A | A B C D D C B A for 16 bigrams →
   exactly 4 per set; for 12 → A B C D D C B A | A B C D → 3 per set. Both divide evenly into 4.
   `baseline_rank` is the pre-deal rank (1-based); the snake maps rank→set, so e.g. ranks {1,8,9,16}
   → set A. For 2-set mode the snake and counts differ (Open Q 1).
6. **Seeded arm shuffle (§3.4 step 6).** Shuffle `DRILL_ARMS = (control, heuristic, markov, llm)`
   with `assignment_seed` (combined with `participant_id`?), then map A→shuffled[0], …,
   D→shuffled[3]. Determinism depends on the exact shuffle algorithm and the seed-derivation rule
   (Open Q 5). With 2 arms the shuffle is over 2 arms.
7. **Re-running assign on an already-frozen participant.** Must not mutate frozen rows (acceptance).
   Must the endpoint be idempotent (return the existing Assignment) or 409? (Open Q 7.)
8. **Partial / abandoned baseline.** If only one baseline session is completed, or a baseline session
   is `abandoned` (D23(b): abandoned sessions excluded from outcomes), the pool/`p0` is computed over
   less data. §14 says assign is allowed "only in baseline-done state" — define what "baseline-done"
   requires (two completed baseline sessions?) (Open Q 6).
9. **A candidate bigram with 0 observations in both sessions.** It never appears in `bigram_stats`
   (zero-attempt bigrams are omitted, §4.4). It is simply not a candidate; it must not be inserted
   as a row with `attempts = 0`.
10. **A bigram with errors but `iki_n = 0`** (every pair paused or none clean): it can still be a
    candidate by error rate but has no IKI for the tie-break — the tie-break must tolerate NULL.
11. **`weakness_score` precision.** Stored as REAL; the primary analysis (§3.5) does not use it
    (it uses `baseline_attempts`/`errors`), so it is a recorded diagnostic. Its float value must be
    reproducible for the determinism test.
12. **New migration bumps HEAD / seeded-row counts.** Adding `assignment_seed` changes
    `SEEDED_CONFIG_ROWS` and the migration-chain HEAD pins in `tests/integration/test_migrations.py`
    (the `0002` precedent: `SEEDED_CONFIG_ROWS = 11  # 5 from 0001 + 6 from 0002` → 12). These test
    constants must be updated or CI fails even with a correct migration.

## 8. Risks

1. **Non-determinism leaking in** via dict/set iteration order, unordered SQL reads feeding the
   ranking/shuffle, or floating-point ties resolved unstably — breaks the primary acceptance and is
   easy to miss because a single run looks fine.
2. **Freeze not actually enforced** (DB has no trigger) — a later re-run or code path mutates
   "frozen" rows after data exists, silently corrupting the experiment's unit of analysis.
3. **The 20-vs-15 reconciliation getting it wrong** — too strict empties the pool; too loose admits
   under-observed bigrams whose smoothed rate is dominated by the prior. The ADR must be explicit and
   match what T1.8 actually produces (~15 observations).
4. **`p0` / z-score definition ambiguity** (Open Q 3/4) leading to a plausible-but-wrong ranking that
   no test catches unless the plan pins exact formulas and hand-computed fixtures (§17.2).
5. **Set count assumption (4 vs 2)** — hard-coding 4 sets breaks the documented 2-set cut-line
   (`arms_enabled`); hard-coding `DRILL_ARMS` order breaks 2-set mode.

## Owner answers

2026-10-21 — answered by the orchestrator under the autonomous pipeline rule, applying
docs/plans/owner-decisions.md (#1 solo builder participant, #6 the ADR, #7 tables exist).
Sources: (a) design doc, (c) earlier plans/ADRs/owner answers, (d) code conventions,
(e) industry practice. Answer 8 (the ADR) is an experiment-design decision the owner already
mandated; its exact wording is flagged for sign-off in the PR.

1. **Sets = `len(arms_enabled)`; per set 4, fallback 3; generalises "16/12".** Source: (a) 3.4
   steps 4–5 and the section 16 cut-line ("2-set mode … 8 bigrams each"). Pool size =
   `per_set × sets` (4-set: 16, else 12; 2-set: 8, else 6). If fewer than `fallback × sets`
   qualify, raise `AssignmentError("too few candidates: n < m")` — never assign a degenerate
   map; the owner decides (more baseline, or lower threshold by ADR). Set labels are the first
   `sets` letters of A–D. Snake order over `sets` columns: forward, then reversed, repeating.

2. **New `experiment_config` keys via data-only migration `0005_assignment_config`:**
   `assignment_seed: 20261021`, `assignment_prior_strength: 20`, `assignment_min_observations:
   15` (the ADR, answer 8), `assignment_per_set: 4`, `assignment_per_set_fallback: 3`. The
   candidate universe is the tracked list in `top_bigrams.json` (`tracked_bigram_count` already
   exists). All are frozen at T3.5. Source: (a) 17.1 and 3.4 step 6 ("a seed stored in
   experiment_config"); (d) 0002 precedent. Update `SEEDED_CONFIG_ROWS` (11 → 16) and head pins.

3. **`p0 = Σerrors / Σattempts` over every `bigram_stats` row of the participant's baseline
   sessions** (all bigrams with any baseline attempts, not only qualifying ones — that is the
   "overall" rate). `Σattempts == 0` → `AssignmentError("no baseline data")`. Posterior mean =
   `(errors + strength × p0) / (attempts + strength)`. Source: (a) 3.4 step 2; (e) standard
   Beta(α=s·p0, β=s·(1−p0)) posterior mean.

4. **Pool raw IKI samples across both baseline sessions' blocks with
   `attribute_block_samples` (T1.7) and take one median per bigram — not a median of the two
   session medians.** Source: (c) T1.7 answer 3 / T1.9 answer 2. z-score population: every
   candidate with a pooled sample (`iki_n > 0`), mean and population std over their medians;
   `std == 0` or fewer than 2 such candidates → all z = 0; a candidate with no sample → z = 0
   (neutral). Rank key: `(−smoothed_rate, −z, bigram)` — the bigram string is the final total
   order so output is deterministic. `weakness_score` stored = smoothed rate; `baseline_rank` =
   1-based rank; `baseline_attempts`/`baseline_errors` = pooled counts.

5. **`random.Random(f"{assignment_seed}:{participant_id}")`, one stream, used only for
   `rng.shuffle(list(arms_enabled))`.** Source: (c) T1.1 answer 17 (global seed + participant
   id); (b) seeded generator passed in by the caller — the service takes `rng: random.Random`
   and the CLI constructs it from config. Snake dealing uses no randomness. Set i (A, B, …) maps
   to `shuffled[i]`. Test: same seed → identical rows across two fresh DBs; different seed →
   different mapping on at least one of several participants (not necessarily every one).

6. **Preconditions only; no status transition.** Source: (a) T2.8 owns participant
   transitions and the 409 guard. `assign_participant` requires: participant exists; exactly
   `baseline_parts` completed `phase == "baseline"` sessions; no existing `bigram_assignment`
   rows for the participant. Violations raise typed errors (`ParticipantNotFoundError`,
   `BaselineIncompleteError`, `AlreadyAssignedError`) that T2.8's endpoint maps to 404/409.
   T2.2 adds the thin CLI `typist assign --pid` (14.1); the `POST /participants/{pid}/assign`
   endpoint comes with T2.8.

7. **Once only, all-or-nothing, frozen at insert, enforced by the database.** Source: (a) 3.4
   "Frozen rows are never updated" and the acceptance clause; (e) a trigger is the only
   enforcement that survives a buggy service. Migration 0005 also adds
   `CREATE TRIGGER trg_bigram_assignment_frozen BEFORE UPDATE ON bigram_assignment WHEN
   OLD.frozen_at IS NOT NULL BEGIN SELECT RAISE(ABORT, 'bigram_assignment rows are frozen');
   END;` (downgrade drops it). Rows are inserted with `frozen_at` set in one transaction, so
   there is no mutable window; re-running raises `AlreadyAssignedError`. Deleting via
   `delete_participant` stays allowed (section 14 "remove all of a participant's data"). Test:
   an UPDATE on a frozen row raises `IntegrityError` and leaves the row unchanged.
