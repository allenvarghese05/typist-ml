## 2. Why it matters

- **Primary user interface for Milestone M4 (Dashboard and write-up, §16):** Task T4.2 delivers the complete visual analytical surface of Typist-ML, exposing all experimental and telemetry findings directly in the web browser.
- **Visualizes the research outcomes (§1, §3.5, §15.2):** Renders the primary outcome (targeting effect on error rate with Beta posterior credible intervals) and the key secondary outcome (targeting effect on median IKI with bootstrap confidence intervals) across experimental arms versus the control set.
- **Enables downstream milestone tasks (§16):**
  - T4.3 (Results notebook and README figures) references the same data representations and structures validated here.
  - T4.4 (README with numbers, method, limitations, and N) draws directly from the verified database views shown on the dashboard.
  - T4.5 (Debrief page) builds upon participant-specific outcome summaries and arm reveals.
- **Daily operational visibility during the pilot (§15.2, §16 pilot runbook, Owner decision #5):** Allows the builder to inspect daily session trends, bigram error heatmaps, generation queue throughput, and instrumentation overhead throughout the 14-day study.
- **What breaks if it is wrong:**
  - **False evidence / Broken acceptance criteria:** If any view relies on mock data, hardcoded fallbacks, or synthetic generators rather than live SQLite database rows, the core acceptance criterion ("All views load from real data") fails, violating D19 honesty rules.
  - **Misleading scientific comparisons:** If effect sign conventions ($d(s) - d(\text{control})$ or $c(s) - c(\text{control})$) are inverted, or if the control set is not clearly marked, a deleterious arm could be mistaken for an improvement.
  - **Hidden bias:** If the builder's unblinded status (`is_builder = true`, `is_blinded = false`) is obscured or if data is pooled across participants, expectation effects are masked (D01, D18).
  - **Pre-registration violations:** If abandoned sessions or dropped bigrams (<20 retest attempts) are included in outcome calculations rather than reported under exclusions, pre-registration rules (D20, D23) are broken.
  - **Statistical errors (median-of-medians):** If phase-level IKI or timing views aggregate stored session medians instead of pooling raw keystroke IKI samples, calculations are mathematically unsound.
  - **Broken engineering claims:** If overhead percentiles or generation throughput (tokens per second) are miscalculated, claims in the README and résumé become inaccurate.

## 5. Inputs and outputs

Section 15.2 specifies six distinct dashboard views. Data flow for each:

### View 1: Bigram Matrix
- **Input:** `session_id` (or `participant_id` and `phase`). Source: `bigram_stats` table for session view, or pooled raw keystrokes / stats across completed phase sessions.
- **Output:** Rendered 26×26 heatmap grid with letter axes (rows = first letter, columns = second letter). Toggle between error rate and median IKI. Cells colored by metric intensity; empty cells transparent. Hover tooltip displaying bigram, attempts, errors, error rate, and median IKI with sample count.

### View 2: Per-set Outcomes
- **Input:** `participant_id`. Source: `GET /api/v1/analysis/participants/{participant_id}` returning `ParticipantResults`.
- **Output:**
  - Per-set table and chart displaying baseline and retest attempts, errors, error rate, and equal-tailed 95% Jeffreys Beta credible intervals (`[lower, upper]`).
  - Error rate change $d(s) = p(s, \text{retest}) - p(s, \text{baseline})$.
  - Targeting effect versus control: $E(s) = d(s) - d(\text{control})$, median of 100,000 Beta posterior draws, 95% posterior credible interval, and share of draws below zero ($P(E(s) < 0)$).
  - Explicit marking of the held-out control set.
  - Pre-registered exclusions report (excluded sessions, dropped bigrams <20 attempts, pause counts).

### View 3: Timing
- **Input:** `participant_id`. Source: `ParticipantResults.sets` from `GET /api/v1/analysis/participants/{participant_id}`.
- **Output:**
  - Per-set table and chart displaying clean IKI sample counts ($n$), baseline and retest median IKI (ms), and interquartile range (IQR in ms).
  - IKI change $c(s) = m(s, \text{retest}) - m(s, \text{baseline})$.
  - IKI targeting effect versus control: $F(s) = c(s) - c(\text{control})$, median of 10,000 bootstrap resamples, and empirical 95% bootstrap confidence interval.
  - Explicit marking of the held-out control set.

### View 4: Trend
- **Input:** `participant_id`. Source: `SessionTrendEntry` list (currently produced by `typist/services/checks.py` via `GET /api/v1/admin/checks/{participant_id}`).
- **Output:**
  - Chronological performance progression across days and phases.
  - Session WPM and accuracy metrics.
  - Per-set error rates on practice text for Sets A, B, C, D across practice sessions.

### View 5: Generation
- **Input:** Records in `generation_jobs`, `generation_attempts`, and `drills`. Source: new overview / generation endpoint (e.g. `GET /api/v1/analysis/overview`).
- **Output:**
  - Per-arm summary table (`control`, `heuristic`, `markov`, `llm`):
    - Accepted drill count and total generation attempts.
    - Acceptance rate (`accepted / total_attempts`).
    - Attempts per accepted drill.
    - Mean target bigram density (calibrated within $[0.10, 0.40]$).
    - Mean word length and real-word ratio.
  - LLM-specific operational stats: measured tokens per second, generation latency (`gen_ms`), and peak memory (MB).

### View 6: Overhead
- **Input:** `keystroke_events.handler_ms` and `keystroke_events.dispatch_lag_ms` joined through `session_blocks`. Source: `overhead_report` in `typist/services/overhead.py`.
- **Output:**
  - Session-by-session table of event counts, handler lag percentiles (p50, p95, p99 in ms), and dispatch lag percentiles (p50, p95, p99 in ms).
  - Pooled "all" summary row.
  - Comparison against the engineering target (handler p95 < 1.0 ms, §12.5).

## 6. Constraints

- **Local-only execution (D06, D19):** No third-party analytics, external fonts, remote CDNs, or cloud APIs. Everything bundles locally and talks to `http://127.0.0.1:8000/api/v1`.
- **Guide honesty rules (D19, §18):** No claims until real numbers exist. Results are descriptive within-person changes. No p-values or significance claims.
- **Platform compatibility:** MLX model generation is restricted to Apple Silicon (`sys_platform == 'darwin' and platform_machine == 'arm64'`). However, the API endpoints, analysis computations, and web dashboard must build, test, and run cleanly on both macOS and Linux CI environments.
- **Frontend engineering standards (§17.1, D07):** TypeScript `strict: true`. No `any` without an explanatory comment. Biome check (`biome check .`) must pass with zero errors or warnings.
- **Rendering performance:** The 26×26 heatmap (676 cells) and trend tables must render without blocking the UI thread or exceeding memory budgets.
- **Single source of truth:** All statistics displayed in the browser originate from server-computed endpoints; the browser never attributes keystrokes or computes statistical intervals locally (CLAUDE.md).

## 7. Edge cases

1. **Participant has not completed the study (`status != 'done'`):**
   - *Example:* A participant is on day 3 of practice (`status == 'practice'`).
   - Calling `GET /api/v1/analysis/participants/{pid}` returns HTTP 409 Conflict (`ParticipantNotDoneError`).
   - The dashboard must not crash. The Per-set Outcomes and Timing views must display an informative banner stating that study-level outcomes require study completion, while Trend, Matrix, Overhead, and Generation views load real data normally.
2. **Newly enrolled participant with zero completed sessions:**
   - *Example:* A participant has consented (`status == 'baseline'`) but has not finished session 1.
   - Trend has 0 entries; Bigram Matrix has no completed session; Overhead has 0 keystroke events.
   - All views must render clean empty states ("No completed sessions yet") without throwing null pointer or division-by-zero exceptions.
3. **Dropped bigrams (<20 retest attempts, D23(c)):**
   - *Example:* Bigram "qu" has only 14 retest attempts across both retest sessions.
   - The bigram is excluded from Set A's pooled attempts and errors in both baseline and retest.
   - The Outcomes and Timing views must display Set A computed over retained bigrams, while the Exclusions card lists "qu" under dropped bigrams with its attempt count.
4. **Zero attempts or errors in a set:**
   - *Example:* In a two-set test or short session, Set C has 0 attempts.
   - Error rate is `null`, Beta credible interval is `null`, and targeting effect is `null`.
   - The UI must display "-" or "N/A" gracefully rather than `NaN%` or `[null, null]`.
5. **Arms with no generation attempts yet:**
   - *Example:* In two-set mode or before the LLM worker runs, `generation_attempts` has no rows for `arm == 'llm'`.
   - Acceptance rate, tokens per second, and attempts per drill must display "-" without dividing by zero.
6. **Bigram matrix sparse data:**
   - *Example:* A baseline session contains only 45 distinct bigrams; 631 cells have 0 attempts.
   - Empty cells must render with transparent background and tooltip "no data". Color scaling must compute max only over non-empty cells.
7. **Single-event or empty session in overhead report:**
   - *Example:* A session aborted with only 1 keystroke row.
   - Inclusive quantile logic produces `p50 == p95 == p99 == value`. If 0 events, handler and dispatch percentiles are `null`. The UI must format `null` as `-/-/-`.
8. **Multiple participants enrolled (Builder vs Peer):**
   - *Example:* Builder (`is_builder = true`, `is_blinded = false`) and peer (`is_builder = false`, `is_blinded = true`) are in the database.
   - The dashboard must provide a participant selector to switch between them. Results must never be pooled across participants (D01).
9. **Two-set contingency mode (D03, §16):**
   - *Example:* The pilot ran with `arms_enabled = ["control", "heuristic"]`.
   - Sets C and D are unassigned. The dashboard must display only active sets (A and B) and explicitly note that Markov and LLM arms were not evaluated, rather than silently omitting them or crashing.

## 8. Risks

1. **Endpoint gap for overview, generation, and overhead:** Section 14 lists `GET /analysis/overview` ("All participants, overhead, generation stats -> Overview"), but neither `GET /analysis/overview` nor an HTTP endpoint for `overhead_report` currently exists. If the API contract is not cleanly established, frontend data loading will fail.
2. **Heavy computation on page load:** `participant_results` generates 100,000 Beta posterior draws and 10,000 bootstrap resamples on the fly. If invoked repeatedly on every tab switch or re-render, it could introduce noticeable UI latency.
3. **Median-of-medians trap in phase-level matrix:** Aggregating bigram median IKI across sessions by averaging stored medians in `bigram_stats` violates statistical principles. Phase-level median IKI requires pooling raw clean IKI samples or handling phase IKI properly.
4. **Third-party charting library dependency vs React 19:** Introducing external charting packages (such as Recharts, mentioned in §5.1) may cause peer dependency conflicts with React 19 or Rolldown/Vite 8 bundling, jeopardizing `just check`. Clean SVG/Tailwind charts avoid external runtime dependencies.
5. **Biome accessibility (a11y) failures:** Interactive heatmap grids and complex statistical tables can trigger Biome accessibility lint errors (`a11y/useKeyWithClickEvents`, missing ARIA roles or table headers), failing CI checks.
