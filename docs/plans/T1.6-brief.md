## 2. Why it matters

What T1.6 enables later:
- **It is the one write path from the browser into `keystroke_events`.** Everything downstream —
  attribution (T1.7, Python-only), `bigram_stats` / WPM / accuracy (T1.9), the bigram matrix and
  overhead report (T1.10), and the whole experiment's primary and secondary outcomes (D05) — reads
  the rows T1.6 persists. If a row is dropped, duplicated, or stored with the wrong `block_id`/`seq`,
  every number downstream is wrong (section 12 opening: "If a keystroke is attributed to the wrong
  bigram, every result downstream is wrong").
- **It makes uploads durable and idempotent.** Retries with backoff (12.4) require that re-sending a
  batch cannot create duplicate rows; this is exactly the acceptance criterion and the reason
  `keystroke_events` has `UNIQUE (block_id, seq)` and the design calls for `ON CONFLICT (block_id, seq)
  DO NOTHING` (12.4, 8.1, 8.2).
- **It completes the telemetry chain** `TextCursor` (T1.3) → `KeystrokeRecorder` (T1.4) →
  `TypingSurface` (T1.5) → **EventBuffer + endpoint (T1.6)** → DB. T1.5 wired a `CollectorSink`
  stand-in and left the real sink to T1.6 (T1.5 owner answers 1, 7).

What breaks if it is wrong:
- **Duplicate rows** (if idempotency fails) corrupt attribution: a repeated `seq` breaks the 12.3
  "a backspace happened between a and b" test and the 12.6 "gaps in seq" check, and `typist stats
  recompute` would not reproduce the same numbers (M1 "Done when").
- **Lost rows** (if a flush/retry/unload path silently drops a batch) make a block have "fewer events
  than characters in the target text" (12.6 check) and understate attempts.
- **Lost key-ups** (if the merge/late-key-up path is wrong) leave `t_up_ms`/`dwell_ms` null forever,
  inflating "share of keyups missing" (12.6) and losing the dwell signal (12.2).
- **A wrong `block_id` or FK violation** (the block row must exist) would reject every event or attach
  rows to the wrong block.

## 4. Current state

### 4.1 The sink contract T1.6 implements (verbatim, `apps/web/src/telemetry/types.ts`)

```ts
export type Outcome = "correct" | "error" | "backspace";

export interface KeystrokeRow {
  readonly seq: number;
  readonly key: string;
  readonly code: string;
  readonly t_down_ms: number;
  readonly t_up_ms: number | null;   // Null in the row the recorder emits; T1.6 fills it from a KeyUpUpdate (or the server does).
  readonly dwell_ms: number | null;  // null while t_up_ms is null.
  readonly iki_ms: number | null;    // null at seq 0.
  readonly target_index: number;
  readonly expected_char: string | null;  // null for Backspace.
  readonly outcome: Outcome;
  readonly first_attempt: boolean | null; // null for Backspace.
  readonly after_pause: boolean;
  readonly handler_ms: number;
  readonly dispatch_lag_ms: number;
}

export interface KeyUpUpdate {
  readonly seq: number;
  readonly t_up_ms: number;
  readonly dwell_ms: number;   // t_up_ms minus that row's t_down_ms.
}

export interface KeystrokeSink {
  onRow(row: KeystrokeRow): void;      // "A new row, created at keydown, with t_up_ms and dwell_ms null. Never mutated afterwards."
  onKeyUp(update: KeyUpUpdate): void;  // "The key-up for an earlier row, early or late."
}
```
Key facts stated in the file's doc comments: the `KeystrokeRow` has **no `block_id` and no `id`**
("id and block_id are not the recorder's (T1.6 adds block_id)") and **no `release_to_press_ms`**
("release_to_press_ms is never a row field (T1.2 answer 10a)"). "Calls are synchronous, from inside
the key handlers, so implementations must be cheap and must not throw." The T1.4 plan contract
(verbatim): "T1.6 | implements `KeystrokeSink` | `onRow(row)`: a new row, `t_up_ms`/`dwell_ms` null.
`onKeyUp(update)`: fill that `seq`'s `t_up_ms` and `dwell_ms` (copy, do not mutate the row object),
or forward it as a late key-up. Must not throw."

### 4.2 The stand-in sink T1.6 replaces or supplements (`apps/web/src/features/session/collector.ts`)

```ts
/** An in-memory sink standing in for T1.6's EventBuffer (owner answer 7). Keeps everything it sees. */
export interface CollectorSink extends KeystrokeSink {
  readonly rows: KeystrokeRow[];
  readonly keyUps: KeyUpUpdate[];
  readonly lifecycle: BlockLifecycleEvent[];
  readonly recordLifecycle: (event: BlockLifecycleEvent) => void;
}
export function createCollectorSink(): CollectorSink
```
`TypingSurface` takes the sink as a prop and fans the recorder's output into both the display store
and `props.sink` (`TypingSurface.tsx`): the recorder is built with `new KeystrokeRecorder({ targetText,
blockStartMs, sink: fanOut })`, where `fanOut.onRow` calls `sinkRef.current.onRow(row)` and
`fanOut.onKeyUp` calls `sinkRef.current.onKeyUp(update)`. Block-level events are a separate channel:
```ts
export type BlockLifecycleEvent =
  | { readonly kind: "start"; readonly attempt: number; readonly blockStartMs: number }
  | { readonly kind: "complete"; readonly attempt: number }
  | { readonly kind: "abandon"; readonly attempt: number };
```
(reported via `props.onLifecycle`, not via the `KeystrokeSink`). So EventBuffer, as a `KeystrokeSink`,
sees rows and key-ups but **not** `block_id`, `blockLabel`, or lifecycle; `block_id` must be supplied
to it some other way (open question 9).

### 4.4 The target table and its constraints (`models/keystroke_events.py`, migration 0001)

```python
class KeystrokeEvent(SQLModel, table=True):
    __tablename__ = "keystroke_events"
    __table_args__ = (
        sa.UniqueConstraint("block_id", "seq"),
        sa.CheckConstraint("outcome IN ('correct','error','backspace')", name="outcome"),
        sa.CheckConstraint("seq >= 0", name="seq"),
    )
    id: int | None = Field(default=None, primary_key=True)   # SQLite rowid
    block_id: str = Field(foreign_key="session_blocks.id")   # FK: block must exist
    seq: int
    key: str
    code: str
    t_down_ms: float
    t_up_ms: float | None = None
    dwell_ms: float | None = None
    iki_ms: float | None = None
    release_to_press_ms: float | None = None   # negative under rollover; "never backfilled"
    target_index: int
    expected_char: str | None = None
    outcome: str
    first_attempt: bool | None = None
    after_pause: bool = Field(default=False, sa_column_kwargs={"server_default": sa.text("0")})
    handler_ms: float
    dispatch_lag_ms: float
```
Facts from the model docstring and migration: `(block_id, seq)` is unique "so uploads can use ON
CONFLICT (block_id, seq) DO NOTHING (section 12.4)"; `block_id` is a **foreign key to
`session_blocks.id`** (WAL, `foreign_keys=ON`), so events for a non-existent block are rejected;
`release_to_press_ms` "is never backfilled" and the browser row never carries it (open question 3);
`t_up_ms`/`dwell_ms` are NULL until the key-up arrives (it may never); `after_pause` has a server
default of 0. Index: `keystroke_events (block_id, seq)` unique (8.2).

## 5. Inputs and outputs

EventBuffer (browser):
- **Inputs:** `KeystrokeRow`s via `onRow` (from the recorder through `TypingSurface`'s fan-out),
  `KeyUpUpdate`s via `onKeyUp` (early or late), and a `block_id` supplied out of band (not on the row;
  open question 9). A clock/timer for the 2 s, 5 s flush, and backoff schedules.
- **Outputs:** HTTP `POST` batches to `apiPath("/blocks/{block_id}/events")` →
  `/api/v1/blocks/{block_id}/events`, each row carrying its `block_id` + the 14 recorder fields (and,
  per the merge, `t_up_ms`/`dwell_ms` when known). On page unload, remaining rows via
  `navigator.sendBeacon`. Failed requests retried with backoff.

Events endpoint (Python):
- **Inputs:** path `block_id`, JSON body = a batch of keystroke rows (request schema, to be designed).
  The `block_id` must already exist in `session_blocks` (FK).
- **Outputs:** writes rows to `keystroke_events` with `ON CONFLICT (block_id, seq) DO NOTHING`;
  returns "accepted and duplicate counts" (section 14) as a response schema (field names to be
  designed — open question 5). Rows land where attribution (T1.7) and `typist stats recompute` (T1.9)
  read them.

Files likely in scope (section 7; not prescriptive): `apps/web/src/telemetry/EventBuffer.ts` + Vitest
tests; a backend `api/routers/events.py` + a `services/` module + `schemas/` DTOs + integration tests;
registration in `main.py`; possibly `apps/web/src/api/client.ts` and/or `gen-types` wiring (open
question 12). No migration is needed — `keystroke_events` and its unique constraint already exist.

## 6. Constraints

- **Idempotent insert via `ON CONFLICT (block_id, seq) DO NOTHING`** (12.4, 8.1): the exact acceptance
  behaviour. Re-sending a batch must not duplicate rows and must not error.
- **Append-only** (6.2, CLAUDE.md): the endpoint may insert, and may fill in the key-up time once (via
  `record_key_up`), but must never otherwise update a stored row. A re-sent row whose content differs
  from the stored one is silently ignored by `DO NOTHING` (a correctness subtlety — open question 11).
- **Thin router, logic in a service, no table models returned** (17.1): the endpoint returns a
  response schema, not `KeystrokeEvent`.
- **Config, not literals** (17.1): the 50-row, 5-second, 2-second thresholds and the backoff schedule
  are parameters and should not be hard-coded inside logic. Where they live (a TS constants module
  like `sessionConfig.ts`, or `experiment_config`) is a design choice; note `block_chars` already
  lives in `experiment_config`.
- **Handler must stay cheap** (12.5 tail): `onRow`/`onKeyUp` run synchronously inside the key handler;
  the EventBuffer must only enqueue (no network, no heavy allocation) in those calls — flushing happens
  on timers/thresholds, off the handler path.
- **Must not throw from the sink** (types.ts; T1.4 contract): buffering and send failures must be
  caught inside the EventBuffer, never propagated into the recorder/handler.
- **FK + WAL + `foreign_keys=ON`** (8.0): events require an existing `session_blocks.id`; integration
  tests must seed a block (see `conftest.py seeded_ids`, which already creates one block and one
  keystroke).
- **Local only** (D06, D19): POST to `127.0.0.1` through the Vite proxy; `sendBeacon` to the same
  same-origin path; no external endpoints.
- **Tooling gates** (D21): `biome ci .`, `biome format .`, `tsc -b`, `vitest run`, `vite build`;
  `ruff`, `pyright` (strict for `src/`), `pytest`. CI is Linux; nothing Apple-Silicon-specific.
- **Strict TS + Biome**: no `any` without a comment, `noUncheckedIndexedAccess`, `erasableSyntaxOnly`,
  `verbatimModuleSyntax`, `noExplicitAny: error`.
- **Scope hygiene**: one task per PR, branch per task, conventional commits; never push to main; never
  merge.

## 7. Edge cases

1. **Exact duplicate batch resent** (the acceptance case). Send `[seq 0..9]` twice: after the second
   POST the table still has 10 rows; the response reports 10 accepted + 10 duplicates (or however the
   schema names it). Driven by `UNIQUE (block_id, seq)` + `DO NOTHING`.
2. **Partial-overlap batch.** First POST `[0..9]`, retry after a flush adds `[8..14]`: rows 8 and 9
   are duplicates, 10–14 are new. The response must distinguish accepted vs duplicate per batch, not
   reject the whole batch.
3. **Row sent without its key-up, key-up arrives later** (the central case). 12.4: "sent once its
   keyup has arrived, or after 2 seconds without one (keyup stays null)." If EventBuffer holds each
   row until its key-up or 2 s, a row is POSTed exactly once with `t_up_ms` already set or null. But a
   **block-end flush or 50-row flush can force a row out before 2 s with no key-up**, and the key-up
   then arrives afterwards — with `DO NOTHING` the re-POST will not update it, so the key-up needs the
   separate `record_key_up` path, which has no route (open questions 1, 2). Example: hold a key across
   the block-end flush.
4. **Key held longer than 2 s (stuck key).** `a` held 2.5 s: row sent at 2 s with `t_up_ms` null; the
   release at 2.5 s yields dwell 2500 ms, which 12.6 flags as a stuck key. Whether that late dwell is
   persisted at all depends on open question 1.
5. **Page unload mid-block.** `navigator.sendBeacon(url, body)` fires the remaining rows with no
   response and limited headers/content-type (often `text/plain` or a `Blob`); the endpoint may need
   to accept the beacon's content type, and the client cannot read accepted/duplicate counts back
   (open question 6). Example: participant closes the tab after typing 40 of 600 chars.
6. **Failed request then retry (backoff).** Network/500 error: the batch is retried; because of
   idempotency a batch that actually committed server-side but whose response was lost is safely
   re-sent (stored once). The EventBuffer must not drop the batch on the first failure.
7. **Empty batch / block with zero keystrokes.** A POST with `[]` (e.g. block-end flush with nothing
   buffered): must be a no-op returning 0/0, not an error.
8. **Out-of-order or non-contiguous `seq` within a batch.** The recorder emits contiguous `seq` from
   0, but flushes/retries can interleave; the endpoint must store by `(block_id, seq)` regardless of
   array order, and 12.6 ("gaps in seq") is a later check, not something T1.6 should "repair".
9. **Nullable fields serialized as JSON.** `t_up_ms`, `dwell_ms`, `iki_ms`, `expected_char`,
   `first_attempt` can be `null`; `after_pause`/`first_attempt` are booleans. JSON `null` must map to
   SQL `NULL`, and booleans to the SQLite 0/1 the model/migration expect (`after_pause` server default
   0). A Backspace row has `expected_char = null`, `first_attempt = null`, `outcome = "backspace"`.
10. **`release_to_press_ms` is not in the browser row.** The column exists and can be negative under
    rollover (12.2), but the recorder never sends it (T1.2 answer 10a) and `record_key_up` "never
    backfills" it. So either the endpoint computes it from the previous row's `t_up_ms` at insert, or
    it stays null forever (open question 3). Example: `t` released at 2700, `h` pressed at 2765 →
    release-to-press 65; `h` pressed before `t` released → negative.
11. **`block_id` for a block that does not exist** (FK violation) or belongs to a different
    participant. In production the block comes from the session plan; in T1.6's world no block/session
    API exists, so tests must seed the block. The endpoint's behaviour on an unknown `block_id`
    (404 vs 409 vs DB error) is unspecified (open question 11b).
12. **Duplicate `seq` with different content.** A buggy client re-sends `seq 5` as a different key.
    `DO NOTHING` keeps the first silently; nothing flags the mismatch. Whether T1.6 should detect and
    report this, or trust the client, is unsettled (open question 11).
13. **Very large block.** 600-char blocks (3.3) with corrections produce >600 rows; the 50-row flush
    means ~12+ POSTs per block. Batches must be bounded and ordering of overlapping in-flight POSTs
    must not corrupt counts.
14. **`block_id` with URL-unsafe characters.** Block ids are UUID strings (`new_id`), so path-safe in
    practice, but `apiPath` only checks the leading "/"; the client builds `/blocks/{id}/events`.
15. **Concurrency / WAL.** Two in-flight POSTs for the same block (a retry racing a fresh flush) both
    insert; `DO NOTHING` + the unique index keep it to one row each, but the per-batch accepted count
    must be computed correctly under this race (e.g. via `changes()`/rowcount, not a pre-count).

## 8. Risks

1. **Late key-ups never reach the database.** With `ON CONFLICT DO NOTHING` and no route wired to
   `record_key_up`, any row flushed before its key-up (block-end or 50-row flush) keeps `t_up_ms` null
   permanently, silently inflating the 12.6 "share of keyups missing" check and losing dwell. Most
   likely correctness gap; hinges on open question 1.
2. **Idempotency implemented as a pre-SELECT instead of `ON CONFLICT`,** creating a race window where
   a concurrent retry double-inserts. The design explicitly names `ON CONFLICT ... DO NOTHING` for
   this reason.
3. **Accepted/duplicate counts computed wrong** (e.g. counting intended rows rather than actual
   inserts) so the client's retry logic or a data check misreads durability.
4. **`sendBeacon` content-type mismatch** causing the endpoint (expecting `application/json`) to
   reject the final unload batch, losing the tail of a block.
5. **EventBuffer doing work inside the handler** (allocating/sending in `onRow`) inflating
   `handler_ms`/`dispatch_lag_ms` and breaking the 12.5 overhead target.
6. **EventBuffer throwing out of `onRow`/`onKeyUp`** into the recorder/handler (contract says it must
   not), breaking typing.
7. **Scope creep** into T1.5 (listeners), T1.9 (block/session creation), or building a whole API
   client / `gen-types` pipeline when a minimal `fetch` would do (open question 12).
8. **Guessing API shapes** for a batch request/response that later diverge from how T1.7/T1.9 read the
   rows or from the generated OpenAPI types.

## 9. Open questions

The design doc does not settle these. They are numbered so the owner can answer by number.

1. **How does a late key-up ever reach the database, given `ON CONFLICT (block_id, seq) DO NOTHING`?**
   12.4 says a row is "sent once its keyup has arrived, or after 2 seconds without one". Two readings:
   (a) EventBuffer **holds each row until its key-up or 2 s**, so each row is POSTed exactly once and
   normally already carries `t_up_ms`; late key-ups only matter when a flush forces a row out early.
   (b) Rows are POSTed eagerly without key-ups and the key-up is sent separately. Which is intended?
   And when a row *was* flushed with `t_up_ms` null, does T1.6 persist the later key-up — via the
   existing `record_key_up` service behind a new route — or is that late key-up simply dropped?
   In plain terms: `record_key_up` exists but nothing calls it over HTTP. If the buffer ever sends a
   row before its release, something has to carry the release in afterwards, and today nothing does.

2. **Does T1.6 add a key-up route, or is `POST /blocks/{bid}/events` the only endpoint it builds?**
   Section 14 lists no key-up endpoint; `record_key_up` is an unrouted service. If key-ups travel
   inside the events batch (reading (a) above), no new route is needed and `record_key_up` stays a CLI
   / server-fill helper. Confirm the single-endpoint scope.

3. **Who sets `release_to_press_ms`, and does T1.6 compute it?** The column exists and is meaningful
   (12.2, can be negative under rollover), but the browser row omits it (T1.2 answer 10a) and
   `record_key_up` "never backfills" it. Should the events endpoint compute
   `release_to_press_ms = t_down_ms − previous row's t_up_ms` at insert (needs the previous row's
   key-up, which may be null or arrive in a later batch), or does it stay null in M1 and get derived at
   analysis time, or is it out of scope entirely for T1.6?

4. **What is the batch request schema?** A JSON array of rows, or `{ "events": [...] }`? Which fields
   are required vs optional (the nullable ones)? Does the client send `block_id` in each row, only in
   the path, or both (and must they match)? This decides the DTO and the generated types.

5. **What exactly are the "accepted and duplicate counts" (section 14)?** The response field names and
   shape — e.g. `{ "accepted": int, "duplicates": int }` vs `{ "inserted", "skipped" }` — and whether
   it echoes anything else (e.g. the max stored `seq`). T1.7/T1.9 and the client's retry logic depend
   on this.

6. **How does the endpoint accept the `navigator.sendBeacon` unload batch?** `sendBeacon` cannot set
   arbitrary headers and typically sends `text/plain` or a `Blob`; the FastAPI route may need to
   accept that content type (or the client must send a `Blob` of type `application/json`). And since
   the client cannot read the beacon's response, is the unload batch considered best-effort (accepted
   on next load's idempotent resend) or must it be guaranteed?

7. **How much of 12.4 is in T1.6's scope versus deferred?** The acceptance criterion names only the
   duplicate-batch behaviour. Does T1.6 build the full durability stack now (2 s rule, 50-row / 5 s /
   block-end flush triggers, backoff, `sendBeacon`), or only the idempotent endpoint plus a minimal
   buffer, leaving some durability refinements to a follow-up? If full, confirm the exact numeric
   parameters and where they live (constants module vs `experiment_config`).

8. **Does T1.6 wire EventBuffer into `TypingSurface` (replacing the collector), or ship it standalone
   with its own tests?** T1.5's `CollectorSink` is the current prop; does T1.6 (a) leave `TypingSurface`
   using the collector and only build/test EventBuffer + endpoint in isolation, or (b) make
   EventBuffer the real sink the surface uses in some integration/demo path? There is no screen or
   session plan to drive it end to end yet.

9. **Where does EventBuffer get its `block_id`?** The `KeystrokeRow` has no `block_id` and the sink
   receives no lifecycle events; `BlockLifecycleEvent.start` (on `onLifecycle`, a separate channel)
   carries `attempt`/`blockStartMs` but not `block_id`. Is `block_id` a constructor argument to
   EventBuffer (supplied from props/fixtures, mirroring T1.5 owner answer 3), and does a restarted
   block (new `attempt`) get a new EventBuffer, or the same one with a new target?

10. **Does the endpoint validate row contents, or trust the client?** The model has CHECK constraints
    on `outcome` and `seq >= 0` and an FK on `block_id`, so some validation is enforced at the DB. Must
    the endpoint additionally validate charset (D13), field combinations (e.g. Backspace ⇒
    `expected_char`/`first_attempt` null), or monotonic `seq`, or is DB-level enforcement sufficient
    for M1?

11. **Idempotency semantics on content mismatch and unknown block.** (a) If a re-sent `(block_id, seq)`
    has *different* content than the stored row, `DO NOTHING` keeps the first silently — should T1.6
    detect and report this as a conflict, or is silent-keep acceptable? (b) What status/shape should an
    events POST for a non-existent `block_id` return (404, 409, validation error), given the FK will
    otherwise raise a DB error?

12. **Does T1.6 introduce the API client / type generation, or hand-roll `fetch`?** Section 7
    anticipates `api/client.ts` and generated `api/schema.d.ts`, and `just gen-types` is a placeholder.
    Does T1.6 add `openapi-typescript` + a `client.ts` (a larger scope, first user of generated types),
    or post with a minimal `fetch`/`sendBeacon` helper built on the existing `apiPath` and leave
    `gen-types` to a later task (as T0.2 deferred Playwright/Recharts to their first users)?

## Owner answers

2026-10-19 — answered by the orchestrator under the autonomous pipeline rule (CLAUDE.md). Source
letters: (a) design doc / D-numbers, (b) CLAUDE.md, (c) earlier briefs, plans and owner answers,
(d) existing code patterns, (e) industry practice. The owner can override any of these in the PR.

1. **Late key-ups: reading (a), and the flushes only ever send *ready* rows.** Source: (a) 12.4
   literally: "sent once its keyup has arrived, or after 2 seconds without one (keyup stays null)".
   A row is *ready* when its key-up has arrived or 2 s have passed since its keydown. The 50-row,
   5 s and block-end flushes send only ready rows; a block-end flush does not force pending rows out,
   the buffer simply keeps living until each pending row becomes ready (≤ 2 s later) and then sends
   it. So every row is POSTed exactly once with its final `t_up_ms`, and the only key-ups that arrive
   after a send are stuck keys held > 2 s (12.6 flags these anyway) and page unload. Those late
   key-ups are **dropped** — "keyup stays null", exactly as 12.4 says. `record_key_up` stays an
   unrouted service for CLI/repair use. Reasoning: this is the literal design-doc text, needs one
   endpoint, and never updates a stored row from the upload path.

2. **Single endpoint.** Source: (a) section 14 lists no key-up route. T1.6 builds only
   `POST /blocks/{bid}/events`.

3. **`release_to_press_ms` is out of scope and stays NULL.** Source: (c) T1.1 answer 6 and T1.2
   answer 10a: "computed from stored timestamps at read time, not stored eagerly", "never
   backfilled". The endpoint does not compute it; the model column is simply left at its default.

4. **Request schema: `{ "events": [row, ...] }`; `block_id` only in the path.** Source: (d) the
   `KeystrokeRow` has no `block_id` and T1.4 said "T1.6 adds block_id" — it adds it by addressing the
   endpoint, not by widening the row; (e) an object wrapper is the standard extensible batch shape in
   OpenAPI and is what `sendBeacon` can carry as one JSON blob. Every one of the 14 recorder fields is
   required; nullable ones are required-but-nullable (`t_up_ms`, `dwell_ms`, `iki_ms`,
   `expected_char`, `first_attempt`), since the recorder always emits them. Field names are snake_case
   as on the row (T1.2 answer 3), so the row serialises with no renaming.

5. **Response: `{ "accepted": int, "duplicates": int }`.** Source: (a) section 14's own words
   "accepted and duplicate counts". `accepted` = rows actually inserted (from the statement rowcount,
   not a pre-count; brief edge case 15), `duplicates` = `len(events) - accepted`. Nothing else echoed.

6. **`sendBeacon` sends a `Blob` of type `application/json`; the unload batch is best-effort.**
   Source: (e) same-origin `sendBeacon` with a JSON-typed Blob reaches FastAPI as a normal JSON body,
   so the endpoint stays JSON-only; the response is unreadable by design, so no retry is possible
   after unload. Idempotency means an earlier successful-but-unacknowledged batch is harmless.

7. **Full 12.4 is in scope; parameters are constructor options with defaults in a TS constants
   module.** Source: (a) 6.1 gives EventBuffer "batching, retries, final flush on unload" and says it
   "must not drop events silently"; (d) T1.5's `sessionConfig.ts` pattern. Defaults:
   `keyUpWaitMs = 2000`, `flushRows = 50`, `flushIntervalMs = 5000`, backoff exponential
   `500 ms × 2^n` capped at 8000 ms, retried indefinitely while the page lives (never dropped). These
   are transport parameters, not experiment parameters, so they live in
   `apps/web/src/telemetry/eventBufferConfig.ts`, not `experiment_config`. Timers and `fetch` are
   injectable so Vitest can use fake timers and a fake transport.

8. **Standalone; `TypingSurface` and the `App` demo are untouched.** Source: (c) T1.5 answer 3 (no
   wiring against things that do not exist): no block row can exist in the DB yet (no session/block
   API), so a live EventBuffer in the demo would only ever 404 on the FK. EventBuffer implements
   `KeystrokeSink` and is tested on its own with a fake transport; the session flow task (T1.9/M2)
   swaps it in for the collector.

9. **`block_id` is a constructor argument; one EventBuffer per attempt.** Source: (d) T1.5 creates a
   fresh recorder and store per attempt; the buffer mirrors that. A restarted block gets a new
   EventBuffer (the old one finishes flushing and is disposed); the later wiring task decides the
   block id for a restarted attempt (owner's flagged future requirement in T1.5 answer 4/5).

10. **Validate shape and invariants in the request schema; trust the DB for the rest.** Source:
    (a) D13 and the 12.1 capture rules; (e) Pydantic is the validation layer. The schema enforces:
    `seq >= 0`; `outcome` in the three literals; `key` matches `^[a-z ]$` or equals `"Backspace"`;
    `code` non-empty; Backspace ⇒ `expected_char` and `first_attempt` are null, non-Backspace ⇒
    both non-null; `t_up_ms` null ⇔ `dwell_ms` null. It does **not** require monotonic or contiguous
    `seq` within a batch (batches interleave under retry; 12.6 checks gaps later). Invalid rows reject
    the whole batch with 422 (nothing partially inserted).

11. **(a) Silent keep. (b) 404.** Source: (a) 12.4 names `DO NOTHING`; content-mismatch detection is
    a 12.6 data-check concern, not an upload concern. For (b), the service checks the block exists
    before inserting and the router returns 404 `{"detail": "block not found"}` rather than leaking
    an FK error as a 500.

12. **Hand-rolled `fetch`/`sendBeacon` on the existing `apiPath`; no `openapi-typescript` yet.**
    Source: (c) T0.2 deferred each tool to its first real user and T1.5 answer 3 declined to build
    `client.ts` early. T1.6 adds a small transport interface inside `EventBuffer.ts` (default
    implementation uses `fetch`, with `sendBeacon` for unload) and a hand-written request/response
    type derived from `KeystrokeRow`. `just gen-types` stays a placeholder.
