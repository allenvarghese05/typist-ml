# T2.4 brief — Control and heuristic generators

*Analyst brief. Facts only; no design or implementation.*

## 1. Task

- **ID:** T2.4 (milestone **M2 "Loop with heuristic and control"**, design doc §16).
- **Title (verbatim, §16):** "Control and heuristic generators".
- **Acceptance criteria (verbatim, §16):** "50 drills each pass the validator; deterministic
  by seed".
- **Test-type mandate (§17.2 verbatim):** "Validator and generators | Each rule, determinism,
  density range | pytest unit".

## 2. Why it matters

The control and heuristic generators are the first two concrete `DrillGenerator` implementations
and are the pair M2's "Done when" ("A test participant goes baseline, assign, practice, retest end
to end") runs on; T3.1 (Markov) and T3.2 (LLM) are added later and must slot into the same
protocol and the same `validate` gate without reshaping either.

- **Control is the comparison floor (D02, §1 Control row).** §3.3: "The control block is
  frequency-weighted random words. It targets nothing, so it provides equal practice time without
  targeting." §13.2: it also records a *natural density* "for each set, which also shows how much
  more exposure the targeted arms gave." If control is wrong, the within-person targeted-vs-plain
  contrast (the primary outcome, D05) has no baseline.
- **Heuristic is the dictionary baseline the LLM must beat (research question, §1).** §13.3 is the
  recipe. If the heuristic cannot reliably produce drills inside the shared density range with
  coverage ≥3, the heuristic arm is starved, and §13.6's bake-off and §15.2 "Generation" view
  (acceptance rate, attempts per accepted drill) compare the LLM against a broken baseline.
- **Both must satisfy the one fairness gate (D16, T2.3's `validate`).** The experiment's core
  comparability claim is that "arms differ only in method" (§13.1). A generator that quietly
  violates length, charset, coverage, density or repetition breaks that claim.

What breaks if it is wrong: a non-deterministic generator breaks the "Same spec and seed gives the
same text" rule (§13.1, §17.2) and makes the drill pool irreproducible; a heuristic that cannot hit
density/coverage starves its arm (§18 risk is stated for the LLM, but the same failure mode applies
if the heuristic cannot pass its own gate); a control generator that repeats a word >3 times trips
`word_repeat` and the acceptance "50 drills each pass" fails.

## 3. Governing decisions (each D-number and what it forces here)

- **D03 (Arms = `control, heuristic, markov, llm`):** T2.4 implements exactly the `control` and
  `heuristic` members of `Arm` (already in `base.py` and `DRILL_ARMS`). Control has **no targets**
  (`DrillSpec.target_bigrams == ()`); heuristic has targets (the frozen per-set bigrams from T2.2).
- **D13 (text scope — a–z + space, letter-letter bigrams only):** both generators emit lowercase
  `a`–`z` + single spaces, no leading/trailing/doubled space; bigram logic uses the one project
  definition `count_bigrams`/`word_bigrams`, never a re-implementation (CLAUDE.md "one source of
  truth").
- **D16 (fairness gate):** every produced drill must pass `validate` — length ≥270, charset,
  density range (heuristic only), per-bigram coverage ≥3 (heuristic only), word/bigram repetition.
  Control skips density/coverage because it has no targets.
- **D17 (word list — wordfreq, a–z):** both generators draw words from the corpus artifacts built
  from wordfreq (`words.json`), never a second word source.
- **D11 (batch generation) / §10.2:** generation is off the typing path; the validator-retry loop
  that turns rejected candidates into accepted drills is the **GenerationService worker (T2.5)**,
  not T2.4. Open Q 3 pins down whether `generate` returns one candidate per call.
- **D19/D06 (local-only, no cloud/WASM):** pure local Python; no mlx-lm import (these two arms are
  non-LLM, importable in Linux CI — CLAUDE.md).
- **D20 / freeze:** `d_min`/`d_max` are frozen in M3 (§13.5 "Frozen for the pilot: … d_min and
  d_max"); the generators must read the range from the spec/config, never hard-code it. §13.3's
  softmax temperature `0.5` and top-`50` are algorithm constants, not experiment knobs (precedent:
  `test_composer.py` keeps them as module literals).

### 4.2 The shared contracts T2.4 implements against (`generation/base.py`, verbatim)

```python
class Arm(StrEnum):
    CONTROL = "control"
    HEURISTIC = "heuristic"
    MARKOV = "markov"
    LLM = "llm"

@dataclass(frozen=True)
class DrillSpec:
    participant_id: str
    arm: Arm
    target_bigrams: tuple[str, ...]  # empty for CONTROL
    length_chars: int = 300
    min_density: float = 0.15
    max_density: float = 0.40
    seed: int = 0

@dataclass(frozen=True)
class DrillCandidate:
    text: str
    raw_output: str
    generator_version: str
    seed: int
    model_id: str | None = None
    prompt_version: str | None = None
    gen_ms: float | None = None
    gen_tokens: int | None = None
    tokens_per_sec: float | None = None
    peak_memory_mb: float | None = None

@runtime_checkable
class DrillGenerator(Protocol):
    arm: Arm
    version: str
    def generate(self, spec: DrillSpec) -> DrillCandidate: ...
```

`DrillCandidate` carries **no fairness metrics** (T2.3 owner answer 1): the validator computes
`target_density`, `mean_word_len`, `real_word_ratio`, coverage, etc. For non-LLM arms `raw_output`
equals `text`, and `model_id`/`prompt_version`/the four timing fields are `None`.

### 4.3 The validator every drill must pass (`generation/validator.py`, verbatim signatures)

```python
def validate(
    text: str,
    spec: DrillSpec,
    config: ValidatorConfig,
    known_words: Collection[str],
) -> ValidationResult: ...

def load_validator_config(session: Session) -> ValidatorConfig: ...

@dataclass(frozen=True)
class ValidatorConfig:
    min_length_chars: int
    min_coverage: int
    max_word_repeats: int
    max_bigram_run: int
    min_real_word_ratio: float

@dataclass(frozen=True)
class DrillMetrics:
    length_chars: int
    target_density: float
    mean_word_len: float
    real_word_ratio: float
    coverage: dict[str, int]
    max_word_count: int
    bigram_run: int

@dataclass(frozen=True)
class ValidationResult:
    accepted: bool
    reasons: tuple[RejectReason, ...]
    metrics: DrillMetrics

class RejectReason(StrEnum):
    TOO_SHORT; BAD_CHARSET; DENSITY_LOW; DENSITY_HIGH; COVERAGE
    WORD_REPEAT; BIGRAM_REPEAT; REAL_WORD_RATIO
```

Rules the generators must satisfy (from `validate`, verbatim behaviour):
- `too_short` when `len(text) < config.min_length_chars` (seeded default `drill_min_length_chars =
  270`).
- `bad_charset` when `text` is empty, has any non-`[a-z ]` char, or any leading/trailing/doubled
  space (`_charset_ok`).
- `density_low`/`density_high` **only when `spec.target_bigrams`** is non-empty: single density =
  Σ(target-bigram occurrences) / all letter-letter bigrams, below `spec.min_density` (0.15) or
  above `spec.max_density` (0.40); bounds inclusive.
- `coverage` only for targeted specs: any target occurs `< config.min_coverage` (3) times.
- `word_repeat` when any non-empty token occurs `> config.max_word_repeats` (3) times (i.e. 4+).
- `bigram_repeat` when the longest same-bigram run at consecutive letter positions **within one
  word** reaches `config.max_bigram_run` (3): `"thth"` → run 2 (ok), `"ththth"` → run 3 (reject);
  never across a space.
- `real_word_ratio` is recorded for every arm but **gates only `Arm.LLM`** — not control or
  heuristic.

### 4.5 The T1.8 composer — a §13.3-style loop to possibly reuse/share (`services/test_composer.py`)

The baseline composer is "a 13.3-style loop" (CLAUDE.md). Its reusable pieces (verbatim
signatures):

```python
# module constants
_TEMPERATURE = 0.5        # 13.3 step 4 softmax temperature
_TOP_CANDIDATES = 50      # 13.3 step 4 "sample one of the top 50"
_CANDIDATE_POOL = 400     # eligible words gathered per step
_MIN_WORD_LEN = 2; _MAX_WORD_LEN = 10
_MAX_USES_PER_PART = 2    # 13.3 step 5 "skip words already used twice"

@dataclass(frozen=True)
class _Candidate:
    log_frequency: float
    target_bigrams: tuple[str, ...]

def _eligible(words: tuple[str, ...], used: dict[str, int]) -> list[str]: ...
def _has_eligible(words: tuple[str, ...], used: dict[str, int]) -> bool: ...
def _source_bigram(tracked, coverage, target, used, by_target, rng) -> str | None: ...
def _choose_word(eligible, candidates, coverage, target, rng) -> str: ...
def compose_baseline(config: BaselineConfig, index: WordIndex, rng: random.Random) -> list[TextPassage]: ...
```

`_choose_word` is the seeded softmax-over-top-50 sampler the heuristic needs:
```python
pool = ranked[:_TOP_CANDIDATES]
scores = [score for score, _ in pool]
highest = max(scores)
weights = [math.exp((score - highest) / _TEMPERATURE) for score in scores]
threshold = rng.random() * sum(weights)   # seeded selection; rng passed by caller
cumulative = 0.0
for word, weight in zip(words, weights, strict=True):
    cumulative += weight
    if threshold <= cumulative:
        return word
return words[-1]
```

**But the §13.3 scoring differs from `_choose_word`'s.** `compose_baseline`'s `_source_bigram`
picks by *largest deficit* against a coverage target (`baseline_min_occurrences`), and
`_choose_word` ranks by `gain = Σ max(target - coverage[b], 0) / (len(word)+1)` then log-frequency.
§13.3 steps 3–4 for drills say: pick the target with the **lowest coverage** (no deficit/target
cap), and score candidate words by `score = target-bigram density of the word × log(frequency)`,
not by deficit-weighted gain per unit length. The constants (`0.5`, top-50, 2-uses, 2–10 letters)
match; the selection formula and the termination condition (composer stops at `baseline_part_chars`
via a coverage-driven `_source_bigram` that can return `None`; the drill runs until `length_chars`
is reached) do not. What is shared vs re-derived is Open Q 4/5.

The composer is **pure and seeded** (takes `random.Random` from the caller), uses `count_bigrams`
for its stored counts, trims to a word boundary, no leading/trailing/doubled space — the exact
properties `validate` requires. `compose_baseline` resets the per-use cap each part; a single drill
has no "parts".

## 6. Constraints

- **Determinism (§13.1, §17.1, §17.2; acceptance):** "Same spec and seed gives the same text."
  Randomness only through a `random.Random` passed/derived from the seed; same spec+seed →
  byte-identical text; different seed → (generally) different text. This is half the acceptance.
- **Pass the validator (acceptance):** each of 50 generated drills must `validate` with
  `accepted is True`. For heuristic: density in `[0.15, 0.40]`, coverage ≥3 per target, length
  ≥270, charset clean, no word >3×, no bigram run ≥3. For control: length/charset/repetition only.
- **No experiment literals in logic (§17.1):** length, density bounds, coverage, repetition limits
  come from the spec/config; `0.5`/top-`50`/2-uses/2–10-letters are §13.3 algorithm constants
  (module literals, per the composer precedent). The "5,000" and "sqrt" weighting of §13.2 are
  algorithm parameters — Open Q 7 asks whether 5,000 is a config key.
- **One bigram definition:** reuse `count_bigrams`/`word_bigrams`; never re-implement (D13,
  CLAUDE.md).
- **Platform:** pure Python, importable on Linux CI; no mlx-lm (both arms are non-LLM).
- **Charset (D13, validator):** lowercase a–z + single spaces, no leading/trailing/doubled space;
  cleaning is the generator's own responsibility (validator never mutates).
- **Performance:** generation is batch/off-path (D11); no stated latency bound, but the composer
  precedent is `O(words × targets)` with a precomputed index, not re-sorting the vocabulary each
  step.

## 7. Edge cases (concrete)

1. **Control word repetition vs `word_repeat` (>3).** sqrt-frequency weighting over the top 5,000
   still oversamples `the`, `of`, `to`. Over a ~50-word, 300-char drill, a word can be drawn 4+
   times → `WORD_REPEAT`. Example: sampling draws `the` five times → reject. The generator must cap
   per-drill word reuse (the composer's `_MAX_USES_PER_PART = 2` is one precedent) even though
   §13.2 does not state a cap. (Open Q 8.)
2. **Control natural density recording.** §13.2: record control's "natural density for each set".
   But `DrillSpec` for control has `target_bigrams=()`, so `validate` records `target_density =
   0.0` and skips density. The natural density of the control text *against the participant's
   control-set bigrams* is a separate measurement not produced by `validate` on an empty-target
   spec. Where/how it is computed and stored is undefined here. Example: control text measured
   against set-D's 4 bigrams might show density 0.06 — the §13.2 "natural density" — but `drills.
   target_density` for the control row is 0.0. (Open Q 9.)
3. **Heuristic density floor with 4 targets and length 300.** ~300 chars ≈ ~50 words ≈ ~250
   letters ≈ ~200 letter-letter bigrams. Density 0.15 needs ≈30 target occurrences across the 4
   targets; coverage needs only ≥3 each (≥12 total). So the **density floor dominates coverage**:
   satisfying coverage (12) is far below the density floor (30). The generator must keep pulling
   target words well past coverage. Example: 4 targets each hit exactly 3× = 12 occurrences →
   density ≈0.06 < 0.15 → `DENSITY_LOW` despite coverage passing.
4. **Heuristic density ceiling (0.40).** Packing too many target words risks density >0.40 →
   `DENSITY_HIGH`. Example: a drill of mostly target-dense words (`clock knock lock track`…) could
   exceed 80 target occurrences in 200 bigrams. The generator must stop/balance before the ceiling.
5. **A target bigram with few corpus words.** An awkward target (e.g. `ck`, `wk`) may have few
   `words_containing(bigram)`; reaching coverage 3 and lifting density without repeating a word >3×
   is tight. Example: only 5 distinct `wk` words 2–10 letters → the 2-use cap gives at most 10 uses.
6. **Fallback set of 3 targets (not 4).** Heuristic must handle 3 targets as well as 4 (T2.2
   fallback), still hitting density/coverage.
7. **Bigram-run trap.** A target like `th` placed in `ththth`-style pseudo-words would trip
   `BIGRAM_REPEAT` — but the heuristic uses **real words**, so a run of 3 same-bigram at every other
   position within one real word is essentially impossible; still, the generator must not
   concatenate target syllables. Example: real words only, so `bigram_run` stays ≤2.
8. **Length cut at a word boundary (§13.1).** Stop at the first word boundary at/after
   `length_chars`; trim any trailing space; the drill may exceed 300 by ≤1 word but must stay ≥270
   (the composer does exactly this with `baseline_part_chars`).
9. **Determinism across runs and a different seed.** Same spec+seed → identical text (acceptance +
   §13.1); the 50-drill test presumably varies the seed per drill (Open Q 6) and checks every
   result validates. A composer-style `test_same_seed_gives_identical_texts` /
   `test_different_seed_gives_different_text` pair is the precedent.
10. **"target-bigram density of the word".** §13.3 step 4 scores a word by its target-bigram
    density × log(frequency). "Density of the word" could mean (target bigrams in word)/(all bigrams
    in word) or /(len). The composer uses a different formula (deficit-weighted per-unit-length).
    Example: word `clock` with targets `ck`,`ow`: 1 target bigram of 4 total → 0.25, or of len 5 →
    0.2. (Open Q 5.)

## 8. Risks

- **Heuristic cannot reach density 0.15 reliably** (edge case 3): the single most likely failure —
  coverage ≥3 is easy, the 0.15 floor over 4 targets is not, so naive "pick lowest-coverage target,
  add one word" loops land short and `generate` would need many retries (the §18 "arm starved"
  failure mode applied to the heuristic). The acceptance "50 drills each pass" fails if the design
  does not drive density, not just coverage.
- **Determinism broken by iteration/ordering:** using a `set`/`dict` iteration order, unseeded
  `random`, or `rng` not threaded from the spec seed breaks "same seed, same text" (the acceptance)
  — the exact trap the composer avoids by sorting candidate lists and taking `rng` from the caller.
- **Control word-repeat rejection** (edge case 1): sqrt weighting plus no per-drill cap trips
  `word_repeat`, failing "50 drills each pass".
- **Scoring/termination divergence from §13.3** (§4.5): copying `_choose_word`'s deficit-weighted
  formula instead of §13.3's `density × log(frequency)` would silently change the heuristic arm's
  behaviour that §13.6's bake-off compares against.
- **Reuse coupling with the composer:** extracting the loop into a shared module risks changing
  T1.8's frozen-once-used baseline output; copying it risks drift between two "13.3-style" loops.
- **5,000-word subset ambiguity:** reading from the full 20,000 vs the top 5,000 changes control's
  word distribution and its recorded natural density.
- **Natural-density ownership gap** (edge case 2): if neither T2.4 nor T2.5 computes §13.2's
  per-set natural density, a §13.2/§15 reporting requirement is silently dropped.

## 9. Open questions (numbered; the design doc does not settle these)

1. **5,000-word source.** No 5,000-word artifact exists; `words.json` is 20,000 in rank order. Is
   the control word pool simply `WordIndex.words[:5000]`, and is 5,000 an algorithm constant or a
   new `experiment_config` key?
2. **Seed derivation for the non-LLM arms.** §13.5 derives the LLM seed from
   `(participant, arm, drill number, attempt)`. Does the control/heuristic `generate` seed its
   `random.Random` solely from `DrillSpec.seed`, or also combine `participant_id`/`arm`/drill
   number? (Determinism — the acceptance — depends on exactly what the seed is.)
3. **One candidate per call vs internal retry.** Is `DrillGenerator.generate` a single-shot
   producer of one `DrillCandidate` (with the validate-and-retry loop owned by the T2.5
   GenerationService worker, as the T2.3 plan states), or does T2.4's `generate` validate and retry
   internally until it returns a passing candidate? "50 drills each pass the validator" could be
   tested either by generating 50 and validating each, or by `generate` guaranteeing a pass.
4. **Share vs duplicate the §13.3 loop.** Should T2.4 extract a shared seeded loop/sampler out of
   `services/test_composer.py` (risking changes to the frozen baseline composer) and reuse it, or
   implement a separate heuristic generator that reuses only `WordIndex`, `count_bigrams`,
   `_TEMPERATURE`/top-50 constants and the softmax idiom?
5. **§13.3 step-4 scoring.** What exactly is "target-bigram density of the word × log(frequency)":
   is "density of the word" (target bigrams in word)/(all bigrams in word) or /(word length), and
   is this scoring used verbatim (differing from the composer's deficit-weighted

## Owner answers

2026-10-21 — answered by the orchestrator under the autonomous pipeline rule. Sources: (a) design
doc, (c) earlier plans, (d) code conventions, (e) industry practice.

1. **`WordIndex.words[:control_word_pool]` with a new `experiment_config` key `control_word_pool:
   5000` (data-only migration `0007_generator_config`).** Source: (a) 13.2 "5,000 most frequent";
   17.1 config rule; (d) 0006 precedent. `words.json` is rank-ordered, so the slice is the list.
   Update `SEEDED_CONFIG_ROWS` (22 → 23) and head pins.

2. **Seed solely from `DrillSpec.seed`: `random.Random(spec.seed)`.** Source: (a) 9.1 "same spec
   and seed gives the same text"; 13.5's `(participant, arm, drill number, attempt)` derivation is
   how T2.5 *computes* `spec.seed`, not something generators repeat. One stream per `generate`
   call; no module-level randomness.

3. **Single-shot: `generate` returns one `DrillCandidate` and never calls `validate`.** The
   validate-and-retry loop is T2.5's. **But** both generators must be built so that a candidate
   passes on the first attempt in practice — the acceptance is "50 drills each pass the
   validator", with no retries in the test. So the heuristic generator is **density-aware**
   (answer 5) and the control generator respects the word-repeat cap (answer 8). Source: (c) the
   T2.3 plan's `DrillGenerator` contract; (a) acceptance.

4. **Separate module; the baseline composer is frozen and untouched.** New
   `generation/control.py`, `generation/heuristic.py`, and a small shared
   `generation/sampling.py` (`softmax_choice(rng, items, scores, temperature)` and
   `weighted_choice`). They reuse `WordIndex`, `count_bigrams`, `word_bigrams` and copy the
   idiom, not the code, of `_choose_word`. Source: (c) T1.8's form A text is frozen once used;
   refactoring its composer now risks changing it.

5. **13.3 scoring verbatim, with a well-defined log and a density governor.** For the chosen
   target `t`, score(word) = `(occurrences of t in word ÷ number of letter bigrams in word)
   × log(frequency(word) ÷ min_frequency)` where `min_frequency` is the smallest frequency in
   the index (so the log is ≥ 0 and never flips the ranking — raw `log(freq)` of a wordfreq
   value is negative). Target choice = lowest coverage counter, ties broken by `rng`. Softmax
   over the top 50 at temperature 0.5; skip words used twice; terminate when `length_chars` is
   reached at a word boundary (then cut back to ≤ `length_chars`; the validator's 270 floor
   makes a 300-target drill safe). **Density governor:** before each pick, if the running target
   density exceeds the midpoint `(d_min + d_max) / 2`, pick a *filler* instead — a word from the
   control pool (answer 1) containing none of the targets, sampled by sqrt-frequency — otherwise
   pick a target word as above. This keeps density inside `[d_min, d_max]` without changing the
   13.3 recipe for target words. Source: (a) 13.3 steps 1–5; (a) 13.1 density range is the gate
   the acceptance requires; (e) a greedy target-dense loop with no governor overshoots 0.40.

6. **The test builds specs directly, 50 seeds each (0–49), with config defaults.** Heuristic
   targets: two fixed 4-bigram sets from the tracked list — one common (`th he in an`) and one
   rarer (the four lowest-ranked tracked bigrams, e.g. from the tail of `top_bigrams.json`,
   chosen in the plan after inspecting the artifact) — all 50 seeds × both sets must pass; plus a
   3-target (fallback) set. Control: 50 seeds with empty targets. Determinism: same seed → same
   text, different seed → different text. The test loads `WordIndex` from a corpus built into
   `tmp_path` by `build_corpus` (wordfreq is offline; ~0.1 s). Source: (c) `test_validator.py`
   `_spec` pattern; T1.8 test precedent.

7. **`control_word_pool` is config (answer 1); sqrt weighting, temperature 0.5, top-50 and the
   2-use cap are algorithm constants, as in the composer.** Source: (c) T1.8 answer 7/T2.3 plan
   O2 drew the same line: experiment parameters in config, recipe constants in code.

8. **Control enforces ≤ 2 uses per word per drill** (the same cap as 13.3 step 5), which is below
   the validator's `drill_max_word_repeats` of 3, so control can never fail `word_repeat`;
   candidates are drawn without that word once the cap is hit. Source: (e) the acceptance must
   hold deterministically; 13.2's silence on repetition is not a prohibition.

9. **Natural density is derived, not stored, and not T2.4's.** The control drill's text is
   stored; its density against any set is `validate(text, spec_with_that_set, …).metrics.
   target_density` whenever T2.5's generation report or T4.1 needs it. T2.4 only guarantees the
   text is stored verbatim. Source: (a) 6.2 "everything else is derived and can be rebuilt".
