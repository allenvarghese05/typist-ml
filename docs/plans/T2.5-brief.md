## 2. Why it matters

`GenerationService` (`generation/service.py`) and the worker loop (`worker.py`) are the persistence and orchestration layer of the entire drill-generation pipeline:

- **Only database writer for generation (§6.1, §9.1).** "The `GenerationService` is the only class that talks to the database during generation, and the `DrillValidator` is the single fairness gate for all arms" (§9.1). Generators (T2.4, T3.1, T3.2) return pure `DrillCandidate` values and never touch SQLite; `GenerationService` loads frozen target bigrams from `bigram_assignment`, constructs `DrillSpec`s with reproducible seeds, runs the validate-and-retry loop (up to 5 attempts per drill, §10.2 / §13.5), logs every attempt in `generation_attempts`, and saves accepted drills in `drills` with `status = "ready"`.
- **Off-loop batch execution (D11, §6.2).** LLM calls take seconds and ~1 GB of memory and can be rejected and retried. Running generation in a separate worker process that polls `generation_jobs` keeps typing-loop and API latency flat and isolates the API from model crashes.
- **Unblocks session planning and the M2 end-to-end loop.** T2.6 (Session planner) selects `ready` drills from `drills` and enqueues `generation_jobs` when the pool falls below target (§13.7: 3 days of ready drills per arm = 6 drills); T2.8 (`assigned → practice` transition when "drill pool ready", §9.3) and T2.9 (Admin page: pool, jobs, checks) read the rows and heartbeat produced here; T3.1 (Markov) and T3.2 (LLM) plug their `DrillGenerator` implementations into this exact service and retry loop; §15.2's "Generation" dashboard view and §3.5's engineering claims (acceptance rate, attempts per accepted drill, tokens per second) read `generation_attempts` and `drills` written here.

What breaks if it is wrong:
- **Non-atomic job claim:** two worker instances (or overlapping poll iterations) claim the same `pending` job, generating duplicate drills, corrupting seed progression, or racing on job status updates.
- **Unlogged attempts or failures:** rejected candidates that are not persisted to `generation_attempts` erase the rejection-rate audit trail required by §3.5, §8.1, §13.5, and §15.2; an unhandled exception or exhausted retry that leaves a job stuck in `running` blocks the queue or hides failures from the admin page (§16 Pilot runbook: "Watch the admin page for failed jobs").
- **Broken or coupled heartbeat on `/health`:** if a missing or stale worker heartbeat flips `/health`'s overall `status` to `"error"` or HTTP 503, Linux CI and API-only tests fail because the worker is macOS-only (`just dev` and `just worker` exit early off Darwin, and T0.3 owner answer 3 / `schemas/health.py` explicitly forbid the heartbeat from changing `status`).
- **Eager `mlx-lm` or missing-arm imports:** importing `mlx-lm` at module load in `service.py` or `worker.py` breaks Linux CI (CLAUDE.md), and requiring Markov/LLM generators before M3 breaks M2's 2-arm loop.

## 3. Governing decisions

- **D03 (Arms = `control, heuristic, markov, llm`):** the service and worker operate on `Arm` / `DRILL_ARMS`. In M2 only `ControlGenerator` and `HeuristicGenerator` exist (T2.4); Markov (T3.1) and LLM (T3.2) arrive in M3 (see §16 cut-line: `arms_enabled` supports 2-set mode with `control` and `heuristic`).
- **D04 (Assignment frozen before practice):** `GenerationService` loads the participant's frozen weak bigrams for the job's arm from `bigram_assignment` (§10.2 step 3: "load frozen bigram set for this arm"). For `control`, `DrillSpec.target_bigrams` is empty `()` (§8.1, §9.1) even though `bigram_assignment` holds 4 control-arm bigrams as the held-out set (D02).
- **D08 (Backend stack):** Python 3.12, SQLModel, SQLite in WAL mode (`PRAGMA journal_mode=WAL, foreign_keys=ON, synchronous=NORMAL`), Typer CLI (`typist worker`).
- **D09 / D10 (Model runtime & model):** `mlx-lm` only runs on Apple Silicon and is not imported by services (§6.1: `Services (Python) | Must not: Import the model runtime`). Even though `worker.py` will load the model in M3 (T3.2), in T2.5 `worker.py` and `generation/service.py` must run unit and integration tests on Linux CI without `mlx-lm`.
- **D11 (Generation timing):** "Batch, via a separate worker process. Keep 3 days of ready drills per arm" (§13.7: 2 drills per block × 3 days = 6 ready drills per arm per participant).
- **D16 (Fairness gate):** every candidate from every arm is checked by `generation.validator.validate` before being accepted; its `DrillMetrics` (`target_density`, `mean_word_len`, `real_word_ratio`) and `reasons` (`RejectReason` tokens) populate `drills` and `generation_attempts`.
- **D19 (No cloud, no WASM):** local SQLite and local process only; no external queue (Redis/Celery explicitly rejected in §6.2).

### 4.7 Design doc sequence & class diagrams for T2.5

- **§6.2 (page 13):** "Jobs through the database. The worker polls `generation_jobs` every few seconds and claims a job with one atomic `UPDATE ... WHERE status = 'pending'`. No Redis or Celery is needed for one machine."
- **§9.1 Figure 4 (page 21):** `GenerationService` has methods `+run_job(job_id)` and `+generate_with_retries(spec) : Drill`.
- **§10.2 Figure 8 "Drill generation job (LLM arm)" (page 24):**
  1. `Worker loop` → `SQLite`: `UPDATE job SET status running (atomic claim)`
  2. `Worker loop` → `GenerationService`: `run_job(job_id)`
  3. `GenerationService` → `SQLite`: `load frozen bigram set for this arm`
  4. Loop `[until accepted or max_attempts (default 5)]`:
     - `GenerationService` → Generator: `generate(spec with seed + attempt)`
     - Generator returns `DrillCandidate`
     - `GenerationService` → `DrillValidator`: `validate(candidate, spec)` → `accepted, density, reasons`
     - `GenerationService` → `SQLite`: `INSERT generation_attempts`
  5. `alt [accepted]`:
     - `GenerationService` → `SQLite`: `INSERT drills (ready)`
  6. `[attempts exhausted]`:
     - `GenerationService` → `SQLite`: `job retries + 1, new seed later`
  7. `GenerationService` → `SQLite`: `UPDATE job SET status done or failed`
- **§13.5 table (page 32):**
  - `Seed`: `Derived from (participant, arm, drill number, attempt), stored on each attempt` (Note: `generation_attempts` has no `seed` column in §8.1; `drills.seed` is `INTEGER`, and T2.4 owner answer 2 states that T2.5 computes `spec.seed` from `(participant, arm, drill number, attempt)` and passes it in `DrillSpec`).
  - `Retries`: `Up to 5 attempts per drill with new seeds; every attempt is logged in generation_attempts`.
  - `No fallback`: `If all attempts fail, the job fails and is retried later. The LLM arm never borrows heuristic text`.

## 6. Constraints

- **Atomic job claim (acceptance criterion 1; §6.2, §10.2):** claiming the next pending job must happen atomically in SQLite (`UPDATE generation_jobs SET status = 'running', started_at = ... WHERE id = (...) AND status = 'pending' RETURNING ...` or equivalent single-statement atomic UPDATE) ordered by `(status, created_at)` using `ix_generation_jobs_status_created_at` (§8.2). Two concurrent claim calls against the same database must never claim the same job.
- **Failures logged (acceptance criterion 2; §8.1, §10.2, §13.5):** every candidate generation attempt (whether accepted or rejected) is logged as a row in `generation_attempts` with its `reject_reasons`, and when a job fails (all attempts for a drill exhausted, or an unexpected exception occurs during job execution), the failure is logged (both to `generation_jobs.error` / `status = 'failed'` / `retries` and Python logger).
- **Heartbeat visible on `/health` (acceptance criterion 3; §14, T0.3 owner answer 3):** `/api/v1/health` must surface the worker heartbeat age, and per `schemas/health.py`: *"T2.5 adds the worker heartbeat as its own field, and that field never changes status (the worker does not run on Linux)."*
- **Deterministic 32-bit/signed integer seed derivation (CLAUDE.md, §13.5, T2.4 owner answer 2):** `DrillSpec.seed` must be an `int` that fits in SQLite `INTEGER` (64-bit signed) and is deterministically derived from `(participant_id, arm, drill_number, attempt)` (and/or a base seed) without using Python's randomized `hash()`.
- **FK constraint ordering on `generation_attempts.drill_id`:** when an attempt is accepted, `generation_attempts.drill_id` is a foreign key to `drills.id` (`fk_generation_attempts_drill_id_drills` with `PRAGMA foreign_keys=ON`). Therefore, on an accepted attempt, the `Drill` row must be flushed/inserted before (or alongside) the `GenerationAttempt` row that references `drill.id` (note §10.2 Figure 8 draws `INSERT generation_attempts` above `INSERT drills (ready)`, which would violate the FK if `drill_id` were set before `drills` exists).
- **Platform & CI:** all T2.5 unit and integration tests must run and pass on Linux CI without `mlx-lm`. `just dev` reaches full M0/M2 readiness on macOS once `worker.py` exists, and `Ctrl-C` in `just dev` must cleanly stop the worker process along with the web and API processes.
- **No table models returned from API (§17.1):** `/health` uses `HealthResponse` in `schemas/health.py`.

## 7. Edge cases

1. **FK order between `drills` and `generation_attempts` on acceptance.** `generation_attempts.drill_id` has an active SQLite FK to `drills.id`, and §8.1 states `"drill_id set when accepted"`. If `GenerationService` inserts `GenerationAttempt(drill_id=drill.id)` before inserting `Drill` into the session/DB, SQLite raises `IntegrityError: FOREIGN KEY constraint failed`. Concrete example: attempt 1 passes validation → `Drill` must be inserted/flushed first so its `id` exists in `drills`, then `GenerationAttempt` is inserted with `drill_id = drill.id`.
2. **Job requesting multiple drills (`job.requested > 1`) where drill 1 succeeds and drill 2 exhausts all 5 attempts.** A job typically requests 6 drills (at initial assignment, §3.2) or 2 drills (after a session, §13.7). If drill 1 is accepted and saved as `ready`, and drill 2 fails all 5 attempts: do the already-saved `ready` drills from drill 1 stay in `drills`, and if the job is later retried, does it generate `requested` drills or only the remaining `requested - already_produced` drills? (See Open Question 4.)
3. **Seed collision across multiple jobs for the same `(participant_id, arm)`.** §13.5 says seed is derived from `(participant, arm, drill number, attempt)`. If "drill number" were `0..job.requested - 1` local to each job, then Job 1 (after day 1) and Job 2 (after day 2) for `(p1, heuristic)` would both use `drill_number = 0, attempt = 0`, producing the **exact same drill text** for the participant on every job. To produce distinct drills across a participant's pilot, `drill_number` (or the seed input) must include the existing drill count for `(participant_id, arm)` or `job.id` / `job.retries` (see Open Question 3).
4. **Control arm `target_bigrams` when `bigram_assignment` has 4 control rows.** T2.2 assigns 4 weak bigrams to `arm = "control"` in `bigram_assignment` (the held-out control set, D02). However, for `Arm.CONTROL`, `DrillSpec.target_bigrams` must be `()` and `drills.target_bigrams` must be `[]` (§8.1: `"target_bigrams | JSON | Empty for control"`, §9.1: `# empty for CONTROL`, T2.3 owner answer 4: validator skips density and coverage only when `spec.target_bigrams` is empty). If `GenerationService` loaded `bigram_assignment` rows into `spec.target_bigrams` for `control`, `ControlGenerator` would ignore them but `validate()` would enforce `min_density >= 0.15` and `coverage >= 3`, rejecting almost every control drill!
5. **Targeted arm job when participant has no `bigram_assignment` rows for that arm.** Example: a job is enqueued for `heuristic`, but the participant has no frozen assignment rows for `heuristic`. `GenerationService` cannot build a targeted `DrillSpec` with empty `target_bigrams` (or it would validate as targetless control). It must fail the job cleanly and log the error.
6. **Unsupported / unbuilt generator arm in M2 (`markov`, `llm`).** `DRILL_ARMS` allows `markov` and `llm`, which are not implemented until T3.1/T3.2 (or `llm` if `mlx-lm` is not available). If a job for an unregistered arm is claimed, the worker/service must fail the job cleanly and record `error` rather than crashing the worker loop.
7. **Database uninitialized or locked during `/health` or worker poll.** `/health` can be called in tests (`test_health.py`) on a brand-new empty SQLite file before any migrations have run (`SELECT 1` succeeds, but no tables exist yet). If `/health` reads the worker heartbeat from a database table (such as `experiment_config` or a heartbeat table), querying that table on an unmigrated DB raises `sqlite3.OperationalError: no such table`, which must not break `test_health_returns_ok_and_creates_the_database`!
8. **Worker started before `typist db migrate` or `typist corpus build`.** `just dev` starts web, API, and worker concurrently. If `data/corpus/words.json` is missing or migrations haven't run, the worker startup or poll loop must handle or report the error clearly without leaving zombie processes.
9. **Graceful shutdown on `SIGINT` / `SIGTERM`.** `just dev` sends `kill $pids` (`SIGTERM`) on exit and `SIGINT` on Ctrl-C. The worker loop must exit cleanly between iterations (or during sleep) when signalled so `just dev` never hangs.

## 8. Risks

1. **`test_health.py` regression on unmigrated DBs or exact JSON match:** `test_health.py` calls `/api/v1/health` on an unmigrated `tmp_path` SQLite file and asserts `response.json() == {"status": "ok", "db": "ok"}`. If the heartbeat check queries a table that doesn't exist yet without catching `OperationalError` (or if it reads a file), and when the new heartbeat field is added to `HealthResponse`, `test_health.py` will fail unless both unmigrated-DB tolerance and the test expectations are aligned.
2. **Race condition in SQLite job claiming:** Using a two-step `SELECT ... WHERE status = 'pending'` followed by `UPDATE ... SET status = 'running'` in separate transactions allows two workers to claim the same job. Even within one transaction, standard `Session` reads in SQLite use `DEFERRED` transactions unless `BEGIN IMMEDIATE` or a single `UPDATE ... WHERE id = (SELECT id FROM generation_jobs WHERE status = 'pending' ORDER BY created_at, id LIMIT 1) AND status = 'pending' RETURNING id` is used.
3. **Control arm accidentally given target bigrams from `bigram_assignment`:** As detailed in Edge Case 4, `bigram_assignment` has rows with `arm = "control"`, but `DrillSpec.target_bigrams` and `Drill.target_bigrams` for `Arm.CONTROL` must be empty or `validate()` will reject control drills on `density_low` / `coverage`.
4. **Duplicate drill generation across jobs due to naive seed formula:** As detailed in Edge Case 3, if `drill_number` resets to `0` on every job for a `(participant, arm)` pair, every replenishment job will generate identical drills with identical seeds.
5. **Ambiguity between per-drill attempt retries and job-level retries:** §10.2 Figure 8 shows an inner loop of up to `max_attempts (default 5)` per drill, and on `[attempts exhausted]` shows `job retries + 1, new seed later` followed by `UPDATE job SET status done or failed`. Without a clear rule for whether an exhausted drill marks the job `failed` immediately or re-queues it as `pending` up to a max job retry count, the worker could loop infinitely on an impossible spec or fail to increment `job.retries`.
