## 2. Why it matters

What T1.1 enables later:
- It is the first Alembic revision. `alembic/versions/` holds only `.gitkeep` today (T0.3 owner
  answer 8: "T1.1 adds the first revision"). T2.1 builds its revision on top of it.
- It creates the first SQLModel table classes. `src/typist/models/__init__.py` is a one-line
  docstring: `"""SQLModel table classes, one module per table group (T1.1 onward)."""`.
- Every M1 task after it writes or reads these tables:
  - T1.6 inserts `keystroke_events` rows with `ON CONFLICT (block_id, seq) DO NOTHING` (12.4). That
    needs the `(block_id, seq)` uniqueness this task creates.
  - T1.7 attribution reads `keystroke_events` (outcome, first_attempt, seq, t_down, target_index,
    and an `after_pause` flag, see edge case 1).
  - T1.8 writes `text_passages` (kind, form, part, text, bigram_counts).
  - T1.9 writes `sessions.wpm`, `sessions.accuracy` and (via T2.1) `bigram_stats`, and "typist stats
    recompute reproduces the same numbers" only if raw rows are complete and unchanged.
  - T2.1 adds tables with foreign keys into these ones: `bigram_stats.session_id` to `sessions`,
    `drills.used_in_block_id` to `session_blocks` (Figure 3, 8.1).
  - T2.2 reads `assignment_seed` from `experiment_config` (3.4 step 6). T3.5 freezes
    `experiment_config` ("Frozen keys reject changes").
  - T2.8 enforces the participant status machine (9.3) on `participants.status`.
  - `typist participant delete --pid` "removes every row for a participant" (4.2, 14.1).
- It is the first time participant data (keystrokes with timestamps) has a place in
  `<repo>/data/typist.db`.

What breaks if it is wrong:
- **Raw data is the one thing that cannot be rebuilt.** Section 10.3: "Anything to the right of
  keystroke_events can be deleted and rebuilt." A missing or lossy column in `keystroke_events`
  (for example no pause flag, or a type that loses precision) cannot be recovered after the pilot
  starts; attribution (T1.7) and the recompute check (M1) would be wrong or impossible. Section 18:
  "Attribution bug | All results wrong".
- **Missing `(block_id, seq)` uniqueness** lets EventBuffer retries (12.4) insert duplicates; the
  T1.6 acceptance ("stores it once") fails, and doubled keystrokes double-count attempts.
- **A downgrade that does not work** blocks the acceptance criterion and leaves no safe way to
  undo a bad revision during M1 to M3. Section 8: "Every schema change is an Alembic migration."
- **Models and migration disagreeing** means the app writes columns that the migrated database
  does not have (or with other types/nullability); tests that build tables differently from the
  migration would hide it.
- **Foreign key choices** decide whether `typist participant delete` can remove "every row" and
  whether later batch migrations (T2.1 onward) can rebuild tables with `foreign_keys=ON`.
- **Type choices on SQLite** (UUID text, DATETIME, JSON, BOOLEAN) are hard to change later: every
  change after data exists is a batch table rebuild over real participant data.

### 4.2 Other design-doc facts about these tables
- **9.3 participant lifecycle (Figure 6):** enrolled to baseline ("consent given"); baseline to
  baseline ("fewer than 2 baseline sessions"); baseline to assigned ("coverage OK, sets frozen");
  assigned to practice ("drill pool ready"); practice to practice ("day below N"); practice to retest
  ("N practice days done"); retest to done ("retest sessions done"); enrolled, baseline and practice
  to withdrawn. "Transitions are enforced in the services layer."
- **9.3 session states:** "in_progress to completed when all blocks are finished, or to abandoned if
  a session is left unfinished for more than 30 minutes. Abandoned practice sessions do not count
  toward N, and their keystrokes are kept but excluded from outcome analysis."
- **3.2:** baseline "Two sessions of fixed test text (form A)"; retest "Two sessions of parallel test
  text (form B)"; practice "Days 2 to 11 (default N = 10)". "Missed practice days are allowed but
  logged".
- **3.3:** "Each practice session has four blocks, one per arm. Each block is 600 characters by
  default (two drills of about 300 characters)." "Block order follows a 4 by 4 Latin square rotated
  by day". "Fixed characters per block, not fixed time ... Time per block is recorded."
- **3.4 step 6:** "Shuffle the arm list with a seed stored in experiment_config and map A to D onto
  the shuffled arms. Freeze by writing frozen_at. Frozen rows are never updated."
- **Section 16 cut-line:** "run the pilot in 2-set mode (control and heuristic, 8 bigrams each),
  which the config supports with `arms_enabled`." (`arms_enabled` is not in 8.1's example key list.)
- **13.5 "Frozen for the pilot":** "model_id, prompt_version, sampler settings, d_min and d_max".
- **12.1:** "On window blur: pause the block, mark the next keystroke as following a pause".
- **12.2:** "Pause | IKI over 2000 ms, or first key after a blur | Excluded from IKI statistics,
  still counted for errors".
- **12.3 attribution pseudocode** (verbatim excerpt): `a = first_attempt keystroke at j-1`,
  `if a backspace happened between a and b: skip`, `elif b.seq == a.seq + 1 and not b.after_pause:`,

- **12.4:** "A row is created on keydown and sent once its keyup has arrived, or after 2 seconds
  without one (keyup stays null)." "The server inserts with ON CONFLICT (block_id, seq) DO NOTHING".
- **12.6 daily checks:** "Gaps in seq within a block." "Negative dwell, or dwell over 1000 ms".
  "Blocks with fewer events than characters in the target text." "Share of keyups missing."
  "Sessions left in_progress."
- **9.2 Figure 5, `KeystrokeEvent` (TS) fields:** `seq: number`, `key: string`, `code: string`,

### 4.3 Code T1.1 must fit into (verbatim)

`services/api/alembic/env.py`:
```python
# Imported for its side effect: table modules register themselves on SQLModel.metadata.
import typist.models  # noqa: F401
from typist.config import get_settings
from typist.db import create_db_engine
...
target_metadata = SQLModel.metadata

def run_migrations_offline() -> None:
    context.configure(
        url=f"sqlite:///{get_settings().db_path}",
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
        render_as_batch=True,
    )
...
def run_migrations_online() -> None:
    """Apply migrations over a connection that has the app's pragmas (WAL, foreign keys)."""
    engine = create_db_engine(get_settings().db_path)
    try:
        with engine.connect() as connection:
            context.configure(
                connection=connection,
                target_metadata=target_metadata,
                render_as_batch=True,
            )
            with context.begin_transaction():
                context.run_migrations()
    finally:
        engine.dispose()
```

## 6. Constraints

- **Acceptance is literal:** "Migration up and down both work". The design doc does not define
  "work" further (open question 1).
- **SQLite only**, with `PRAGMA foreign_keys=ON` on every connection, including the migration
  connection (T0.3 answer 5: env.py "applies the same pragmas ... so T1.1 doesn't revisit it").
- **Batch mode** (`render_as_batch=True`) is already on for both online and offline runs.
- **Types (section 8 intro):** UUID strings for ids "except for the two high-volume tables, which
  use integer ids" (`keystroke_events` is INTEGER PK here; `bigram_stats` is the other, T2.1);
  "Timestamps are UTC ISO-8601"; "Durations are milliseconds stored as REAL".
- **Append-only raw data:** `keystroke_events` rows "are never updated after insert, except to fill
  in the key-up time" (6.2, CLAUDE.md).
- **Frozen config:** "frozen keys cannot change" (8.1), "Never change keys in `experiment_config`
  after they are frozen" (CLAUDE.md). Enforcement is T3.5's, but the schema holds `frozen_at`.
- **Privacy:** "Participants are stored by alias only. No name, email or free text is stored"
  (4.2). `typist participant delete --pid` "removes every row for a participant".
- **Gate:** D21 via `just check` / `just check-api`, and CI `api` on Linux: ruff check, ruff format

- **Revision files** are rewritten by ruff on creation (post-write hooks), and must pass
  `ruff format --check` afterwards. They are excluded from pyright.
- **Test isolation:** tests must use the temp DB from `isolated_settings`; none may touch
  `<repo>/data/` (T0.3 plan Review focus 1: "This is the privacy guarantee from T1.1 on").
- **Platform:** everything in T1.1 runs on Linux and macOS; no mlx involvement. No `@pytest.mark.mlx`.
- **Performance:** no stated limit on migration time. Data volume estimate from 3.3: 4 blocks x 600
  characters per practice session, 10 practice sessions, plus 4 test sessions, per participant, so
  on the order of tens of thousands of `keystroke_events` rows per participant (backspaces and

- **Sandbox (T0.3 answer 23; auto-memory "Sandbox owner-run steps"):** network, commits, ports and
  `.env.example` are blocked or hidden for agents; owner-run resume points are the precedent. T1.1
  needs no new dependency and no port, so `uv run --locked` offline is expected to suffice (verify

## 7. Edge cases

1. **`after_pause` has no column.** 12.3 uses `b.after_pause`; 12.1 says "mark the next keystroke
   as following a pause"; 12.2 defines a pause as "IKI over 2000 ms, or first key after a blur".
   8.1 `keystroke_events` has no pause column, and Figure 5 `KeystrokeEvent` has no pause field.
   The IKI-over-2000-ms half can be derived from `iki_ms`; the blur half cannot be derived from any
   8.1 column. Example: user blurs the window for 1.5 s, returns and types `h` 1.8 s after `t`.
   IKI is 1800 ms (under 2000), so without a stored flag the pair `th` enters `iki_samples`,
   contrary to 12.2. T1.2's fixture must include "a pause".
2. **First keystroke of a block.** `iki_ms` ("t_down minus previous keystroke's t_down") and
   `release_to_press_ms` ("t_down minus previous key's t_up") have no previous key at `seq = 0`.
   Example: block starts, first key `t` at 812.4 ms: `iki_ms` and `release_to_press_ms` must be
   NULL (or something else); 8.1 does not mark them NULL.
3. **Missing key-up.** "t_up may be null if the page closed" (8.1); 12.4: sent "after 2 seconds
   without one (keyup stays null)". Then `dwell_ms` has no value either, and the NEXT row's
   `release_to_press_ms` has no previous `t_up`. Example: `a` held 2.5 s (stuck key): the row is
   sent at 2 s with `t_up_ms` NULL; the key-up at 2.5 s arrives later and the row gets its
   `t_up_ms` filled in, which is the one allowed update. Whether `dwell_ms` (same row) and the next
   row's `release_to_press_ms` are also filled in is not stated. 12.6 checks "Negative dwell, or
   dwell over 1000 ms" and "Share of keyups missing", so missing and odd values must be storable.
4. **Negative values.** `release_to_press_ms` is "negative under rollover" (D15). Example: `t`
   down 0, `h` down 60, `t` up 95: `release_to_press_ms` for `h` is 60 - 95 = -35. Any CHECK
   `>= 0` on it would reject real data. `dwell_ms` can be negative only through a bug (12.6 checks
   for it), so a CHECK there would drop evidence of the bug instead of flagging it.
5. **Backspace rows.** `outcome` = `backspace`; `key` = `"Backspace"`, `code` = `"Backspace"`.
   `expected_char` ("Target character at that position") and `first_attempt` ("True if this is the
   first keystroke at this target position") have no obvious meaning for a backspace; 8.1 marks
   neither nullable. Example: target `the`, typed `t`, `x`, Backspace: the Backspace row's
   `target_index` is 2 (cursor position when pressed) and it removes position 1.
6. **Space key.** `key` is `" "` (a single space) and `code` is `"Space"`; `expected_char` may be
   `" "`. A column type or validation that strips whitespace would turn `" "` into `""`.
7. **Column named `key`, table named `sessions`, column named `text`.** `key` is an SQLite keyword
   usable as an identifier (verify quoting in generated DDL). A SQLModel class named `Session`
   would shadow `sqlmodel.Session`, which `db.py` imports as the ORM session. `text` shadows
   `sqlalchemy.text` if both are used in one module.
8. **UUID storage.** 8.1 says `TEXT PK` / "UUID". SQLModel maps a `uuid.UUID` field to SQLAlchemy's
   `Uuid` type, which on SQLite is stored as `CHAR(32)` hex without hyphens (verify for SQLModel
   0.0.47 / SQLAlchemy 2.0.54). A `str` field stores whatever string is given (36 chars with
   hyphens, typically). Mixing the two across tables makes FK joins between `TEXT` and `CHAR(32)`
   values fail silently (no match). Example: `participants.id` stored as
   `"3f2b...c9"` (32 hex) while `sessions.participant_id` holds `"3f2b...-...-c9"` (36 chars).
9. **UUID randomness vs the seeded-randomness rule.** CLAUDE.md: "Randomness always comes from a
   seeded generator passed in by the caller." `uuid.uuid4()` uses `os.urandom`. Ids do not affect
   results, but the rule is worded "always".
10. **DATETIME on SQLite.** SQLite has no datetime type. SQLAlchemy's SQLite `DateTime` stores
    strings like `2026-09-29 14:03:05.123456` (space separator, no offset) and drops tzinfo
    (verify for 2.0.54). Section 8: "Timestamps are UTC ISO-8601". Example: an aware
    `datetime(2026, 9, 29, 14, 3, tzinfo=UTC)` is written without `+00:00` and read back naive;
    comparisons with aware datetimes then raise `TypeError`. A raw SQL writer (T1.6's
    `ON CONFLICT` insert, notebooks) could write `2026-09-29T14:03:05Z`, and string ordering between
    the two formats is wrong (`' '` sorts before `'T'`).
11. **JSON on SQLite.** `experiment_config.value`, `text_passages.bigram_counts` and
    `sessions.client_info` are JSON. SQLite stores JSON as TEXT; SQLAlchemy's `JSON` type
    serialises on write (verify). SQLModel does not map `dict`/`Any` fields to a column without an
    explicit `sa_column`/`sa_type` (verify). `experiment_config.value` holds scalars too (for
    example `10`, `0.15`, `"mlx-community/Llama-3.2-1B-Instruct-4bit"`); a JSON `null` value and a
    SQL NULL are different things. SQLAlchemy JSON change tracking does not see in-place mutation
    of a dict (verify).
12. **BOOLEAN on SQLite.** Stored as integer 0/1 (NUMERIC affinity). SQLite accepts any value in
    the column unless a CHECK exists; SQLAlchemy 2.x `Boolean` does not create a CHECK by default
    (verify). Example: a raw insert of `'true'` is accepted and read back as a truthy string.
13. **Enumerated TEXT columns.** `participants.status` (7 values), `sessions.phase` (3),
    `sessions.status` (3), `session_blocks.arm` (5, including `test`), `text_passages.kind` (2),
    `text_passages.form` (2), `keystroke_events.outcome` (3). Without CHECK constraints, a typo
    such as `"complete"` instead of `"completed"` is stored and the session is never counted
    (9.3, D23). With CHECK constraints, adding a value later (for example a fifth arm in v2,
    20.2) is a batch table rebuild over real data.
14. **Type affinity and DDL names.** 8.1 uses `TEXT`, `REAL`, `INTEGER`, `BOOLEAN`, `DATETIME`,
    `JSON`. SQLModel's `str` renders as `VARCHAR` (AutoString), `float` as `FLOAT`, `bool` as
    `BOOLEAN` (verify). SQLite maps `VARCHAR` to TEXT affinity and `FLOAT` to REAL affinity, so
    storage is the same, but `PRAGMA table_info` shows different declared types than 8.1.
    Autogenerated revisions render `sqlmodel.sql.sqltypes.AutoString()`, which keeps
    `import sqlmodel` in the revision file (the ruff post-write hook removes it only when unused).
15. **NOT NULL where 8.1 is silent.** Only `experiment_config.frozen_at`, `text_passages.participant_id`
    and `session_blocks.passage_id` are marked NULL. Columns that cannot have a value at insert
    time: `participants.consent_at` (enrolled, before consent), `sessions.wpm`, `accuracy`
    ("Computed on completion"), `sessions.ended_at`, `session_blocks.started_at`/`ended_at` (set by
    `/blocks/{bid}/start` and `/complete`), `keystroke_events.t_up_ms` ("may be null"),
    `iki_ms`/`release_to_press_ms` (edge case 2), `dwell_ms` (edge case 3). Unclear:
    `participants.keyboard_label`, `sessions.block_order` for baseline and retest sessions (no
    Latin square), `sessions.client_info`, `session_blocks.target_text` before planning.
16. **`block_index` "0 to 3" and test sessions.** Practice sessions have four blocks (3.3). How many
    blocks a baseline or retest session has, and whether `block_index` 0 to 3 still holds, is not
    stated. `text_passages.part` is "Order within a session", which suggests several passages per
    test session. Example: if a baseline session had five passages (parts 0 to 4), block_index 4
    would break the "0 to 3" note and any CHECK built on it.
17. **Uniqueness not stated in 8.1/8.2.**
    - `session_blocks (session_id, block_index)`: two blocks with index 2 in one session would be
      accepted.
    - `sessions (participant_id, phase, day_index)` is an index, not marked unique (compare
      "keystroke_events (block_id, seq) unique"). An abandoned practice session "does not count
      toward N"; whether the retried session reuses the same `day_index` is not stated, so a unique
      constraint could block a legitimate retry.
    - `text_passages`: shared baseline rows have `participant_id` NULL. SQLite treats NULLs as
      distinct in UNIQUE constraints, so a unique `(kind, form, part, participant_id)` would not
      stop two shared passages with the same part (verify).
18. **`ON CONFLICT (block_id, seq)` needs a matching unique index.** SQLite's upsert conflict target
    must match a UNIQUE index or constraint on exactly those columns (verify). A non-unique index
    or a constraint on `(seq, block_id)` in a different form may not qualify.
19. **Integer id for `keystroke_events`.** `INTEGER PRIMARY KEY` is an alias of SQLite's rowid;
    without `AUTOINCREMENT`, ids of deleted rows can be reused after `typist participant delete`
    removes the highest ids (verify). Example: participant B's rows get ids that participant A's
    deleted rows had; exported CSVs from before and after the delete then share ids.
20. **Participant delete vs foreign keys.** With `foreign_keys=ON`, deleting a `participants` row
    that still has `sessions` rows fails unless the FK has `ON DELETE CASCADE` or the children are
    deleted first. Chain depth: participants to sessions to session_blocks to keystroke_events, and
    (T2.1) to `bigram_stats`, `drills`, etc. Shared `text_passages` (participant_id NULL) must
    survive a participant delete; `session_blocks.passage_id` references passages, so deleting a
    retest passage owned by the participant needs its blocks gone first. CASCADE also deletes
    `keystroke_events`, which is a delete, not an update, of append-only rows (4.2 requires it).
21. **Downgrade with data and `foreign_keys=ON`.** SQLite's `DROP TABLE` on a parent table performs
    an implicit `DELETE FROM` first; with foreign keys on, that fails if child rows still reference
    it (verify). So dropping in the wrong order fails on a non-empty database even though it works
    on an empty one. Example: `downgrade` drops `sessions` before `session_blocks` while a block row
    exists: `FOREIGN KEY constraint failed`. On a real database, a successful downgrade destroys all
    keystroke data.
22. **`PRAGMA foreign_keys` inside a transaction.** SQLite ignores changes to `foreign_keys` inside
    an open transaction (verify). `env.py` wraps migrations in `context.begin_transaction()`, so a
    migration that tries to turn FKs off for a batch rebuild would silently keep them on. This is
    the IMPROVEMENTS "Follow-up for T1.1". For T1.1's own revision (new tables only, no alters)
    batch rebuilds may not occur; they will from the first ALTER onward (T2.1 or later).
23. **Transactional DDL on SQLite.** Alembic's SQLite dialect is not marked as having transactional
    DDL, and Python's `sqlite3` module does not open a transaction before `CREATE TABLE` in its
    legacy mode (verify both for alembic 1.20.0, Python 3.12). Example: the revision creates four
    tables, the fifth fails; the four stay, `alembic_version` is not written, and re-running
    `upgrade` fails with `table participants already exists`.
24. **Constraint names and batch mode.** `SQLModel.metadata` has no naming convention. SQLite
    stores unnamed constraints; a later batch migration that must drop or alter an unnamed UNIQUE,
    CHECK or FK constraint cannot address it by name (verify Alembic batch behaviour). Choices made
    in the first revision carry into every later one.
25. **Autogenerate needs the models imported.** `env.py` relies on `import typist.models` for side
    effects. If `models/__init__.py` does not import the table modules, `SQLModel.metadata` is
    empty, autogenerate produces an empty revision, and `alembic check` (if used) passes vacuously.
26. **SQLModel default table names.** A `table=True` class gets the lowercase class name as table
    name (for example `participant`, `keystrokeevent`) unless `__tablename__` is set (verify for
    0.0.47). 8.1 names are plural/snake case (`participants`, `keystroke_events`). Setting
    `__tablename__` on a SQLModel class is known to produce pyright diagnostics in some versions
    (`declared_attr` typing) (verify under strict mode for `src/`).
27. **pyright strict on SQLModel.** `Field(...)`, `sa_column=Column(JSON)` and `Relationship(...)`
    are partially typed; strict mode may report `reportUnknownMemberType`,
    `reportUnknownVariableType` or `reportIncompatibleVariableOverride` (verify). T0.3 brief edge
    case 17 flagged this for T1.1.
28. **Existing tests after the first revision.**
    - `test_upgrade_head_on_empty_history_uses_the_configured_database` still passes (it now creates
      tables) but its name describes a state that no longer exists.
    - `test_new_revision_is_fixed_and_formatted_by_ruff` copies the whole `alembic/` directory,
      including T1.1's revision, then asserts the new probe revision's `down_revision` is `None`.
      With a head present, Alembic sets `down_revision` to that head (verify), so the assertion
      fails.
    - The ruff post-write hook also rewrites the copied probe file only; T1.1's own revision is
      formatted once when generated, then edited by hand, then must still pass `ruff format --check`.
29. **Models and migration drifting.** If tests create tables with `SQLModel.metadata.create_all`
    instead of running the migration, a column present in the model but missing from the revision
    (or with different nullability) is never noticed until real use. Section 5.2 rejected "create_all
    only".
30. **Offline mode.** `run_migrations_offline()` (`alembic upgrade head --sql`) renders SQL with
    `literal_binds=True`. Batch operations cannot be rendered offline for SQLite in some cases
    (verify); pure `create_table` can.
31. **`experiment_config` is global.** Its PK is `key` alone, with no `participant_id`. 3.4 step 6
    stores "a seed" there. With two participants, one `assignment_seed` shared by both means both
    shuffles use the same seed; whether that is intended is not stated (the set contents differ, so
    the arm-to-set-letter mapping would be identical for both people).
32. **`frozen_at` meaning.** 8.1: frozen_at is per row ("frozen keys cannot change"). 3.4 step 6
    ("Freeze by writing frozen_at. Frozen rows are never updated") is about `bigram_assignment`
    (T2.1). Section 13.5 lists which keys are "Frozen for the pilot". Nothing in T1.1's schema stops
    an UPDATE of a frozen row; T3.5 owns "Frozen keys reject changes".
33. **`is_builder` / `is_blinded` consistency.** "False for the builder". Nothing stops a row with
    `is_builder = 1` and `is_blinded = 1`. With the builder only (20.1 default), every row is
    unblinded.
34. **Alembic log format.** Per IMPROVEMENTS, every Alembic log line currently prints the raw
    format string instead of `INFO  [alembic.runtime.migration] Running upgrade  -> <rev>`. A
    human running `just migrate` or a downgrade cannot see which revision ran. pytest captures
    these lines, so tests are unaffected.
35. **Where `alembic_version` lives.** Downgrading to `base` leaves the `alembic_version` table
    (empty) in the database (verify). A test that asserts "no tables after downgrade" must account
    for it (and for SQLite's internal `sqlite_sequence` if `AUTOINCREMENT` is used).
36. **WAL files.** Every migration run creates `typist.db-wal` and `typist.db-shm` next to the
    database; in tests these sit in `tmp_path`. `.gitignore` covers `*.db-wal`/`*.db-shm` at any
    depth and `/data/`, `/*.db` at the root only.

## 8. Risks

1. **An irreversible gap in `keystroke_events`.** The pause flag (edge case 1), nullability of
   timing columns (edge cases 2 and 3) and backspace semantics (edge case 5) are the inputs to
   attribution. A wrong call here is found only when T1.2's fixture or T1.7's tests are written,
   and then needs a second migration; after the pilot starts it is unrecoverable (10.3).
2. **Up works, down does not (or only on an empty DB).** FK ordering and SQLite's implicit delete on
   `DROP TABLE` (edge case 21) make a downgrade that passes on an empty test database fail on a
   populated one. The acceptance wording does not say which.
3. **Model/migration drift.** Hand-written or edited revisions and SQLModel classes diverge
   silently (edge cases 14, 25, 29), especially types (UUID, JSON, DATETIME) and nullability.
4. **SQLite type surprises becoming permanent.** UUID as CHAR(32) vs TEXT, naive vs aware datetimes,
   JSON serialisation, 0/1 booleans (edge cases 8, 10, 11, 12). Every later task inherits them, and
   raw-SQL writers (T1.6 upsert) may disagree with ORM writers.
5. **pyright strict failures in `src/typist/models/`** from SQLModel typing (edge cases 26 and 27),
   which the gate (D21, CI `api`) blocks.
6. **Breaking existing tests** (`test_new_revision_is_fixed_and_formatted_by_ruff`, edge case 28),
   which then tempts a test edit whose correctness the reviewer has to judge.
7. **Scope creep.** Participant CLI commands, DTOs, endpoints, config seeding, freeze enforcement,
   status transitions and a downgrade CLI are all adjacent; none is in T1.1's title. Leaving them
   out may push schema-affecting choices (CASCADE, CHECKs, defaults) into later tasks that then
   need migrations.
8. **Constraints that later block legitimate data** (a `>= 0` CHECK on release-to-press, a unique
   session day index that blocks a retried session, a closed arm list) or constraints that are
   missing and let bad data in. Both are hard to change once participant data exists.

## 9. Open questions

1. **What proves "Migration up and down both work"?** Is it enough to upgrade an empty database to
   head and downgrade it to base? Must it also (a) upgrade again after the downgrade (round trip),
   (b) downgrade a database that contains rows in every table, and (c) show that the migrated
   schema matches the SQLModel models (for example no difference reported by Alembic's
   autogenerate comparison or `alembic check`)?
2. **Revision layout.** One revision for all six tables, or one per table group? Is there a
   required revision id or file-name style (Alembic's random hex, or a readable sequential id such
   as `0001`)?
3. **SQLModel table classes in scope?** Does T1.1 create the SQLModel table classes for all six
   tables (section 7: "SQLModel table classes (one file per table group)"), and if so, what are the
   table groups and module names? Should the classes declare relationship attributes, or only
   columns and foreign keys?
4. **Pause flag (edge case 1).** Should `keystroke_events` get a column for "following a pause"
   (12.1, 12.3 `after_pause`), which 8.1 does not list? If yes: its name, type, and whether it
   covers only blur pauses or also IKI over 2000 ms. If no: how is the blur pause meant to be
   recovered from the stored rows? A new column changes the 8.1 schema; does that need an ADR
   (section 17.3)?
5. **Nullability of `keystroke_events` columns.** Which of these may be NULL: `t_up_ms` (8.1 says
   "may be null"), `dwell_ms`, `iki_ms` and `release_to_press_ms` for `seq = 0`,
   `release_to_press_ms` when the previous key-up is missing, `expected_char` and `first_attempt`
   for backspace rows, `handler_ms`, `dispatch_lag_ms`? For backspace rows, what are
   `expected_char` and `first_attempt` meant to hold?
6. **The one allowed update.** "Except to fill in the key-up time": does the update touch only
   `t_up_ms`, or also `dwell_ms` on the same row and `release_to_press_ms` on the next row? Should
   append-only be enforced in the database (for example by triggers), or by code convention only?
7. **Nullability elsewhere.** Is every column not marked "NULL" in 8.1 meant to be NOT NULL? In
   particular: `participants.consent_at`, `participants.keyboard_label`, `sessions.block_order`
   (baseline and retest sessions have no Latin square), `sessions.wpm`, `accuracy`, `ended_at`,

1. Proof of migrations working: all three, (a), (b), and (c). This is exactly the kind of thing worth being thorough about, since a migration bug corrupts real data silently.
2. Revision layout: one revision covering all six tables for this task — they're introduced together as a coherent schema, splitting them serves no purpose yet. Use a readable sequential id (`0001_initial_schema`), not Alembic's random hex — easier to read in `alembic history` for a solo project with few revisions.
3. SQLModel classes: yes, create all six as table classes now. Table groups/modules: `participants.py`, `experiment_config.py`, `text_passages.py`, `sessions.py` (holding both `Session` and `SessionBlock`, since they're tightly coupled), `keystroke_events.py`. Columns and foreign keys only — no `relationship()` attributes. Services query directly; add relationships later only if a real need shows up.
4. Pause flag: yes, add a column — `after_pause: bool`, `NOT NULL DEFAULT FALSE`. It should capture only what can't be derived from timestamps alone: that the keystroke followed a window-blur resume. A long gap from IKI alone is already computable from stored timestamps at analysis time and needs no separate column. This is a real deviation from section 8.1's listed columns, so write it up as `docs/decisions/D24-keystroke-events-after-pause-column.md`.
5. Nullability, `keystroke_events`:
   * `t_up_ms`, `dwell_ms`: nullable (dwell unknown until keyup arrives)
   * `iki_ms`, `release_to_press_ms`: nullable (undefined at `seq = 0`, or when the prior key's `t_up` is missing)
   * `expected_char`, `first_attempt`: nullable — both `NULL` for backspace rows, since neither concept applies to a control key
   * `handler_ms`, `dispatch_lag_ms`: `NOT NULL` — always computed for every captured event
6. The one allowed update: touches `t_up_ms` and `dwell_ms` on the same row only, once the matching keyup arrives. `release_to_press_ms` on other rows is never backfilled — it's computed from stored timestamps at read time, not stored eagerly. Enforce append-only by code convention (one single write path in the service layer), not database triggers — triggers complicate SQLite migrations for little benefit here. Add a test that a second attempt to update `t_up_ms` is rejected by the application layer.
7. Nullability elsewhere: yes, everything not explicitly marked nullable in 8.1 is `NOT NULL`, with these confirmed exceptions: `participants.consent_at` and `keyboard_label` (nullable — not yet known at enrollment), `sessions.block_order`, `wpm`, `accuracy`, `ended_at` (nullable — null until the session type has one or it completes), `session_blocks.started_at`, `ended_at` (nullable — null until reached/finished). `session_blocks.target_text` and `sessions.client_info` are `NOT NULL` — both are set at creation time.
8. CHECK constraints: yes, enforce all the listed value sets at the database level (`participants.status`, `sessions.phase`/`status`, `session_blocks.arm`, `text_passages.kind`/`form`, `keystroke_events.outcome`), plus `seq >= 0` and `day_index >= 1`. For `block_index`, don't hard-code `0 to 3` at the DB level — see #12 below, test sessions need more range. Also add a table-level check for `is_blinded = 0 OR is_builder = 0` — cheap, catches a real logic error early. Defense in depth is worth it here; Python-only checks can be bypassed by a bug elsewhere in the codebase, the database can't.
9. Defaults: yes to all — `participants.status = 'enrolled'`, `sessions.status = 'in_progress'`, `is_builder = false`, `is_blinded = true` as Python-side defaults (since all writes go through the app). `created_at` should use a server-side default (SQLite's `CURRENT_TIMESTAMP`, which is already UTC) so it's correct even if something ever bypasses the ORM layer.
10. Deleting a participant: explicit service-layer deletion in child-to-parent order, no `ON DELETE CASCADE`. Delete the participant's own `text_passages` (where `participant_id` is set, i.e. their retest texts); never touch shared ones (`participant_id IS NULL`).
