## 2. Why it matters

- **Public capstone of Milestone M4 (Dashboard and write-up, §16):**
  `README.md` is the primary entry point and public record of the Typist-ML experiment. It presents the experimental methodology, measured outcomes, engineering overhead, and limitations to readers, reviewers, and researchers.
- **Answers the core research question (§1):**
  Section 1 poses the fundamental empirical question: *"does a small on-device language model write better drills than a dictionary heuristic or a Markov chain?"* Task T4.4 documents the answer based strictly on measured evidence, upholding the honesty rule: *"if the heuristic or the control does as well as the LLM, that is the finding"*.
- **Enforces scientific integrity and unbroken chain of custody (§15.3, §16):**
  The acceptance criterion *"Every claim traces to a number in the database"* mandates that every metric, table cell, interval, and statement in `README.md` maps directly to verified data in the SQLite database without hand-waving, fabrication, or rounding distortion.
- **Synthesizes upstream analytical artifacts (§15.3):**
  T4.4 integrates the four required elements specified in Design Doc §15.3:
  1. One chart: per-set error rate change with intervals, control set marked (`docs/figures/set_error_rate_change.png` and `.svg` from T4.3).
  2. One table: arm, drills, mean density, real-word ratio, acceptance rate (`format_generation_table`).
  3. One line: overhead p95 and LLM tokens per second, measured (`format_overhead_line`).
  4. A limitations paragraph that states $N$, completed sessions, and total keystrokes (`format_limitations_paragraph`).
- **Prerequisite for study conclusion and debrief (§16):**
  Completing the README public write-up precedes task T4.5 (Debrief page: Shows arm mapping only after retest).
- **What breaks if it is wrong:**
  - **Falsification or claim divergence:** If numbers cited in `README.md` do not match the database, the acceptance criterion fails and the study loses scientific credibility.
  - **Violation of D19 honesty rules:** If the README makes WASM claims, asserts statistical significance for $N=1$, or claims improvement before or contrary to database proof, foundational project rules are violated.
  - **Concealed confounding or bias:** If the builder's unblinded status is omitted, or if $N$ is not stated plainly as $N=1$ (or $N=2$), readers will assume standard blinded randomized multi-subject conditions.
  - **Silent drift:** If README claims are not verified by an automated test in `just check`, future schema or database changes could invalidate README numbers without warning.

## 6. Constraints

- **Traceability rule (Acceptance criteria):**
  *"Every claim traces to a number in the database."* Every single numeric figure, percentage, interval, keystroke count, session count, throughput number, and latency percentile reported in the README must match the database.
- **Honesty rules (D19, §1, §18):**
  - No WASM claims.
  - No claims of statistical significance, hypothesis tests, or p-values for $N=1$ (or $N=2$).
  - Results must be presented as descriptive within-person comparisons.
  - No claims before real numbers exist.
- **Blinding and participant reporting (D01, D18, §18):**
  - The builder's unblinded status (`is_builder = True`, `is_blinded = False`) must be stated explicitly.
  - If a second participant completed the study, results must be presented separately, never pooled across participants.
- **Exclusion rules (D23, `docs/analysis-plan.md`):**
  - Abandoned sessions excluded from outcome statistics.
  - Pauses excluded from IKI only.
  - Weak bigrams with $<20$ retest attempts dropped from both baseline and retest, and documented under exclusions.
- **Data privacy and CI limits (`GEMINI.md`, `CLAUDE.md`):**
  - Never commit anything under `data/` (`data/typist.db` is gitignored).
  - CI runs on Linux without local database files. Unit tests checking README numbers must use deterministic fixtures, test databases, or mock sessions to verify reproducibility in CI.
- **Tooling and formatting (D07, D08, D21):**
  - Must pass `just check` cleanly on macOS and Linux CI.

## 7. Edge cases

1. **Empty database in a fresh checkout or CI environment:**
   - *Example:* On a fresh clone, `data/typist.db` is empty or does not exist. `just figures` fails with `ParticipantNotDoneError: no completed participants found (status 'done')`. Tests in CI that verify README claims against the database must run against a fixture or test database with known data matching the README numbers.
2. **$N = 1$ (Builder only) vs $N = 2$ (Builder + Peer):**
   - *Example:* If only the builder completes the pilot ($N = 1$), the limitations paragraph reads:
     `"This pilot reports findings from N = 1 participant (builder, unblinded) across 14 completed sessions and 28,450 total keystrokes..."`
     If a peer also completed ($N = 2$), the README must report two distinct panels/sections without pooling:
     `"This pilot reports findings from N = 2 participants (1 unblinded builder and 1 blinded peer)..."`
3. **Control set outperforms all targeted arms:**
   - *Example:* Heuristic targeting effect $E(\text{heuristic}) = +0.012$ (share below zero = $14.2\%$), LLM targeting effect $E(\text{llm}) = +0.005$ (share below zero = $38.1\%$). The README must state clearly that targeted arms did not outperform plain practice on the held-out control set.
4. **Weak bigrams dropped due to $<20$ retest attempts:**
   - *Example:* Bigram `"qz"` has only 15 attempts at retest due to low corpus occurrence. It must be dropped from baseline and retest for primary and key secondary outcomes, and documented in the exclusions report.
5. **Zero observed errors in a set:**
   - *Example:* A participant has 0 errors in 240 attempts at retest for the LLM set. The Jeffreys prior evaluates $\text{Beta}(0.5, 240.5)$, yielding credible interval $[0.0001, 0.0160]$ (approx $0.0\%$ to $1.6\%$). The README must report the credible interval rather than claiming $0.00\%$ without uncertainty bounds.
6. **Negative difference-in-differences sign convention:**
   - *Example:* Error rate change $d(\text{llm}) = -0.045$, $d(\text{control}) = -0.010$. Targeting effect $E(\text{llm}) = -0.045 - (-0.010) = -0.035$ (a $3.5\%$ greater reduction in error rate). Negative represents improvement. The README must define this sign convention clearly.
7. **Two-set contingency mode:**
   - *Example:* If the pilot ran in two-set mode (`arms_enabled = ["control", "heuristic"]`), the README documents that Markov and LLM arms were omitted per the contingency plan, reporting heuristic vs control only.

## 8. Risks

1. **Discrepancy between README text and database numbers:**
   - *Risk:* Manual transcription of numbers into `README.md` introduces typos or rounding discrepancies, failing the acceptance criteria.
   - *Mitigation:* Generate README snippets programmatically using `services/api/src/typist/services/figures.py` and enforce exact matching with an automated unit test.
2. **Git-ignoring `data/` vs CI test execution:**
   - *Risk:* `data/` cannot be committed. If a unit test strictly reads `data/typist.db` in CI, the test will fail in GitHub Actions.
   - *Mitigation:* Ensure CI tests evaluate claims against a committed golden test database fixture or against the output of the figures service with fixed parameters.
3. **Accidental use of simulation data as empirical findings:**
   - *Risk:* Synthetic scripted data (from `test-pipeline`) is mistaken for real human pilot data, violating `GEMINI.md` honesty rules.
   - *Mitigation:* Verify participant status and audit participant metadata (`is_builder`, session dates) to ensure only completed pilot data is reported.
4. **Drift between figures and markdown text:**
   - *Risk:* If figures are regenerated with new data but `README.md` text is not updated, charts and tables will contradict each other.
   - *Mitigation:* Ensure README references the generated image files directly and verifies that snippet text matches `docs/figures/readme_snippets.md`.
