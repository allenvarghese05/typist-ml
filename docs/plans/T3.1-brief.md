# T3.1 brief — Character n-gram model and Markov generator; tune beta

*Analyst brief. Facts only; no design or implementation.*

## 1. Task

- **ID:** T3.1 (milestone **M3 "Markov, LLM, bake-off, freeze"**, design doc §16).
- **Title (verbatim, §16):** "Character n-gram model and Markov generator; tune beta".
- **Acceptance criteria (verbatim, §16):** "Median density inside the shared range".
- **Test-type mandate (§17.2 verbatim):** "Validator and generators | Each rule, determinism, density range | pytest unit".

## 2. Why it matters

The Markov generator is the third drill generator in Typist-ML and implements `Arm.MARKOV` (D03). Up through Milestone 2, the pipeline ran in 2-arm mode (`control` and `heuristic`), with Markov and LLM unbuilt (§16 cut-line). T3.1 provides the character-level statistical generator needed for the complete 4-arm within-person experiment.

- **Fulfills the core research question (§1, §3.1).** The central question of the experiment is: *"do targeted drills beat plain practice, and does a small on-device language model write better drills than a dictionary heuristic or a Markov chain?"* The Markov arm represents the intermediate baseline: unlike the heuristic arm which selects real English dictionary words, Markov produces pseudo-words shaped by character transition probabilities and target bigram bias (§13.4: *"Markov output is mostly pseudo-words. That is part of what the arm is, and it is reported as a difference between arms, not hidden."*).
- **Unblocks the 4-arm Latin square and drill pool replenishment.** In M2, session planning and drill pools were limited to 2 active arms or mock generators. Once `MarkovGenerator` is registered in `build_default_generators` (T2.5 / `worker.py`), the generation worker can autonomously claim and generate drills for `Arm.MARKOV` jobs, enabling 4-arm practice blocks (D01, D03, §3.3).
- **Tunes exposure via beta (§13.4 step 4, §13.1).** The shared fairness gate requires target density to fall between `d_min` (0.15) and `d_max` (0.40) and coverage $\ge 3$ per target bigram. The bias factor $\beta$ (default 4) scales the transition probability of the second letter of a target bigram when preceded by its first letter. Tuning $\beta$ ensures that the Markov arm's median density lands inside the shared range $[d_{min}, d_{max}]$ rather than under-targeting (density too low) or over-targeting (density too high, tripping repetition rules).
- **Prerequisite for T3.4 calibration and T3.5 freeze.** In T3.4, `d_min` and `d_max` are calibrated so that each targeted arm (heuristic, Markov, LLM) accepts 80% or more of drills within 5 attempts. Tuning $\beta$ in T3.1 is the necessary calibration step for the Markov arm before `d_min`, `d_max`, and `markov_beta` are frozen in T3.5.

**What breaks if it is wrong:**
- If $\beta$ is tuned incorrectly or left untuned: median density falls below 0.15 (under-targeting, failing the acceptance criteria) or overshoots 0.40 (failing `density_high`), causing high rejection rates in the worker's 5-attempt retry loop and starving the Markov drill pool.
- If character sampling is non-deterministic: breaks D16 and §13.1 determinism (*"Same spec and seed gives the same text"*), making drill generation irreproducible.
- If pseudo-words generate runaway repetitions (e.g., `ththth`): trips `RejectReason.BIGRAM_REPEAT` or `RejectReason.WORD_REPEAT`.
- If pseudo-words violate word length limits ($3 \le \text{length} \le 10$): violates §13.4 step 3.
- If off-Mac execution is broken (e.g., introducing MLX or platform-specific dependencies): breaks CI on Linux.

## 3. Governing decisions (each D-number and what it forces here)

- **D03 (Arms = `control, heuristic, markov, llm`):** T3.1 implements `Arm.MARKOV` (already declared in `typist.generation.base.Arm` and `typist.models.drills.DRILL_ARMS`). Markov is a targeted arm: its `DrillSpec.target_bigrams` is populated from the participant's frozen `bigram_assignment` rows (T2.2).
- **D06 / D08 / D09 (Deployment, backend stack, and platform independence):** Pure Python 3.12 within `services/api`. Unlike the LLM generator (T3.2 / `mlx-lm`), the character n-gram model and Markov generator do NOT require Apple Silicon, GPU acceleration, or `mlx-lm`. They must run and test cleanly in Linux CI as well as macOS.
- **D11 (Batch generation via worker):** Generation happens in background jobs managed by `GenerationService` and `worker.py`. `MarkovGenerator` implements `DrillGenerator.generate(spec) -> DrillCandidate` purely in memory without database queries. Validation, retries, and persistence are performed by `GenerationService`.
- **D13 (Text scope — lowercase `a`–`z` and single space only):** Output must contain only lowercase ASCII characters `a`–`z` and single space delimiters, with no punctuation, no digits, and no leading/trailing/doubled spaces. Bigram counts and validation reuse the project-wide definitions in `typist.corpus.word_index`.
- **D16 (Fairness gate):** Every generated drill is evaluated against the shared validator `validate()`: length $\ge 270$ chars (target 300), target density in $[d_{min}, d_{max}]$, coverage $\ge 3$ per target bigram, max word repeat $\le 3$, bigram run $< 3$. Per §13.1 and `validator.py`, `real_word_ratio` is measured and recorded on `drills`, but does NOT gate `Arm.MARKOV` (it gates only `Arm.LLM`).
- **D17 (Word list — `wordfreq`, `a`–`z`):** The character n-gram model is trained on the same 20,000 words as the heuristic generator (`words.json` built from `wordfreq`), weighted by $\sqrt{\text{frequency}}$ (§13.4 step 1).
- **D20 / Freeze (Configuration parameters):** `markov_beta` is an experiment parameter. Per §13.4 step 4, it is tuned in M3 and frozen in T3.5. It must be read from `experiment_config`, never hardcoded as an untracked literal.

class Arm(StrEnum):
    """The four generated arms (D03); mirrors models.drills.DRILL_ARMS. CONTROL has no targets."""

    LLM = "llm"

    max_density are the d_min/d_max range the validator enforces for targeted arms; length_chars is
    the target length the generator aims for (the validator's floor is a separate config key). seed

    participant_id: str
    arm: Arm
    target_bigrams: tuple[str, ...]  # empty for CONTROL

    min_density: float = 0.15
    max_density: float = 0.40
    seed: int = 0

class DrillCandidate:
    """A generator's output before validation (owner answer 1). text is the cleaned a-z+space drill

    fields; model_id/prompt_version are LLM-only (None otherwise); gen_ms/gen_tokens/

    NO fairness metrics -- the validator computes those."""

    text: str
    raw_output: str
    generator_version: str
    seed: int
    model_id: str | None = None
    prompt_version: str | None = None
    gen_ms: float | None = None
    gen_tokens: int | None = None
    tokens_per_sec: float | None = None
    peak_memory_mb: float | None = None

class DrillGenerator(Protocol):

### 4.6 Worker generator wiring (`services/api/src/typist/worker.py`, verbatim)

```python
def build_default_generators(
    session: Session, index: WordIndex
) -> tuple[dict[Arm, DrillGenerator], ValidatorConfig]:
    """Build the M2 default generators (CONTROL and HEURISTIC) from experiment_config and index.

    Reads validator_config via load_validator_config(session) and control_word_pool from
    experiment_config (raising MissingConfigError if absent). Returns (generators, validator_config).
    """
    validator_config = load_validator_config(session)
    pool_row = session.get(ExperimentConfig, "control_word_pool")
    if pool_row is None:
        raise MissingConfigError("control_word_pool")
    pool_size = int(pool_row.value)
    generators: dict[Arm, DrillGenerator] = {
        Arm.CONTROL: ControlGenerator(index, validator_config, pool_size),
        Arm.HEURISTIC: HeuristicGenerator(index, validator_config, pool_size),
    }
    return generators, validator_config
```

## 5. Inputs and outputs

### Inputs
1. **Training data:** 20,000 most frequent English words with frequencies from `words.json` in `TYPIST_CORPUS_DIR`.
2. **`DrillSpec` (per drill candidate):**
   - `participant_id`: string identifier
   - `arm`: `Arm.MARKOV`
   - `target_bigrams`: tuple of target bigram strings (e.g. `("th", "he", "in", "an")`)
   - `length_chars`: 300
   - `min_density`: $d_{min}$ (default 0.15)
   - `max_density`: $d_{max}$ (default 0.40)
   - `seed`: integer seed derived deterministically by `GenerationService` from `(assignment_seed, participant_id, arm, drill_index, attempt_index)`
3. **Configuration parameters:**
   - `markov_beta`: float bias factor (default 4.0 in §13.4, tuned in T3.1) stored in `experiment_config`.
   - `ValidatorConfig`: `min_length_chars` (270), `min_coverage` (3), `max_word_repeats` (3), `max_bigram_run` (3), `min_real_word_ratio` (0.8).

### Outputs
1. **`DrillCandidate`:**
   - `text`: generated pseudo-words separated by single spaces, total length $\le 300$ characters at a word boundary (and $\ge 270$ chars to satisfy the validator).
   - `raw_output`: identical to `text` for non-LLM arms.
   - `generator_version`: `"markov-v1"`.
   - `seed`: echoes `spec.seed`.
   - `model_id`: `None`.
   - `prompt_version`: `None`.
   - `gen_ms`: `None` (or elapsed ms).
   - `gen_tokens`, `tokens_per_sec`, `peak_memory_mb`: `None`.
2. **Database migration & `experiment_config` row:**
   - Migration (e.g. `0009_markov_config.py`) inserting `markov_beta` with its initial default and tuned value.
3. **Corpus artifact (if built at corpus build time):**
   - Trained character n-gram model transition tables (or built in memory from `WordIndex`).

## 6. Constraints

- **Platform compatibility:** Pure Python 3.12. Must run and pass all tests on Linux in GitHub Actions CI without requiring Apple Silicon or `mlx-lm`.
- **Determinism:** Given a `DrillSpec` with a fixed `seed`, `MarkovGenerator.generate(spec)` must produce the exact same text every time using a seeded `random.Random(spec.seed)`.
- **Word length bounds:** Generated pseudo-words must be between 3 and 10 characters (§13.4 step 3).
- **Drill length floor and ceiling:** Target length is 300 characters, cut at a word boundary without exceeding 300 characters. Must meet or exceed the validator's `min_length_chars` floor of 270 characters (§13.1).
- **Target density acceptance criteria:** Across generated drills for representative target sets, the median target density must land inside the shared range $[d_{min}, d_{max}] = [0.15, 0.40]$ (§16 T3.1 acceptance criteria).
- **Validator compliance:** Candidates must pass all shared validator rules: charset (`a-z` and single spaces only), coverage ($\ge 3$ per target bigram), max word repeats ($\le 3$), and bigram run ($< 3$).
- **Performance:** In-memory transition table lookup and sampling must generate 50 drills in well under 1 second. N-gram model training on 20,000 words must complete in under 0.5 seconds.

## 7. Edge cases

1. **Dead-end context before minimum word length ($< 3$ characters):**
   *Example:* Suppose context `(^^, 'q')` in training data only ever transitioned to `'u'`. If `('q', 'u')` transitions only to a few letters, or if a context has only end marker `$` as a transition when current pseudo-word length is only 1 or 2 characters. The sampler cannot emit `$` because word length must be $\ge 3$. If all available transitions have zero weight, sampling cannot proceed without a backoff, fallback, or discarding the candidate word and restarting.
2. **Word reaching maximum length (10 characters) without emitting end marker `$`.**
   *Example:* At character 10, the model samples another letter instead of `$`. If unchecked, pseudo-words could exceed 10 characters, violating §13.4 step 3. The generator must force the word to terminate at 10 characters or resample.
3. **Target bigram's second letter has zero probability in the n-gram context:**
   *Example:* Target bigram is `'qj'` or an awkward bigram where character `j` never occurred after context `(x, 'q')` in the 20,000-word corpus. Multiplying transition count 0 by $\beta$ yields $0 \times \beta = 0$. The target transition cannot be sampled from that context.
4. **Target bigram first letter never appears:**
   *Example:* Target set contains rare bigram `uc`. Section 13.4 step 2 specifies boosting the second letter `c` only when the previous character is `u`. If `u` is sampled with low frequency, `uc` will rarely be created. If `u` never appears, $\beta$ bias is never triggered for that bigram.
5. **Overlapping or chained target bigrams:**
   *Example:* Target bigrams include both `'th'` and `'he'` (or `'an'` and `'na'`). When the previous character is `'t'`, `'h'` is boosted by $\beta$. If `'h'` is chosen, the new previous character is `'h'`, which is the first letter of `'he'`, so `'e'` is boosted by $\beta$.
6. **Multiple target bigrams sharing the same first letter:**
   *Example:* Target set includes `'th'` and `'tr'`. When previous character is `'t'`, both `'h'` and `'r'` receive the $\beta$ multiplier before renormalisation.
7. **Runaway bigram repetition tripping `RejectReason.BIGRAM_REPEAT`:**
   *Example:* High $\beta$ on target `'th'` might encourage transitions `'th'` followed by high transition back to `'t'`. If `ththth` is emitted within a single pseudo-word, `bigram_run` equals 3, causing the validator to reject the drill with `BIGRAM_REPEAT`.
8. **Repeated pseudo-words tripping `RejectReason.WORD_REPEAT`:**
   *Example:* An order-3 Markov chain on English character frequencies will naturally generate high-probability common pseudo-words (e.g. `'the'`, `'ing'`, `'ter'`). If the same 3-letter word is emitted 4 times in a 300-character drill, the validator rejects with `WORD_REPEAT` (`max_word_count > 3`).
9. **Targetless spec (control-like edge case in tests):**
   *Example:* `spec.target_bigrams == ()`. Previous character is never the first letter of a target bigram. No $\beta$ multiplier is applied; transitions sample purely from base character n-gram distribution.
10. **Length cutoff leaving text under 270 characters:**
    *Example:* Total length reaches 268 characters. The next sampled word has length 8. Adding 1 space + 8 chars = 9 chars would reach 277, which is $\le 300$. But if the next word has length 10 and length was 292, $292 + 1 + 10 = 303 > 300$. Stopping at 292 is valid ($292 \ge 270$). However, if the generator prematurely stops when text is $< 270$, it triggers `RejectReason.TOO_SHORT`.

## 8. Risks

1. **Target coverage failure on rare bigrams (§13.1 coverage $\ge 3$):**
   Unsteered Markov generation only biases the second letter of a target bigram *after* the first letter has already been sampled. For lower-frequency bigrams, the first letter may not appear often enough in a 300-character drill (~45–55 words) to achieve $\ge 3$ occurrences, causing high rejection rates under `RejectReason.COVERAGE`.
2. **Trade-off between target density and repetition rules:**
   If $\beta$ is tuned too high to force rare bigrams to appear, common bigrams may overshoot `d_max` (0.40) or generate repetitive letter loops that trip `RejectReason.BIGRAM_REPEAT` ($run \ge 3$).
3. **Training latency / startup overhead:**
   If the n-gram model is trained from scratch on every generator instantiation or job claim without caching, it could introduce unnecessary disk I/O and processing latency in the worker loop and unit test suites.
4. **Drift between corpus build artifacts and runtime expectations:**
   If the n-gram model is serialized to disk during `typist corpus build`, any changes to `words.json` or model format require rebuilding corpus artifacts; if missing, commands or tests could fail with `FileNotFoundError`.

## 9. Open questions

1. **Model storage and serialization:** Should the character n-gram model be precomputed and saved as a corpus artifact (e.g., `data/corpus/ngram.json`) by `typist corpus build` / `build_corpus()`, or should it be built in memory from `WordIndex` upon generator initialization?
2. **Context length definition of "order 3":** Does "a character-level model of order 3" (§13.4 step 1) mean conditioning on the previous 2 characters ($P(c_i \mid c_{i-2}, c_{i-1})$, i.e. trigram model where context length is 2), or conditioning on the previous 3 characters ($P(c_i \mid c_{i-3}, c_{i-2}, c_{i-1})$, i.e. 4-gram model where context length is 3)?
3. **Start and end marker tokens:** How should start and end markers be represented in the context tuples (e.g., sentinel characters `^` and `$`, or dedicated string symbols)?
4. **Enforcing word length bounds ($3 \le \text{length} \le 10$):**
   - If an end marker is sampled when word length is $< 3$, should the end marker transition be masked out, or should the entire word be discarded and resampled?
   - If word length reaches 10 without generating an end marker, should the word be truncated/ended at 10 characters, or discarded and resampled?
5. **Handling contexts with no valid next transitions:** If the sampler reaches a context that has no valid outgoing character transitions (or only the end marker before length 3), how should the sampler recover?
6. **Configuration key and migration:** What should the `experiment_config` key for $\beta$ be named (e.g., `markov_beta`), and what initial default value should be seeded in an Alembic migration (e.g., `4.0` per §13.4)?
7. **First-letter sampling:** Section 13.4 step 2 specifies boosting the second letter when the previous character is the first letter of a target bigram. Does the design permit any steering or boosting of the *first* letter when sampling (e.g., at word start or after other letters) to ensure target bigrams with less common initial letters can achieve coverage $\ge 3$?
8. **Word repeat cap in generator:** Should `MarkovGenerator` track generated pseudo-words within a drill and cap them at 2 uses (matching `ControlGenerator` and `HeuristicGenerator`) to guarantee it never fails the validator's `drill_max_word_repeats` (3) rule?
9. **Generator registration and interface:** What signature should `MarkovGenerator.__init__` accept, and how should it be wired into `build_default_generators()` in `services/api/src/typist/worker.py`?

## 10. Owner answers (2026-10-28)

1. **Model storage and serialization:**
   - **Answer:** Build the character n-gram model in memory from `WordIndex` (words and frequencies) inside `MarkovGenerator` / `typist.generation.markov` (or `typist.corpus.ngram`). Training on 20,000 words takes < 50ms and avoids uncommitted file dependencies under `data/`.
   - **Source:** (a) Design doc §13.4; (b) `GEMINI.md` ("Never commit anything under data/"); (d) `ControlGenerator` and `HeuristicGenerator` initialization patterns.

2. **Context length definition of "order 3":**
   - **Answer:** Trigram model (history of 2 previous characters, $P(c_i \mid c_{i-2}, c_{i-1})$). This provides phonotactically plausible English-like pseudo-words without over-memorizing the vocabulary.
   - **Source:** (a) Design doc §13.4 step 1; (e) standard character language modeling conventions.

3. **Start and end marker tokens:**
   - **Answer:** Use sentinel characters `'^'` for word start and `'$'` for word end. Context at word start is `('^', '^')`.
   - **Source:** (a) Design doc §13.4 step 1; (d) standard character-level Markov modeling.

4. **Enforcing word length bounds ($3 \le \text{length} \le 10$):**
   - **Answer:** (a) When word length is $< 3$, mask out the end marker `'$'` from available transitions so words are at least 3 letters. (b) When word length reaches 10, force word end (or pick `'$'` if available, or end the word).
   - **Source:** (a) Design doc §13.4 step 3; (e) standard rejection/masking.

5. **Handling contexts with no valid next transitions:**
   - **Answer:** If an invalid context or dead end is reached, discard the current in-progress pseudo-word and resample a new word from the start using the seeded RNG.
   - **Source:** (a) Design doc §13.4; (d) deterministic rejection-sampling pattern.

6. **Configuration key and migration:**
   - **Answer:** Name the key `markov_beta`. Add Alembic migration `0009_markov_config.py` inserting `markov_beta` with default `4.0` (or the tuned value) in `experiment_config`.
   - **Source:** (a) Design doc §13.4 steps 2 and 4; (d) migration pattern from `0007_generator_config.py`.

7. **First-letter sampling:**
   - **Answer:** Follow §13.4 step 2 strictly: multiply the second letter's probability by $\beta$ when the immediately preceding character is the first letter of a target bigram. Rely on $\beta$ tuning and the worker's 5-attempt retry loop to meet coverage.
   - **Source:** (a) Design doc §13.4 step 2; (d) `GenerationService` retry loop.

8. **Word repeat cap in generator:**
   - **Answer:** Yes, track pseudo-words within the drill and cap each at 2 uses, identical to `ControlGenerator` and `HeuristicGenerator`.
   - **Source:** (a) Design doc §13.1; (d) `control.py` and `heuristic.py`.

9. **Generator registration and interface:**
   - **Answer:** `MarkovGenerator(index, validator_config, beta)`. Wire `Arm.MARKOV` into `build_default_generators()` in `services/api/src/typist/worker.py` by reading `markov_beta` from `experiment_config`.
   - **Source:** (a) Design doc §13.4; (d) `services/api/src/typist/worker.py`.
