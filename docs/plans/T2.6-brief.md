# T2.6 brief — Session planner: Latin square, pool selection, marking drills used

*Analyst brief. Facts only; no design or implementation.*

## 1. Task

- **ID:** T2.6 (milestone **M2 "Loop with heuristic and control"**, design doc §16; M2 "Done when": "A test participant goes baseline, assign, practice, retest end to end").
- **Title (verbatim, §16):** "Session planner: Latin square, pool selection, marking drills used".
- **Acceptance criteria (verbatim, §16):** "Block order rotates daily; no drill used twice".

## 2. Why it matters

`session_planner.py` (`services/api/src/typist/services/session_planner.py`, §7) is the service that turns a participant's current phase, test passages (`text_passages`), and pre-generated drill pool (`drills`) into playable `sessions` and `session_blocks` rows:

- **Counterbalances warm-up and fatigue across arms (§3.3, D01, D03).** In a within-person design where every participant types all arms in each practice session, a fixed block order would confound the first arm with warm-up and the last arm with fatigue. Rotating the block order daily via a Latin square (§3.3) removes within-session order bias across practice days.
- **Enforces single-use drill selection from the pre-generated pool (D11, §8.1, §13.7).** Each practice block (~600 characters) is built from two ready drills (~300 characters each) for that block's arm, picked in creation order (`created_at`, `id`), marked `status = "used"`, and linked to the block via `drills.used_in_block_id`. If a drill were used twice, the participant would repeat identical text across sessions, confounding typing improvement with memorisation of a specific passage and violating the acceptance criterion.
- **Connects drill generation (T2.4, T2.5) to the typing loop and triggers pool replenishment (§10.1, §13.7, §14).** `POST /participants/{pid}/sessions` and `GET /sessions/{sid}` return `SessionPlan` (the blinded blocks and target texts the frontend renders, D18); `POST /sessions/{sid}/complete` (partially built in T1.9 as stats-only, with a docstring deferring job enqueue and phase updates to M2) enqueues `generation_jobs` when an arm's `ready` drill pool drops below the 3-day target (6 drills per arm, §13.7).
- **Unblocks T2.7, T2.8, T2.9, and T2.10.** T2.7 (Retest composer) plugs form B passages into retest session planning; T2.8 (Participant state transitions) enforces phase transitions (`enrolled → baseline → assigned → practice → retest → done`, returning 409 on invalid transitions); T2.9 (Admin page) displays the ready drill pool per arm; T2.10 runs the dev-only scripted-keystroke pipeline end to end.

What breaks if it is wrong:
- **Broken Latin square rotation:** an arm appears twice in the same session, an arm is omitted, or the same arm is always first/last across days, invalidating the counterbalancing guarantee (§3.3) and failing `"Block order rotates daily"`.
- **Reusing a drill or failing to update `drills.status` / `used_in_block_id`:** the next practice session selects the same `Drill` rows again, failing `"no drill used twice"`, or leaves `used_in_block_id` NULL so downstream analysis cannot trace which drills were typed in which block (§8.1).
- **Non-atomic session planning on pool exhaustion:** if arm 1's drills are marked `used` and committed before checking that arm 2 has enough `ready` drills, a failed session-start call consumes drills into an orphaned or uncreated session.
- **Leaking arm names in blinded UI fields (D18, §3.3, §8.1):** blocks must be labelled `"Block 1"` to `"Block 4"` in the UI while recording `arm` and `block_order` (e.g. `"LCHM"`) in SQLite.
- **Wrong `day_index` progression or open-session handling (§8.1, §9.3, §14):** returning a newly created session when an `in_progress` session already exists violates §14 (`"returns the open one if it exists"`), and reusing an abandoned session's `day_index` or counting abandoned sessions toward the practice-day rotation misaligns the Latin square and violates T1.1 owner answer 11 (`"A retried abandoned session gets the next day_index, never the abandoned one's"`).

## 3. Governing decisions

- **D01 (Experiment unit — within-person):** each practice session tests all enabled arms for the participant, one block per arm.
- **D02 (Control):** the control arm has its own block of equal length (2 control drills of ~300 chars = ~600 chars) rotated in the Latin square alongside the targeted arms.
- **D03 (Arms = `control, heuristic, markov, llm`):** the full design uses 4 arms (`4 by 4 Latin square`, §3.3), and the §16 cut-line states: *"If M3 slips, run the pilot in 2-set mode (control and heuristic, 8 bigrams each), which the config supports with `arms_enabled`."* (See Open Question 1 on how the Latin square and `block_order` handle `arms_enabled`.)
- **D08 (Backend stack):** Python 3.12, FastAPI, SQLModel, SQLite in WAL mode with `PRAGMA foreign_keys=ON`.
- **D11 (Generation timing):** *"Batch, via a separate worker process. Keep 3 days of ready drills per arm."* The session planner never invokes generators directly; it selects `status = "ready"` rows from `drills` and enqueues `GenerationJob` rows when the pool is below target (§10.1, §13.7).
- **D13 (Text scope):** lowercase `a` to `z` and single spaces. When two drills of ~300 characters are joined to form a 600-character practice block's `target_text`, they must be joined with a single space `" "` so the combined `target_text` has no double spaces and remains valid under `TextCursor` (`/^[a-z ]+$/`).
- **D18 (Blinding):** *"Blocks are labelled Block 1 to 4. The second participant is not told the mapping. The builder is flagged as unblinded."* Also §3.3: *"Blocks are shown as Block 1 to Block 4. The UI never names the arm."*

## 6. Constraints

- **Block order rotates daily (acceptance criterion 1; §3.3, §8.1):** for practice sessions, block order follows a Latin square rotated by day so no arm is always first or last. `sessions.block_order` records the compact arm-order code (e.g. `"LCHM"` in §8.1) and `session_blocks.block_index` is `0..len(arms)-1` in that order.
- **No drill used twice (acceptance criterion 2; §8.1, §13.7):** drills are selected from `drills` where `status == "ready"` in creation order (`ORDER BY created_at ASC, id ASC`), and immediately marked `status = "used"` with `used_in_block_id = block.id` inside the same database transaction that creates the `session_blocks` rows.
- **Blinding (D18, §3.3):** block labels exposed to the participant UI are `"Block 1"` through `"Block 4"` (`f"Block {block_index + 1}"`); arm names must not be shown to a blinded participant.
- **Charset validity of combined practice block `target_text` (D13):** each `Drill.text` is 270–300 chars of `^[a-z ]+$` with no leading/trailing spaces. Joining the two drills of a block with `" ".join(drill.text for drill in picked_drills)` preserves `^[a-z ]+$` with no leading, trailing, or double spaces.
- **Database integrity (`PRAGMA foreign_keys=ON`):** `drills.used_in_block_id` has a foreign key to `session_blocks.id` (`fk_drills_used_in_block_id_session_blocks`), so `SessionBlock` rows must be flushed (`session.flush()`) before setting `drill.used_in_block_id = block.id`.
- **Platform & CI (CLAUDE.md):** pure Python + SQLite; must run and pass on Linux CI without `mlx-lm`.
- **No table models returned from API (§17.1):** any API endpoints added or updated must return Pydantic schemas from `schemas/sessions.py`.

## 7. Edge cases

1. **`drills.created_at` ties within the same second (creation order determinism).** In SQLite, `drills.created_at` defaults to `CURRENT_TIMESTAMP` (whole-second resolution) or is inserted in fast succession by `GenerationService`. Two drills for the same `(participant_id, arm)` often have identical `created_at` timestamps. Ordering only by `ORDER BY created_at ASC` leaves tie-breaking arbitrary in SQLite. Concrete example: drill D1 and D2 are created in the same millisecond; `ORDER BY created_at ASC, id ASC` (or `rowid ASC`) is required for a deterministic creation order.
2. **Insufficient `ready` drills in the pool for one or more arms.** A practice block requires 2 `ready` drills per arm (`block_chars = 600`, `drill_length_chars = 300`). If `control` has 6 ready drills, `heuristic` has 1 ready drill (below 2), and `plan_session` is called: it must fail cleanly and roll back without marking `control`'s 2 drills as `used` or leaving a half-built `Session` in the database.
3. **`drills.used_in_block_id` FK flush order.** Because `PRAGMA foreign_keys=ON` is active on every connection, updating `drill.used_in_block_id = block.id` before `block` is flushed to `session_blocks` can trigger `IntegrityError: FOREIGN KEY constraint failed` if SQLAlchemy flushes the `Drill` update before the `SessionBlock` insert. Flushing `SessionBlock` first guarantees `block.id` exists in `session_blocks`.
4. **Abandoned practice sessions vs Latin-square rotation and `day_index`.**
   - `models/sessions.py` states: *"day_index is 1-based within the phase. A retried abandoned session gets the next day_index, never the abandoned one's (T1.1 owner answer 11)"*.
   - §9.3 states: *"Abandoned practice sessions do not count toward N"*.
   - Concrete example: a participant completes Practice Day 1 (`day_index=1`, row 0 of Latin square), starts Practice Day 2 (`day_index=2`) which is abandoned after 30 minutes, and comes back the next day. The new session gets `day_index=3` per T1.1 owner answer 11, or does Latin square rotation index by completed practice sessions vs `day_index`? And what happens to the drills that were marked `used` in the abandoned session — they stay `used` ("no drill used twice") while pool replenishment tops up the pool! (See Open Question 1 & 3.)
5. **Returning an existing open (`in_progress`) session vs 30-minute abandonment (§9.3, §14).** §14 states `POST /participants/{pid}/sessions` *"returns the open one if it exists"*. Calling `plan_session` twice while a session is `in_progress` must return that existing session and its blocks without consuming new drills from `drills`! And what if the existing `in_progress` session is > 30 minutes old (§9.3)? (See Open Question 3 & 4.)
6. **2-set cut-line mode (`arms_enabled = ["control", "heuristic"]`) vs 4-arm mode (`["control", "heuristic", "markov", "llm"]`).** In §16's cut-line, `arms_enabled` can have 2 arms instead of 4. A 4×4 Latin square over 4 arms rotates over 4 days (`"CHML"`, etc.), whereas 2 arms rotate over a 2×2 Latin square (`"CH"`, `"HC"`). Furthermore, does a participant's Latin square start from a fixed canonical order or a per-participant seeded order? (See Open Question 1.)
7. **Baseline and retest block mapping (`part` vs `day_index`).**
   - `models/sessions.py` docstring (written in T1.1) says: *"Test sessions (baseline, retest) have one block per passage, arm 'test', block_index equal to the passage's part"*.
   - Later, in T1.8, the owner chose **Option A** (`docs/plans/T1.8-brief.md` line 475): *"each baseline session types **one** part of form A (day 0 → part 0, day 1 → part 1)"*.
   - Concrete example: on Baseline session 1 (`day_index=1`), the participant types only `part=0` of form A (1 block in the session), and on Baseline session 2 (`day_index=2`), the participant types `part=1` of form A (1 block in the session). In session 2 (`part=1`), is `session_blocks.block_index` `0` (0-based within the session) or `1` (`passage.part` per `models/sessions.py` docstring)? (See Open Question 2.)
8. **Duplicate job enqueueing when pool is low (§10.1, §13.7).** §13.7 says: *"Target: 3 days of ready drills per arm per participant (2 drills per block times 3 days = 6). After each session completes, the API enqueues a job for any arm whose pool is below target."* Suppose `ready` count for `heuristic` is 4 (deficit = 2), and there is already a `pending` or `running` `GenerationJob` for `(participant_id, "heuristic")` requesting 2 drills (because the worker hasn't finished it yet). If `replenish_pool` only checks `count(drills WHERE status='ready')` and ignores `pending`/`running` jobs, it will enqueue redundant jobs. (See Open Question 5.)

## 8. Risks

1. **Mismatch between T1.1's `SessionBlock` docstring and T1.8 Option A for baseline/retest sessions:** T1.1's docstring assumed a test session has multiple blocks (one per passage part, `block_index == part`), whereas T1.8's owner decision Option A decided each of the two baseline sessions types *one* part (`day_index 1 → part 0`, `day_index 2 → part 1`). 3. **Accidental drill consumption on retry or open session:** If `POST /participants/{pid}/sessions` creates a new session or selects drills before checking for an existing `in_progress` session, page refreshes will drain the drill pool and mark unused drills as `used`.
4. **FK violation when linking `drills.used_in_block_id`:** Setting `drill.used_in_block_id = block.id` without flushing `block` first under `PRAGMA foreign_keys=ON`.
