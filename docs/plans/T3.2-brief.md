## 2. Why it matters

The LLM generator is the fourth and final drill generator in Typist-ML and implements `Arm.LLM` (D03). Up through Milestone 2 and Task T3.1, the pipeline ran in 2-arm and 3-arm modes (`control`, `heuristic`, and `markov`). T3.2 builds the local on-device neural language model generator, fulfilling the core comparison of the experiment.

- **Fulfills the core research question (§1, §3.1).** The central question of the experiment is: *"do targeted drills beat plain practice, and does a small on-device language model write better drills than a dictionary heuristic or a Markov chain?"* The LLM arm provides real English sentences/word-sequences generated conditionally based on weak bigram prompts, contrasting with the dictionary-frequency heuristic and the statistical Markov pseudo-words.
- **Unblocks Milestone 3 bake-off (T3.3) and calibration (T3.4).** In T3.3, candidate models are evaluated across 10 synthetic target sets (20 drills per set) through the real validator, recording acceptance rate, attempts per accepted drill, density, real-word ratio, tokens per second, and peak memory in `notebooks/02_model_bakeoff`. T3.3 directly depends on `MLXRuntime` and the LLM generator. In T3.4, `d_min` and `d_max` are calibrated so that each targeted arm (heuristic, Markov, LLM) accepts $\ge 80\%$ of drills within 5 attempts.
- **Enables full 4-arm within-person drill generation in the worker (§10.2, §13.7).** Once `Arm.LLM` is wired into `worker.py::build_default_generators`, the batch generation worker autonomously claims pending jobs for `Arm.LLM` and pre-generates 3 days of ready drills into the pool.
- **Audits neural generation efficiency and resource constraints (§3.5, §8.1).** LLM generation attempts record execution time (`gen_ms`), token counts (`gen_tokens`), throughput (`tokens_per_sec`), and memory footprint (`peak_memory_mb`) on every model call (accepted or rejected) in `generation_attempts`, proving engineering claims in Milestone 4 (README: *"One line: overhead p95 and LLM tokens per second, measured"*).

**What breaks if it is wrong:**
- If top-level imports of `mlx`, `mlx_lm`, or `huggingface_hub` leak into modules loaded on non-Apple-Silicon systems or outside optional paths, Linux CI (`uv sync --locked`) and `just check-api` immediately fail.
- If pyright in `src/` encounters missing stubs or unresolvable imports on Linux CI, pyright strict fails.
- If model loading attempts to download weights during generation rather than loading offline from the local Hugging Face cache snapshot (violating D19 and D23), the application violates privacy and offline guarantees.
- If the seed is not applied to `mx.random.seed` before completion or prompt formatting varies across runs, determinism (§13.1) breaks, making drills irreproducible.
- If `tokens_per_sec` or `peak_memory_mb` are missing, malformed, or have unit errors (e.g. storing GB instead of MB, see ADR `T0.5-mlx-lm-api-check.md`), attempt logging in `generation_attempts` fails or records corrupt audit numbers.
- If post-processing does not produce text conforming to `[a-z ]` single-spaced lowercase text or drops too many words below length floor 270, the validator rejects all 5 attempts, starving the LLM drill pool and triggering `DrillGenerationExhaustedError`.

## 3. Governing decisions (each D-number and what it forces here)

- **D03 (Arms: `control, heuristic, markov, llm`):** T3.2 implements `Arm.LLM` (declared in `typist.generation.base.Arm` and `typist.models.drills.DRILL_ARMS`). It is a targeted arm: its `DrillSpec.target_bigrams` is populated from the participant's frozen `bigram_assignment` rows (T2.2).
- **D06 (Deployment: Local-only on the MacBook Pro M1 Pro):** Everything runs on one machine. The model runtime executes locally on Apple Silicon unified memory; no remote inference server or external machine is involved.
- **D08 (Backend stack: Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite WAL, Typer CLI, ruff, pyright, pytest):** Generator logic is written in Python 3.12 inside `services/api`.
- **D09 (Model runtime: `mlx-lm` Python API, version pinned in `uv.lock`):** Direct control of sampling, seeds, and tokens-per-second stats. Pinned in `pyproject.toml` extra `mlx` (`mlx==0.32.3`, `mlx-lm==0.31.3` with marker `sys_platform == 'darwin' and platform_machine == 'arm64'`).
- **D10 (Model: Default `mlx-community/Llama-3.2-1B-Instruct-4bit`):** Pinned Hugging Face commit `08231374eeacb049a0eade7922910865b8fce912` (from T0.5 / D23).
- **D11 (Generation timing: Batch, via a separate worker process):** LLM generation occurs asynchronously in background jobs via `GenerationService` and `worker.py`. Generating drills does not block typing or API requests. The pool maintains 3 days of ready drills per arm.
- **D13 (Text scope: Lowercase `a`–`z` and single spaces only, no punctuation):** The LLM raw output must be post-processed to lowercase ASCII `a`–`z` with single spaces, with no digits, punctuation, leading, trailing, or doubled spaces.
- **D16 (Fairness gate: All targeted arms pass one shared validator):** LLM drill candidates must pass `validator.validate()`: target length 300 (floor 270), target density $\in [d_{min}, d_{max}]$, coverage $\ge 3$ per target bigram, max word repeat $\le 3$, bigram run $< 3$. In addition, `real_word_ratio >= 0.8` gates only `Arm.LLM` (§13.1: *"Recorded for all; gate for LLM"*).
- **D17 (Word list: `wordfreq` English list, filtered to `a`–`z` words):** Post-processing references the corpus word list to evaluate real-word ratio and filter tokens.
- **D19 (No cloud, no WASM):** No cloud AI APIs (no OpenAI, Anthropic, or external inference calls). Everything runs locally on device.
- **D20 (Pre-registration / Freeze):** Sampler settings (`temperature`, `top_p`, `max_tokens`), `model_id`, `prompt_version`, `d_min`, and `d_max` are experiment parameters that are frozen before the pilot begins (T3.5).
- **D23 (Model download / Hugging Face cache):** Model weights are downloaded once by the owner via `just mlx-smoke --download` into the default cache outside the repository (`~/.cache/huggingface/hub`). All subsequent loads set `HF_HUB_OFFLINE=1` and `HF_HUB_DISABLE_TELEMETRY=1` before `huggingface_hub` is imported, and resolve the snapshot with `local_files_only=True`. The model runtime never contacts the network.

    MARKOV = "markov"

    max_density are the d_min/d_max range the validator enforces for targeted arms; length_chars is
    the target length the generator aims for (the validator's floor is a separate config key). seed
    makes generation reproducible (determinism, 13.1)."""

    participant_id: str
    arm: Arm
    target_bigrams: tuple[str, ...]  # empty for CONTROL

    max_density: float = 0.40
    seed: int = 0

    """A generator's output before validation (owner answer 1). text is the cleaned a-z+space drill

    raw_output: str
    generator_version: str
    seed: int
    model_id: str | None = None
    prompt_version: str | None = None
    gen_ms: float | None = None
    gen_tokens: int | None = None
    tokens_per_sec: float | None = None
    peak_memory_mb: float | None = None

### 4.5 Worker generator builder (`services/api/src/typist/worker.py`, verbatim)

```python
def build_default_generators(
    session: Session, index: WordIndex
) -> tuple[dict[Arm, DrillGenerator], ValidatorConfig]:
    validator_config = load_validator_config(session)
    pool_row = session.get(ExperimentConfig, "control_word_pool")
    if pool_row is None:
        raise MissingConfigError("control_word_pool")
    pool_size = int(pool_row.value)
    beta_row = session.get(ExperimentConfig, "markov_beta")
    if beta_row is None:
        raise MissingConfigError("markov_beta")
    markov_beta = float(beta_row.value)
    generators: dict[Arm, DrillGenerator] = {
        Arm.CONTROL: ControlGenerator(index, validator_config, pool_size),
        Arm.HEURISTIC: HeuristicGenerator(index, validator_config, pool_size),
        Arm.MARKOV: MarkovGenerator(index, validator_config, markov_beta),
    }
    return generators, validator_config
```

## 5. Inputs and outputs

### Inputs
1. **`DrillSpec` (in-memory):**
   - `participant_id: str`
   - `arm: Arm` (`Arm.LLM`)
   - `target_bigrams: tuple[str, ...]` (e.g. `("th", "ea", "in", "st")`, 4 targets for standard set, or 3 for fallback set)
   - `length_chars: int = 300` (target character length)
   - `min_density: float = 0.15`
   - `max_density: float = 0.40`
   - `seed: int` (deterministic attempt seed derived via `derive_drill_seed`)
2. **Model Snapshot Weights (local file system):**
   - Cached weights for `mlx-community/Llama-3.2-1B-Instruct-4bit` at commit `08231374eeacb049a0eade7922910865b8fce912` located in `~/.cache/huggingface/hub/`.
3. **Corpus Word Vocabulary (in-memory):**
   - `WordIndex.words` loaded from `data/words.json` (20,000 words).
4. **Experiment Configuration (SQLite `experiment_config` table):**
   - Model parameters: `model_id`, `prompt_version`, `temperature`, `top_p`, `max_tokens`.
   - Shared parameters: `d_min`, `d_max`, `drill_min_length_chars`, `drill_min_coverage`, `drill_max_word_repeats`, `drill_max_bigram_run`, `drill_min_real_word_ratio`.

### Outputs
1. **`DrillCandidate` (in-memory):**
   - `text: str`: post-processed typing practice text (lowercase `a`–`z`, single spaces, length $\ge 270$ and $\le 300$, non-dictionary words filtered, cut to length at word boundary).
   - `raw_output: str`: raw text emitted by `stream_generate` before post-processing.
   - `generator_version: str`: e.g. `"llm-v1"`.
   - `seed: int`: matching `spec.seed`.
   - `model_id: str`: e.g. `"mlx-community/Llama-3.2-1B-Instruct-4bit"`.
   - `prompt_version: str`: e.g. `"v1"`.
   - `gen_ms: float`: generation latency in milliseconds.
   - `gen_tokens: int`: number of tokens generated (`response.generation_tokens`).
   - `tokens_per_sec: float`: generation throughput (`response.generation_tps`).
   - `peak_memory_mb: float`: peak memory in MB (`response.peak_memory * 1000.0`).
2. **Database Rows (persisted by `GenerationService`):**
   - `generation_attempts`: row inserted for every attempt (accepted or rejected) storing raw and clean text, target density, rejection reasons, `gen_ms`, `gen_tokens`, `tokens_per_sec`, and `peak_memory_mb`.
   - `drills`: row inserted upon acceptance with `status = "ready"`, storing text, metrics (`target_density`, `mean_word_len`, `real_word_ratio`), `model_id`, `prompt_version`, and `seed`.

## 6. Constraints

- **Platform limit (Apple Silicon):** `mlx` and `mlx-lm` execute only on macOS on Apple Silicon (`arm64`). They are listed under `[project.optional-dependencies]` in `services/api/pyproject.toml` with the marker `sys_platform == 'darwin' and platform_machine == 'arm64'`.
- **Linux CI compatibility:** Cloud CI runs on Linux x86_64 without `mlx` or `mlx-lm`. No file in `src/` may import `mlx`, `mlx_lm`, or `huggingface_hub` at module top-level. Modules must import cleanly on Linux.
- **Pyright strict mode:** `services/api/pyproject.toml` configures `strict = ["src"]`. Type annotations must be strict, fully resolved, and must not fail on Linux CI when `mlx` and `mlx-lm` packages are absent.
- **Offline / Privacy constraint (D19, D23):** Generation must run completely offline without contacting Hugging Face or external APIs. Environment variables `HF_HUB_OFFLINE=1` and `HF_HUB_DISABLE_TELEMETRY=1` must be set prior to Hub library imports, and snapshots loaded with `local_files_only=True`.
- **Determinism constraint (D16, §13.1):** Given the same `DrillSpec` and `seed`, generation must produce identical output. MLX's PRNG must be seeded via `mx.random.seed(seed)` immediately before generation.
- **Retry ceiling & no fallback (§13.5):** Generation is limited to at most 5 attempts per drill. If all 5 attempts fail the validator, the job fails with `DrillGenerationExhaustedError`. The LLM arm must never fall back to heuristic or Markov text.
- **Throughput target (§13.6):** The design requires $\ge 30$ tokens per second for candidate models on Apple Silicon.
- **Test execution rules (CLAUDE.md):** Unit tests that load real models must be marked with `@pytest.mark.mlx` and run only on Apple Silicon. Off-Mac CI and standard unit tests must use a fake/mock runtime.

## 7. Edge cases

1. **Empty stream output:**
   - *Example:* The model immediately emits an end-of-sequence token, so `stream_generate` yields zero chunks. `last` is `None`. Accessing `last.generation_tokens` or `last.generation_tps` would raise `AttributeError`. The wrapper must handle empty yields cleanly (as in `scripts/mlx_smoke.py`, which checks for `last is None`).
2. **Preamble, conversational filler, or formatting quotes in output:**
   - *Example:* The model emits: `"Here are your words: back know clock snow check brown quick..."` or encloses the text in quotes `"... "`.
   - *Consequence:* If post-processing does not strip preambles, words like `"here"`, `"are"`, `"your"` become part of the drill text, diluting target density or failing `real_word_ratio`.
3. **Punctuation and capitalization:**
   - *Example:* The model produces capitalized words with commas or periods: `"Back, know, clock. Snow, check!"`
   - *Consequence:* Post-processing must lowercase text and replace any non-`[a-z]` character with a space, then collapse repeated spaces into a single space.
4. **Length truncation cutting words in half:**
   - *Example:* Slicing raw text at character position 300 slices `"brown"` into `"bro"`.
   - *Consequence:* Slicing must truncate at a space/word boundary to preserve valid dictionary words. If truncating at a word boundary leaves fewer than 270 characters, the candidate must trigger `RejectReason.TOO_SHORT` in the validator.
5. **Real-word filtering stripping target words:**
   - *Example:* Model invents a pseudo-word containing a target bigram (e.g. `"snowck"` for `ck`).
   - *Consequence:* Post-processing drops words not in the word list. Dropping `"snowck"` reduces length and removes an occurrence of `ck`, which may cause `RejectReason.COVERAGE` or `RejectReason.TOO_SHORT`.
6. **Repetitive loops tripping repetition gates:**
   - *Example:* The model loops on a single target word: `"clock clock clock clock clock"`.
   - *Consequence:* `ValidatorConfig.max_word_repeats = 3`. More than 3 occurrences trips `RejectReason.WORD_REPEAT`.
7. **Bigram runs within model output:**
   - *Example:* Model outputs `"murmur"` or `"banana"` or stuttering characters (`"ththth"`).
   - *Consequence:* If any bigram repeats at every other letter position 3 or more times consecutively within a word, `RejectReason.BIGRAM_REPEAT` is triggered.
8. **Target bigram formatting in Prompt v1:**
   - *Example:* `target_bigrams` is `("ck", "ow")`. Prompt v1 interpolates `{bigrams}` as `"ck, ow"`.
   - *Edge Case:* When fallback occurs and only 3 target bigrams exist (e.g. `("th", "er", "on")`), or 4 exist in standard mode, formatting must format arbitrary tuple lengths (e.g. `", ".join(spec.target_bigrams)`).
9. **Missing local model snapshot in cache:**
   - *Example:* A user runs the worker without having run `just mlx-smoke --download`.
   - *Consequence:* `snapshot_download` raises `FileNotFoundError` / `OSError`. The error must be caught and report an informative message directing the user to run `just mlx-smoke --download`, rather than crashing with an unhandled traceback.
10. **Peak memory unit conversion:**
    - *Example:* `response.peak_memory` returns `0.812` (in GB).
    - *Consequence:* If written directly to `generation_attempts.peak_memory_mb`, the stored value is `0.812` MB instead of `812.0` MB. Must convert via `gb * 1000.0`.

## 8. Risks

1. **Rejection rate and generation latency:** LLM generation is significantly slower than heuristic or Markov sampling (~1–3 seconds per attempt). If Prompt v1 achieves a low first-attempt acceptance rate ($< 50\%$), retrying 5 times per drill could take 10–15 seconds per drill. For a batch of 6 drills (up to 30 attempts), worker execution could take several minutes.
2. **Linux CI failure due to Apple Silicon dependencies:** If any type annotation, import, or module initialization in `src/` requires `mlx` or `mlx_lm` unconditionally, CI jobs on Linux (`api` check, pyright strict, pytest) will fail.
3. **Discrepancy in vocabulary list between generator post-processing and validator:** Section 13.5 states post-processing drops words not in the "50,000-word list", while the corpus build creates a 20,000-word list (`words.json`). If post-processing keeps words between ranks 20,001 and 50,000, `validator.validate()` (which tests against `WordIndex.words`, 20,000 words) will count them as non-words and reject the drill for `REAL_WORD_RATIO`.
4. **Chat template non-determinism via system timestamp:** Some tokenizer chat templates inject the current system date or timestamp into the rendered prompt if not explicitly parameterized, which could cause identical seeds to produce different prompts on different days.
5. **Memory leaks or uncollected weights across worker jobs:** If `MLXRuntime` repeatedly loads the model into memory rather than loading once per worker process, unified memory usage could grow across jobs and cause out-of-memory errors on 16 GB machines.

## 9. Open questions

1. **Vocabulary list for post-processing vs validator:** Section 13.5 post-processing states: *"drop words not in the 50,000-word list"*, whereas the corpus build (`corpus/build.py`, T1.8, T2.3 owner answer 3) creates a 20,000-word list (`words.json`). If post-processing drops words outside a 50,000-word list, but the validator measures `real_word_ratio` against the 20,000-word `WordIndex.words`, words in ranks 20,001–50,000 will be treated as non-words by the validator, potentially tripping `RejectReason.REAL_WORD_RATIO`. Should post-processing drop words not in the existing 20,000-word `WordIndex.words`, or does T3.2 build/load an additional 50,000-word artifact?
2. **Order and semantics of dropping words vs validator `real_word_ratio`:** Section 13.5 lists post-processing steps: *"measure real-word ratio, drop words not in the 50,000-word list, cut to length"*. However, `DrillCandidate` does not carry `real_word_ratio` (owner answer 1: *"Carries NO fairness metrics — the validator computes those"*), and `validator.validate()` computes `real_word_ratio` on `candidate.text`. If the generator drops all non-dictionary words during post-processing, `candidate.text` will contain only dictionary words, causing `validator.py` to always measure `real_word_ratio = 1.0` and rendering the `RejectReason.REAL_WORD_RATIO` gate in the validator inert. Should the LLM generator drop non-dictionary words before handing text to the validator, or should it leave the cleaned words in place so the validator's `drill_min_real_word_ratio` gate (0.8) actually evaluates the candidate?
3. **Experiment config keys for LLM generator:** Section 13.5 lists *"Frozen for the pilot: model_id, prompt_version, sampler settings, d_min and d_max"*. `d_min` and `d_max` already exist in `experiment_config`. What exact keys should be added in a new Alembic migration (e.g. `0010_llm_config.py`): e.g. `llm_model_id` (default `"mlx-community/Llama-3.2-1B-Instruct-4bit"`), `llm_prompt_version` (default `"v1"`), `llm_temperature` (default `0.8`), `llm_top_p` (default `0.9`), `llm_max_tokens` (default `160`), or should they be stored under different names (e.g. `model_id`, `prompt_version`)?
4. **Target bigrams prompt interpolation format:** Section 13.5 prompt template shows `pairs: {bigrams}`. When `target_bigrams` is e.g. `("ck", "ow", "th", "re")`, how should `{bigrams}` be formatted? For example, comma-space separated `"ck, ow, th, re"` matching the example turn (`"ck, ow"`), or space-separated?
5. **Handling model load failure in `build_default_generators` on non-Mac or un-downloaded environments:** `worker.py::build_default_generators` currently constructs `ControlGenerator`, `HeuristicGenerator`, and `MarkovGenerator`. If `worker.py` attempts to instantiate `LLMGenerator` with `MLXRuntime` on Linux CI or on a Mac where `just mlx-smoke --download` has not been run, `MLXRuntime` cannot load the model. Should `build_default_generators` conditionally include `Arm.LLM` only if `is_apple_silicon()` and the snapshot exists (or accept an injectable runtime/factory), so `test_generation_service.py` and Linux CI worker tests continue to pass without error?

## 10. Owner answers (2026-10-28)

1. **Vocabulary list for post-processing vs validator:**
   - **Answer:** Use `WordIndex.words` (the 20,000-word vocabulary built by `corpus/build.py`) as the dictionary word list for both post-processing and validation, unifying the vocabulary across the entire project.
   - **Source:** (a) Design doc §13.1, §17.1; (c) T2.3 owner answer 3; (d) `validator.py` `known_words`.

2. **Order and semantics of dropping words vs validator `real_word_ratio`:**
   - **Answer:** The generator performs character cleaning (lowercasing, non-letters replaced by spaces, collapsing multiple spaces) and word-boundary truncation up to 300 characters, leaving the cleaned tokens in `candidate.text`. `validator.validate()` computes `real_word_ratio` directly on `candidate.text` and enforces the `drill_min_real_word_ratio` gate (0.8) for `Arm.LLM`.
   - **Source:** (a) Design doc §13.1 ("Gate for LLM"); (d) `validator.py` line 176.

3. **Experiment config keys for LLM generator:**
   - **Answer:** Add Alembic migration `0010_llm_config.py` inserting the following keys into `experiment_config`:
     - `llm_model_id`: `"mlx-community/Llama-3.2-1B-Instruct-4bit"`
     - `llm_model_revision`: `"08231374eeacb049a0eade7922910865b8fce912"` (D10, D23)
     - `llm_prompt_version`: `"v1"`
     - `llm_temperature`: `0.8`
     - `llm_top_p`: `0.9`
     - `llm_max_tokens`: `160`
   - **Source:** (a) Design doc §13.5; (d) `0007_generator_config.py`, `0009_markov_config.py`.

4. **Target bigrams prompt interpolation format:**
   - **Answer:** Interpolate with `", ".join(spec.target_bigrams)` (comma-space separated, e.g. `"ck, ow"`), matching the Prompt v1 example turn in §13.5 verbatim.
   - **Source:** (a) Design doc §13.5.

5. **Handling model load failure in `build_default_generators` on non-Mac or un-downloaded environments:**
   - **Answer:** `build_default_generators` accepts an optional `runtime: LLMRuntimeProtocol | None = None`. If provided, it registers `Arm.LLM: LLMGenerator(index, validator_config, runtime=runtime, ...)`. If omitted, it attempts to load `MLXRuntime` if running on Apple Silicon (`is_apple_silicon()`) and the local model snapshot directory exists; otherwise, it skips `Arm.LLM` (or uses a provided runtime), allowing Linux CI and tests to pass cleanly without errors.
   - **Source:** (b) `GEMINI.md` / `CLAUDE.md`; (d) `test_mlx_smoke.py`, `conftest.py`.

6. **Abstract interface / Protocol for `MLXRuntime` for testability:**
   - **Answer:** Define `LLMOutput` dataclass (`text`, `tokens`, `tokens_per_sec`, `peak_memory_mb`) and `LLMRuntimeProtocol` with `complete(messages, *, max_tokens, temp, top_p, seed) -> LLMOutput`. Implement `MLXRuntime` (lazily importing `mlx` and `mlx_lm`) and `FakeLLMRuntime` (for unit tests and CI). `LLMGenerator.__init__` accepts any `LLMRuntimeProtocol`.
   - **Source:** (a) Design doc §13.5; (b) `GEMINI.md` / `CLAUDE.md` ("Code that talks to the model goes through MLXRuntime; tests use a fake runtime").
