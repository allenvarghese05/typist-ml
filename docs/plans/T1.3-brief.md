## 2. Why it matters

What T1.3 enables later:
- **T1.4 (KeystrokeRecorder)** builds each `keystroke_events` row. Four of its fields come from the
  cursor: `target_index`, `expected_char`, `outcome`, `first_attempt` (T1.2 owner answers 2 and 4).
  Every row the experiment ever stores carries the cursor's answer.
- **T1.5 (TypingSurface)** needs the cursor to know where the typist is, which characters are
  wrong ("wrong characters shown in red and left in place until corrected with Backspace", 11.3)
  and when the block is finished (`isDone()`).
- **T1.7 (attribution.py)** trusts `outcome`, `first_attempt` and `target_index` as ground truth
  (answer 2: "attribution takes outcome/target_index as ground truth"). It never re-aligns. A wrong
  cursor therefore poisons attribution silently, even though attribution itself passes its own
  fixture tests (it reads the fixture's correct rows, not the browser's rows).
- **Cross-language agreement:** T1.3 is the TypeScript half of the section 7 guarantee. Until it
  passes, nothing ties the browser's idea of an error to the fixture.

What breaks if it is wrong:
- **Every stored row from the pilot onwards.** `keystroke_events` is "the raw data that cannot be
  rebuilt" (D24 context, citing 10.3) and is append-only (CLAUDE.md). A first-attempt or
  target-index bug cannot be repaired after data collection; `typist stats recompute` (T1.9)
  recomputes from these rows and would reproduce the same wrong numbers.
- **The primary outcome (D05).** Errors and attempts per bigram come from `outcome` and
  `first_attempt`. Section 18: "Attribution bug | All results wrong".
- **A test that passes for the wrong reason.** If the test compares fewer fields than answer 4
  requires, or reads a copy of the fixture, or re-derives expected values in TypeScript, T1.3 can
  pass while the browser and Python disagree.

## 4. Current state

### 4.1 Design rules for the cursor (verbatim)
- **12.3:** "The TextCursor holds the target text and an index. Each printable keystroke is compared with target[index], recorded as correct or error, and the index moves forward one position either way. Backspace moves the index back. The first keystroke ever recorded at a position is its first attempt; retyping after a correction is not."
- **11.3:** "Typing surface rules: monospace font, the whole block visible, one character per keystroke, wrong characters shown in red and left in place until corrected with Backspace, no autocorrect or spellcheck, and the block pauses if the window loses focus."
- **12.1:** "Ignore events where e.repeat is true, modifier-only keys, and any event with Ctrl, Meta or Alt held. Shift is allowed but not needed in v1." / "Handle only a to z, space and Backspace." / "Use e.key to decide the character and store e.code for the physical key."
- **Figure 10.3 (Figure 9):** "Normalise t = event.timeStamp, drop repeat and modifiers" then "Align to target text outcome + first attempt per position" then `keystroke_events`.
- **Signed derivation A.4 (the cursor walk the owner approved):** "The cursor starts at 0. A printable key compares with `target[index]`, records `target_index = index`, then does `index += 1`. A Backspace does `index = max(index − 1, 0)` and records the new index. A key is a first attempt when no earlier row was recorded at its `target_index` by a printable key."

### 4.2 Design types (Figure 5, section 9.2; none exists in code)
- `TextCursor`: `+target: string`, `+index: number`, `-firstAttempt: boolean[]`,
  `+type(char) : Outcome`, `+backspace() : void`, `+isDone() : boolean`. `firstAttempt` is private
  (`-`); `backspace()` returns `void`; `Outcome` is not defined further in any quoted text.
- `KeystrokeEvent` (TS): `seq: number`, `key: string`, `code: string`, `tDown: number`,
  `tUp: number`, `iki: number`, `targetIndex: number`, `expected: string`, `outcome: Outcome`,
  `firstAttempt: boolean`, `handlerMs: number`. D24: "Figure 5's `KeystrokeEvent` type gains this
  field" (`after_pause`).
- `KeystrokeRecorder`: `-openKeys: Map<string, PendingKey>`, `-lastDownT: number`,
  `+onKeyDown(e: KeyboardEvent)`, `+onKeyUp(e: KeyboardEvent)`. `EventBuffer`:
  `+completeDwell(seq, tUp) : void`.
- Section 6.1 (via T0.2 brief): KeystrokeRecorder must not "Depend on React; it is a plain class so
  it can be unit tested". Section 9.2: "React subscribes to it with useSyncExternalStore".

## 6. Constraints

- **Read the fixture in place.** No copy, symlink or generated TS module of it inside `apps/web`
  (answer 20; section 7's "cannot drift apart").
- **Never edit the fixture.** If a value looks wrong, flag it in the PR (CLAUDE.md); a change needs
  an owner-approved PR with a changelog entry (answer 19).
- **Compare all four fields on every row, with exact equality** (answers 4, 13b). Only the cursor
  produces actual values; the test must not recompute expected values from the target text.
- **No attribution in TypeScript.** The T1.3 tests must not compute or assert
  `expected_bigram_stats`, pair skips or IKI samples (CLAUDE.md, 6.2). `review_aid_*` fields are
  never asserted.
- **Purely positional alignment** (answer 9c, 12.3): no word-based realignment, no skipping to the
  next word on space, no "extra characters" appended to a word.
- **Monkeytype is a behaviour reference only** and its code (GPL) must not be copied. Its default
  behaviour differs from this project in at least three ways relevant here: it aligns by word
  (space jumps to the next word; extra letters are appended), it restricts backspacing into an
  already-correct previous word by default, and it times tests differently. The fixture requires
  positional alignment (cases f, h), backspacing over correct characters and spaces (cases c, d),
  and Backspace at index 0 as a recorded no-op (case e).
- **TypeScript strictness** (`tsconfig.app.json`): `noUncheckedIndexedAccess` makes `target[i]`
  `string | undefined`; `erasableSyntaxOnly` forbids `enum`, `namespace` and constructor parameter
  properties (so `Outcome` cannot be a TS `enum`); `verbatimModuleSyntax` requires `import type`
  for type-only imports; `noUnusedLocals`/`noUnusedParameters` are on. Biome
  `noExplicitAny: error`; section 17.1 "no any without a comment explaining why". `JSON.parse`
  returns `any` (an untyped fixture value must be narrowed or typed).
- **Performance:** the cursor runs inside the keydown handler. Section 12.5 target: "handler p95
  under 1 ms"; section 12 frontend rule: "no React state updates inside [the handler], no
  allocation-heavy work, no network calls. Rendering happens through the external store." T1.5:
  "Typing 300 characters feels instant". Real blocks are 600 characters (3.3).
- **No React dependency** in telemetry classes (6.1 says this for the recorder; the cursor sits in
  the same `telemetry/` folder and is tested in Vitest's `node` environment).
- **No randomness** is involved; if any appears it must come from a seeded generator passed in
  (CLAUDE.md).
- **Gate:** `just check` / CI `web`: `biome ci .`, `biome format .`, `tsc -b`, `vitest run`,

## 7. Edge cases

Positions refer to the fixture target `the small hill on the other side of the old red barn and the farm`.

1. **Backspace at index 0 as the very first key** (seq 0, case e). Expected: `target_index 0`,
   `outcome "backspace"`, `expected_char null`, `first_attempt null`; the index stays 0; the next
   key `t` (seq 1) is still `first_attempt: true`. A cursor that marks position 0 "touched" on
   Backspace fails seq 1.
2. **Backspace landing index** (D25). seq 8: cursor at 7 → lands on 6 → `target_index 6`; seq 9 →
   5. A cursor that reports the pre-press index gives 7 and 6 and fails.
3. **Omission cascade** (case f, seq 5 to 11). `a` typed at 5 (expected `m`) and `l` at 6
   (expected `a`) are errors; two Backspaces; `m`, `a` retyped at 5, 6 are `correct` with
   `first_attempt: false`; `l` at 7 (seq 12) is a first attempt. Word-based realignment would
   produce different outcomes.
4. **Space typed for a letter** (seq 16): `" "` at 11 (expected `i`) is `error`, index moves to 12.
   **Letter typed for a space** (seq 21): `b` at 14 (expected `" "`) is `error`. A cursor that
   treats space as "jump to next word" fails here.
5. **First attempt survives a correct erase** (case c, seq 40 to 42): `i` at 29 correct (first),
   Backspace (target_index 29), `i` retyped correct with `first_attempt: false`.
6. **Over-erasing across a space** (case d, seq 46 to 52): three Backspaces land on 33, 32, 31; the
   retypes `e`, `" "`, `o` at 31, 32, 33 are `first_attempt: false` even though their first
   attempts were correct.
7. **Transposition** (case g, seq 56 to 61): `e` at 37 and `h` at 38 are both `error`; after two
   Backspaces both retypes are `correct`, `first_attempt: false`.
8. **Error right after a blur** (seq 68): `w` at 45 is `error`, `first_attempt: true`. Its
   `after_pause: true` is not the cursor's field.
9. **Uncorrected error, then continue** (case i, seq 87 to 88): `s` at 62 is `error` and stays; `r`
   at 63 is `correct`, `first_attempt: true`. Final index 64; `isDone()` false (row 88 `_note`).
10. **Repeated Backspace at 0.** Not in the fixture beyond one press. Answer 8b: each is a row with
    `target_index 0`; the index never goes negative.
11. **isDone and keys afterwards** (F7, not in the fixture). Example: target `"ab"`, type `a`, `x`
    → index 2, `isDone()` true even though position 1 is an error (answer 9a). A further `c` or a
    Backspace is "ignored, not recorded" (answer 9b): index and first-attempt state unchanged.
    Consequence of 9b as written: a typist whose last character is wrong cannot correct it,
    because the block is done the moment the index reaches the end (see open question 2).
12. **Finished block with errors** (F7): the fixture cannot show it; it needs a synthetic test.
13. **Empty or invalid target text.** An empty target makes `isDone()` true before any key. A
    target with uppercase, punctuation or double spaces is outside D13; behaviour is not stated
    (open question 3).
14. **Out-of-scope characters reaching the cursor.** The recorder filters them (answers 9d, 21),
    but if `"T"`, `"é"`, `"Tab"`, `""` or a two-character string reaches `type()`, the behaviour is
    not stated. Treating it as an error would create a row whose `key` violates the fixture's own
    structural rule (`key in TYPED_CHARS`) (open question 3).
15. **`null` vs `undefined`.** The fixture has JSON `null` for `expected_char` and `first_attempt`
    on Backspace rows. Vitest `toBe(null)` fails on `undefined`; `toEqual` treats object properties
    whose value is `undefined` as absent, which can hide a mismatch (verify for Vitest 4.1).
16. **Outcome type range.** `type(char)` only ever yields `correct` or `error`, while
    `KeystrokeEvent.outcome: Outcome` (Figure 5) must also hold `backspace` (fixture, DB CHECK).
    Whether `Outcome` includes `"backspace"` is a typing decision for the plan.
17. **Figure 5 vs the needed outputs.** `type(char): Outcome` returns only the outcome;
    `backspace(): void` returns nothing; `firstAttempt` is private. The fixture needs four fields per
    key, including first-attempt status and the Backspace landing index (open question 1).
18. **Field naming across the boundary.** Figure 5 uses `targetIndex`, `expected`, `firstAttempt`;
    the fixture and DB use `target_index`, `expected_char`, `first_attempt`. Answer 3: "TypeScript
    reads it as plain JSON, no renaming needed" (about reading the fixture). Which names the TS
    types use affects T1.4 and the T1.6 payload (open question 7).
19. **Shared state across tests.** One cursor instance reused across `it` blocks, or a cached
    fixture object mutated by a test, would make test order matter.
20. **Fixture rows order.** Rows are already in `seq` order; a test that relies on file order
    rather than `seq` is correct only because the Python test enforces contiguity.
21. **Case-sensitive paths.** Linux CI is case-sensitive; `golden_session.json` and directory
    names must match exactly (T0.2 edge case 6).

## 8. Risks

1. **Passing the wrong comparison.** Asserting only `outcome` (or only rows where it changes), or
   asserting a recomputed expectation instead of the fixture's stored values, lets a first-attempt
   or D25 bug through. Answer 4 requires all four fields.
2. **Monkeytype-shaped logic.** An implementation modelled on Monkeytype's word-based behaviour
   (space skips ahead, extra letters, no backspace into correct words) contradicts 12.3 and fails
   cases d, f, h. Copying its code would also breach the GPL rule.
3. **Off-by-one on Backspace.** Pre-press vs post-press index (D25), and the index-0 clamp (case e)
   are the most likely single-line bugs.
4. **First-attempt bookkeeping.** Marking a position "attempted" on Backspace, or clearing the mark
   when a character is erased, flips `first_attempt` on seq 1 or on the 12 retype rows.
5. **Fixture loading breaks the gate on one platform.** A path or config that works in `vitest run`
   but fails `tsc -b`, `biome ci .` or `vite build`, or works on macOS but not Linux CI.
6. **Fixture drift by copy.** Copying the JSON into `apps/web` to avoid config work re-creates the
   two-sources problem section 7 exists to prevent.
7. **Attribution creeping into TS.** A test helper that counts bigrams or session accuracy to
   "double-check" duplicates Python's job (CLAUDE.md).
8. **Scope creep into T1.4/T1.5.** Adding filtering, timestamps, `after_pause`, highlight state or
   React wiring to the cursor in this PR.
9. **Typing the fixture with `any`.** Biome `noExplicitAny` and 17.1 reject it; an unchecked cast
   could hide a renamed field.
10. **Interface churn.** If T1.3 departs from Figure 5 without recording it, T1.4/T1.5 plans built
    from the design doc will not match the code.

## 9. Open questions

1. **May TextCursor's public interface differ from Figure 5?** Figure 5 has `type(char): Outcome`,
   `backspace(): void` and a private `firstAttempt` array, but each keystroke row needs four values
   from the cursor (`target_index`, `expected_char`, `outcome`, `first_attempt`). May T1.3 change
   the return values (and expose first-attempt status), keeping the names `target`, `index`,
   `type`, `backspace`, `isDone`, and does that need an ADR?
   In plain terms: the design's sketch of TextCursor only hands back "correct" or "error". The
   recorder also needs to know "was this the first try at this position?" and, for Backspace,
   "where did the cursor land?". Example: after `t`, `x`, Backspace, `h`, the `h` row must say
   position 1, expected `h`, correct, not a first attempt. The sketch has no way to say that last
   part.
   Suggested default: yes, keep the Figure 5 names and let `type()` and `backspace()` return
   everything a row needs; no ADR (Figure 5 is not a section 2 decision), but the plan records the
   difference so T1.4 is built against the real interface.

2. **After the last character, is Backspace also ignored?** Answer 9b says keys after `isDone()`
   are ignored. Confirm this includes Backspace, so the block ends the instant the index reaches
   the end even if the last character is wrong.
   In plain terms: in the fixture text, if the typist ends with `farn` instead of `farm`, the block
   is over the moment `n` is pressed and they cannot go back to fix it. The alternative is to let
   Backspace work until some other "finish" signal.
   Suggested default: yes, Backspace is ignored too (answer 9b as written); the wrong last
   character stays as a first-attempt error.

3. **What should the cursor do with input it should never receive?** If `type()` gets something
   other than a to z or space (`"T"`, `"é"`, `"Tab"`, `""`), or the target text is empty or
   contains such characters, should it throw an error, silently ignore it, or count it as a typing
   error?
   In plain terms: the recorder is supposed to filter these out first, so this only happens if
   there is a bug elsewhere. Counting `T` as an error would store a row the fixture rules say can
   never exist; throwing makes the bug loud in tests.
   Suggested default: throw (like `apiPath` throws `RangeError`), both for bad keys and for a bad
   target text; ignoring or counting is never done silently.

4. **Does T1.3 check anything beyond the four per-keystroke fields?** Should the TS test also
   check session counts from the cursor (for example 55 correct first attempts out of 64, from
   `expected_session`), or only the four row fields plus the final index and `isDone()`?
   In plain terms: accuracy and WPM are computed in Python (T1.9). Having the browser also prove
   "55 of 64" is a second calculation of a Python statistic, which CLAUDE.md tries to avoid; but it
   would catch a cursor that gets every row right and still loses count.
   Suggested default: only the four row fields on all 89 rows, plus final index 64 and
   `isDone()` false; `expected_session` stays T1.9's.

5. **Does the cursor also keep what is shown on screen?** Section 11.3 wants wrong characters shown
   in red until corrected. Should T1.3's cursor also remember what was typed at each position (so
   the surface can draw red letters), or is that state built in T1.5's store?
   In plain terms: the cursor knows position 5 was an error when `a` was typed there, but after
   Backspace and retype, the screen must show `m` in normal colour. Someone has to track "what is
   currently typed at each position". Example: after `s`, `a` in "small", position 5 shows a red
   `a`.
   Suggested default: keep T1.3 to alignment only (the Figure 5 members plus what question 1
   adds); per-position display state is built in T1.5.

6. **May T1.3 add a test dependency?** For example fast-check for property tests (similar to
   T1.7's hypothesis), or none at all.
   In plain terms: a property test would try thousands of random key sequences and check rules
   such as "the index never goes below 0 or past the end". It is extra safety but a new package in
   the lockfile, and its randomness must be seeded (CLAUDE.md).
   Suggested default: no new dependency; example-based tests from the fixture plus hand-written
   synthetic sequences for F7.

7. **Which field names do the TypeScript types use?** Figure 5 uses camelCase (`targetIndex`,
   `expected`, `firstAttempt`); the fixture and database use snake_case (`target_index`,
   `expected_char`, `first_attempt`).
   In plain terms: the test has to compare the cursor's output with the fixture. If the TS names
   match the fixture, no translation is needed and the same names can later travel to the API
   (T1.6). If they follow Figure 5, the test (and later the recorder) translates names, which is
   one more place to make a mistake.
   Suggested default: the cursor's output uses the fixture/database snake_case names
   (`target_index`, `expected_char`, `outcome`, `first_attempt`), matching answer 3's "canonical
   schema name"; Figure 5's camelCase is not followed for these fields.

## Owner answers

Date: 2026-10-13

1. Interface vs. Figure 5: confirmed, no ADR. Keep the Figure 5 names (type, backspace, isDone), but have type() and backspace() return the full row (target_index, expected_char, outcome, first_attempt). This is an implementation-detail refinement of a diagram, not a section 2 decision — those are reserved for things like D24/D25 that change documented schema or semantics. Record the difference in the plan so T1.4 is built against the real signature, not the sketch.

2. Backspace after isDone(): confirmed, ignored — consistent with 9b. The block ends the instant the index reaches target length; a wrong last character stands as a permanent first-attempt error with no chance to correct it. This is a real, if slightly harsh, consequence worth stating plainly in the plan so it isn't a surprise later when reviewing real session data.

3. Invalid input: confirmed, throw. Matches the existing apiPath precedent (RangeError on malformed input) and the project's broader stance that a bug in the upstream filter should be loud, never silently absorbed as a false "error" row or a dropped keystroke — either of those would corrupt data without leaving a trace.

4. Scope of T1.3's checks: confirmed, the four per-keystroke fields across all rows, plus final index and isDone(), nothing session-level. Session-level stats (WPM, accuracy) stay exclusively T1.9's — this is the same "one source of truth" principle already applied to bigram attribution; duplicating it in TypeScript would create a second place that could quietly drift from the Python implementation.

5. Per-position display state: confirmed, out of scope for T1.3. TextCursor stays limited to alignment; what's currently shown on screen (for the red-highlight behavior in section 11.3) is T1.5's store to own.

6. Property testing: confirmed, no new dependency for now — example-based tests from the fixture plus hand-written synthetic sequences cover F7 adequately at this stage. One addition: note in the plan, as a flagged future consideration (not a task), that fast-check could be revisited once the cursor's invariants are well understood and stable — introducing property testing before the rules themselves are fully settled risks writing properties that encode an early misunderstanding rather than genuinely stress-testing the logic.

7. Field naming: confirmed, snake_case (target_index, expected_char, outcome, first_attempt), matching the fixture and database. This is consistent with T1.2's existing answer #3, which already established snake_case as the canonical name for anything crossing the TS/Python boundary — no translation layer, no second naming scheme to keep in sync.
