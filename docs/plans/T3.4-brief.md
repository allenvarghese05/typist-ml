# T3.4 brief — Calibrate d_min and d_max so all targeted arms can reach them

*Analyst brief. Facts only; no design or implementation.*

- **Title (verbatim, §16):** "Calibrate d_min and d_max so all targeted arms can reach them".
- **Acceptance criteria (verbatim, §16):** "Each targeted arm accepts 80% or more of drills within 5 attempts".

## 2. Why it matters

T3.4 is the calibration step that sets the permanent density window $[d_{min}, d_{max}]$ of the shared fairness gate (D16, §13.1) immediately before the configuration is permanently frozen in T3.5 ("Freeze `experiment_config`") and the analysis plan is committed in T3.6.

- **Ensures drill pool reliability and prevents job exhaustion (§13.7, §18).** During the 10-day RCT pilot, each participant completes 4 blocks per daily session (one block per arm). Each block requires 2 drills of ~300 characters (600 characters total per block). To prevent typing latency, the generation worker maintains a 3-day buffer (6 ready drills per arm per participant). When a generation job runs, `GenerationService` allows up to 5 attempts per drill. If all 5 attempts fail the validator, `GenerationService` raises `DrillGenerationExhaustedError`, marking the job as failed (`status='failed'`). If any targeted arm cannot achieve $\ge 80\%$ acceptance across 5 attempts, the background worker will suffer repeated job failures, starving the participant's drill pool and stalling the pilot.
- **Maintains the core experimental fairness gate (D16, §13.1).** Typist-ML tests whether the *method* of drill generation (heuristic dictionary selection, character Markov chain, or neural language model) affects typing skill acquisition. If one arm generated drills with 35% target bigram density while another generated drills with 8% density, any observed outcome difference could simply reflect total repetition volume rather than text composition method. The shared density range $[d_{min}, d_{max}]$ bounds target exposure so all targeted arms are comparable.
- **Accommodates natural empirical variation across arms and target sets (§3.4, §13.6).**
  - `HeuristicGenerator` uses a density governor targeting the midpoint $(d_{min} + d_{max}) / 2$, achieving ~0.25 density.
  - `LLMGenerator` (`Llama-3.2-1B-Instruct-4bit`) achieved empirical density $0.231 \pm 0.042$ in the T3.3 bake-off, with an 84.5% 5-attempt acceptance rate under the initial $[0.15, 0.40]$ window.
  - `MarkovGenerator` ($\beta = 10.0$) achieves ~0.175 density on common 4-target sets, but its density drops to ~0.10–0.14 on challenging bigram sets and on fallback 3-target sets (§3.4 step 4).
  - Under the uncalibrated $d_{min} = 0.15$, drills with density 0.10–0.14 are rejected with `RejectReason.DENSITY_LOW`, causing Markov acceptance to plummet to 65% on 3-target sets and lower on awkward combinations. Calibrating $d_{min}$ allows all targeted arms to reliably clear the 80% threshold across 5 attempts.

**What breaks if it is wrong:**
- If $d_{min}$ is set too high (e.g. left at 0.15): Markov and LLM will frequently trip `RejectReason.DENSITY_LOW` on fallback 3-target sets or low-frequency tracked pairs, dropping below 80% acceptance and causing background generation jobs to fail in production.
- If $d_{max}$ is set too low: high-density drills will trip `RejectReason.DENSITY_HIGH`.
- If the $[d_{min}, d_{max}]$ range is made too wide (e.g. $[0.01, 0.90]$): the fairness gate ceases to constrain the generators, allowing massive exposure disparities between arms and confounding the pilot.
- If `experiment_config` in SQLite and `DrillSpec` dataclass defaults in `services/api/src/typist/generation/base.py` fall out of sync: background generation via `GenerationService` (which reads SQLite) and direct unit tests or standalone generation (which use `DrillSpec` defaults) will evaluate drills against conflicting density boundaries.
- If calibration is not grounded in empirical measurements across all targeted arms: the frozen parameters in T3.5 will lack scientific justification in the pre-registered analysis plan.

## 3. Governing decisions (each D-number and what it forces here)

- **D01 (Experiment unit: Within-person):** Each participant's weak bigrams are partitioned into 4 matched sets, and each set is assigned to one arm. All arms are practiced by the same participant on the same days.
- **D02 (Control arm):** The control set receives no targeted drills (`spec.target_bigrams = ()`). Target density and coverage checks are skipped for `Arm.CONTROL` in `validator.validate()`. The calibration of $[d_{min}, d_{max}]$ applies specifically to the three targeted arms (`Arm.HEURISTIC`, `Arm.MARKOV`, `Arm.LLM`).
- **D03 (Arms: `control`, `heuristic`, `markov`, `llm`):** The three targeted arms are `heuristic`, `markov`, and `llm`. Each must accept $\ge 80\%$ of drills within 5 attempts under the calibrated density range.
- **D04 (Assignment: Snake split & freeze):** Top 16 weak bigrams (4 per set) or fallback 12 weak bigrams (3 per set) are dealt in snake order. Calibration must support both 4-target sets and 3-target fallback sets.
- **D06 (Deployment: Local-only on MacBook Pro M1 Pro):** Everything runs on one local machine.
- **D08 (Backend stack: Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite WAL):** Configuration values live in the `experiment_config` table; database updates require an Alembic migration.
- **D09 / D10 (Model runtime & model choice):** `Arm.LLM` is powered by `mlx-community/Llama-3.2-1B-Instruct-4bit` at commit `08231374eeacb049a0eade7922910865b8fce912`, as settled by ADR D29.
- **D11 (Batch generation via worker):** Drills are generated by `GenerationService` in background worker jobs using up to 5 attempts per drill (`DEFAULT_MAX_ATTEMPTS = 5`).
- **D13 (Text scope: Lowercase `a`–`z` and single space only):** Tracked bigrams are letter-letter only, drawn from the ~150 most frequent bigrams in English.
- **D16 (Fairness gate: All targeted arms pass one shared validator):** The validator enforces length $\in [270, 300]$, valid charset, target density $\in [d_{min}, d_{max}]$, coverage $\ge 3$ per target bigram, max word repeat $\le 3$, bigram run $< 3$, and real-word ratio $\ge 0.8$ for LLM. All targeted arms must share the identical $[d_{min}, d_{max}]$ bounds.
- **D17 (Word list: `wordfreq` English list, filtered to `a`–`z` words):** 20,000 words from `data/words.json`.
- **D19 (No cloud, no WASM):** Purely local execution; no external APIs.
- **D20 (Pre-registration / Freeze):** `d_min` and `d_max` are calibrated in M3 (T3.4) and frozen in T3.5 prior to the pilot.
- **D23 (Offline model snapshots):** Local cache only; CI runs on Linux x86_64 and must not attempt model downloads or live neural inference.
- **D29 (Model bake-off selection):** Pinned Llama-3.2-1B-Instruct-4bit with empirical density $0.231 \pm 0.042$.

## 5. Inputs and outputs

### Inputs
1. **Initial density bounds:** `d_min = 0.15` and `d_max = 0.40` seeded in `experiment_config` (migration `0001_initial_schema.py`) and default values on `DrillSpec` (`base.py`).
2. **Empirical density distributions and metrics across targeted arms:**
   - **`Arm.HEURISTIC`:** Governed by midpoint $(d_{min} + d_{max})/2$. Mean density $0.255 \pm 0.023$ (min 0.191, max 0.280), first-attempt acceptance 100%, 5-attempt acceptance 100%.
   - **`Arm.MARKOV`:** $\beta = 10.0$. On standard common 4-target sets: median density ~0.1754, 5-attempt acceptance 100%. On challenging tracked sets or fallback 3-target sets: mean density ~0.10–0.14, with attempts between 0.10 and 0.15 currently failing with `RejectReason.DENSITY_LOW`.
   - **`Arm.LLM` (`Llama-3.2-1B-Instruct-4bit`):** Empirical bake-off results (ADR D29): mean density $0.231 \pm 0.042$, first-attempt acceptance 61.5%, 5-attempt acceptance 84.5% under $[0.15, 0.40]$.
3. **Target Bigram Sets for Evaluation:**
   - Real experiment sets derived from snake-splitting the top 150 tracked bigrams (§3.4): 4-target sets and 3-target fallback sets.
   - Canonical 10 synthetic sets from bake-off (`SYNTHETIC_TARGET_SETS` from §13.6).
4. **Validator configuration:** `min_length_chars = 270`, `min_coverage = 3`, `max_word_repeats = 3`, `max_bigram_run = 3`, `min_real_word_ratio = 0.8` (for LLM).
5. **Vocabulary:** `WordIndex.words` (20,000 words from `data/words.json`).

## 6. Constraints

- **Acceptance threshold constraint (§16):** Each targeted arm (`heuristic`, `markov`, `llm`) must accept 80% or more of drills within 5 attempts.
- **Fairness gate constraint (D16, §13.1):** All targeted arms must pass the exact same shared validator with the exact same $[d_{min}, d_{max}]$ density range. Separate or per-arm density ranges are strictly disallowed.
- **Pre-freeze constraint (D20, GEMINI.md rule 34):** `d_min` and `d_max` are modified while still unfrozen (`frozen_at IS NULL`). T3.5 subsequently freezes them.
- **Offline / CI execution (D06, D19, D23, GEMINI.md):** Cloud sessions and CI run on Linux x86_64 without Apple Silicon or downloaded model weights. Automated test suites run by `just check` must pass without executing live MLX models (using `FakeLLMRuntime`, reference distributions, or skipping via `@pytest.mark.mlx`).
- **Deterministic derivation (§13.1, §13.5):** All retry attempts derive seeds deterministically via `derive_drill_seed(...)`.
- **Heuristic governor coupling:** `HeuristicGenerator` computes `midpoint = (spec.min_density + spec.max_density) / 2`. Adjusting `d_min` shifts this midpoint.

## 7. Edge cases

1. **Fallback 3-target sets (§3.4 step 4):**
   - *Example:* If fewer than 16 bigrams meet the baseline observation threshold (at least 20 observations), the experiment falls back to 12 weak bigrams (3 per set, e.g. `('th', 'he', 'in')`).
   - *Consequence:* A 3-target drill naturally contains ~3/4 of the target bigram occurrences of a 4-target drill. Under $d_{min} = 0.15$, Markov's median density on 3-target sets is ~0.135, causing 5-attempt acceptance to fall to 65%. If $d_{min}$ is calibrated to $\le 0.12$ (e.g. 0.10), Markov 3-target acceptance rises to 100%.
2. **Untracked awkward bigrams in bake-off sets vs tracked bigrams in actual experiment:**
   - *Example:* `SYNTHETIC_TARGET_SETS[8]` is `('kn', 'wr', 'qu', 'sw')`. None of these bigrams are in `index.tracked_bigrams` (~150 most common in English).
   - *Consequence:* Letters like `k`, `w`, `q` have low unigram frequencies in English. In `MarkovGenerator`, second letters are boosted only when preceded by their first letter, but first letters are not boosted. Consequently, `kn` or `wr` rarely appear even once in 300 characters, failing `RejectReason.COVERAGE` ($< 3$) and `RejectReason.DENSITY_LOW` ($< 0.02$). However, per §3.4 step 1, real participant weak bigrams are *strictly* sampled from the ~150 tracked bigrams, where unigram frequencies are sufficient.
3. **Bigram `of` inside words vs standalone word:**
   - *Example:* Tracked bigram `of` (tracked bigram #12 in English frequency).
   - *Consequence:* The bigram `of` appears almost exclusively as the standalone 2-letter word `"of"`. However, `MarkovGenerator` constrains pseudo-words to lengths 3–10 (`_MIN_WORD_LEN = 3`) and caps word repeat at 2 (`_MAX_USES_PER_DRILL = 2`). Thus, Markov struggles to generate `of` 3 times within 3–10 letter pseudo-words, failing coverage on sets containing `of`.
4. **Lower bound of $d_{min}$ constrained by `min_coverage = 3`:**
   - *Example:* A standard drill is ~300 characters, containing ~45 words and ~220 total letter-letter bigrams.
   - *Consequence:* For a 4-target set, achieving the minimum coverage of 3 per target requires at least $4 \times 3 = 12$ target bigram occurrences. $12 / 220 \approx 0.0545$ density (5.45%). Setting $d_{min}$ below 0.06 would mean a drill could satisfy density while failing coverage. A calibrated $d_{min}$ around 0.10 or 0.12 safely exceeds this mathematical coverage floor while allowing natural sampling variance.
5. **Upper bound $d_{max}$ behavior across arms:**
   - *Example:* Heuristic generator achieves maximum density ~0.28; Markov achieves maximum density ~0.25; LLM empirical bake-off mean was $0.231 \pm 0.042$ (maximum observed ~0.35).
   - *Consequence:* None of the targeted arms overshoot $d_{max} = 0.40$. Keeping $d_{max} = 0.40$ (or setting it to 0.35) prevents `RejectReason.DENSITY_HIGH` while bounding exposure.
6. **Interaction between $d_{min}$ and Heuristic governor:**
   - *Example:* If $d_{min}$ is calibrated from 0.15 to 0.10 while $d_{max} = 0.40$, the governor midpoint shifts from 0.275 to 0.250.
   - *Consequence:* `HeuristicGenerator` begins inserting filler words slightly earlier, gently reducing its average density from ~0.255 to ~0.245, which actually brings it closer to the LLM mean (0.231) and Markov mean (0.175), improving cross-arm comparability.

## 8. Risks

1. **Evaluation set selection risk:** If T3.4 evaluates acceptance rates solely on the 10 synthetic bake-off sets (which include non-tracked pairs like `kn`, `wr`, `qu`), `MarkovGenerator` will fail the 80% acceptance criterion because it cannot reach coverage on those specific untracked bigrams without algorithmic changes. The evaluation sets must be clearly aligned with what can actually be assigned during the pilot per §3.4.
2. **Cross-arm exposure disparity risk:** If $d_{min}$ is lowered excessively (e.g. to 0.05), Markov could accept drills with very low density (~0.06) while Heuristic produces drills with ~0.25 density. A 4x exposure difference would violate the intent of D16 ("The validator forces all targeted arms into the same range... so the write-up can show the arms were comparable").
3. **Database migration and code drift risk:** If Alembic migration `0011` updates SQLite `experiment_config`, but `DrillSpec` dataclass defaults in `base.py` or `EXPECTED_CONFIG` in `test_schema.py` are overlooked, unit tests running without a migrated database session will behave differently from services running with one.
4. **CI test environment limitation:** Automated CI cannot load `Llama-3.2-1B-Instruct-4bit` to verify LLM acceptance live. Tests validating that LLM accepts $\ge 80\%$ must use reference benchmark data (`REFERENCE_LLAMA_SUMMARY` from D29) or `FakeLLMRuntime`, while keeping live generation under `@pytest.mark.mlx`.
