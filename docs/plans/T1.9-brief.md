# T1.9 — Session completion: bigram_stats, WPM, accuracy — Analyst brief

> Analysis only. This brief records facts and open questions. It designs nothing and writes no
> code. The owner/architect decide the solution.

## 1. Task

- **Id:** T1.9 (milestone M1 "Telemetry and matrix", design doc section 16).
- **Title (verbatim):** "Session completion: bigram_stats, WPM, accuracy".
- **Acceptance criteria (verbatim):** "typist stats recompute reproduces the same numbers".

Milestone context (section 16, verbatim): "M1 Telemetry and matrix … A baseline session produces
a bigram matrix; overhead reported; **recompute gives identical stats**."

## 2. Why it matters

- T1.9 is the first task that turns raw `keystroke_events` rows into the derived, per-session facts
  the whole experiment is scored on: `sessions.wpm`, `sessions.accuracy`, and the `bigram_stats`
  rows (`attempts`, `errors`, `iki_median_ms`, `iki_n`) per `(session_id, bigram)`.
- It enables **T2.2** (`assignment.py`), which chooses each participant's weak bigrams from a
  smoothed error rate and a median-IKI z-score (section 3.4) computed from `bigram_stats`. Those
  are the sets dealt to arms and frozen (D01, D04) — if the numbers are wrong, the wrong bigrams
  are drilled for the whole pilot and every result is wrong.
- It enables **D05** outcomes (set error-rate change, set median-IKI change) and the analysis in
  section 3.5 / 15, all built on `bigram_stats`.
- The acceptance criterion is the project's anti-drift guarantee (section 6.2, CLAUDE.md): because
  raw rows are append-only, `typist stats recompute` must rebuild `bigram_stats` and the session
  stats to byte-identical values after any bug fix. If recompute is not deterministic/idempotent, a
  bug fix can silently change history.
- What breaks if wrong: weak-bigram selection (T2.2), drills (M2/M3), every reported number, and
  the golden-fixture cross-language contract between TextCursor (TS) and attribution (Python).

## 3. Governing decisions

- **D26** (`docs/decisions/D26-wpm-elapsed-time-and-idle-limit.md`, "recorded T1.2; built T1.5 and
  **T1.9**"): Session WPM = correct first-attempt characters / 5 / **elapsed** minutes. "Elapsed
  time runs continuously from the first keystroke's press (`t_down_ms` of the block's first row) to
  the press of the final character; for a block that never reaches the end, to the last row's
  press. Pauses and time away from the window (blur) are included, not removed." This **deviates
  from section 12.3's** "minutes of active typing (pauses removed)". Consequence (verbatim): "T1.9
  computes `sessions.wpm` this way. Attribution (T1.7) and `bigram_stats` are unchanged." Also:
  "No press-to-press gap inside a completed block can exceed 10 s, so a pause adds at most about
  10 s to a block's elapsed time."
- **D24 / D23(a)** (attribution amendments the fixture pins): a pair is paused when
  `b.after_pause` is true OR press-to-press gap > 2000 ms (strict; exactly 2000 ms is **not** a
  pause); paused and error pairs still count an attempt (and an error), only the IKI sample drops.
  T1.9 must pool across blocks without re-deciding any of this — it is already in `attribution.py`.
- **D13** (design doc section 2): tracked bigrams are letter-letter only (a–z), no space bigrams.
- **D23 analysis-plan** (`D23-analysis-plan-definitions.md`): rule (a) pauses excluded from IKI
  only, still counted for errors — already honoured by attribution; (b) abandoned sessions' rows
  are kept but excluded from **outcome analysis** (that exclusion is T4.1's, not T1.9's); T1.9 must
  still decide whether it computes stats for abandoned sessions/blocks.
- **D27** (`D27-iki-and-dwell-computed-in-browser.md`): `iki_ms`/`dwell_ms` are browser-computed and
  stored; `release_to_press_ms` is not stored. Attribution uses `t_down_ms`, not these, so T1.9's
  stats do not depend on them.
- **D15** (section 2): IKI = press-to-press, always positive; the measure T1.9 pools.
- **Section 6.2 / CLAUDE.md:** one source of truth (Python only); raw rows append-only; everything
  derived can be rebuilt by recompute. Randomness (none expected here) via a seeded generator.

## 5. Inputs and outputs

### Inputs
- `sessions` row (id, participant_id, phase, status) and its `session_blocks` (target_text,
  block_index, started_at/ended_at), from the DB.
- `keystroke_events` rows per block (append-only; may have null `t_up_ms`/`dwell_ms`).
- Attribution output per block via `attribute_block_samples` (counts + raw IKI samples).

### Outputs (where they live)
- `sessions.wpm` and `sessions.accuracy` (REAL, currently NULL) on the session row.
- `bigram_stats` rows: columns per design doc 8.1 — `id INTEGER PK`, `participant_id`,
  `session_id` (FK), `bigram` (2 lowercase letters), `attempts`, `errors` INTEGER,
  `iki_median_ms REAL`, `iki_n INTEGER`; `UNIQUE (session_id, bigram)`; index
  `(participant_id, bigram)` (section 8.2). **This table does not exist yet** (§9 Open Q 1).
- Session-level definitions (section 12.3, amended by D26):
  - **WPM** = correct first-attempt characters / 5 / elapsed minutes (D26 time base, §3).
  - **Accuracy** = correct first attempts / all first attempts (spaces included — fixture note).
- Surfaced by (design doc 14 / 14.1): `POST /sessions/{sid}/complete` → `SessionSummary`
  ("Compute stats, update phase, enqueue jobs") and the CLI `typist stats recompute [--pid]`
  ("Rebuild bigram_stats from raw keystrokes"). The acceptance criterion targets the CLI path.

### Golden-fixture expected values (verbatim, `expected_session`)
```json
{ "correct_first_attempts": 55, "first_attempts": 64,
  "accuracy": 0.859375, "typing_time_ms": 30000, "wpm": 22 }
```
Note (verbatim): "WPM = correct first-attempt characters / 5 / elapsed minutes (D26). Elapsed time
runs from the first row's t_down_ms to the t_down_ms of the final character; this block is
unfinished (case j), so the end is the last row's t_down_ms. Pauses and blur are included, not

attempts, spaces included." (55/5/0.5 min = 22.) The 19 `expected_bigram_stats` rows (e.g. `th`
attempts 5 / errors 2 / iki_median_ms 95 / iki_n 2; `ld` iki_median_ms 2000; `ol` attempts 1 /
iki_n 0) are the per-session targets for one block.

## 6. Constraints

- **Python-only attribution** (CLAUDE.md): the browser computes display stats only; `bigram_stats`
  and the authoritative WPM/accuracy are Python's.
- **Append-only raw data** (6.2): T1.9 must not mutate `keystroke_events` (except the existing
  `record_key_up` path, which is not T1.9's). Recompute rebuilds only derived rows.
- **Determinism / idempotency**: "recompute reproduces the same numbers" requires a stable merge
  (pool raw IKI samples, then one `statistics.median`; `attempts`/`errors` summed) and stable
  handling of `(session_id, bigram)` uniqueness on re-run.
- **Never edit the frozen golden fixture** to pass (CLAUDE.md) — flag mismatches in the PR.
- **Pooling rule (T1.7 owner answer 3, verbatim):** session-level merge is "sum attempts/errors,
  pool IKI samples before taking the median — **not** a median of medians". Pairs never cross a
  block boundary (attribution is per block; T1.9 aggregates the per-block `BigramSamples`).
- **Platform:** no mlx-lm involved; T1.9 is pure-Python and runs in CI on Linux.
- **Config, not literals** (17.1): any parameter (e.g. the 5 chars/word divisor, 2000 ms pause) is
  already in attribution/D26; T1.9 should not reintroduce literals.

## 7. Edge cases (concrete)

1. **WPM time base per D26 vs multi-block sessions.** The fixture and D26 define elapsed time for a
   single block (first row `t_down_ms` → final-character/last-row `t_down_ms`). A practice session
   has four blocks typed at different clock times (section 3.3). How "elapsed minutes" aggregates
   across blocks is not stated — sum of per-block elapsed, or session `started_at`→`ended_at`? (The
   golden fixture is single-block and cannot disambiguate.) See Open Q 2.
2. **Unfinished block (fixture case j).** The target text is longer than what was typed; elapsed
   ends at the last row's `t_down_ms`, not the final target character's press. T1.9 must detect
   "block never reached the end" the same way the fixture does (55 correct of 64 first attempts; 65
   target chars).
3. **Zero correct / zero first attempts.** An empty or all-backspace block gives WPM/accuracy with
   a 0 denominator (0 first attempts → accuracy undefined; 0 elapsed minutes → WPM undefined).
   Behaviour (0, null, skip) is unspecified. See Open Q 5.
4. **Pause/blur inside elapsed time.** A 2000-ms-plus gap or a blur still counts toward WPM elapsed
   time (D26), but the same pair contributes an attempt/error with **no** IKI sample (D24). The
   same keystroke affects WPM and bigram IKI differently.
5. **`ld` boundary (iki 2000) and `ol` gap 2500.** Exactly 2000 ms yields an IKI sample; 2500 ms
   yields an attempt with no sample. Already pinned in attribution — T1.9's pool must preserve this
   when merging, e.g. a bigram appearing in two blocks where one sample is exactly 2000.
6. **Even-count median after pooling.** `th` has samples [90,100] → 95; `ll` [160,170.5] → 165.25.
   When T1.9 pools samples across blocks the combined count parity can change, so the median must be
   taken over the **pooled** list, never per-block then averaged.
7. **Bigram present in one block, absent in another.** Pooling must union bigrams across blocks and
   sum only where present; zero-attempt bigrams are omitted entirely (attribution already omits).
8. **Space-adjacent and non-letter positions.** `the small …`: `e␣`, `␣s` are not tracked (D13).
   Accuracy still counts the space keystrokes as first attempts (fixture note "spaces included"),
   but no space bigram enters `bigram_stats`.
9. **Abandoned / in_progress sessions.** `sessions.status` can be `abandoned` or `in_progress`.
   Whether recompute writes stats for non-`completed` sessions, and whether it sets `status`/`wpm`
   at all, is unspecified for the CLI path. See Open Q 4, 6.
10. **Re-running recompute (idempotency).** `UNIQUE (session_id, bigram)` means a second run must
    upsert/replace, not duplicate; and a bigram that disappears (never will from unchanged raw rows,
    but could after a logic fix) must not leave a stale row. See Open Q 7.
11. **Null `t_up_ms`.** Fixture bigram `on` note: "b's key-up is missing; unaffected." WPM/IKI use
    `t_down_ms` only, so null key-ups never affect T1.9's numbers (good to confirm in a test).
12. **Multiple blocks → one `bigram_stats` per `(session_id, bigram)`.** Section 8.1 keys
    `bigram_stats` on session, not block, so per-block rows are merged into one row per bigram.

## 8. Risks

- **Writing to a table that does not exist yet.** `bigram_stats` is assigned to T2.1 in the design
  doc but T1.9 (which precedes T2.1) must populate it; mis-sequencing the migration blocks T1.9
  entirely (Open Q 1). High-likelihood blocker.
- **WPM aggregation across blocks** diverges from what the owner intends, making baseline vs retest
  WPM incomparable (D26 "Revisit if … the WPM time base makes baseline and retest incomparable").
- **Median-of-medians mistake.** Easy to accidentally reduce per block then merge, violating T1.7
  answer 3 and silently biasing IKI. The golden fixture is single-block so it will **not** catch
  this — a multi-block test is needed but no multi-block fixture exists.
- **Idempotency/recompute drift**: a non-deterministic merge order or a partial delete leaves stale
  `bigram_stats`, failing the one acceptance criterion.
- **Scope creep**: design doc ties `bigram_stats` population to both the API `/complete` endpoint
  and the `stats recompute` CLI; the acceptance criterion names only the CLI. Over-building the API
  (phase/`enqueue jobs`, SessionSummary) pulls in M2 concerns (Open Q 3).
- **No session/block lifecycle API exists yet** (T1.6 answers 8/9, T1.5): there is no way to create
  a completed multi-block session except in tests; T1.9 may need to build or stub that surface.

## 9. Open questions (answer by number)

1. **`bigram_stats` table ownership vs T1.9 ordering.** Section 16 lists `bigram_stats` under
   **T2.1** ("Tables: bigram_stats, bigram_assignment, drills, generation_jobs,
   generation_attempts"), and the T1.1 brief says T1.9 writes `bigram_stats` "(via T2.1)". But T1.9
   is an **M1** task (before T2.1) whose title is "Session completion: bigram_stats, WPM, accuracy"
   and whose acceptance is "recompute reproduces the same numbers" — impossible without the table.
   Does T1.9 create the `bigram_stats` table (its model + a new migration 0003) itself, leaving
   T2.1 to add only the four remaining M2 tables; or is the design doc's milestone split
   authoritative, so T1.9 must be reordered after/bundled with T2.1? The design doc does not
   reconcile this.
2. **WPM elapsed-time aggregation across a multi-block session.** D26 and the single-block golden
   fixture define elapsed time per block (first press → final/last press). For a four-block
   practice session (section 3.3) typed across the sitting, is session elapsed minutes the **sum of
   per-block elapsed times**, or `sessions.started_at`→`ended_at`, or correct-chars over summed
   per-block elapsed? And is correct-first-attempt-character count pooled across all blocks? The doc
   defines only the single-block case.
3. **Scope: CLI only, or CLI + API `/sessions/{sid}/complete`?** The acceptance criterion names only
   `typist stats recompute`. Section 14 also specifies `POST /sessions/{sid}/complete` ("Compute
   stats, update phase, **enqueue jobs**", returning `SessionSummary`). Phase transitions and job
   enqueue are M2 concerns (assignment, worker). Does T1.9 build the `/complete` endpoint and
   `SessionSummary` now (stats only, deferring phase-update/enqueue), or only the CLI recompute and
   the shared stats service, leaving the endpoint to M2?
4. **Which sessions does `recompute` process, and does it write `sessions.wpm`/`accuracy`?** The CLI
   row says only "Rebuild bigram_stats from raw keystrokes" — it does not mention WPM/accuracy. Does
   `typist stats recompute [--pid]` also recompute and overwrite `sessions.wpm`/`accuracy`, or only
   `bigram_stats`? (The task title bundles all three, but the CLI description names only
   bigram_stats.)
5. **Zero-denominator WPM/accuracy.** For a session/block with 0 first attempts (accuracy divide by
   zero) or 0 elapsed minutes (WPM divide by zero), what value is stored — `NULL`, `0`, or is the
   session skipped? The design doc and D26 do not say.
6. **Abandoned / in_progress sessions.** `sessions.status` includes `abandoned` and `in_progress`.
   D23(b) excludes abandoned sessions from **outcome analysis** (T4.1) but keeps their rows. Does
   T1.9's recompute still compute and store `bigram_stats`/WPM/accuracy for abandoned and
   in_progress sessions, or only for `completed` ones? Note `session_blocks` has **no status
   column** (D26 left abandoned-block persistence undesigned and T1.5 did not add it), so T1.9
   cannot currently tell an abandoned block from a completed one at the block level.
7. **Recompute idempotency semantics.** On re-run, must `bigram_stats` rows for a session be
   deleted-and-reinserted, upserted on `UNIQUE (session_id, bigram)`, or diffed? The acceptance
   criterion requires identical output, but the delete/replace strategy (and whether it is
   transactional per session) is unspecified.
8. **Does completion mark the session?** `sessions.status`/`ended_at` are still `in_progress`/NULL
   until "the session completes" (model docstring). Is setting `status = 'completed'` and
   `ended_at` part of T1.9 (the `/complete` endpoint path), or does T1.9 assume completion already
   happened and only compute derived stats? (Related to Open Q 3; the recompute CLI presumably does
   not re-close sessions.)

## Owner answers

2026-10-19 — answered by the orchestrator under the autonomous pipeline rule. Sources: (a) design
doc / D-numbers, (b) CLAUDE.md, (c) earlier briefs/plans/owner answers/ADRs, (d) existing code
patterns, (e) industry practice. Answer 1 moves one table from T2.1 to T1.9 and is flagged for the
owner in the PR.

1. **T1.9 creates `bigram_stats` (model + migration `0003_bigram_stats`); T2.1 keeps the other
   four tables.** Source: (a) T1.9's acceptance cannot be met without the table and M1's "Done
   when" needs a bigram matrix; the section 16 ordering is the inconsistency, not the dependency.
   Columns exactly per 8.1: `id INTEGER PK`, `participant_id TEXT FK`, `session_id TEXT FK`,
   `bigram TEXT`, `attempts INTEGER`, `errors INTEGER`, `iki_median_ms REAL NULL`, `iki_n INTEGER`;
   `UNIQUE (session_id, bigram)`; index `(participant_id, bigram)` (8.2); CHECK `attempts >= 0`,
   `errors >= 0`, `iki_n >= 0`, `length(bigram) = 2`. T2.1's brief must note the table already
   exists.

2. **Session WPM = pooled correct first-attempt characters / 5 / (sum of per-block elapsed
   minutes).** Source: (c) D26 defines elapsed per block (first row's `t_down_ms` to the
   `t_down_ms` of the final character, or the last row if unfinished) and the fixture note; time
   between blocks (intros, breaks) is not typing. Accuracy = pooled correct first attempts / pooled
   first attempts (spaces included). A block with no rows contributes 0 to every numerator and
   denominator. Session `bigram_stats` = per-block `attribute_block_samples` merged by summing
   `attempts`/`errors` and pooling raw IKI samples, then one `statistics.median` per bigram (T1.7
   answer 3); bigrams with zero pooled attempts are omitted.

3. **CLI + service + the `POST /sessions/{sid}/complete` endpoint, stats-only.** Source: (a) the
   task title is "Session completion" and section 14 names the endpoint; its "update phase" and
   "enqueue jobs" parts belong to M2 (assignment/worker) and are left as documented follow-ups in
   the router docstring. The endpoint: 404 unknown session; 409 if `status != "in_progress"`
   (section 14 "Invalid state transitions … return 409"); otherwise computes stats, sets
   `status="completed"`, `ended_at`, `wpm`, `accuracy`, writes `bigram_stats`, returns
   `SessionSummary {session_id, wpm, accuracy, bigram_count, blocks}`. Table models are never
   returned (17.1).

4. **`recompute` rewrites both `bigram_stats` and `sessions.wpm`/`accuracy`.** Source: (a) the
   acceptance says "reproduces the same numbers" and the task names all three outputs; 6.2
   "Everything else is derived and can be rebuilt." It never touches `status`/`ended_at`.

5. **NULL.** Source: (d) both columns are nullable and the docstring says they "stay NULL" until
   known; (a) 12.6's checks are where anomalies surface. `wpm = None` when elapsed ≤ 0 or no
   correct first attempts can be timed; `accuracy = None` when there are 0 first attempts. No
   zeros, no exceptions.

6. **Only `status == "completed"` sessions.** Source: (d) model docstring; (a) 6.2. `recompute`
   reports counts of recomputed and skipped sessions. Abandoned-attempt rows sharing a `block_id`
   remain the deferred attempt-identity requirement (T1.5 answer 4/5); T1.9 computes over all rows
   of the block as stored.

7. **Per session, one transaction: delete that session's `bigram_stats`, insert fresh, update
   `wpm`/`accuracy`; commit.** Source: (e) delete-and-reinsert of a derived table is the simplest
   provably idempotent rebuild and the computation is deterministic. Test: complete a seeded
   session via the service, snapshot (`bigram_stats` rows sorted, `wpm`, `accuracy`), run
   `recompute` twice, assert all three snapshots are identical and equal the golden fixture's
   `expected_session` and `expected_bigram_stats`. Add a two-block test (split the fixture rows
   across two blocks of the same session with the same target halves is not possible; instead
   seed a second block with a small hand-built row set) proving pooled-median ≠ median-of-medians
   and that elapsed sums per block.

8. **The endpoint marks completion; `recompute` never does.** Source: (a) section 14. `ended_at`
   is set from an injectable `now` (default `datetime.now(UTC)`) so tests are deterministic.
   Block `started_at`/`ended_at` are not touched (block endpoints are a later task).
