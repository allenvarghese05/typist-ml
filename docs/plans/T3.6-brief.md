## 2. Why it matters

- **Prerequisite for starting practice sessions (D20, §16):** Milestone M3 is complete when *"All four arms produce valid drills; config and analysis plan frozen"*. Practice sessions cannot begin until the dated analysis plan is committed before the first practice session (Acceptance criteria, D20).
- **Prevents outcome-shopping (D20):** Pre-registering experimental hypotheses, primary difference-in-differences outcomes, secondary metrics, exclusion rules, prior distributions, and sampling parameters prevents post-hoc metric selection or statistical manipulation after viewing participant data.
- **Contract for Milestone M4 (Analysis and Dashboard):** Task T3.6 locks the exact mathematical and methodological contract that T4.1 (`analysis.py`), T4.2 (dashboard pages), T4.3 (results notebook and README figures), T4.4 (README write-up), and T4.5 (debrief page) must implement.
- **Honesty rule compliance (§1, D19):** *"No WASM claim, no improvement claim until real numbers exist, results are reported as descriptive per-participant changes, and if the heuristic or the control does as well as the LLM, that is the finding."*
- **What breaks if it is wrong:**
  - If analysis definitions deviate from telemetry attribution (D14), pause handling (D23), WPM elapsed time (D26), or candidate threshold (D28), M4 analysis scripts will calculate incorrect or mismatched metrics.
  - If the pre-registration date recorded in the document does not match the git commit date or is created after practice commences, the pre-registration timestamp guarantee is invalidated.
  - If tests in `test_analysis_plan_doc.py` or links in `README.md` are not updated consistently with the new status line and dates, CI will fail.

## 7. Edge cases

1. **Commit date vs in-file date discrepancy:**
   - *Example:* The analysis plan records `Date: 2026-10-30`, but if committed across midnight UTC or in a different timezone, `git log` might show a differing calendar date.
   - *Impact:* D20 and T0.6 owner answer 4 require that the in-file date and git commit date match.
2. **Idle-abandoned blocks (D26) vs session exclusions (D23):**
   - *Example:* In a baseline session, a participant pauses for 12 seconds during Block 2. Under D26, Block 2 is abandoned after 10 seconds of inactivity and restarted. The abandoned block's keystrokes are recorded in `keystroke_events`.
   - *Question:* Does the outcome analysis exclude keystroke rows from the abandoned block attempts and include only the completed restart block, or are all keystrokes pooled?
3. **Session re-run after abandonment in baseline or retest:**
   - *Example:* A participant completes Part 1 of Form A, but abandons Part 2 due to interruption.
   - *Question:* Does the participant re-run Part 2 only, or re-run the entire baseline from Part 1? When completed, do the most recent 2 completed baseline sessions count, while the abandoned session is logged as an exclusion?
4. **Three-day baseline expiration (§3.2):**
   - *Example:* A participant completes baseline sessions on Day 0 and Day 1, but cannot start practice until Day 6 (> 3 days).
   - *Question:* Section 3.2 requires baseline to be redone. The participant completes two new baseline sessions. The analysis plan must specify that only the two most recent completed baseline sessions immediately preceding practice are used for baseline outcome analysis and assignment.
5. **Retest bigram dropping (< 20 retest attempts, D23):**
   - *Example:* Tracked bigram `qu` has 42 baseline attempts, but due to attribution filtering in retest, only achieves 18 attempts in Form B.
   - *Impact:* Under D23(c), `qu` is dropped from its set in both baseline and retest for the primary and secondary comparisons, and explicitly reported in the write-up exclusions table.
6. **Posterior sampling reproducibility:**
   - *Example:* Evaluating targeting effect $E(s) = d(s) - d(\text{control})$ by drawing from four Beta posteriors. If the sampling count and random seed are not pre-registered, two independent evaluations in T4.1 or notebooks could yield differing median effect values or differing shares below zero.
7. **IKI targeting effect uncertainty method:**
   - *Example:* For the key secondary outcome $F(s) = c(s) - c(\text{control})$, median IKI differences do not have an analytical Beta posterior conjugate.
   - *Question:* How is uncertainty quantified without an analytical conjugate? (e.g. non-parametric bootstrap over keystroke IKI samples).
8. **Candidate qualification under fallback:**
   - *Example:* A participant only has 14 qualifying bigrams with $\ge 15$ baseline observations. 14 is $\ge 12$ (the fallback threshold $3 \times 4$), so 12 bigrams are assigned (3 per set) and logged.
   - *Impact:* Outcomes pool over 3 bigrams per set instead of 4; the analysis plan definitions apply unchanged as pooled sums.

## 8. Risks

1. **Pre-registration date mismatch with Git commit:**
   If the date string placed in `docs/analysis-plan.md` does not match the actual date of the Git commit, the pre-registration requirement of D20 is formally violated.
2. **Breaking heading structure validated by `test_analysis_plan_doc.py`:**
   `test_analysis_plan_doc.py` tests for exact heading lines in `SECTION_15_1_HEADINGS` and `EXTRA_HEADINGS` (including `### Values to Be Fixed in T3.6`). Renaming or removing headings without synchronizing the test assertions will fail CI.
3. **Ambiguity in statistical definitions for T4.1:**
   If posterior draw count, random seed, or the IKI uncertainty method are left vague or unspecified, the builder of T4.1 (`analysis.py`) will have to make unguided methodological choices mid-pilot.
4. **Discrepancy with `experiment_config`:**
   Listing parameter values in `docs/analysis-plan.md` that do not match the values frozen in migration 0012 will create an immediate contradiction between the database enforcement and the pre-registration text.

   - *Answer:* 100,000 Monte Carlo draws per Beta posterior, generated with pseudo-random seed `20261030` passed in by the caller.
   - *Source:* Design doc §3.5, CLAUDE.md / GEMINI.md ("Randomness always comes from a seeded generator passed in by the caller").

6. **Key Secondary Outcome (IKI) Uncertainty Method:**
   - *Answer:* Empirical non-parametric bootstrap 95% confidence interval (equal-tailed 2.5th to 97.5th percentiles of difference-in-differences $F(s)$ over 10,000 bootstrap resamples of bigram IKI samples within set and phase), using seeded generator `20261030`. In addition, report sample counts ($n$) and interquartile range (IQR, 25th–75th percentiles) for each set and phase.
   - *Source:* Design doc §3.5, standard non-parametric statistical practice.
   - *Reasoning:* Provides a distribution-free, robust uncertainty estimate for differences of sample medians on skewed keystroke timing distributions without assuming normality.

7. **Session and Block Re-run Policy:**
   - *Answer:*
     - (a) Abandoned baseline or retest sessions are excluded from outcome analysis; the participant re-runs the session so that 2 completed sessions exist per phase. The 2 most recent completed sessions immediately preceding the phase transition (or practice) count for outcome analysis, and all abandoned sessions are documented in the exclusions table.
     - (b) Under D26, keystrokes from blocks abandoned due to the 10-second idle limit are excluded from outcome analysis; only keystrokes from completed blocks count toward session and outcome statistics.
   - *Source:* Design doc §9.3 ("Abandoned practice sessions do not count toward N, and their keystrokes are kept but excluded from outcome analysis. The same rule applies to baseline and retest sessions"), D23, D26.
   - *Reasoning:* Guarantees that only valid, complete, uninterrupted blocks and sessions contribute to primary and secondary outcomes while retaining all raw telemetry for auditing.

   - *Answer:* Keep the markdown heading `### Values to Be Fixed in T3.6` verbatim in `docs/analysis-plan.md`, and under it present the resolved pre-registration parameter table and specifications.
