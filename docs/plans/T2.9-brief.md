## 2. Why it matters

T2.9 provides the operational command centre for the entire Typist-ML pilot study:

- **Enables the builder to run the 14-calendar-day pilot workflow (§16 Pilot runbook):**
  - **Day 0 and 1:** Both participants do the two baseline sessions. Run `typist check` each evening.
  - **End of Day 1:** Run `assign` for each participant; confirm the pool has 3 days of ready drills per arm.
  - **Days 2 to 11:** One practice session per day each. Watch the admin page for failed jobs.
  - **Day 12 and 13:** Retest sessions, then debrief.
  Without T2.9, the builder must execute manual terminal CLI commands, SQL queries, or raw HTTP curl requests to enroll participants, trigger assignment, monitor drill pool buffers, watch generation jobs, and verify telemetry integrity across the entire two-week study.
- **Directly satisfies the acceptance criterion:** Starting the local environment with `just dev` (which launches Vite on `127.0.0.1:5173`, FastAPI on `127.0.0.1:8000`, and `typist worker` in the background) must be the *only* terminal interaction needed. Every subsequent pilot action—participant creation, baseline-to-assignment triggering, drill pool replenishment, worker job monitoring, data quality auditing, and viewing daily session trends—is operated through the web UI at `http://localhost:5173/#/admin`.
- **Integrates backend admin APIs (§14) with frontend admin feature components (§7, §11.3):**
  - **Backend endpoints (§14):**
    - `POST /api/v1/admin/participants/{pid}/assign` (Implemented in T2.8)
    - `GET /api/v1/admin/pool`: Ready drills per participant and arm (`Pool`)
    - `GET /api/v1/admin/jobs`: List jobs (`Jobs`)
    - `POST /api/v1/admin/jobs`: Enqueue manually (`Jobs`)
    - `GET /api/v1/admin/checks/{pid}`: Data-quality report (`Checks`)
  - **Frontend components (§7, §11.3):**
    - `apps/web/src/features/admin/`: `AdminPage`, `JobsTable`, `DataChecks`
  - **CLI command parity (§14.1, Owner decision 2026-10-21 #5):**
    - `typist check --pid`: Daily data-quality report + session trend table.
- **Enforces daily data quality guarantees (§12.6):**
  Daily checks detect anomalies before they corrupt subsequent experiment days:
  - sequence gaps in block event streams,
  - stuck keys (dwell > 1000 ms) or negative dwell,
  - truncated blocks (fewer events than target characters),
  - dropped keyup events (missing keyup share),
  - orphaned sessions left in `in_progress` status.
- **Provides daily visibility into pilot trends (Owner decision 2026-10-21 #5):**
  Pulls forward a minimal trend table showing per-session WPM, accuracy, and per-set error rates on practice text alongside the data-quality checks, without altering frozen experiment semantics.

What breaks if it is wrong:
- **Acceptance criteria failure:** If the builder still has to use the terminal for routine pilot operations (e.g. running assignment, checking job status, inspecting drill counts, running daily checks), the acceptance criterion is directly violated.
- **Silent data corruption:** If data-quality checks miss sequence gaps, negative dwells, or dropped events, corrupt telemetry enters derived statistics (`bigram_stats`) and biases the final pilot outcomes.
- **Session blockage from pool starvation:** If failed generation jobs are invisible or cannot be manually enqueued/retried from the UI, the drill pool can be exhausted, triggering `DrillPoolExhaustedError` (HTTP 409) during daily practice typing.
- **Blinding leakage:** If the admin UI leaks arm assignments to blinded participants or exposes internal arm keys during typing flows, D18 blinding is broken.

## 3. Governing decisions

- **D01 (Experiment unit — within-person):** Each participant has their own weak bigrams and arm mapping, transitioning independently through the lifecycle. Admin page displays participant-level status, pools, and checks independently.
- **D03 (Arms — control, heuristic, markov, llm):** Drill pools and jobs operate over `DRILL_ARMS` (`"control"`, `"heuristic"`, `"markov"`, `"llm"`).
- **D04 (Assignment freeze before practice):** "Rank weak bigrams, deal into sets in snake order, map sets to arms with a seeded shuffle, freeze before practice. Balances weakness across sets and removes builder choice. Never mid-pilot." Admin page triggers assignment only when participant is in `baseline` status with completed baseline sessions.
- **D06 (Deployment — local-only on MacBook Pro):** Single-machine deployment. No cloud databases, auth services, or external logins. Admin page lives at `http://localhost:5173/#/admin`.
- **D07 (Frontend stack):** Vite 8, React 19, TypeScript (strict), pnpm, Biome, Vitest, Tailwind CSS.
- **D08 (Backend stack):** Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite in WAL mode, Typer CLI, ruff, pyright, pytest.
- **D11 (Generation timing — batch via worker):** "Batch, via a separate worker process. Keep 3 days of ready drills per arm" (§13.7: 2 drills per block $\times$ 3 days = 6 ready drills per arm). Admin page monitors ready drill pool and job queues.
- **D14 (Error definition):** First-attempt substitution at position j, counted only when position j-1 was correct on first attempt. Backspace allowed.
- **D15 (Timing definitions):** Event timestamps from `event.timeStamp`. `IKI = t_down(i) - t_down(i-1)`. `Dwell = t_up - t_down`. Dwell is stored even when odd; negative dwell is an anomaly.
- **D16 (Fairness gate):** All targeted arms pass one shared validator: length, charset, density range, per-bigram coverage, repetition limits.
- **D18 (Blinding):** The builder is flagged as unblinded (`is_builder = True`, `is_blinded = False`, database check `is_builder = 0 OR is_blinded = 0`). Admin page is explicitly the builder's tool (§11.2, §11.3).
- **D19 (No cloud, no WASM):** Local execution only. OpenAPI schema served at `/api/v1/openapi.json`.
- **D21 (`just check`):** Must pass lint, format-check, types, test, and build across both `apps/web` and `services/api`.
- **D24 (`keystroke_events.after_pause`):** Keystroke events track blur/focus pause transitions.
- **D26 (WPM elapsed-time base):** Elapsed time based on per-block keypress spans.
- **Owner decision (2026-10-21 #1):** "Participants. Only the owner (builder) for the pilot, on the owner's Mac. The owner's participant row is `is_builder = true`, `is_blinded = false`. Second-participant features (blinding, separate reporting) stay in the code but are not exercised."
- **Owner decision (2026-10-21 #5 — verbatim):** "Daily visibility. The owner wants to see progress every day. Pull a minimal "Trend" view forward into M2: `typist check --pid` prints per-session WPM, accuracy and per-set error rate on practice text alongside the data-quality checks, and the admin page (T2.9) shows the same table. This adds no experiment semantics; the primary outcome is still baseline vs retest and nothing frozen may change mid-pilot."
- **§11.3 Screens specification (verbatim):**
  - Route: `/admin`
  - Screen: `Admin`
  - Purpose: `Builder tools`
  - Key elements: `Participants and phases, drill pool per arm, job queue, data checks`
- **§12.6 Daily data checks (typist check) (verbatim):**
  - Gaps in seq within a block.
  - Negative dwell, or dwell over 1000 ms (stuck key).
  - Blocks with fewer events than characters in the target text.
  - Share of keyups missing.
  - Sessions left in_progress.
- **§14 API specification (verbatim):**
  - `POST /admin/participants/{pid}/assign`: Rank, split, map and freeze (only in baseline-done state) -> Assignment
  - `GET /admin/pool`: Ready drills per participant and arm -> Pool
  - `GET / POST /admin/jobs`: List jobs or enqueue manually -> Jobs
  - `GET /admin/checks/{pid}`: Data-quality report -> Checks
- **§14.1 CLI specification (verbatim):**
  - `typist check --pid`: Daily data-quality report
- **§17.1 Engineering standards:**
  - TypeScript strict: true, no any without a comment explaining why.
  - Python type hints everywhere, pyright in strict mode for `src/`.
  - Routers are thin. Business logic lives in services. Table models are never returned from the API; use response schemas.
  - Every experiment parameter lives in config.

## 5. Inputs and outputs

### 5.1 Inputs

- **HTTP Requests:**
  - `GET /api/v1/admin/pool`:
    Query parameter: `participant_id: str | None = None`.
  - `POST /api/v1/admin/pool/replenish`:
    Query parameter or body: `participant_id: str`. Triggers `replenish_drill_pool`.
  - `GET /api/v1/admin/jobs`:
    Query parameters: `participant_id: str | None = None`, `status: str | None = None`, `limit: int = 50`.
  - `POST /api/v1/admin/jobs`:
    JSON Body: `participant_id: str`, `arm: str`, `requested: int = 1`.
  - `GET /api/v1/admin/checks/{pid}`:
    Path parameter: `pid: str`.
  - Existing endpoints utilized:
    `GET /api/v1/participants`, `POST /api/v1/participants`, `POST /api/v1/admin/participants/{pid}/assign`.
- **CLI Commands:**
  - `typist check --pid <PID>` (or `typist check` across participants).
- **Database Tables Read:**
  - `participants`: `id`, `alias`, `status`, `is_builder`, `is_blinded`, `created_at`, `consent_at`.
  - `drills`: `participant_id`, `arm`, `status`.
  - `generation_jobs`: `id`, `participant_id`, `arm`, `requested`, `status`, `retries`, `error`, `created_at`, `started_at`, `finished_at`.
  - `sessions`: `id`, `participant_id`, `phase`, `day_index`, `status`, `wpm`, `accuracy`, `started_at`, `ended_at`.
  - `session_blocks`: `id`, `session_id`, `block_index`, `target_text`, `started_at`, `ended_at`.
  - `keystroke_events`: `block_id`, `seq`, `t_down_ms`, `t_up_ms`, `dwell_ms`, `outcome`, `first_attempt`.
  - `bigram_stats`: `session_id`, `participant_id`, `bigram`, `attempts`, `errors`.
  - `bigram_assignment`: `participant_id`, `set_label`, `arm`, `bigram`.
  - `experiment_config`: `pool_target_days`, `block_chars`, `drill_length_chars`, `arms_enabled`.

## 6. Constraints

- **Platform compatibility:** Linux CI and macOS. Web app runs in modern browsers; services/api in Python 3.12. No imports of `mlx-lm` in router or service logic.
- **Tooling and Quality Gates:** Must pass `just check` (Biome lint, Biome format, tsc strict, vitest, ruff, pyright strict, pytest, vite build).
- **Architecture and Standards (§17.1):**
  - Routers are thin; logic in `services/checks.py` (or `data_checks.py`), `services/session_planner.py`, etc.
  - Table models are never returned directly from FastAPI; schemas in `schemas/admin.py`.
  - Frontend components adhere to strict TypeScript (`readonly` props, no `any` without comment).
- **Acceptance criteria constraint:** "Builder can run the pilot without the terminal except just dev". The UI must be self-contained for pilot operations.
- **Blinding (D18):** UI displays builder status accurately; builder data is flagged unblinded (`is_builder = True`).
- **No changes to frozen keys mid-pilot (CLAUDE.md / D20):** Read-only checks; no mutation of frozen assignments or historical events.

## 7. Edge cases

1. **Participant has 0 sessions (brand new or enrolled):**
   - *Example:* Participant `p-new` was just created. `GET /admin/checks/p-new` is called.
   - *Behaviour:* Quality checks should pass (0 events, 0 gaps, 0 short blocks, 0 missing keyups, 0 in_progress sessions), trend table is empty (`trend = []`), returns 200 OK.
2. **Block has 0 keystroke events (abandoned or unstarted block):**
   - *Example:* Session started, block created, but window was closed immediately before typing any character (`len(events) == 0`). Target text is 300 chars.
   - *Behaviour:* If block or session is marked completed, `short_blocks` check flags it (0 events < 300 chars). If session is in_progress, `in_progress_sessions` flags the session.
3. **Session left in_progress for days:**
   - *Example:* Participant started a session 3 days ago and walked away. Session has `status = "in_progress"`.
   - *Behaviour:* `in_progress_sessions` check fails (`passed = False`), returning the stale session id in the report.
4. **Rollover typing creating negative release-to-press vs negative dwell:**
   - *Example:* Fast typist presses next key before releasing previous (`release_to_press_ms < 0`).
   - *Behaviour:* Negative release-to-press is expected and valid under rollover (D15). But `dwell_ms < 0` (key up before key down on the SAME physical key) is physically impossible and MUST be flagged by `dwell_anomalies`.
5. **Key held down across window blur or pause (dwell > 1000ms):**
   - *Example:* Typist holds down spacebar while thinking or window loses focus while key is depressed, resulting in `dwell_ms = 1850.0`.
   - *Behaviour:* `dwell_anomalies` flags this keystroke (`over_1000ms_count >= 1`), check fails.
6. **Seq gaps due to dropped upload batches:**
   - *Example:* Block has events with seq `[0, 1, 2, 5, 6, 7]`. Batch with seq 3 and 4 failed network transmission.
   - *Behaviour:* `seq_gaps` flags the block (`passed = False`, `count = 1`, detail notes gap between 2 and 5).
7. **Participant before assignment vs after assignment for trend table:**
   - *Example:* Participant completed 2 baseline sessions. `GET /admin/checks/{pid}` is called.
   - *Behaviour:* Baseline sessions have WPM and accuracy, but `bigram_assignment` rows do not exist yet. `per_set_error_rate` for sets A, B, C, D is empty or null for baseline sessions. Once assigned, subsequent practice sessions display per-set error rates for sets A, B, C, D.
8. **Manual job enqueue for unassigned participant:**
   - *Example:* Builder tries to enqueue a job for arm `heuristic` for participant `p-enrolled` who has not been assigned.
   - *Behaviour:* `POST /admin/jobs` returns 409 Conflict: participant has no frozen bigram assignment. (Heuristic generation requires target bigrams).
9. **Manual job enqueue for control arm:**
   - *Example:* Builder enqueues 2 drills for `control` arm for participant `p-enrolled`.
   - *Behaviour:* Control arm requires no target bigrams. Does it allow enqueueing for any participant, or require assignment?
10. **Generation job failed with error:**
    - *Example:* LLM generator fails due to token length or validator rejection after 5 retries. Job status becomes `failed` and `error = "exceeded max attempts without valid drill"`.
    - *Behaviour:* `GET /admin/jobs` lists the failed job with its error message; UI displays the error in red and allows builder to re-enqueue.
11. **Drill pool deficit with running jobs:**
    - *Example:* Target is 6 drills. Ready = 2. A job is currently running for 4 drills.
    - *Behaviour:* `queued = 4`. Deficit is `6 - (2 + 4) = 0`. Status is `generating` or `pending`, avoiding duplicate enqueuing.
12. **Participant deleted while admin page is open:**
    - *Example:* Builder deletes participant via CLI or UI in another tab, then clicks "Replenish" on `/admin`.
    - *Behaviour:* API returns 404 Not Found; UI gracefully clears selection or displays not-found alert.
13. **Missing keyups on blur at the end of block:**
    - *Example:* The final character of a block is typed and the session finishes immediately, before `keyup` fires or is captured.
    - *Behaviour:* 1 missing keyup in 300 events is 0.33% missing share. `missing_keyups` threshold (e.g. share > 5% or > 10%) should distinguish normal boundary keyup loss from systemic pairing failures.

## 8. Risks

1. **Scope explosion on the frontend:**
   Acceptance criteria requires that builder can run the pilot without the terminal. If the admin UI tries to build a complex state management framework or multi-page dashboard before M4, it can become bloated and brittle. It needs to be cleanly modularized into `AdminPage`, `JobsTable`, `DataChecks` as outlined in §7.
2. **Missing keyup threshold calibration:**
   If `missing_keyups` check fails on a single trailing keyup at the end of a block, it will fail on every normal session and cry wolf. The check must allow a reasonable tolerance (e.g. threshold > 5% or > 10% missing share).
3. **Session trend computation performance:**
   If a participant has completed 10 practice sessions and 2 baseline sessions (each with multiple blocks and hundreds of bigrams), computing bigram stats and per-set error rates on the fly could be slow if unindexed queries are run. Fortunately, `bigram_stats` already has the computed attempts and errors per session, so joining `bigram_stats` with `bigram_assignment` is fast.
4. **Worker concurrency / heartbeat visibility:**
   The admin page monitors the drill pool and job queue. If the worker (`typist worker`) is not running, jobs will sit in `pending` indefinitely. The admin page should display worker status / heartbeat age (from `/api/v1/health`) so the builder knows immediately if the worker stopped.
5. **Navigability between admin view and typing sessions:**
   Currently `useHashRoute.ts` only knows `demo` and `matrix`. If navigation between `#/admin`, `#/session/:id`, `#/matrix/:id`, and `#/` is not clear, the builder might get stranded on `/admin` without a way to start or test a session.

## Owner answers

*Recorded on 2026-10-27 by Orchestrator per pipeline rules.*

### Answer 1: Pool replenishment trigger
- **Decision:** Support both (a) dedicated `POST /api/v1/admin/pool/replenish` (request body `{"participant_id": str}`) and (b) `POST /api/v1/admin/jobs` with optional `arm: str | None` and `drills_needed: int | None`. In `POST /api/v1/admin/pool/replenish`, the backend delegates directly to `GenerationService.replenish_drill_pool(participant_id, target_ready_per_arm=6)`. The Admin UI provides a prominent "Replenish Pool" button that calls `POST /admin/pool/replenish`, as well as a per-arm "Enqueue Drills" modal/button calling `POST /admin/jobs`.
- **Authority / Source:** (a) Design doc §13.7, §14, §16, and (d) existing `GenerationService.replenish_drill_pool` implementation in `services/api/src/typist/services/generation.py`.
- **Reasoning:** The pilot runbook specifically mandates "confirm the pool has 3 days of drills per arm" (6 drills), and `GenerationService` already has `replenish_drill_pool` built for this exact purpose. Having the endpoint directly call `replenish_drill_pool` allows a single button click in the UI to bring all arms up to target without terminal intervention.

### Answer 2: Missing keyup threshold
- **Decision:** (c) Report exact missing keyup count and percentage in the check item, marking the check as failed only if `missing_share > 0.05` (5%).
- **Authority / Source:** (a) Design doc §12.6 ("Share of keyups missing") and (e) web typing telemetry standard practice.
- **Reasoning:** A single block typically contains 200–350 keystrokes, so 1 trailing uncaptured keyup represents ~0.3–0.5% missing share; a 5% threshold comfortably tolerates natural blur/transition edge cases while catching true failure modes like browser keyup listener drops.

### Answer 3: CLI `typist check` without `--pid`
- **Decision:** (a) When `--pid` is omitted, `typist check` runs checks and reports trends across all active participants in the database (or prompts to specify `--pid` if no participants exist). When `--pid` is supplied, it runs for that specific participant.
- **Authority / Source:** (d) Existing CLI pattern in `typist stats recompute [--pid]` and `typist analyze [--pid]` in `services/api/src/typist/cli.py`.
- **Reasoning:** CLI parity with other commands that accept an optional `--pid` allows the builder to inspect all participants at once or a single participant specifically.

### Answer 4: Drill pool status response format
- **Decision:** (a) `GET /api/v1/admin/pool` accepts an optional `participant_id: str | None` query parameter. If provided, it returns pool status for that participant; if omitted, it returns pool status for all active participants.
- **Authority / Source:** (a) Design doc §14 (`GET /admin/pool: Ready drills per participant and arm -> Pool`).
- **Reasoning:** This is standard REST query-parameter filtering and lets the Admin page render either an overview table of all participants or focus on the currently selected participant.

### Answer 5: Worker heartbeat integration on `/admin`
- **Decision:** Yes. The Admin page fetches `/api/v1/health` and displays the worker status and heartbeat age (e.g., "Worker Active (heartbeat 4s ago)" with a green badge, or "Worker Inactive" with a warning badge) at the top of the Admin dashboard.
- **Authority / Source:** (a) Design doc §11.3, §14 (`GET /health`), and acceptance criteria ("Builder can run the pilot without the terminal").
- **Reasoning:** If the background worker terminates or was not started with `just dev`, the builder must know immediately why jobs are pending rather than assuming generation is frozen.

### Answer 6: Navigation / hash routes in `apps/web`
- **Decision:** Extend `useHashRoute.ts` to recognize `#/admin` (and optionally sub-views `#/admin?participant=<pid>`). Add top-bar navigation links in `App.tsx` / header allowing the user to switch between Typing, Bigram Matrix, and Admin pages cleanly.
- **Authority / Source:** (a) Design doc §11.3 ("11.3 Screens: Admin /admin Builder tools").
- **Reasoning:** Clear top navigation makes the Admin dashboard instantly accessible from any page without manually editing the browser URL bar.
