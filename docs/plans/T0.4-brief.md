## 2. Why it matters

What T0.4 enables later:
- It turns on the required status checks that `main`'s ruleset already demands (`web`, `api`).
  Since T0.1, every PR has been merged by the owner as admin because those checks never report
  (T0.1 owner answer 14: "the owner merges PRs T0.1 through T0.3 as the repo admin ... until T0.4
  adds the actual CI jobs; then the ruleset enforces normally from there on").
- Every later PR (T0.5 onward) merges only when `web` and `api` pass. Section 17.3 and CLAUDE.md
  make "CI green" the merge condition.
- It is one of the three M0 done-when items ("CI green").
- D21 was written so that "passing locally predicts passing in CI"; T0.4 is the first time that
  claim is tested on Linux.
- T2.10's acceptance ("Full flow passes in CI") builds on whatever CI T0.4 creates.
- T0.2 owner answer 20 and `IMPROVEMENTS.md` ("T0.4: add CodeQL `python`, and the CI `api` job")
  put the CodeQL language update here.

What breaks if it is wrong:
- **Job names that do not match `web` / `api` exactly:** every PR shows "Expected: waiting for
  status to be reported" and can never merge without bypass.
- **A check that is red for environment reasons:** unrelated PRs are blocked (for example a
  network-dependent step, or a check whose result changes without code changes).
- **A check that is green when it should be red:** the gate is false. For example, a recipe that
  skips because a tool or app is "not found" prints a message and exits 0 (justfile design), so a
  missing toolchain on the runner turns into a pass.
- **Required checks that run only for some changes** (path filters): docs-only PRs can never merge.
- **Linux-only breakage now blocks merges:** anything platform-specific in the lockfiles, the mlx
  marker (from T0.5), or case-sensitive imports.
- **Something leaving the repo that should not:** D19 and CLAUDE.md "Everything stays local"
  (secrets, third-party upload actions, analytics).

### 4.2 The ruleset (`scripts/bootstrap-github.sh`, verbatim)

```json
{
  "name": "protect-main",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [

        "require_last_push_approval": false,
        "required_review_thread_resolution": true
      } },
    { "type": "required_status_checks",
      "parameters": {
        "strict_required_status_checks_policy": true,
        "required_status_checks": [ { "context": "web" }, { "context": "api" } ]
      } }

```
Facts:
- Required contexts are exactly `web` and `api`. No `integration_id` is set, so a check or status
  from any source with that name satisfies the rule (verify).
- `strict_required_status_checks_policy: true`: the PR branch must be up to date with `main`
  before merging.
- The script's JSON has no `bypass_actors`. For rulesets, only listed bypass actors can bypass
  (repository admins are not exempt by default) (verify). Yet T0.1 owner answer 14 says the owner
  merged T0.1 to T0.3 "as the repo admin (bypassing the required-checks rule)". So the live
  ruleset either differs from the script (bypass added in the UI) or was not created (the script
  prints "Could not create the ruleset" for private repos without GitHub Pro). The live state
  cannot be checked from the sandbox (see Open questions).
- Merge settings from the same script: squash merge only, merge commits and rebase merges off,
  delete branch on merge, auto-merge allowed. So every merge to `main` is a single squash commit
  pushed by GitHub.
- For GitHub Actions, the check-run name that a ruleset matches is the job's `name:` if set,
  otherwise the job's key; matrix jobs get a suffix like `web (22)`; jobs in a called reusable
  workflow are named `<caller> / <callee>` (verify).

## 6. Constraints

- **Acceptance is observed on GitHub, not locally.** "CI green on main" means a workflow run on
  `main` (after the squash merge) with `web` and `api` successful. The builder and reviewer run in
  a sandbox that blocks network, `gh` and GitHub access, so pushing, watching runs, and reading
  the ruleset are owner-run steps. Local verification is limited to reading the YAML and running
  `just check`.
- **Required check names:** `web` and `api`, exact, as the ruleset's `context` values.
- **Platform:** CI runs on Linux (CLAUDE.md). mlx-lm must never be installed there; `mlx` tests
  skip off-Mac (conftest). `just dev`/`worker` exit 0 on Linux without doing anything.
- **Lockfiles are the source of truth** (section 5, section 18 "Lockfiles; no upgrades between
  freeze and retest"). Installs must not rewrite them: `uv ... --locked` everywhere (D21 T0.3
  amendment), `pnpm install --frozen-lockfile` (README).

## 7. Edge cases

1. **Check name mismatch.** A job keyed `web` but given `name: Web (lint, types, tests)` reports
   the context `Web (lint, types, tests)`, not `web`; the ruleset keeps waiting. A matrix job
   `web` with `node: [22]` reports `web (22)`. A reusable workflow reports `ci / web`.
2. **Duplicate contexts.** If both a `push` run and a `pull_request` run execute for the PR head
   commit, two check runs named `web` exist on the same SHA. How the ruleset treats one green and
   one red run with the same name is not settled here (verify). The same applies if any other
   workflow or app reports a check named `web` or `api` (no `integration_id` restriction).
3. **Path filters on required checks.** Example: `ci.yml` with `paths: ["apps/web/**"]` for the
   web job; a README-only PR never gets a `web` check, so it can never merge (required checks that
   never run stay "Expected") (verify: GitHub treats skipped jobs via `if:` as success, but
   workflows not triggered at all as missing).
4. **Strict up-to-date policy.** After PR A merges, PR B must merge `main` in and re-run `web`
   and `api` before it can merge. Each update triggers new runs.
5. **`just check` in a split job.** Both marker files exist, so `just check` in a job meant to be
   `web` also runs `uv run --locked ruff check .` etc.; without uv on that runner it fails with
   "uv: command not found" (the check recipes skip on a missing app, not a missing tool). The
   same holds in reverse for pnpm in the `api` job.
6. **Silent green from skip logic.** `security`, `security-py`, `security-web` exit 0 when a tool
   is missing or a registry probe fails. Example: CI runs `just security` without installing
   semgrep; the log says "semgrep: skipped (not installed)" and the step is green. Same for
   `just check` if a marker file were ever renamed: "apps/web not yet scaffolded, skipping" and
   exit 0.
7. **Advisory drift.** `pnpm audit` and `pip-audit` results change when new advisories are
   published, with no code change. Example: a high-severity advisory for a Vite dependency
   appears on a Tuesday; every PR's check turns red until someone upgrades a pinned dependency
   (which touches the lockfile, section 18). semgrep's `p/security-audit` alias can also change
   results without a code change (D22).
8. **pnpm version selection.** No root `package.json`; `packageManager` is in
   `apps/web/package.json`. A setup step that looks for `packageManager` at the repository root
   finds nothing and either fails or installs a different pnpm (verify for the chosen action). A
   different pnpm major may refuse or rewrite the lockfile (`lockfileVersion`, the first YAML
   document with `packageManagerDependencies`). pnpm 11+ may itself switch to the version in
   `packageManager`/the lockfile by downloading `@pnpm/exe.linux-x64@12.6.0` (verify).
9. **pnpm needs to exist before `setup-node` caching.** `actions/setup-node` with `cache: pnpm`
   calls `pnpm store path`, so pnpm must be installed first; the lockfile path must be given as
   `apps/web/pnpm-lock.yaml` because there is none at the root (verify).
10. **Node engine check.** `engines.node` is `>=22.12.0 <23`. The runner image's preinstalled Node
    (possibly 20 or 24) outside that range may make pnpm refuse to install
    (`ERR_PNPM_UNSUPPORTED_ENGINE`) or warn (verify), if Node is not set up from `.nvmrc`.
11. **Dependency build scripts.** pnpm 10+ does not run dependency lifecycle scripts unless
    allowed; newer pnpm versions may fail the install on unapproved build scripts in CI
    (`strictDepBuilds`) (verify for 12.6.0). The local install exited 0 per T0.2, with no
    approval list in the repo.
12. **Native binaries.** If the install omits optional dependencies (for example `--no-optional`)
    Rolldown, Biome, Tailwind's oxide or lightningcss fail at runtime with "Cannot find native
    binding" / "Cannot find module '@rolldown/binding-linux-x64-gnu'".
13. **Case-sensitive file system.** An import that differs only in case from the file name passes
    on macOS and fails `tsc -b`, Vitest or `vite build` on Linux. Same for Python module names.
14. **Python version.** `requires-python` allows any 3.12.x. The Mac recorded 3.12.2; the runner
    may use the image's system 3.12 or a uv-managed 3.12 (latest patch). Behaviour differences
    between patches are unlikely but possible. If the runner's default `python3` is 3.13 or 3.14
    and uv is not told which interpreter to use, uv picks or downloads a 3.12 (verify); with
    `UV_PYTHON_DOWNLOADS=never` and no 3.12 present, `uv sync` fails.
15. **uv version.** The lock was written by uv 0.12.18. A much newer uv may treat the lock
    differently (revision field, `--locked` check), and a much older one may not read it
    (verify). `uv_build==0.12.19` is fetched from PyPI to build the editable `typist-api` package
    unless the running uv can build it itself (verify).
16. **venv location.** `uv sync --locked` creates `services/api/.venv`. Setting
    `UV_PROJECT_ENVIRONMENT`, or activating a different environment (some setup actions offer
    this), moves it; then pyright (`venv = ".venv"`) cannot resolve imports and
    `test_new_revision_is_fixed_and_formatted_by_ruff` fails because
    `services/api/.venv/bin/ruff` does not exist.
17. **pyright wrapper at first run.** `uv run --locked pyright` downloads the `pyright` npm package
    (1.1.414) into a user cache (for example `~/.cache/pyright-python`) and needs Node: it uses a
    `node` on PATH or downloads one via `nodeenv` (verify). In an `api` job without Node set up,
    the runner image's preinstalled Node is used, or a download happens; either can change or
    fail. The wrapper also checks PyPI for a newer pyright and prints a warning (T0.3 plan). A
    network blip makes `types` red.
18. **Biome in CI.** `biome ci` detects GitHub Actions and may emit annotations and a different
    reporter (verify). The deprecation notice for `"recommended": true` (IMPROVEMENTS) appears on
    every run. `vcs.root: "../.."` must resolve to a directory containing `.git`; a checkout into
    a subdirectory (`path:` option) would change that.
19. **`just check` stops at the first failure** (D21). A lint failure in web hides whether the API
    tests pass in the same run.
20. **Running pre-commit in CI.** Hooks auto-fix (`ruff --fix`, `ruff format`, `biome check
    --write`), so on CI a hook "fails" by modifying files. `pre-commit run --all-files` would run
    bandit on all of `services/api/src/` and Biome on every file in `apps/web/`. They need
    `pre-commit` plus uv and pnpm on the runner (`language: system`). The golden fixture is
    excluded globally.
21. **bandit only outside `just check`.** If CI runs only `just check`, bandit never runs in CI;
    it runs in the local pre-commit hook and in `just security`.
22. **semgrep scanning the workflow files.** `just security` scans the whole repo, including
    `.github/workflows/*.yml`; `p/security-audit` may include GitHub Actions rules (for example
    shell injection via `${{ github.event... }}` in `run:`) (verify). The CodeQL `actions`
    language already analyses workflows and may raise alerts such as missing `permissions` or
    unpinned third-party actions (verify which queries are in the default suite).
23. **CodeQL additions.** `python` and `javascript-typescript` use `build-mode: none` (no build).
    CodeQL Python would also scan `tests/` and `alembic/`; CodeQL JS/TS would scan
    `apps/web/node_modules` only if it were present (it is not installed in the CodeQL job) and
    `apps/web/dist` only if built (verify default exclusions). CodeQL on a private repository needs
    GitHub Code Security (GHAS) (verify); if CodeQL default setup is also enabled in the repo
    settings, the advanced workflow's upload fails (verify).
24. **CodeQL is not a required check.** Its red or green state does not gate merges under the
    current ruleset. Alerts appear in the Security tab and may annotate PRs.
25. **Concurrency.** Without a `concurrency` group, rapid pushes to a PR run in parallel. With
    `cancel-in-progress: true` keyed on the branch, a push to `main` right after another could
    cancel the earlier `main` run, leaving that commit without a completed `web`/`api` result.
26. **Default `GITHUB_TOKEN` permissions** depend on a repository/organisation setting (read-only
    or read-write) that cannot be seen from files. The CI jobs only need to read the repository.
    CodeQL needs `security-events: write`.
27. **Fork PRs.** Solo repository; PRs from forks run with a read-only token and no secrets. Not
    expected, but `pull_request_target` would change this.
28. **Action references.** `actions/checkout@v7` and `github/codeql-action@v4` are major-tag
    references; tags are mutable. Commit SHAs are immutable but need an update mechanism; there is
    no Dependabot config. Older action majors running on a deprecated Node runtime print warnings
    or stop working when GitHub removes that runtime (verify current state).
29. **Runner image drift.** `ubuntu-latest` moves to a newer Ubuntu over time (for example 24.04
    to 26.04) (verify timing). The preinstalled Node, Python and tools change with it.
30. **just on the runner.** GitHub's Ubuntu images do not include `just` (verify). The recipes use
    `[private]`, `just_executable()` and shebang recipes, which need a reasonably recent just;
    Ubuntu's apt package may be older than 1.58.0 (verify). `uv tool install rust-just` installs
    the latest from PyPI unless pinned.
31. **Shell.** Shebang recipes call `/usr/bin/env bash`; the `security` recipe says "Must stay
    bash 3.2 compatible (macOS)". Linux runners have bash 5; nothing breaks, but bash-5-only
    syntax added for CI would break the Mac.
32. **Caching.** Caches (pnpm store, uv cache, pyright-python cache) speed runs but can mask
    install problems, and a poisoned cache from one branch can reach others under GitHub's
    cache-scope rules (verify). The first run on `main` has no cache. uv's cache can grow large
    unless pruned (setup-uv offers pruning, verify).
33. **The T0.4 PR itself.** Its checks run from the PR's own `ci.yml` (same-repo PRs use the
    head's workflow files), so `web` and `api` report for the first time on this PR. If they
    fail, the owner must either fix or bypass.
34. **"CI green on main" timing.** The push to `main` happens when GitHub squash-merges the PR.
    If the merge is done through a bypass before the PR's checks pass, `main` can be red. If the
    `main` run is cancelled (edge 25) or skipped, there is no green run to point to.
35. **Commits that skip CI.** `[skip ci]` in a commit message skips push and pull_request
    workflows (verify); a skipped required check blocks the PR.
36. **Timeouts.** Default job timeout is 360 minutes (verify). A hung step (for example a network
    download without a timeout) holds a runner and the required check for hours.
37. **Future: T0.5 adds the mlx extra.** A CI step using `uv sync --all-extras` or `--extra mlx`
    would fail on Linux; `uv sync --locked` without extras stays valid (verify). `uv lock` still
    resolves mlx-lm for darwin-arm64 on any machine.
38. **Future: `gen-types`.** When implemented, `schema.d.ts` is gitignored and generated from the
    API's OpenAPI schema; web type-checking in CI then needs the Python side first, or the web
    job fails on a missing module.
39. **Future: Playwright and hypothesis.** Playwright needs browser binaries on the runner;
    hypothesis may pick different examples per run unless configured (derandomised or seeded),
    against CLAUDE.md's seeded-randomness rule.
40. **Leftover GitHub state.** A `CODACY_PROJECT_TOKEN` secret and old Codacy code-scanning alerts
    may still exist (chore-security-scans: GitHub-side cleanup not part of that task).

## 8. Risks

1. **Required checks never match** (names, matrix suffixes, reusable workflows, path filters):
   every PR is blocked, and the owner falls back to bypassing, which defeats the ruleset.
2. **The ruleset is not what the script says.** If it was never created, or has bypass actors,
   "CI must pass before merge" is not actually enforced. If it exists without bypass actors, the
   history in T0.1 answer 14 is inconsistent with it. Either way this can only be checked by the
   owner.
3. **Network-dependent red checks.** pyright's first-run download, pnpm self-install, uv_build
   download, Python download, and (if included) semgrep/pip-audit/pnpm audit all need the
   network. Transient failures turn required checks red.
4. **Non-deterministic gates.** Advisory databases and the semgrep alias change without code
   changes (edge 7); placing them in a required check makes merges depend on the day.
5. **False green.** The skip-on-missing design of the justfile (and especially of the security
   recipes) can make a misconfigured runner pass.
6. **Local vs CI divergence.** D21's purpose is that local `just check` predicts CI. If CI runs
   individual commands instead, the two can drift as recipes change; if CI runs `just check`,
   the split into `web` and `api` jobs does not map onto recipes that always run both apps.
7. **Toolchain drift.** Unpinned uv, just, runner image and action tags can change behaviour
   between two runs of the same commit.
8. **Linux-only failures surface now** and block the first CI run: lockfile platform binaries,
   case sensitivity, venv location, pnpm version selection, Node engine range.
9. **CodeQL friction.** Adding languages can fail the CodeQL workflow for licensing or
   default-setup reasons (private repo), or raise alerts in existing code; not merge-blocking,
   but visible red checks on every PR.
10. **Scope creep.** Security scanning, pre-commit in CI, caching strategy, Dependabot, badges,
    workflow linters and README changes can each grow the PR ("One task per PR").
11. **Unverifiable inside the pipeline.** The builder and reviewer cannot run or observe GitHub
    Actions; YAML mistakes show up only after the owner pushes. Each fix cycle needs an owner push.
