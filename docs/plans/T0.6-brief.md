## 2. Why it matters

What T0.6 enables later:
- **It is the file D20 pre-registers.** T3.6 commits the dated version of this same path before
  the first practice session, and M3 is only done when the "analysis plan [is] frozen". T0.6
  creates the path and its structure; T3.6 dates and freezes it.
- **It is the only sanctioned place to change outcomes.** D05's "Revisit if" says outcomes change
  "Before retest only, by editing the analysis plan". Any later change to the primary or key
  secondary outcome goes through this file.
- **It defines what T4.1 (`analysis.py`), T4.2 (dashboard, section 15.2), T4.3 (README figures,
  15.3) and T4.4 ("README with numbers, method, limitations, N") must compute and label.** 15.1
  says "Everything else is exploratory and labelled as such", so anything the plan does not name
  as primary or key secondary must be labelled exploratory in the write-up.
- **Closes M0.** M0 is T0.1 to T0.6. T0.5 is the last task already done in this clone.

What breaks if it is wrong:
- **Pre-registration loses its force.** If the skeleton states outcomes, exclusions or methods
  that differ from sections 3.5 and 15.1, the dated plan in T3.6 may inherit them, and the pilot
  is analysed against a plan that disagrees with the design (D05, D20).
- **A skeleton read as the pre-registration.** If the T0.6 commit looks like a dated, final plan,
  the D20 record becomes ambiguous: which commit and date is the pre-registration, T0.6's or
  T3.6's?
- **Honesty rule.** Section 1: "no improvement claim until real numbers exist"; CLAUDE.md: do not
  "write result numbers into the README before real data exists". A skeleton that contains
  expected effect sizes or placeholder numbers that look like results would break this in spirit.
- **Acceptance cannot be checked if "sections from 15.1" is read differently by builder and
  reviewer** (open question 1).

### Design doc content the plan's sections point to (verbatim or near-verbatim)
- **3.5 Outcomes table:**

  | Outcome | Definition | Role |
  |---|---|---|
  | Set error rate change | For each set, pooled errors divided by pooled attempts over its bigrams, retest minus baseline | Primary |
  | Targeting effect | Set error rate change minus the control set's change (difference in differences) | Primary comparison |
  | Set IKI change | Median inter-key interval over the set's bigrams, retest minus baseline, minus the control set's change | Key secondary |
  | Overall WPM and accuracy | Session-level, baseline versus retest | Check that speed was not lost elsewhere |

- **3.5 Method:** "For each set and phase, report errors, attempts and a 95% interval from a Beta
  posterior (Jeffreys prior). For the targeting effect, draw samples from the four posteriors and
  report the median effect and the share of samples below zero. This is a description of one or
  two people, not a significance test. The write-up states the number of participants, sessions
  and keystrokes plainly."

## 7. Edge cases

1. **What counts as a "section" of 15.1.** 15.1 is five bullets, not headed subsections. The fifth
   bullet ("Commit this plan with a date before the first practice session (D20)") is an
   instruction, not content. Example: a file with headings "Primary", "Key secondary",
   "Exclusions", "Exploratory" satisfies one reading; a reviewer may expect a fifth heading for
   the date/commit rule, or expect headings named after the full bullet text.
2. **"Primary" is two rows in 3.5.** 3.5 lists "Set error rate change" (Primary) and "Targeting
   effect" (Primary comparison). 15.1's primary is the targeting effect. Example: a heading
   "Primary outcome: set error rate change" contradicts 15.1's wording, which names the
   difference-in-differences.
3. **Three primary comparisons, not one.** 15.1: heuristic, Markov and LLM, "each versus the
   control set". The plan has three primary contrasts per participant. Whether the arms are also
   compared with each other (for example LLM versus heuristic, the research question in section 1:
   "does a small on-device language model write better drills than a dictionary heuristic or a
   Markov chain?") is not stated in 15.1; under "Everything else is exploratory" such a comparison
   would be exploratory.
4. **2-set mode.** If M3 slips, only control and heuristic run ("8 bigrams each"). The primary
   comparison list in 15.1 then shrinks to one. The skeleton written at M0 names all three.
5. **12-bigram fallback.** 3.4: "If fewer than 16 qualify, take 12 (3 per set) and log it."
   Set sizes differ between participants; outcomes are pooled per set, so the definition still
   holds, but the counts in "Known weakness" (about 200 attempts per set) change.
6. **"Pauses" as an exclusion.** 12.2 excludes pauses from IKI statistics but still counts them
   for errors. Example: a keystroke after a 3000 ms pause is an error attempt for the primary
   outcome but not an IKI sample for the key secondary. 15.1 lists "pauses" among exclusions
   without that split.
7. **"Abandoned sessions" beyond practice.** 9.3 excludes abandoned *practice* sessions from
   outcome analysis. Baseline and retest sessions can also be `abandoned` (8.1 `sessions.status`),
   and baseline/retest sessions are what the outcomes are computed from. 15.1 does not say whether
   an abandoned retest session is excluded, replaced or partly used. Example: a retest session
   abandoned after 3 of 4 passages.
8. **"Fewer than 20 retest attempts".** Unclear whether 20 is counted per bigram across both retest
   sessions or per session, and whether "attempts" means `bigram_stats.attempts` (12.3 clean
   pairs) or all first-attempt observations. The retest composer (T2.7) is designed to give at
   least 40 per tracked bigram, so this exclusion only triggers when a session is lost or
   attribution skips many pairs. Also unclear: is the whole bigram dropped from its set for both
   phases, or only from retest? "(reported, not silently dropped)" requires the dropped bigrams to
   be listed.
9. **Two different 20s.** 3.4 requires "at least 20 first-attempt observations in the two baseline
   sessions" (candidate rule) and uses a prior "with strength 20". 15.1 excludes "fewer than 20
   retest attempts". Three different uses of the number 20.
10. **Two different Beta priors.** Ranking (3.4) uses an empirical-Bayes Beta prior of strength
    20; outcome intervals (3.5) use a Jeffreys prior. A skeleton that says "Beta posterior"
    without the prior is ambiguous.
11. **Sign convention.** Changes are "retest minus baseline"; a drop in error rate is negative.
    3.5 reports "the share of samples below zero" for the targeting effect, so "below zero" means
    the targeted set improved more than control. The same holds for IKI (faster is negative).
12. **Four posteriors.** 3.5: "draw samples from the four posteriors" for the targeting effect
    (targeted set baseline and retest, control set baseline and retest). This is per targeted arm
    and per participant.
13. **Pooling across participants.** 3.5 and section 1 say results are "descriptive
    per-participant changes". 15.1 does not say whether any pooled (two-person) figure is shown.
14. **Builder versus second participant.** D18 and section 18 flag the builder as unblinded and
    say "show the second participant separately". 15.1 does not mention it. If only the builder
    takes part (20.1 default "Builder only"), all data is unblinded.
15. **Missed days and the 3-day baseline rule.** 3.2: missed practice days are "logged"; baseline
    must finish no more than 3 days before the first practice session or be redone. 15.1 does not
    list these as exclusions or deviations. Example: a participant whose baseline was redone has
    four baseline sessions; which two count is not stated.
16. **Deviations during the pilot.** The runbook logs bug fixes affecting telemetry, generation or
    text composition "as deviations in the write-up". 15.1 has no deviations section. A
    `typist stats recompute` after an attribution bug fix (6.2) changes stored stats after
    pre-registration.
17. **Secondary outcomes in 3.5 not in 15.1.** Overall WPM and accuracy ("Check that speed was
    not lost elsewhere"), instrumentation overhead and LLM generation ("Engineering claim") and
    drill quality ("Checks fairness between arms") have roles in 3.5 but fall under 15.1's
    "Everything else is exploratory". Labelling the fairness check or the overhead claim
    "exploratory" may read oddly against their 3.5 roles.
18. **Values not known at M0.** N (practice days), d_min/d_max, final model and the second
    participant are decided at M3 or before baseline (20.1). Example: writing "N = 10" in the
    skeleton fixes a value that T3.5 freezes later and may change.
19. **The date.** D20 requires the plan be committed "with the date". A skeleton that carries a
    date line (for example "Date: 2026-09-29") could be mistaken for the pre-registration date;
    a skeleton with no date must gain one in T3.6. Whether "with the date" means a date written in
    the file, the git commit date, or both is not stated.
20. **Amendments after T3.6.** D05 allows editing outcomes "Before retest only, by editing the
    analysis plan", which permits changes after the D20 pre-registration commit (before the first
    practice session) but before retest. There is no stated record format for such edits (for
    example an amendments log in the file).
21. **The file is under `docs/`, not `data/`.** It must never hold participant data or results;
    `/data/` is the only gitignored data path.
22. **Stale `main` ref.** In this clone `main` and `origin/main` point at `952e513`, so the
    reviewer's `git diff main...HEAD` would show T0.1 to T0.6 together unless the refs are
    updated (section 4).
23. **Markdown rendering.** GitHub renders the file; there is no linter. Relative links (for
    example to the PDF or to D-number ADRs) break silently if a path is mistyped. D01 to D20 exist
    only inside the PDF, which has no anchors per decision.

## 8. Risks

1. **Acceptance ambiguity.** "Sections from 15.1" has more than one reasonable reading (edge case
   1); the builder and reviewer may disagree without an owner answer.
2. **Scope creep into T3.6.** Filling the skeleton with full definitions, thresholds and methods
   effectively writes the pre-registration at M0, before N, density range, model and the second
   participant are settled (edge case 18), and blurs which commit is the D20 record (edge case
   19).
3. **Silent drift from the design.** Paraphrasing 15.1 or 3.5 can change meaning (edge cases 2,
   6, 7, 8, 10). Once T3.6 dates the file, a paraphrase becomes the binding definition.
4. **Honesty rule breach.** Placeholder or example numbers that look like results (edge case 11
   sign examples, expected effect sizes) in a committed, public document.
5. **No automated proof.** The reviewer expects every acceptance criterion "proven by a test";
   none exists for docs (open question 7). Without an owner answer the review may block.
6. **Reviewer diff noise** from the stale `main` ref (edge case 22).
