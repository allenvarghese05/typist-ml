## 2. Why it matters

The bake-off is the empirical gate that settles which language model powers `Arm.LLM` throughout the entire randomized controlled trial. While T3.2 built the technical foundation (`MLXRuntime`, Prompt v1, post-processing, and `LLMGenerator`), T3.3 performs the rigorous comparative evaluation mandated by §13.6 and D10.

- **Empirically validates the neural arm before freeze (§13.6, D10, D20).** Up to this point, `mlx-community/Llama-3.2-1B-Instruct-4bit` has been the default assumption. T3.3 pits it against the challenger (`mlx-community/Qwen3-1.7B-4bit`) across 10 synthetic weak-bigram target sets (mix of common and awkward bigrams), generating 200 drills per candidate through the shared fairness validator (`typist.generation.validator.validate`).
- **Verifies production throughput and latency under load (§13.6, §8.1).** The design doc requires the selected model to run at $\ge 30$ tokens per second on Apple Silicon. Generating hundreds of drills under retry conditions tests sustained token throughput, peak unified memory consumption (ensuring it operates comfortably within MacBook unified memory alongside the browser and API), and latency.
- **Evaluates real-world validator acceptance (§13.1, §13.5).** Prompt v1 instructs the model to produce 60 words containing specific target bigrams. If a model generates pseudo-words, repetitive n-grams, or fails to include target bigrams at least 3 times each, the validator rejects the drill. The bake-off measures first-attempt and 5-attempt acceptance rates, ensuring the worker will not suffer from drill exhaustion or starvation in the 3-day buffer pool (§13.7, §18).
- **Enables density calibration (T3.4) and final config freeze (T3.5).** In T3.4, `d_min` and `d_max` are calibrated so that each targeted arm (heuristic, Markov, LLM) accepts $\ge 80\%$ of drills within 5 attempts. That calibration depends directly on knowing which LLM model is selected and its empirical density distribution. T3.5 subsequently freezes the configuration parameters.
- **Documents scientific integrity and pre-registration (ADR D29, §17.3).** Recording the comparative metrics (acceptance rate, attempts per accepted drill, density, real-word ratio, tokens per second, peak memory) in `notebooks/02_model_bakeoff` and a formal ADR in `docs/decisions/` satisfies pre-registration standards before any participant begins practice.

**What breaks if it is wrong:**
- If an unverified model is chosen that fails the $\ge 30$ tokens/s floor or frequently trips validator rejection rules ($< 80\%$ acceptance across 5 attempts), the background generation worker will exhaust its retry budget, failing generation jobs and starving the participant's LLM drill pool during the pilot.
- If the notebook or evaluation script attempts network access or non-cached downloads during testing or CI, it violates D19 ("No cloud, no WASM") and D23 (offline snapshot requirement).
- If the challenger model's "thinking mode" is not disabled, the model will output thousands of reasoning tokens (`<think>...</think>`), blowing past `max_tokens=160` and emitting zero valid practice words.
- If division-by-zero is unhandled when calculating attempts per accepted drill for an awkward set with 0 accepted drills, the notebook or benchmark crashes.
- If the ADR or frozen model ID diverges between documentation, `experiment_config`, and `MLXRuntime`, the pilot runs with unverified weights or mismatched reproducibility hashes.

- **D03 (Arms: `control, heuristic, markov, llm`):** T3.3 selects and finalizes the specific neural model powering `Arm.LLM`.
- **D06 (Deployment: Local-only on the MacBook Pro M1 Pro):** Everything runs on one machine. The bake-off benchmark executes locally on Apple Silicon unified memory; no external cloud AI APIs, remote inference endpoints, or off-device servers are permitted.
- **D08 (Backend stack: Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite WAL, Typer CLI, ruff, pyright, pytest):** Python 3.12 within `services/api` drives the model runtime and validation.
- **D09 (Model runtime: `mlx-lm` Python API, version pinned in `uv.lock`):** Candidates are loaded and sampled using `mlx-lm` (pinned in `pyproject.toml` extra `mlx`: `mlx==0.32.3`, `mlx-lm==0.31.3` with marker `sys_platform == 'darwin' and platform_machine == 'arm64'`).
- **D10 (Model choice and bake-off rule):** "Default `mlx-community/Llama-3.2-1B-Instruct-4bit`. Short bake-off against `Qwen3-1.7B` (4-bit) before the pilot, then frozen. Revisit if: Bake-off shows another model clearly accepts more drills."
- **D16 (Fairness gate: All targeted arms pass one shared validator):** All bake-off drill candidates must pass `validator.validate()`: target length 300 (floor 270), target density $\in [d_{min}, d_{max}]$ (0.15 to 0.40), coverage $\ge 3$ per target bigram, max word repeat $\le 3$, bigram run $< 3$. In addition, `real_word_ratio >= 0.8` gates `Arm.LLM`.
- **D17 (Word list: `wordfreq` English list, filtered to `a`–`z` words):** The validator evaluates real-word ratio against the project-wide 20,000-word vocabulary (`WordIndex.words` from `data/words.json`).
- **D19 (No cloud, no WASM):** Strictly local execution; no remote inference, no external API calls, and no telemetry.
- **D20 (Pre-registration / Freeze):** The model choice, prompt version (`v1`), sampler settings (`temperature=0.8`, `top_p=0.9`, `max_tokens=160`), `d_min`, and `d_max` are recorded in an ADR and frozen before the pilot begins.
- **D23 (Model download / Hugging Face cache):** Model weights are downloaded once by the repository owner via `just mlx-smoke --download` at pinned commit SHAs into the local cache (`~/.cache/huggingface/hub`). All subsequent executions set `HF_HUB_OFFLINE=1` and `HF_HUB_DISABLE_TELEMETRY=1`, reading local files only. CI and sandboxes never download models.

## 6. Constraints

- **Platform limit (Apple Silicon):** `mlx` and `mlx-lm` execute only on macOS on Apple Silicon (`arm64`). All neural model completions require Apple Silicon unified memory.
- **Offline / Privacy constraint (D19, D23):** Generation must run completely offline without contacting Hugging Face or external APIs. Weight snapshots must be present in the local Hugging Face cache (`~/.cache/huggingface/hub/`). No network requests are made during notebook execution or tests.
- **Fairness gate constraint (D16, §13.1):** Models are evaluated through the exact same shared validator (`validate`) as all other arms: length $\in [270, 300]$, target density $\in [0.15, 0.40]$, coverage $\ge 3$ per target bigram, max word repeat $\le 3$, bigram run $< 3$, and real-word ratio $\ge 0.8$.
- **Attempt ceiling constraint (§13.5):** Each drill allows up to 5 attempts. If all 5 attempts fail validation, that drill is counted as rejected.
- **Selection rule constraint (§13.6 step 4):**
  - Minimum throughput: $\ge 30$ tokens per second.
  - Primary criterion: Highest acceptance rate.
  - Tie-breaker: Keep `Llama-3.2-1B-Instruct-4bit`.
- **Prompt invariance (§13.6 step 5):** Prompt v1 does not change after the bake-off.
- **CI and Sandboxes:** Automated CI runs on Linux x86_64 where MLX cannot be installed or executed. Any tests added for the bake-off notebook or benchmark harness must pass cleanly under `just check` on Linux and off-Mac environments (using mocks, fake runtimes, or `@pytest.mark.mlx` skips).

## 7. Edge cases

1. **Awkward bigram combinations with zero dictionary occurrences:**
   - *Example:* A synthetic set contains an awkward bigram like `("pq", "xj", "qz", "vk")`.
   - *Consequence:* The English vocabulary has virtually no common words containing `pq` or `xj`. The model may hallucinate pseudo-words (e.g. `"pquick"`). If post-processing keeps them, `validate()` rejects the drill with `RejectReason.REAL_WORD_RATIO` ($< 0.8$). If it fails to include them, `validate()` rejects with `RejectReason.COVERAGE`.
   - *Impact on Bake-off:* An entire synthetic set may yield 0 accepted drills out of 20 across all 5 attempts (0% acceptance rate).
2. **Division by zero in attempts per accepted drill:**
   - *Example:* In a set where 0 out of 20 drills are accepted, computing `total_attempts / accepted_drills` divides by zero.
   - *Consequence:* The evaluation code must define this case cleanly (e.g. `NaN`, `None`, or 5.0) rather than throwing `ZeroDivisionError`.
3. **Chat template incompatibility or thinking tokens in challenger models:**
   - *Example:* `mlx-community/Qwen3-1.7B-4bit` features a dual "thinking mode" that outputs `<think>...</think>` reasoning tokens before answering.
   - *Consequence:* With `max_tokens=160`, the model's output would consist entirely of thinking tokens and zero practice words, resulting in 100% rejection. Thinking mode must be explicitly disabled (as noted in §13.5).
4. **Different chat template formats across model families:**
   - *Example:* Llama 3.2 uses `<|start_header_id|>system<|end_header_id|>...`, whereas Qwen uses `<|im_start|>system...`.
   - *Consequence:* Both models rely on `tokenizer.apply_chat_template`. If a tokenizer's chat template expects a different role convention or lacks default template strings, generation fails.
5. **Execution duration of full benchmark:**
   - *Example:* 2 candidate models $\times$ 10 sets $\times$ 20 drills = 400 drills. With retries (up to 5 attempts per drill), this could require 400 to 2,000 model completions. At ~2 seconds per completion on Apple Silicon, generating all drills sequentially takes 15 to 45 minutes of continuous GPU generation.
   - *Consequence:* An interactive notebook cell that runs the entire benchmark in one block without checkpointing, intermediate caching, or progress tracking risks timeout or memory exhaustion.
6. **Execution in non-Mac / CI or un-downloaded environments:**
   - *Example:* A developer on Linux or without cached weights opens the notebook or runs pytest.
   - *Consequence:* `MLXRuntime` raises `ModelNotDownloadedError` or `RuntimeError`. The notebook and any accompanying test suite must support loading pre-computed benchmark results or skipping real execution when weights are absent.
7. **Tied acceptance rates:**
   - *Example:* Candidate 1 and Candidate 2 both achieve an 85% acceptance rate (170/200 drills accepted) and both exceed 30 tokens/s (e.g. 42 tps vs 38 tps).
   - *Consequence:* Per §13.6 step 4, if tied, `Llama-3.2-1B-Instruct-4bit` must be retained. The selection rule does not pick the faster model if acceptance rates are tied.

## 8. Risks

1. **Missing challenger weights in local cache (D23):** In subagent sandboxes and CI, network access is prohibited. If the challenger model (`mlx-community/Qwen3-1.7B-4bit`) is not downloaded in the local Hugging Face cache, real generation cannot execute inside an automated sandbox.
2. **Challenger model naming or release drift on Hugging Face:** The design doc mentions `mlx-community/Qwen3-1.7B-4bit`. If the repository on Hugging Face Hub uses a different quantization tag, model revision, or naming convention (or requires specific inference flags), downloading or running it without owner intervention will fail.
3. **Low overall acceptance rate across awkward sets ($< 80\%$):** If Prompt v1 struggles to embed awkward bigrams 3 times each while keeping real-word ratio $\ge 0.8$, both models may achieve low acceptance rates on the awkward sets, highlighting the difficulty of constrained generation without logit masking.
4. **Notebook corruption or dependency bloat:** Modifying `pyproject.toml` to add Jupyter/IPython can introduce massive dependency graphs and conflicting transitive pins into `uv.lock`. Keeping the notebook clean and maintaining testable Python code outside the notebook avoids lockfile churn.
5. **Memory leak across long benchmark generation loops:** Repeated calls to `stream_generate` or holding thousands of generation objects in unified memory on a 16 GB MacBook could cause memory pressure or swapping if MLX cache arrays are not periodically cleared.
