## 2. Why it matters

What T1.4 enables later:
- **Every `keystroke_events` row is born here.** The recorder turns browser key events into rows:
  it decides which events become rows at all (filters), assigns `seq`, timestamps, pairs key-ups
  for dwell, computes or carries IKI, sets `after_pause` (D24: "The browser client captures the
  flag and sends it with each keystroke") and measures `handler_ms` / `dispatch_lag_ms`. It is the
  only caller of `TextCursor` for real data.
- **T1.5** wires the recorder to the window and the typing surface (11.3 rules, pause on blur, the
  D26 idle rule, red highlight). Its "feels instant" criterion depends on the recorder's cost per
  key.
- **T1.6** buffers and posts the rows (12.4 "A row is created on keydown and sent once its keyup
  has arrived, or after 2 seconds without one (keyup stays null)"; Figure 5
  `EventBuffer.completeDwell(seq, tUp)`), and the endpoint stores them with
  `ON CONFLICT (block_id, seq) DO NOTHING`.
- **T1.7 / T1.9** trust the stored rows: `seq` order ("a backspace happened between a and b" is a
  `seq` test), `after_pause`, `t_down_ms` (IKI samples are `b.t_down - a.t_down`, WPM time from
  first to last press, D26), `first_attempt`, `outcome`.
- **The overhead claim** (analysis plan, 3.5: "Instrumentation overhead | Handler time and dispatch
  lag per keystroke, p50, p95, p99 | Engineering claim"; README "reports overhead p95"; M1 "overhead
  reported"; CLI `typist overhead`, 14.1) is computed from `handler_ms` and `dispatch_lag_ms`.

What breaks if it is wrong:
- **Raw data cannot be repaired.** `keystroke_events` is "the raw data that cannot be rebuilt" (D24
  context, citing 10.3), rows are append-only (CLAUDE.md, 6.2). A filter that lets a repeat or a
  chord through creates a false error row and a false attempt; a filter that drops a real key
  shifts every later `target_index` (positional alignment, T1.2 answer 9c); a `seq` gap or
  duplicate breaks the 12.3 "between" test and 12.6 checks. `typist stats recompute` would
  faithfully reproduce the wrong numbers.
- **Wrong dwell pairing** (pairing by `key` or by order instead of by `code`) gives wrong dwell
  under rollover; 12.1: "This is what makes dwell correct when keys overlap."
- **Wrong timestamps** (`Date.now()`, a wrong origin, `performance.now()` at handler time instead
  of `event.timeStamp`) distort IKI, the key secondary outcome (D05), and WPM.
- **Wrong `after_pause`** puts blur-interrupted pairs into IKI samples (D24 context example) or
  removes clean ones.
- **Throwing in the handler.** `TextCursor.type()` throws `RangeError` on any key outside a to z
  and space (T1.3 owner answer 3). A filter gap means an exception inside a live keydown handler.
- **Overhead fields measured inconsistently** make the engineering claim meaningless; they are
  `NOT NULL` (T1.1 answer 5), so a row without them cannot be stored.

### 4.1 Design rules for capture and timing (verbatim)
- **12.1:** "Listen to keydown and keyup on window while a block is active and the page has focus."
  / "Ignore events where e.repeat is true, modifier-only keys, and any event with Ctrl, Meta or Alt
  held. Shift is allowed but not needed in v1." / "Handle only a to z, space and Backspace." / "Use
  e.key to decide the character and store e.code for the physical key." / "Pair keyup with its
  keydown by e.code, using a map of open keys. This is what makes dwell correct when keys overlap."
  / "On window blur: pause the block, mark the next keystroke as following a pause, and resume on
  focus."
- **12.2 table:** Timestamp `e.timeStamp` ("Do not use Date.now()"); Dwell "t_up minus t_down, same
  physical key"; IKI "t_down(i) minus t_down(i-1) ... Always positive"; Release to press "t_down(i)
  minus t_up(i-1) ... negative whenever the next key is pressed before the previous one is released
  (rollover)"; Pause "IKI over 2000 ms, or first key after a blur | Excluded from IKI statistics,
  still counted for errors". Also (T0.2 brief): "Browsers coarsen timers slightly for security".
- **12.4:** "A row is created on keydown and sent once its keyup has arrived, or after 2 seconds
  without one (keyup stays null)." "The server inserts with ON CONFLICT (block_id, seq) DO NOTHING".
- **12.5:** target "handler p95 under 1 ms". The definitions of handler time and dispatch lag are
  not available to this analysis (see Sources; open question 1).
- **12.6 checks:** "Gaps in seq within a block." / "Negative dwell, or dwell over 1000 ms (stuck
  key)." / "Blocks with fewer events than characters in the target text." / "Share of keyups
  missing."
- **10.3 Figure 9:** "Normalise t = event.timeStamp, drop repeat and modifiers" then "Align to
  target text outcome + first attempt per position" then `keystroke_events`.
- **8.1 `keystroke_events`:** `seq` "Order within the block, from 0"; `key, code` "KeyboardEvent.key
  (character) and .code (physical key)"; `t_down_ms, t_up_ms` "event.timeStamp relative to block
  start; t_up may be null if the page closed"; `dwell_ms` "t_up minus t_down for this key";
  `iki_ms` "t_down minus previous keystroke's t_down (press-to-press)"; `handler_ms,
  dispatch_lag_ms` "Instrumentation overhead (section 12.5)".
- **14:** `POST /blocks/{bid}/start | Mark block start time`; `POST /blocks/{bid}/events | Batch of
  keystroke rows (idempotent)`; `POST /blocks/{bid}/complete | Mark block end`.
- **Section 7 layout:** `telemetry/  # KeystrokeRecorder.ts, TextCursor.ts, EventBuffer.ts,
  overhead.ts, types.ts, __tests__/`.

### 4.4 What a stored row must contain (Python, merged)

`services/api/src/typist/models/keystroke_events.py`, class `KeystrokeEvent` columns:
`id: int | None` (rowid), `block_id: str`, `seq: int`, `key: str`, `code: str`, `t_down_ms: float`,
`t_up_ms: float | None`, `dwell_ms: float | None`, `iki_ms: float | None`,
`release_to_press_ms: float | None`, `target_index: int`, `expected_char: str | None`,
`outcome: str`, `first_attempt: bool | None`, `after_pause: bool = False` (server default 0),
`handler_ms: float`, `dispatch_lag_ms: float`. Constraints: `UNIQUE (block_id, seq)`,

release-to-press ("dwell_ms is stored even when odd (section 12.6 checks flag it)").

Discrepancy to be aware of (not T1.4's to fix): the model docstring says `release_to_press_ms` is
NULL "when the previous key's t_up was unknown at insert (it is never backfilled)", implying a
value may be inserted; T1.2 answer 10a says it "is not stored" at all. Either way the recorder
does not compute it (T1.2 answer 3 omits it from rows).

`services/api/src/typist/services/keystrokes.py`:
```python
def record_key_up(session: Session, block_id: str, seq: int, t_up_ms: float) -> KeystrokeEvent:
```
"Sets t_up_ms and dwell_ms = t_up_ms - t_down_ms on the row (block_id, seq)"; raises
`KeystrokeEventNotFoundError` if no row, `KeyUpAlreadyRecordedError` if `t_up_ms` is already set.
So a late key-up for an already-stored row can be filled in exactly once, server-side, with dwell

## 5. Inputs and outputs

Inputs:
- Browser `KeyboardEvent`s (`keydown`, `keyup`) on `window` (12.1): fields used `key`, `code`,
  `repeat`, `ctrlKey`, `metaKey`, `altKey`, `shiftKey`, `timeStamp` (and possibly `isComposing`,
  `isTrusted`; open question 10). In tests: synthetic events (form: open question 9).
- Window blur and focus notifications (12.1, D24).
- The block's target text, for a `TextCursor` (from `session_blocks.target_text`, D13).
- A block-start time origin so times are "relative to block start" (T1.2 answer 13c; open
  question 3).
- A high-resolution clock for the overhead fields (definition: open question 1).

Outputs:
- One row per accepted keydown, in snake_case `keystroke_events` shape: `seq` (contiguous from 0
  per block), `key`, `code`, `t_down_ms`, `t_up_ms` (null until/unless the key-up arrives),
  `dwell_ms` (null when `t_up_ms` is null), `iki_ms` (null at seq 0), the four cursor fields,
  `after_pause`, `handler_ms`, `dispatch_lag_ms`. No `release_to_press_ms`. `block_id` and `id`:
  not the recorder's per 4.7.

## 6. Constraints

- **Filter before the cursor.** `TextCursor.type()` throws on anything but `/^[a-z ]$/`; the
  recorder must never pass anything else. `null` from the cursor means "record no row" (no `seq`
  consumed, no IKI anchor moved, no open-key entry kept).
- **Timestamps:** `event.timeStamp`, never `Date.now()` (12.2, D15); milliseconds relative to block
  start (T1.2 answer 13c); stored as REAL (8 intro: "Durations are milliseconds stored as REAL").
- **Dwell pairing by `e.code`** through a map of open keys (12.1), not by `e.key` (a key-up can
  report a different `key` than its key-down, for example after Shift changes; verify) and not by
  order.
- **Append-only spirit:** after a row leaves the recorder, the only later change is the key-up time
  (and dwell) of that same row (T1.1 answer 6, CLAUDE.md).
- **No attribution, no 2000 ms pause logic, no WPM** in the recorder (CLAUDE.md, 6.2, D24, D26).
- **Plain class, no React** (6.1); runs in the Vitest `node` environment unless a DOM environment is
  added.
- **Performance:** handler p95 under 1 ms (12.5); "no React state updates inside [the handler], no
  allocation-heavy work, no network calls" (12). T1.5: "Typing 300 characters feels instant". Real
  blocks are 600 characters (3.3).
- **Timer resolution:** browsers coarsen `performance.now()`/`timeStamp` (12.2 note); resolution
  depends on cross-origin isolation (COOP/COEP) and browser (verify); sub-millisecond overhead
  values may read as 0 or as a coarse step.
- **TypeScript:** strict, `noUncheckedIndexedAccess` (`Map.get` returns `T | undefined`),
  `erasableSyntaxOnly`, `verbatimModuleSyntax`; Biome `noExplicitAny`; 17.1 "no any without a
  comment".
- **Randomness:** none expected; if any appears it comes from a seeded generator passed in
  (CLAUDE.md).
- **Tests:** the acceptance requires synthetic `KeyboardEvent` tests covering "repeat, modifiers,
  overlapping keys". The golden fixture is not T1.4's test input (T1.2 answer 1).
- **Platform:** no mlx; nothing Apple-Silicon specific; CI runs on Linux. The real typist uses
  macOS (MacBook, D06), so macOS browser key-event behaviour is what the data reflects.
- **Gate:** `just check` / CI `web` (`biome ci .`, `biome format .`, `tsc -b`, `vitest run`, `vite
  build`). Any new dependency needs a lockfile update; network is an owner-run step in the sandbox
  (auto-memory).
- **No GPL code** (Monkeytype is behaviour reference only).
- **Workflow:** branch `t1-4-keystroke-recorder`, conventional commits, one task per PR; commits are
  owner-run in the sandbox.

## 7. Edge cases

Times below are `event.timeStamp` values minus the block origin, in ms.

1. **Auto-repeat.** Holding `a`: keydown `a` (repeat false) at 100, keydowns with `repeat: true` at
   600, 633, 666 ..., one keyup at 900. Only one row (seq n, `t_down_ms` 100, `t_up_ms` 900, dwell
   800). Repeats consume no `seq` and do not move the IKI anchor. Holding Backspace likewise erases
   only one character.
2. **Modifier-only keys.** `Shift`, `Control`, `Alt`, `Meta`, `CapsLock`, `Fn` keydowns/keyups never
   become rows and never enter the open-key map. `e.key` values for these are the modifier names;
   `e.code` is e.g. `ShiftLeft`, `MetaRight` (verify).
3. **Chords.** `Cmd+a`, `Ctrl+a`, `Alt/Option+e` (macOS Option produces `e.key` like `"´"` or
   `"Dead"`), `Alt+Backspace` (word delete), `Cmd+Backspace` (line delete): all dropped (12.1).
   D25's "Revisit if" mentions word delete as out of scope.
4. **Chord released out of order.** Ctrl down, `a` down (dropped: Ctrl held), Ctrl up, `a` up at
   300. The `a` keyup arrives with no modifier held. It must not pair with anything; if an earlier
   accepted `a` is still open under `KeyA` (its keyup was lost), pairing this keyup with it would
   give a false dwell.
5. **Shift and uppercase.** Shift+`t` gives `e.key` `"T"`: dropped (T1.2 answer 9d). Shift+Space
   gives `e.key` `" "` with `shiftKey` true; Shift+Backspace gives `"Backspace"` with `shiftKey`
   true. Whether these two are dropped is not settled (open question 7). Target texts have no
   capitals (D13), so Shift is only ever pressed by accident or out of habit.
6. **Caps Lock on.** Every letter arrives as `"T"`, `"H"` with no Shift held; all dropped. The
   typist sees nothing happen. The recorder records nothing; any user hint is T1.5's.
7. **Non-letter printable keys.** `"."`, `","`, `"1"`, `"Enter"`, `"Tab"`, `"Escape"`, arrows,
   `"Delete"`, `"Unidentified"`, `"Dead"`, `"Process"` (IME), accented `"é"`: all dropped. `Tab`
   also moves browser focus (a possible blur source; verify).
8. **IME / dead keys / composition.** `isComposing` true or `e.key === "Dead"`; a dead key followed
   by `e` can yield `"é"`. Dropped by the a to z rule; whether `isComposing` needs its own check is
   not stated.
9. **Keyboard layout.** D13 assumes QWERTY. On another layout `e.key` `"a"` can have `e.code`
   `"KeyQ"` (AZERTY). The recorder stores `code` as given; dwell pairing still works because it
   uses the same `code` for down and up.
10. **Simple rollover** (fixture case k shape): `t` down 2675, `h` down 2765, `t` up 2795, `h` up
    2850. Two open entries at once; dwell `t` 120, `h` 85; IKI `h` 90.
11. **Nested overlap** (case l shape): `e` down 15930.5, `r` down 15990.5, `r` up 16040.5, `e` up
    16090.5. Key-ups arrive in the opposite order; `r`'s row completes before `e`'s.
12. **Same physical key twice, key-up lost** (missing key-up followed by the same key, cf. cases q and
    s): `n` down 100 (key-up never arrives), later `n` down 400 (repeat false), `n` up 470. The map
    already has an open `KeyN` entry when the second press arrives. Which press the 470 key-up
    belongs to decides whether dwell is 70 or 370 (open question 8).
13. **Missing key-up (case q).** Reasons: blur while held (key-up goes to another window), the page
    closes, macOS not delivering key-ups for other keys while `Cmd` is held (verify), a
    browser/OS swallow. 12.4: row "sent ... after 2 seconds without one (keyup stays null)". Then:
    `t_up_ms` and `dwell_ms` null; the next row's `iki_ms` is unaffected (uses `t_down`).
14. **Key-up after the 2 s cut-off.** `a` held for 2.5 s (stuck key): row sent at 2 s with null
    `t_up_ms`, key-up arrives at 2.5 s. `record_key_up` (T1.1) can fill it once server-side
    (dwell 2500, flagged by 12.6 "dwell over 1000 ms"). Whether the client forwards it is open
    question 4.
15. **Key-up with no open entry.** A key pressed before the block started, a filtered keydown
    (repeat/chord/uppercase) whose keyup arrives clean, or a key ignored after `isDone()`: the
    key-up must not create or complete any row.
16. **Seq 0.** `iki_ms` null. The first row may be a Backspace at index 0 (fixture case e) and still
    starts the WPM clock (F15) and is the IKI anchor for the next key (fixture seq 1: 824).
17. **IKI anchor is the previous recorded row**, not the previous keydown event: filtered keys and
    keys ignored after `isDone()` do not move it. Backspace rows do.
18. **Equal or tiny timestamps.** 12.2 says IKI "Always positive". With timer coarsening two
    keydowns can carry the same `timeStamp`, giving `iki_ms` 0 (verify). Monotonic order of
    `timeStamp` across events is assumed (verify).
19. **Floating point.** `timeStamp - origin` produces values like `1234.5000000000001`; live data has
    no exactness requirement, but synthetic tests that compare with exact equality need
    exactly-representable inputs (T1.2 answer 13a precedent: whole numbers or multiples of 0.25).
20. **Keys after `isDone()`.** The final correct or wrong character makes the block done; a further
    `x` or Backspace returns `null`; no row, no `seq`, no open entry; its key-up is ignored. Its
    timestamp must not shift IKI or the WPM end (F16 "the last key pressed" means the last
    recorded row).
21. **Blur then focus, next key a Backspace** (case p): flag on the Backspace only; the following key
    is not flagged (answer 11c).
22. **Blur then focus, next keydown filtered or ignored.** The typist clicks back in and presses
    `Shift` or `Cmd` first, or a repeat event from a key held across the blur arrives first, then
    types `h`. Whether the flag waits for the first recorded row is not stated (open question 6).
23. **Several blurs without a key in between.** blur, focus, blur, focus, `h`: one flagged row.
24. **Blur before the first key of a block.** The first row (seq 0) carries `after_pause` true under
    D24's literal wording; it has no IKI anyway.
25. **Keys while blurred.** Normally the window receives no key events while blurred; events between
    the `blur` event and the pause taking effect, or a keydown delivered after `blur` in the same
    task, must be dropped (T1.2 answer 9d/21 list "keys while blurred").
26. **Blur longer than 10 s.** D26: "Blur counts as idle"; after 10 s the block is abandoned (T1.5).
    The recorder's state for that block then ends; a restarted block has its own `seq` from 0 and
    its own origin (D26 consequences; migration 0002 not yet designed).
27. **What counts as blur.** `window` `blur`/`focus`, `document` `visibilitychange`, focus moving
    into DevTools or an iframe, the OS screen lock, Cmd-Tab. These do not always fire together
    (verify). D24 says "window regains focus following a blur".
28. **Untrusted events.** Synthetic test events and any script-dispatched event have `isTrusted`
    false; real typing has `isTrusted` true. T2.10 ("Dev-only pipeline test using scripted
    keystrokes", T0.2 brief) will rely on scripted events (open question 10).
29. **`KeyboardEvent.timeStamp` in tests.** On a real `KeyboardEvent` the `timeStamp` is set at
    construction and is read-only (verify); a test that needs `t_down` 100 then 190 cannot pass
    those values through the constructor.
30. **Default browser actions.** Space scrolls the page, Backspace can act on a focused input,
    `'` / `/` open Firefox quick find. Who calls `preventDefault` is not stated (open question 5).
31. **React StrictMode double mount** (T0.2 edge case 25): listeners registered twice would record
    each key twice with the same `timeStamp`; relevant when T1.5 wires the recorder.
32. **Overhead measurement placement.** If `handler_ms` must describe the handler that creates the
    row, the end time is known only after the row object exists; the value is written into the row
    at the end of the same handler. `dispatch_lag_ms` compares two clocks that must share an origin
    (`event.timeStamp` and `performance.now()` share the performance timeline in current browsers;
    verify). Filtered events have no row, so their handler cost is not recorded anywhere.
33. **Key-up handler overhead.** The key-up handler also runs per key; no column stores its cost
    (`handler_ms` is one value per row).

## 8. Risks

1. **Filter gaps that throw or corrupt.** Any path that lets `"T"`, `"Dead"` or `""` reach
   `TextCursor.type()` throws in the live handler; any path that drops a real a to z key shifts
   every later `target_index`. Both corrupt append-only data silently (the throw loses the key).
2. **Pairing by order or by `key`** instead of by `code`: correct on slow typing, wrong under
   rollover and nested overlap, which are exactly the acceptance cases.
3. **Stale open-key entries** (lost key-ups) pairing with a later, unrelated key-up, producing
   plausible but false dwell values that 12.6 cannot detect.
4. **IKI anchored to the wrong event** (a filtered keydown, a repeat, an ignored post-done key) or
   reset by a Backspace.
5. **Timestamp origin errors**: using `performance.now()` at handler time (adds dispatch lag to
   every time), `Date.now()`, or an origin that differs between blocks or restarts.
6. **`after_pause` placed on a filtered event** (lost), or set twice, or left on until the next blur.
7. **Overhead fields defined loosely** so the reported p95 is not comparable to the 1 ms target, or
   the measurement itself allocates and inflates the cost.
8. **Testing a fake that is not a `KeyboardEvent`.** If tests pass hand-built objects, the
   recorder might read a field that real events lack or vice versa; if tests construct real
   events, `timeStamp` control and a DOM environment become issues.
9. **Scope creep** into T1.5 (window listeners, pause UI, idle timers, display store), T1.6 (the
   2 s rule, batching, POST) or Python (release-to-press, 2000 ms pause, overhead percentiles).
10. **Duplicate computation drifting**: if both the browser and the service layer compute `iki_ms`
    or `dwell_ms` with different rules (T1.2 answer 10a vs Figure 5), two sources of truth for one
    stored column.

## 9. Open questions

1. **What exactly are `handler_ms` and `dispatch_lag_ms`?** Section 12.5 could not be read here,
   and no earlier brief quotes its definitions. Please confirm (or quote 12.5): is `handler_ms`
   the time spent inside the keydown handler (clock at handler end minus clock at handler start,
   including the cursor and row creation), and is `dispatch_lag_ms` the delay between the
   browser stamping the event and the handler starting (clock at handler start minus
   `event.timeStamp`)? Are they measured only for keydown, and only for keys that become rows?
   In plain terms: these two numbers back the "overhead p95" claim in the README. When you press
   `t`, the browser notes the moment (say 1000.0 ms), our code starts running at 1001.2 and
   finishes at 1001.5. Under the suggested reading, dispatch lag is 1.2 ms and handler time is
   0.3 ms. If the design meant something else, every stored value would measure the wrong thing.
   Suggested default: exactly that reading, measured with `performance.now()`, on keydown only,
   for rows only; key-up handlers and filtered keys are not measured.

2. **Who computes `iki_ms` and `dwell_ms`: the browser, the server, or both?** Figure 5 gives the
   recorder `lastDownT` and an `iki` field, and T1.4's title says "IKI"; T1.2 answer 10a says both
   are "computed by the service layer" (dwell when the key-up arrives, IKI at insert from the prior
   row's `t_down`), and `record_key_up` already computes dwell on the server.
   In plain terms: for `t` pressed at 2675 and `h` at 2765, someone has to write `iki_ms = 90` on
   `h`'s row. If the browser writes it and the server also computes it, there are two places that
   can disagree. If only the server does it, the recorder just sends times.
   Suggested default: the recorder computes `iki_ms` (from the previous recorded row's
   `t_down_ms`, null at seq 0) and `dwell_ms` (when the key-up arrives before the row leaves) and
   puts them in the row; the server's `record_key_up` computes dwell only for late key-ups;
   whether T1.6 re-checks the browser values is T1.6's question.

3. **What is "block start", the zero point for all times?** Rows store times "relative to block
   start" (answer 13c), and the fixture's first key is at 1851 ms, so the zero point comes before
   the first key. Is it the moment the block's text is shown, the `POST /blocks/{bid}/start` call,
   or something else, and who supplies it?
   In plain terms: if the text appears at 10:00:00.000 and the first `t` is pressed 1.85 s later,
   the row says 1851 only if the clock started when the text appeared. If the clock starts at the
   first key, every first row says 0 and reading time is lost.
   Suggested default: the caller (T1.5) gives the recorder a start value on the browser's
   performance clock (the same clock as `event.timeStamp`) when the block becomes active, and
   every stored time is `event.timeStamp` minus that value.

4. **Where does T1.4 stop and T1.6 (EventBuffer) begin, for key-ups and the 2-second rule?** Does
   T1.4 hand out a row at keydown and then report the key-up separately when it arrives (Figure 5
   `completeDwell(seq, tUp)`), leaving the 2-second "send without key-up" timer to T1.6? And if a
   key-up arrives after the row was already sent, should the recorder still report it (the server
   can fill it in once via `record_key_up`) or drop it?
   In plain terms: you hold `a` for 2.5 seconds. At 2 seconds the row is sent with no release time
   (case q). At 2.5 seconds the release arrives. Either it is passed on and the stored row gets
   dwell 2500 (which the daily check flags as a stuck key), or it is thrown away and the row keeps
   "release unknown" forever.
   Suggested default: T1.4 reports the row at keydown and every matching key-up whenever it
   arrives; the 2-second timer, batching and sending are T1.6; late key-ups are passed on, not
   dropped.

5. **Where does T1.4 stop and T1.5 (TypingSurface) begin, for listeners, blur and default browser
   actions?** Does the recorder attach its own `window` listeners, or is it fed events through
   `onKeyDown`/`onKeyUp` (Figure 5) plus blur/focus calls from T1.5? Who calls `preventDefault`
   (for example so Space does not scroll the page)?
   In plain terms: T1.5's title includes "pause on blur", and D24 says the browser marks the next
   key after a blur. Someone must notice "the window lost focus" and someone must remember "the
   next key gets the flag". Testing is simpler if the recorder only receives events and never
   touches `window` itself.
   Suggested default: the recorder is fed events and blur/focus notifications by the caller and
   never touches `window` or `document`; it drops keys between blur and focus and sets
   `after_pause` on the next recorded row. T1.5 attaches the listeners, calls `preventDefault`,
   shows the pause and runs the idle rule.

6. **If the first key after returning to the window is not recorded, does the pause flag wait for
   the next recorded key?** D24 puts the flag on "the first keystroke after the window regains
   focus", and answer 11c covers a Backspace. It does not cover a first keydown that is filtered
   (Shift, Cmd, a repeat) or ignored (the block is already done).
   In plain terms: you Cmd-Tab back to the page, your thumb is still on Cmd, then you type `h`.
   The first keydown seen is Cmd (dropped). If the flag is "used up" on Cmd, `h` is unflagged
   and the pair before it may enter the speed statistics even though you were away.
   Suggested default: the flag waits and goes on the first row actually recorded after the focus
   returns, whatever key that is.

7. **Are Space and Backspace with Shift held recorded or dropped?** Section 12.1 says "Shift is
   allowed but not needed in v1"; answer 9d says "Uppercase/Shift input is out of scope entirely
   ... filtered upstream by the recorder". Shift+letter is uppercase and is dropped either way;
   Shift+Space still gives `" "` and Shift+Backspace still gives `"Backspace"`.
   In plain terms: you brush Shift by accident (or out of habit) just as you hit the space bar in
   "the small". If that space is dropped, the cursor does not move and your next letters all land
   one position early, a cascade of errors caused by a key the screen never showed. If it is
   accepted, it counts like a normal space.
   Suggested default: decide by the character only. Accept `" "` and `"Backspace"` even with Shift
   held; drop any uppercase letter; Ctrl, Meta and Alt still drop everything.

8. **When a key is pressed again while its previous press never got a key-up, which press does the
   next key-up belong to?** Dwell pairing is by physical key (`e.code`). If a key-up was lost, the
   map still holds the old press when the same key is pressed again.
   In plain terms: you type `n` at 100 ms but its release is lost (for example you switched windows
   while holding it). Later you press `n` again at 400 and release at 470. If the release is matched
   to the newest press, dwell is 70 and the old row stays "release unknown". If matched to the
   old press, the old row gets a false dwell of 370 and the new one gets none.
   Suggested default: a new press of the same physical key replaces the old open entry; the old row
   keeps no release time; a key-up always pairs with the most recent press of that key.

9. **Must the tests use real `KeyboardEvent` objects (which means adding jsdom or happy-dom), or may
   they use plain objects with the same fields?** The acceptance says "synthetic KeyboardEvents".
   Vitest here runs in Node, where `KeyboardEvent` does not exist (verify), and T0.2 answer 5 left
   adding a DOM environment to T1.3/T1.4. A real `KeyboardEvent` also sets its own `timeStamp`, so
   a test cannot simply say "pressed at 100 ms" (verify).
   In plain terms: a test wants "press `t` at 100, press `h` at 160, release `t` at 195". With plain
   objects that is easy and needs no new package. With real browser events it is closer to the
   real thing but needs a new dev dependency and a workaround to set the times.
   Suggested default: no new dependency. The recorder accepts only the fields it reads (`key`,
   `code`, `repeat`, `ctrlKey`, `metaKey`, `altKey`, `shiftKey`, `timeStamp`), typed as a subset of
   `KeyboardEvent`, and tests pass plain objects of that shape. A DOM environment waits for T1.5's
   component tests.

10. **Should the recorder ignore events not generated by a real keyboard (`isTrusted` false)?**
    Browser events created by a script are marked untrusted.
    In plain terms: rejecting them would stop a stray script or extension from inserting fake
    keystrokes, but it would also reject the test events of T1.4 and the scripted keystrokes T2.10
    plans to use ("Dev-only pipeline test using scripted keystrokes").
    Suggested default: no `isTrusted` check; the app is local-only (D06, D19), so the risk is low.
