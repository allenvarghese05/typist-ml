# T4.5 Brief — Debrief page: Shows arm mapping only after retest

*Analyst brief. Facts only; no design or implementation.*

## 1. Task

- **ID:** T4.5
- **Title:** Debrief page
- **Acceptance criteria:** Shows arm mapping only after retest

*(Copied word for word from `docs/design/Typist-ML_Technical_Design.pdf`, Section 16, page 38).*

---

## 2. Why it matters

- **Culmination of the participant study lifecycle (§11.1, §11.3):**
  Task T4.5 delivers the final screen of the participant study flow (Design Doc §11.1, Figure 10: "What a participant sees from first visit to debrief"). Following enrollment, baseline testing, 10 practice sessions, and post-practice retest sessions, the Debrief page brings closure to the participant's 14-day study participation.
- **Enforces experimental blinding and scientific validity (D18, §3.2, §11.3, §18):**
  Typist-ML is conducted as a randomized single-blind experiment. Throughout the 10 practice days, blocks are presented anonymously as "Block 1", "Block 2", "Block 3", and "Block 4" without disclosing training methods. Revealing the arm mapping prematurely (e.g. during baseline, assignment, practice, or early retest) would induce demand characteristics, conscious compensation, and expectation bias, invalidating the within-person comparison.
- **Answers the core participant curiosity via the "Arm Reveal" (§3.2, §11.3):**
  Section 3.2 specifies the post-retest debrief: *"Show weak bigrams, changes, and the arm mapping (5 minutes)"*. Section 11.3 defines the screen elements: *"Weak bigrams, baseline versus retest per set, arm reveal"*. The Debrief page unmasks which experimental generator (Control, Heuristic, Markov, or LLM) was assigned to each set and block.
- **Delivers personalized, transparent feedback on typing progress (D01, D05, D19, §3.5):**
  Participants see how their weak bigrams were distributed across balanced sets, how pooled error rates and median inter-key intervals (IKIs) changed between baseline and retest ($d(s)$ and $c(s)$), and whether targeted arms achieved a targeting effect beyond the held-out control set ($E(s)$ and $F(s)$).
- **Final task of Milestone M4 and the entire technical design (§16):**
  T4.5 completes Milestone M4 (Dashboard and write-up) and represents the final developmental milestone task specified in Section 16 of the technical design document.
- **What breaks if it is wrong:**
  - **Blinding breach:** If `/results/:pid` displays the arm mapping before the participant completes the retest phase (e.g. while status is `enrolled`, `baseline`, `assigned`, `practice`, or `retest`), participant blinding is broken.
  - **Acceptance criteria violation:** The single acceptance criterion is *"Shows arm mapping only after retest"*. If arm mappings are visible prior to `status == "done"`, the acceptance criterion fails.
  - **Broken participant flow / unhandled errors:** If a participant visits `/results/:pid` mid-study and encounters an unhandled HTTP 409 crash or a blank screen instead of a helpful locked state explaining that debrief unblinds after retest, user experience is degraded.
  - **Inconsistent statistics:** If debrief calculations diverge from the pre-registered analysis plan (`docs/analysis-plan.md`, D20, D23) or the dashboard (T4.2), reporting contradicts published study figures.
  - **Builder bias unflagged:** If builder data is shown without the unblinded badge (`is_builder = true`, `is_blinded = false`), external observers may assume standard blinded participant conditions.

## 3. Governing decisions

| ID | Decision (Design Doc §2 or ADR) | What it forces on T4.5 |
|---|---|---|
| **D01** | *"Within-person design: Each participant's weak bigrams are split into 4 sets; each set is assigned one arm"* | Debrief displays results for one participant as a within-person comparison. Outcomes are never pooled across participants. |
| **D02** | *"Control set: Control bigram set with no targeted drills, plus a random-text block of equal length each session"* | The Debrief page must clearly identify and highlight the held-out control set as the baseline comparison for targeting effects. |
| **D03** | *"Arms: control, heuristic, markov, llm (as in the guide)"* | Arm reveal unmasks all 4 arms (or 2 arms in two-set contingency mode). |
| **D04** | *"Assignment: Rank weak bigrams, deal into sets in snake order, map sets to arms with a seeded shuffle, freeze before practice; Never mid-pilot"* | Bigrams and arm assignments shown in the debrief must be read from frozen `bigram_assignment` records. |
| **D05** | *"Outcomes: Primary: change in pooled error rate per set minus change in the control set. Key secondary: same for median inter-key interval"* | Debrief displays per-set error rate changes $d(s)$ and targeting effects $E(s)$, plus median IKI changes $c(s)$ and timing targeting effects $F(s)$. |
| **D06** | *"Deployment: Local-only on the MacBook Pro (M1 Pro)"* | Debrief runs locally in the browser against the local API and SQLite database. No external network telemetry. |
| **D07** | *"Frontend: Vite 8, React 19, TypeScript (strict), pnpm, Biome, Vitest"* | Web components reside in `apps/web/src/features/debrief/` (or `features/results/`) under strict TypeScript and tested via Vitest. |
| **D08** | *"Backend: Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite in WAL mode, Typer CLI, ruff, pyright, pytest"* | Backend analysis endpoints reside in `services/api/src/typist/api/routers/analysis.py`. |
| **D12** | *"Live nudges: Not during the pilot; shown in the post-retest debrief"* | Practice typing was unguided by live nudges; debrief provides the post-study diagnostic feedback. |
| **D13** | *"Tracked bigrams: English, QWERTY, lowercase a to z and space. Tracked bigrams are letter-letter only"* | Debrief weak bigrams and set outcomes consist strictly of letter-letter bigrams. |
| **D14** | *"Error definition: First-attempt substitution at position j, counted only when position j-1 was correct on first attempt. Backspace allowed"* | Bigram attempts and errors displayed in debrief adhere to first-attempt attribution. |
| **D15** | *"Inter-key interval (IKI): Press to press. Bigram (a, b) gives an IKI sample only for a clean, correct pair (b.seq == a.seq + 1) and not after pause"* | Timing metrics in debrief reflect clean, unpaused, correct keystroke pairs. |
| **D18** | *"Blinding: Blocks are labelled Block 1 to 4. The second participant is not told the mapping. The builder is flagged as unblinded"* | Arm mapping is strictly hidden during the study and revealed only after retest. Builder data is explicitly flagged as unblinded. |
| **D19** | *"No cloud, no WASM; Guide honesty rules"* | Results are presented descriptively; no statistical significance claims or p-values. |
| **D20** | *"Pre-registration: Commit docs/analysis-plan.md with the date before the first practice session"* | Statistical summaries in debrief adhere to pre-registered definitions (Jeffreys prior, bootstrap resamples, difference-in-differences). |
| **D21** | *"just check: lint, format-check, types, test, build"* | All new frontend code, routes, and tests must pass `just check` cleanly. |
| **D23** | *"Analysis plan exclusions: (a) Pauses excluded from IKI only; (b) Abandoned sessions excluded from outcome analysis; (c) Bigrams with fewer than 20 retest attempts dropped from both baseline and retest"* | Retained vs. dropped bigrams and exclusions are disclosed in the debrief summary. |
| **D26** | *"Session WPM time base, and idle limit: WPM = correct first-attempt characters / 5 / elapsed minutes; 10s idle abandons block"* | Overall session WPM and accuracy progression shown in debrief follow D26. |

## 5. Inputs and outputs

### 5.1 Inputs
- **Browser Route Hash:**
  `#/results/:pid` (or `#/results?participant=:pid`), matching Design Doc §11.3 screen route `/results/:pid`.
- **API Responses:**
  - `fetchParticipantResults(participantId)`: calls `GET /api/v1/analysis/participants/{participant_id}`.
    - Status 200: Returns `ParticipantResults` (weak bigram sets, arm identities, baseline/retest error rates, median IKIs, credible intervals, exclusions).
    - Status 409: Returns `ParticipantNotDoneError` (`status: "not-done"`), indicating the participant is still in progress (`enrolled`, `baseline`, `assigned`, `practice`, `retest`) or unassigned.
    - Status 404: Returns `status: "not-found"`.
  - `fetchParticipants()`: calls `GET /api/v1/participants` to resolve participant alias, current status, and builder/blinded flags when the analysis endpoint returns 409 or when no `participantId` is supplied in the URL.

### 5.2 Outputs
- **Rendered Debrief Page (`DebriefPage` / `ResultsPage`):**
  - **Locked View (when `status != "done"`):**
    - Displays clear participant identity (alias, status badge).
    - Informs the participant that the study is actively in progress.
    - Explicitly communicates that arm mappings and debrief findings remain blinded until all retest sessions are completed (D18).
    - Shows zero arm names, zero block-to-arm mappings, and zero targeting statistics.
  - **Revealed View (when `status == "done"`):**
    - **Header & Blinding Status:** Displays alias, completion status, and builder/blinded badge (`is_builder = true` flagged as unblinded builder; peer flagged as blinded participant).
    - **Debrief Narrative:** Explains the experimental structure: weak bigrams were identified in baseline, split into 4 matched sets, and trained across 4 different arms masked as Blocks 1 to 4 during practice.
    - **The Arm Reveal:** Explicitly maps each set / block (A, B, C, D) to its true experimental generator (Control, Heuristic, Markov, LLM).
    - **Weak Bigrams by Set:** Lists the targeted bigrams assigned to each set, identifying any retained vs. dropped bigrams (<20 retest observations per D23).
    - **Per-Set Primary Outcomes (Error Rate):** Baseline vs. retest error rates ($d(s)$), targeting effect vs. control ($E(s)$), and 95% Jeffreys Beta credible intervals.
    - **Per-Set Secondary Outcomes (Timing):** Baseline vs. retest median IKI ($c(s)$), timing targeting effect vs. control ($F(s)$), and bootstrap confidence intervals.
    - **Overall Progression:** Baseline session WPM and accuracy vs. retest session WPM and accuracy.

## 6. Constraints

- **Strict Blinding Protection (D18, §16):**
  Under no circumstances may the arm mapping or generator identities be presented to a participant or rendered on the page before retest completion (`participant.status == "done"`).
- **No Cloud, No WASM, Local-Only (D06, D19):**
  All assets, data fetching, and state management run purely client-side against the local FastAPI instance. No external fonts, analytics, or remote calls.
- **Pre-registered Statistical Integrity (D20, D23, §15.1):**
  Debrief metrics must reflect pre-registered analysis definitions. Difference-in-differences sign conventions ($d(s) - d(\text{control})$ and $c(s) - c(\text{control})$) must match `services/api/src/typist/services/analysis.py`.
- **Honesty Rules (D19, §18):**
  No hypothesis significance tests, no p-values, and no superiority claims for small sample sizes ($N=1$ or $N=2$).
- **Tooling and Quality Gate (D07, D21):**
  TypeScript strict mode, React 19 idiomatic components, Biome formatting and linting, Vitest component test coverage. Must pass `just check` without warnings or failures.

## 7. Edge cases

1. **Participant in `practice` phase visits `#/results/:pid`:**
   *Example:* Participant `p-peer` has completed 6 of 10 practice days (`status = "practice"`).
   *Behavior:* Backend returns 409 Conflict. Page displays locked status: "Debrief locked. Practice in progress (Session 6 of 10). Arm mappings and targeting results will unlock after retest." No arm names are displayed.
2. **Participant in `retest` phase (1 of 2 completed) visits `#/results/:pid`:**
   *Example:* Participant has completed form B session 1 of 2 (`status = "retest"`).
   *Behavior:* Status is not `"done"`. The page remains locked: "Debrief locked. Retest phase in progress (Session 1 of 2 completed)." Arm mappings remain hidden.
3. **Participant in `baseline` or `assigned` visits `#/results/:pid`:**
   *Example:* Participant `p-new` has finished baseline, but practice has not begun (`status = "assigned"`).
   *Behavior:* Backend returns 409 Conflict (`ParticipantNotDoneError`). Page shows locked state: "Debrief locked. Baseline complete; study has not concluded."
4. **Participant completes final retest session:**
   *Example:* Participant finishes retest session 2; `session_stats.py` transitions `participant.status` to `"done"`.
   *Behavior:* Page reloads or fetches analysis successfully (HTTP 200). Unlocks the full debrief view: narrative, arm reveal, weak bigram sets, and per-set error rate and IKI changes.
5. **Builder participant visits debrief before retest:**
   *Example:* Participant `p-builder` has `is_builder = true`, `is_blinded = false`, but `status = "practice"`.
   *Behavior:* Acceptance criteria specifies: "Shows arm mapping only after retest". Backend returns 409 because status is not `"done"`. UI shows the locked debrief state.
6. **Navigation to debrief without a participant ID (`#/results`):**
   *Example:* User types `#/results` into the address bar or clicks a navbar link.
   *Behavior:* If participants exist, page renders a participant selector or selects the first available participant. If no participants exist, displays an empty state.
7. **Participant ID does not exist (`#/results/invalid-uuid`):**
   *Example:* URL contains a non-existent participant ID.
   *Behavior:* API returns 404. UI displays an error alert: "Participant not found" with navigation back to the participant picker or home.
8. **Participant withdrew from study (`status = "withdrawn"`):**
   *Example:* Participant withdrew before completing retest.
   *Behavior:* UI displays: "Participant study withdrawn; debrief outcomes are unavailable."
9. **Dropped bigrams due to low retest attempts (<20 observations):**
   *Example:* Bigram `an` in Set B received only 15 attempts during retest.
   *Behavior:* Per D23(c), debrief notes that `an` was dropped from pooled set comparisons, displaying it clearly under dropped bigrams while presenting pooled stats for retained bigrams.
10. **Two-set contingency mode (Cut-line, D03):**
    *Example:* Pilot ran in 2-set mode (Control and Heuristic).
    *Behavior:* Debrief dynamically handles 2 sets (Sets A and B) without throwing errors expecting 4 sets.

## 8. Risks

1. **Client-side arm leakage via unauthorized API endpoints:**
   If the debrief component attempted to query `BigramAssignment` or admin endpoints (`/admin/participants/{pid}/assign`) to display bigram names before status is `"done"`, arm mappings would leak in the browser network tab.
   *Mitigation:* The frontend must strictly query `/analysis/participants/{pid}` (which requires `status == "done"`) and `/participants` (which does not expose arm mappings).
2. **Hash route parsing collisions or inconsistencies:**
   Design Doc §11.3 specifies route `/results/:pid`. If `parseHash` in `useHashRoute.ts` only expects `#results` or strictly formatted paths, navigation from different links could misroute to `demo`.
   *Mitigation:* Ensure `parseHash` robustly matches `^#\/results(?:\/([^?]+))?(?:\?(.*))?$` and supports query parameter fallback (`?participant=...`).
3. **Duplication of outcome visualization logic with Dashboard:**
   `DashboardPage` already features an `OutcomesTab` displaying similar tables and `IntervalPlot` charts. Rebuilding these from scratch could cause visual and behavioral drift.
   *Mitigation:* Share visual components or utility formatters (`formatPercent`, `formatRate`, `formatMs`, `IntervalPlot`) between the dashboard and debrief features.
4. **Poor participant comprehension of difference-in-differences:**
   Raw statistics like $E(s) = d(s) - d(\text{control})$ and $F(s) = c(s) - c(\text{control})$ can be confusing without contextual explanation.
   *Mitigation:* The debrief page must provide plain-language explanations alongside the metrics (e.g. explaining that a negative targeting effect indicates error or time reduction beyond standard un-targeted practice).

## 10. Owner answers (2026-10-31)

1. **Route naming in `useHashRoute.ts`:**
   - **Answer:** Name the route type `debrief` (`{ readonly name: "debrief"; readonly participantId?: string }`). In `parseHash`, match `^#\/results(?:\/([^?]+))?(?:\?(.*))?$` and `^#\/debrief(?:\/([^?]+))?(?:\?(.*))?$` so both URLs route seamlessly to the debrief page.
   - **Source:** Design doc §11.3 (`/results/:pid`, screen `Debrief`), existing `useHashRoute.ts`.
   - **Reasoning:** Conforms to design doc URL naming while giving descriptive TypeScript route typing and handling query parameters.

2. **Top-level navigation bar link:**
   - **Answer:** Add a `Debrief` link (`#/results`) to the header navigation in `App.tsx` alongside Typing Demo, Admin Dashboard, and Dashboard. Also add a direct "Debrief" link on participant rows in `AdminPage` for quick navigation.
   - **Source:** Design doc §11.3, existing `App.tsx` and `AdminPage.tsx`.
   - **Reasoning:** Makes the debrief view easily discoverable in the demo app while preserving direct participant link flows.

3. **Fallback behavior for bare `#/results` without `:pid`:**
   - **Answer:** Render a participant selector dropdown at the top of the debrief page (matching `DashboardPage`), automatically defaulting to the first completed participant (or first enrolled participant if none are done).
   - **Source:** Established pattern in `DashboardPage.tsx` and `AdminPage.tsx`.
   - **Reasoning:** Prevents dead ends and allows easy participant switching.

4. **Visual staging of the "Arm Reveal":**
   - **Answer:** When `status === "done"`, display an "Arm Reveal" section prominently that maps each set / block to its training arm (`Control (held-out)`, `Dictionary Heuristic`, `Markov Chain`, `On-device 1B LLM`), with a toggle button allowing the participant to mask/unmask the identities. When `status !== "done"`, the entire debrief page displays a locked banner explaining that blinding is in effect until retest completion, rendering zero arm names or mappings.
   - **Source:** Design doc §3.2, §11.3, D18, acceptance criteria.
   - **Reasoning:** Maximizes educational payoff and transparency for completed participants while strictly enforcing experimental blinding before retest.

5. **Persistent weakness advice / Nudges (D12):**
   - **Answer:** Include a post-retest diagnostic feedback card ("Targeting Diagnostic & Next Steps") listing any assigned bigrams that still showed elevated error rates ($> 5\%$) or higher latencies at retest, fulfilling D12's directive for debrief-stage nudges without impacting study telemetry.
   - **Source:** Decision D12, Design doc §3.2.
   - **Reasoning:** Delivers on the design doc's promise of post-retest guidance in a clean, non-intrusive advisory card.
