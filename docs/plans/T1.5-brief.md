## 2. Why it matters

What T1.5 enables later:
- **It is the first real React screen** and the glue between the DOM and the telemetry classes. It
  attaches the `window` keydown/keyup/blur/focus listeners, calls `preventDefault`, constructs one
  `KeystrokeRecorder` per block, and routes its rows onward. Everything the participant actually types
  into `keystroke_events` flows through this wiring (sections 11.3, 12.1; D24; T1.4 owner answer 5).
- **It owns the live display** (section 6.2: "The browser computes only what it needs for live
  display (current WPM, error highlight)"). The red-highlight behaviour of section 11.3 and the
  per-position display state that T1.3 explicitly left to T1.5 (T1.3 owner answer 5) are built here.
- **It establishes the DOM test environment** for the whole web app. T0.2 deferred jsdom/happy-dom
  and component tests to "T1.5 when there's an actual component" (T0.2 owner answers 4, 5).
- **It builds the idle rule and block lifecycle** (D26): 5 s warning, 10 s abandon-and-restart,
  blur-as-idle, and the still-undesigned persistence of abandoned/restarted blocks.
- **It feeds T1.6** (EventBuffer + `POST /blocks/{bid}/events`) by implementing or wiring the
  `KeystrokeSink` the recorder emits to, and consumes the block-start time (`POST /blocks/{bid}/start`
  per section 14).

What breaks if it is wrong:
- **A full re-render per keystroke** defeats section 9.2's whole reason for `useSyncExternalStore` and
  fails the acceptance criterion; at 600 characters per block (3.3) typing would feel laggy.
- **React state updates inside the handler** violate section 12 ("no React state updates inside [the
  handler], no allocation-heavy work, no network calls") and inflate `handler_ms` / `dispatch_lag_ms`
  (the engineering overhead claim, 12.5, 3.5).
- **Missing or doubled `preventDefault`/listeners** (e.g. StrictMode double-mount) would scroll the
  page on Space, delete elsewhere on Backspace, or record every key twice.
- **Blur not wired to `onBlur`/`onFocus`** loses the one fact that cannot be recomputed later
  (`after_pause`, D24) and breaks pause-on-blur (11.3) and blur-as-idle (D26).
- **A wrong block-start origin** passed to the recorder makes every `t_down_ms` wrong (T1.4 owner
  answer 3: every stored time is `event.timeStamp` minus `blockStartMs`).
- **A badly designed abandon/restart** could violate the append-only rule or the
  `UNIQUE (session_id, block_index)` constraint (D26 consequences).

## 4. Current state

### 4.1 Merged telemetry the surface must drive (verbatim signatures)

`apps/web/src/telemetry/KeystrokeRecorder.ts`:
```ts
export type KeyInput = Pick<
  KeyboardEvent,
  "key" | "code" | "repeat" | "ctrlKey" | "metaKey" | "altKey" | "shiftKey" | "timeStamp"
>;

export interface KeystrokeRecorderOptions {
  readonly targetText: string;
  readonly blockStartMs: number;   // same clock as KeyboardEvent.timeStamp (T1.4 answer 3)
  readonly sink: KeystrokeSink;
  readonly now?: () => number;      // defaults to () => performance.now()
}

export class KeystrokeRecorder {
  constructor(options: KeystrokeRecorderOptions) // throws RangeError on non-finite blockStartMs or bad targetText
  isDone(): boolean
  onKeyDown(e: KeyInput): void
  onKeyUp(e: KeyInput): void
  onBlur(): void
  onFocus(): void
}
```
A real `KeyboardEvent` is assignable to `KeyInput`. The recorder "never touches window or document"
(T1.4 answer 5): the caller (T1.5) attaches listeners and forwards events and blur/focus. `onKeyDown`
and `onKeyUp` are the only places preventDefault would matter, and preventDefault is T1.5's
(T1.4 plan contract: "Pass the real `KeyboardEvent`; `preventDefault` is T1.5's.").

From T1.4-plan.md, the interface contract for T1.5 (verbatim rows):
- "`new KeystrokeRecorder({ targetText, blockStartMs: performance.now(), sink })` when the block
  becomes active | One recorder per block (a restarted block gets a new one: `seq` from 0, new
  origin)."
- "`onKeyDown(e)`, `onKeyUp(e)` from its `window` listeners | Pass the real `KeyboardEvent`;
  `preventDefault` is T1.5's."
- "`onBlur()`, `onFocus()` | From `window` blur/focus. Call `onBlur()` right after construction if the
  page is not focused."
- "`isDone()` | True once the cursor reached the end of the target."

`apps/web/src/telemetry/types.ts` (the sink T1.5 must provide or wire, verbatim):
```ts
export interface KeystrokeRow {
  readonly seq: number; readonly key: string; readonly code: string;
  readonly t_down_ms: number; readonly t_up_ms: number | null; readonly dwell_ms: number | null;
  readonly iki_ms: number | null; readonly target_index: number;
  readonly expected_char: string | null; readonly outcome: Outcome;
  readonly first_attempt: boolean | null; readonly after_pause: boolean;
  readonly handler_ms: number; readonly dispatch_lag_ms: number;
}
export interface KeyUpUpdate { readonly seq: number; readonly t_up_ms: number; readonly dwell_ms: number; }
export interface KeystrokeSink {
  onRow(row: KeystrokeRow): void;      // called synchronously inside the key handlers; must be cheap and must not throw
  onKeyUp(update: KeyUpUpdate): void;
}
export type Outcome = "correct" | "error" | "backspace";
```
Note (from T1.4-plan interface table): the sink is "implemented by T1.6's EventBuffer". The row's
cursor fields (`target_index`, `expected_char`, `outcome`, `first_attempt`) are the only per-key
signal the recorder exposes to anything downstream — the recorder does **not** expose the cursor's
current index or a per-position outcome array to a display layer. `TextCursor` is private inside the
recorder (`readonly #cursor`), so the surface cannot read it directly (open question 2).

`apps/web/src/telemetry/TextCursor.ts` (what the display concepts map to):
```ts
export class TextCursor {
  readonly target: string;
  constructor(target: string)   // throws RangeError unless /^[a-z ]+$/
  get index(): number           // 0 .. target.length
  isDone(): boolean
  type(char: string): TypedStep | null
  backspace(): BackspaceStep | null
}
```
T1.3 owner answer 5 (verbatim): "Per-position display state: confirmed, out of scope for T1.3.
TextCursor stays limited to alignment; what's currently shown on screen (for the red-highlight
behavior in section 11.3) is T1.5's store to own."

## 5. Inputs and outputs

Inputs:
- The block to type: its `target_text` (a to z / space, `/^[a-z ]+$/`), its `block_id`, and its arm
  label shown only as "Block N" (3.3, 8.1). In production these come from the session plan
  (section 14 `GET /sessions/{sid}` / `POST /participants/{pid}/sessions`), which has no endpoint yet
  (open question 3). For tests, props/fixtures.
- Browser `KeyboardEvent`s on `window` (keydown, keyup) while the block is active and focused (12.1),
  and `window` blur/focus events.
- A block-start time on the performance clock (for `blockStartMs`), ideally tied to
  `POST /blocks/{bid}/start` (14) — endpoint not built (open question 6).
- A clock for the idle timers (D26) and for display WPM elapsed time (D26).

Outputs:
- Rendered DOM: the target text in monospace, the whole block visible, cursor position, wrong
  characters in red left in place until Backspace, a progress bar, the block label, a pause overlay
  on blur, an idle warning at 5 s (11.3, D26).
- `KeystrokeRow`s and `KeyUpUpdate`s emitted by the recorder into the `KeystrokeSink` the surface
  wires up (to T1.6's EventBuffer when it exists; to a stand-in otherwise — open question 7).
- Display state driven through `useSyncExternalStore` (9.2): at minimum the data the text/cursor/
  highlight render needs, updated without a full re-render per key.
- Block lifecycle signals: block start, block complete (`isDone()` true), block abandoned (10 s
  idle) and its restart (D26) — persistence target undecided (open questions 4, 5).
- Files (section 7 layout): a `TypingSurface` under `apps/web/src/features/session/`, likely a display
  store module, component tests under the web app, and almost certainly `package.json` /
  `pnpm-lock.yaml` / `vite.config.ts` changes to add and select a DOM test environment and a testing
  library (open question 9). Possibly `services/api` migration 0002 if the abandon/restart schema is
  built here (open questions 4, 5).

## 6. Constraints

- **No full re-render per key; no React state updates in the handler** (9.2; 12.5 tail). Rendering
  flows through the external store. The handler must stay cheap (handler p95 under 1 ms is the overhead
  target, 12.5) and must not allocate heavily or do network I/O.
- **`useSyncExternalStore` is named in the acceptance context** (title + 9.2): the chosen store
  mechanism is this React hook.
- **The recorder stays React-free** (6.1). The surface may not push React into
  `KeystrokeRecorder`/`TextCursor`.
- **preventDefault on handled keys** so Space does not scroll and Backspace does not navigate/delete
  elsewhere (12.1); but only on keys the recorder handles.
- **Listen on `window`, only while a block is active and focused** (12.1). Blur → `onBlur()`, focus
  → `onFocus()`; call `onBlur()` right after construction if the page is not focused (T1.4 contract).
- **One recorder per block**, new `seq` from 0 and new origin on restart (T1.4 contract; D26).
- **Append-only data** (6.2, CLAUDE.md): abandoned-block rows are kept; the restart must not break
  `UNIQUE (session_id, block_index)` (D26).
- **Display stats only in the browser** (6.2, CLAUDE.md): no bigram attribution, no authoritative
  WPM/accuracy. Display WPM, if shown, uses elapsed time with pauses included (D26).
- **Config, not literals** (17.1): 5 s / 10 s idle thresholds, 2000 ms pause, block length are
  experiment/display parameters; where they live is a design choice (D26, `experiment_config` has
  `block_chars`).
- **Platform:** CI runs on Linux; the real typist is on macOS (D06). Component tests must pass
  headless in CI. No mlx, nothing Apple-Silicon-specific.
- **Tooling gate (D21):** `biome ci .`, `biome format .`, `tsc -b`, `vitest run`, `vite build` — the
  last means the component ships in the production bundle. Any new dependency updates
  `pnpm-lock.yaml` (lockfile is source of truth); installs may be an owner-run step in the sandbox.
- **Strict TS + Biome:** no `any` without a comment, `noUncheckedIndexedAccess`, `erasableSyntaxOnly`,
  `verbatimModuleSyntax`, `a11y: error` (the typing field needs accessible markup), `noExplicitAny`.
- **Accessibility:** `a11y: error` in Biome will flag the interactive typing surface (focus
  management, labels, no silent `div` click handlers).
- **No new cloud/analytics/telemetry; no GPL/Monkeytype copying** (D19, CLAUDE.md).
- **Scope hygiene:** one task per PR, branch per task, conventional commits; never push to main;
  never merge.

## 7. Edge cases

1. **StrictMode double mount** (T0.2 edge case 25): `main.tsx` wraps `<App/>` in `<StrictMode>`,
   which mounts/unmounts/remounts and runs effects twice in development. Listeners registered in an
   effect without cleanup would attach twice and record every key twice with the same `timeStamp`.
   Example: press `a` once → two `seq 0` rows.
2. **Focus not on the window at block start.** The participant alt-tabs in after the block renders.
   The recorder must be told it is blurred (T1.4 contract: "Call `onBlur()` right after construction
   if the page is not focused"), or the first key would be recorded without `after_pause`.
3. **Blur while a key is held.** Hold `h`, click away: the keyup goes to another window and is lost;
   `h`'s row stays `t_up_ms` null (T1.4 edge case 13). Blur also counts as idle (D26): a 10 s blur
   abandons the block.
4. **Idle at exactly 5 s / 10 s.** No keypress for 5 s → warning while the timer keeps running; 10 s
   → abandon-and-restart (D26). Example: last press at t=0; warning fires ~t=5 s; abandon ~t=10 s.
   What "no keypress" means (any key, or only recorded rows) and whether filtered keys reset the
   timer is not stated (open question 10).
5. **Resume typing during the 5 s warning (before 10 s).** The block must continue, the timer resets,
   the warning clears; no abandon. The next recorded row still carries `after_pause` only if a blur
   happened (D24) — a mere long pause is not `after_pause` (it is derived from timestamps, D24).
6. **Abandon-and-restart collides with the schema.** `session_blocks` has no status and
   `UNIQUE (session_id, block_index)` blocks a second row with the same index (D26 consequence). A
   restart needs either a status column, a new table, or a different key — undesigned (open q. 4, 5).
7. **Block already done, extra keys.** After the final character, `recorder.isDone()` is true; further
   keys produce no row (T1.4 edge case 20). The surface must stop (show complete / move on) and must
   not keep the idle timer running past completion.
8. **Wrong characters left in place (11.3).** Type `teh` for target `the`: positions 1 and 2 show red,
   the cursor is at index 3; Backspace to index 1 and retype. The display store must show red at the
   mis-typed positions until corrected, not auto-advance or auto-fix. The recorder exposes only the
   per-key `outcome`/`target_index` (not a live per-position array), so the surface must build its own
   (open question 2).
9. **600-character block.** Real blocks are 600 chars (3.3), not 300. The acceptance says "300
   characters"; the component must stay smooth at the real length too. "The whole block visible"
   (11.3) means the full 600 chars render — a large DOM that must not re-render per key.
10. **Rapid rollover.** Keys overlap (fixture cases k/l); keyups arrive out of order. The recorder
    handles pairing; the surface must still render the forward progress correctly and not stall on a
    missing keyup.
11. **Space scrolls / Backspace navigates.** Without `preventDefault`, Space scrolls the page and
    Backspace can trigger browser back / delete in a field (12.1). Only handled keys get
    `preventDefault`; Tab/Cmd-Tab/arrows must still work for navigation and focus.
12. **IME / dead keys / non-Latin layout.** Dropped by the recorder's a-to-z rule (T1.4 edge cases
    7, 8), but the surface should not show spurious cursor movement for them.
13. **Autocorrect / spellcheck / autocapitalize.** The input surface must disable these (11.3: "no
    autocorrect or spellcheck"); on a `contenteditable`/`textarea` these are on by default.
14. **Paste / drag-drop / context menu.** A paste would insert many characters at once with no
    keydowns; the design never mentions it. Whether the surface blocks paste is not stated.
15. **Window never focused in a headless test.** jsdom/happy-dom focus and `KeyboardEvent.timeStamp`
    semantics differ from a real browser; `timeStamp` on a constructed event may be 0 (T1.4 edge case
    29). Component tests must control time deterministically.
16. **`useSyncExternalStore` snapshot identity.** Returning a fresh object/array from `getSnapshot`
    on every call (without memoization) causes an infinite render loop in React 19. This is a known
    hook pitfall the design does not mention (risk, not a decision).
17. **Multiple blocks in one session.** Four blocks per practice session (3.3); the surface is
    reused or remounted per block. Each block is a new recorder, new origin, `seq` from 0 — listeners
    and timers from the previous block must be torn down cleanly (ties to edge case 1).
18. **Progress bar vs. errors.** Progress is by cursor index (characters typed), independent of how
    many are wrong; a block can be "done" with errors still red on screen (TextCursor `isDone()` is
    index-based, not correctness-based).

## 8. Risks

1. **A full re-render per key** (storing cursor state in `useState` and re-rendering the whole 600-char
   text) — directly fails the acceptance criterion and section 9.2. Most likely failure mode.
2. **`getSnapshot` returning a new reference each call** → infinite loop or constant re-render,
   masking the performance win of `useSyncExternalStore`.
3. **React state updates or allocation inside the keydown handler**, inflating `handler_ms` /
   `dispatch_lag_ms` and breaking the overhead claim (12.5).
4. **StrictMode / effect-cleanup bugs** doubling listeners or leaking timers across block changes.
5. **Designing the abandon/restart persistence inside T1.5** without an ADR, touching `services/api`
   and migrations — a scope and process risk (D26 says the schema "is settled first"; CLAUDE.md:
   "One task per PR", "Plan problems go back to the owner").
6. **Pulling in unplanned dependencies** (react-router, TanStack Query, Recharts) — T0.2 owner answer
   2 keeps those with the tasks that first use them. T1.5 likely needs only a DOM test env + a
   testing library, but the exact set is unsettled (open question 9).
7. **Building display WPM/accuracy that drifts from Python** — the browser must stay "display only"
   (6.2, CLAUDE.md); any number shown must be clearly non-authoritative.
8. **preventDefault too broad** (swallowing Tab/Cmd-Tab/arrows) or too narrow (Space scrolls).
9. **No live backend** (no block/session/events endpoints): building the surface against an imagined
   API shape that later diverges from section 14 / generated types.
10. **Subjective acceptance** ("feels instant") with no measurable test, leading to a component that
    passes review but regresses silently later (open question 8).

## 9. Open questions

The design doc does not settle these. They are numbered so the owner can answer by number.

1. **Scope of the idle rule and block lifecycle in T1.5.** D26 says "T1.5 builds the idle warning
   (5 s), the abandon-and-restart (10 s) and blur-as-idle", but also says the abandoned/restarted-
   block persistence "is settled first, when the idle rule is designed (T1.5, or a small dedicated
   task before it)." Does T1.5 include the full idle rule *and* the persistence design/migration, or
   should the persistence be split into a separate task (and if so, is it a blocker for T1.5)?
   In plain terms: T1.5 can show a 5 s warning and a 10 s abandon in the UI, but "abandoned" and
   "restarted" have nowhere to live in the database yet. Either T1.5 also changes the schema, or it
   stops at the UI and leaves the storage to another task.

2. **Where does the surface's display state come from?** Section 9.2 says React subscribes to "it"
   (the recorder) via `useSyncExternalStore`, but the merged recorder exposes only `isDone()` and
   emits `KeystrokeRow`/`KeyUpUpdate` through a sink; its `TextCursor` is private and there is no
   per-position outcome array or current-index getter. T1.3 answer 5 says the per-position display
   state is "T1.5's store to own." Does the surface (a) build a separate display store that observes
   the recorder's row stream, (b) have the recorder gain a React-friendly snapshot/subscribe surface
   (which would risk the 6.1 "no React" boundary — the store can still be a plain class), or (c)
   something else? Which object does `useSyncExternalStore` subscribe to?
   In plain terms: something has to tell React "the cursor is now at position 12 and positions 3 and 7
   are red." The recorder does not expose that today; who holds it?

3. **What does T1.5 integrate against, given no session/block API exists?** Section 14 lists
   `GET /sessions/{sid}`, `POST /participants/{pid}/sessions`, `POST /blocks/{bid}/start|events|
   complete`, but only `/health` is implemented. Should T1.5 render from props/fixtures and a
   stand-in sink (deferring all networking to T1.6 and later), or does T1.5 also build a `client.ts` /
   route / data loading? If the latter, that is a large scope increase and depends on unbuilt
   endpoints.
   In plain terms: there is no screen to route to and no API to fetch a block from. Does T1.5 just
   build the typing widget with its text passed in, or the whole `/session/:id` page and its data
   plumbing?

4. **How are abandoned and restarted blocks stored?** `session_blocks` has no `status` column and
   `UNIQUE (session_id, block_index)` prevents a second row with the same index. D26 says the owner
   "has decided that abandoned and restarted blocks are tracked in the database, through a status
   column or a new table in migration 0002." Which is it — a `status` column on `session_blocks`, an
   attempt/restart counter, or a new table? (This also decides whether `keystroke_events.block_id`
   points at the abandoned block, the restart, or both.)

5. **If migration 0002 is in scope, does it belong in this PR?** CLAUDE.md requires one task per PR
   and keeps Python/migration work separate from the TS surface. If the schema change is needed for
   T1.5's abandon/restart, should it be a prerequisite task (and PR) the owner wants done first?

6. **What is the block-start origin and who supplies it?** The recorder needs `blockStartMs` on the
   performance clock (T1.4 answer 3), and section 14 has `POST /blocks/{bid}/start`. Should T1.5 use
   `performance.now()` at the moment the block becomes active (as the T1.4 plan example shows), tie it
   to the server start call, or both? Does display elapsed time (D26 WPM) use the same origin?
   In plain terms: when the clock "zero" is set decides every `t_down_ms`. Is it the instant the text
   appears in the browser, or a round-trip to the server?

7. **What sink does T1.5 wire up before T1.6's EventBuffer exists?** The recorder needs a
   `KeystrokeSink`. T1.6 implements it. For T1.5 alone, is the sink a no-op/collector (rows discarded
   or kept in memory for the demo/tests), or does T1.5 depend on T1.6 being built first?
   In plain terms: the recorder hands every row to "the buffer", but the buffer does not exist yet.
   What catches the rows during T1.5?

8. **How is "feels instant; no full re-render per key" verified?** There is no numeric threshold in
   the design. Is a test that asserts the text container does not re-render on each key (e.g. a render
   counter / React Profiler, or that `useSyncExternalStore` drives updates) sufficient, plus a manual
   check? Or does the owner want a measured input-latency / handler-cost budget (tying to the 12.5
   "handler p95 under 1 ms" overhead target)?
   In plain terms: how does the reviewer prove it is fast enough, since "feels instant" cannot be
   unit-tested directly?

9. **Which test infrastructure and dependencies does T1.5 add?** T0.2 deferred the DOM test
   environment and component tests to T1.5. Which packages: jsdom vs happy-dom? `@testing-library/
   react` (+ `@testing-library/user-event`, `@testing-library/jest-dom`)? And is the Vitest
   `environment` switched globally to a DOM one, or per-file (keeping the recorder's node tests as-is)?
   Does T1.5 also add the Playwright e2e smoke (17.2, section 7 `e2e/`), or does that stay with a later
   task (T0.2 answer 2 kept Playwright out of T0.2)?

10. **What exactly resets/triggers the idle timers?** D26 says "after 5 s with no keypress" and "10 s
    with no keypress", and "Blur counts as idle." Does "keypress" mean any `keydown`, only recorded
    rows (a to z / space / Backspace), or does a filtered/modifier key also reset the timer? Does the
    timer run on real elapsed time (even while blurred) so that a blur that lasts 10 s abandons the
    block? Confirm the precise trigger and reset conditions.

## Owner answers

2026-10-19

1. **Scope of idle rule and block lifecycle: split.** The idle rule itself (detecting no recorded activity for N seconds, surfacing an abandon/restart signal to the caller) is in scope for T1.5; it is client-side behaviour, no backend needed. Persistence of "this block was abandoned" is a separate task and not a blocker for T1.5. With only a stand-in sink wired up (per Q3), nothing T1.5 builds talks to a real server yet, so there is nothing to persist against. T1.5 emits the abandon/restart event to its sink interface and stops there.

2. **Where display state lives: a new, separate display store that observes the recorder's row stream**, not a store bolted onto the recorder. This is what T1.3's own answer pointed toward ("per-position display state is built in T1.5"). Keeping the recorder a plain, React-agnostic class that only emits rows keeps it unit-testable with plain objects, exactly as T1.3/T1.4 established. `useSyncExternalStore` subscribes to this new display store, not to the recorder directly.

3. **What T1.5 integrates against: render from props/fixtures with a stand-in sink.** Building `client.ts` or real routes against section 14 endpoints that do not exist yet would mean guessing API shapes before they are designed (same reasoning as T0.2 choosing a Vite proxy over guessing CORS needs early).

4 & 5. **Abandoned/restarted block storage: defer entirely.** No schema change in this PR, no migration 0002. Since T1.5 has no real backend wiring there is no row to persist, so deciding "status column vs counter vs new table" now would be designing a schema for a problem not yet concretely hit. **Flagged future requirement for the architect:** append-only `keystroke_events` plus restartable blocks means a restarted block's earlier partial keystrokes can never be deleted, so whichever later task implements this needs a way to distinguish the final completed attempt's rows from an earlier abandoned attempt's rows for the same `block_id`; likely an attempt number becomes part of the block's identity. Note now, do not solve today.

6. **Block-start origin: `performance.now()` captured client-side when the block becomes active**, not tied to `POST /blocks/{bid}/start` (out of scope). The displayed elapsed time uses the exact same origin value as what is stored for keystroke timing: a single clock for both guarantees the number on screen matches the data rather than two independently drifting measurements.

7. **Sink before EventBuffer exists: a no-op/collector sink** (in-memory array or simple log). T1.5 does not depend on T1.6 being built first.

8. **Verifying "feels instant": a structural render-counter assertion** (the top-level surface does not re-render on every keystroke; only the minimal subscribed cell does) plus a manual check. No hard numeric latency assertion in the test suite: jsdom timing is not representative of a real browser, so a "handler p95 under 1 ms" assertion in a component test would measure noise. The real 12.5 budget is the telemetry layer's job (T1.3/T1.4 `overhead.ts`) with real browser measurement.

9. **Test infrastructure: jsdom, not happy-dom.** Add `@testing-library/react`, `@testing-library/user-event` and `@testing-library/jest-dom`. Use a per-file environment pragma (`// @vitest-environment jsdom`), not a global switch, so T1.3's non-DOM tests stay fast and unaffected. No Playwright e2e smoke in T1.5; that is its own later task.

10. **Idle timer activity: only recorded rows count**, not raw `keydown` events and not filtered/modifier-only keys. This mirrors T1.4's `after_pause` principle (only recorded keystrokes matter). The timer runs on real wall-clock elapsed time, so a 10 s blur with zero recorded activity does trigger the idle/abandon path regardless of focus; the rule cares about the user not typing, not window focus specifically.
