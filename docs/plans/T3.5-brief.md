## 2. Why it matters

- **Prerequisite for T3.6 (Pre-registered analysis plan):** Task T3.6 commits the dated analysis plan (`docs/analysis-plan.md`) before the first practice session (D20, §16). The analysis plan pre-registers experimental hypotheses, arm definitions, sample sizes, and tuning parameters. Freezing `experiment_config` in T3.5 provides the hard database-level guarantee that parameters recorded in the analysis plan cannot be silently mutated or retroactively tuned.
- **Integrity of the Randomized Controlled Trial (RCT):** During Days 2 to 11, each participant completes practice sessions where 4 arms are evaluated within-person (D01, §3.2). Background jobs continuously generate practice drills according to the parameters in `experiment_config`. If parameters like `d_min`, `d_max`, `llm_temperature`, `llm_model_id`, or `markov_beta` could change mid-pilot, drills would be generated under divergent conditions across days, destroying the shared fairness gate (D16) and invalidating the trial.
- **Auditability and immutability:** CLAUDE.md and GEMINI.md state: *"Never change keys in `experiment_config` after they are frozen."* Enforcing this in the database guarantees that neither application code, background workers, administrative actions, nor manual SQL queries can alter the frozen experiment configuration without an explicit database integrity violation.
- **What breaks if it is wrong:**
  - If frozen keys can be updated: subtle configuration drift or accidental edits can compromise the pilot without detection.
  - If frozen keys can be deleted: critical configuration rows could be dropped, causing runtime crashes or unrecoverable loss of the pre-registered parameter state.
  - If the migration or trigger breaks downgrade / upgrade cycles: test suites like `test_migrations.py` and `test_schema.py` will fail, blocking CI and deployments.

## 3. Governing decisions

- **D04 (Assignment & Freeze):** *"Rank weak bigrams, deal into sets in snake order, map sets to arms with a seeded shuffle, freeze before practice"*; *"Never mid-pilot"*. Requires assignment configuration (`assignment_seed`, `assignment_prior_strength`, `assignment_min_observations`, `assignment_per_set`, `assignment_per_set_fallback`) to be frozen alongside the arm map before practice begins.
- **D08 (Backend Stack):** *"Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite in WAL mode, Typer CLI, ruff, pyright, pytest"*. All database mechanisms must be implemented via standard SQLite features (e.g. SQLite triggers with `RAISE(ABORT)`), Alembic migrations, and SQLAlchemy/SQLModel models.
- **D10 / D29 (Model & Bake-off):** D10: *"Default mlx-community/Llama-3.2-1B-Instruct-4bit. Short bake-off against Qwen3-1.7B (4-bit) before the pilot, then frozen"*. D29: selects `mlx-community/Llama-3.2-1B-Instruct-4bit` at revision `08231374eeacb049a0eade7922910865b8fce912`. The bake-off is complete (T3.3); all neural generation parameters (`llm_model_id`, `llm_model_revision`, `llm_prompt_version`, `llm_temperature`, `llm_top_p`, `llm_max_tokens`) must now be frozen.
- **D16 (Fairness Gate):** *"All targeted arms pass one shared validator: length, charset, density range, per-bigram coverage, repetition limits"*. The validator configuration (`drill_length_chars`, `drill_min_length_chars`, `drill_min_coverage`, `drill_max_word_repeats`, `drill_max_bigram_run`, `drill_min_real_word_ratio`) must be immutable across all arms.
- **D19 (No Cloud, No WASM):** All verification and enforcement runs locally on SQLite on the local host.
- **D20 (Pre-registration):** *"Commit docs/analysis-plan.md with the date before the first practice session. Stops outcome-shopping after seeing data."* All experimental parameters must be frozen prior to locking the analysis plan in T3.6.
- **D30 (Density Calibration):** *"Calibrate shared density window $[d_{min}, d_{max}]$ to $[0.10, 0.40]$."* Calibrated in T3.4 via migration `0011_calibrate_density.py`; must now be frozen alongside all other parameters.

### 4.3 Trigger Precedent from Migration 0005
Migration `0005_assignment_config.py` established how SQLite immutability triggers are created and tested in this codebase:
```python
_CREATE_FREEZE_TRIGGER = (
    "CREATE TRIGGER trg_bigram_assignment_frozen "
    "BEFORE UPDATE ON bigram_assignment "
    "WHEN OLD.frozen_at IS NOT NULL "
    "BEGIN SELECT RAISE(ABORT, 'bigram_assignment rows are frozen'); END"
)
```
Its downgrade drops the trigger:
```python
def downgrade() -> None:
    op.execute("DROP TRIGGER IF EXISTS trg_bigram_assignment_frozen")
    ...
```

## 5. Inputs and outputs

- **Inputs:**
  - Existing `experiment_config` rows in the database (33 keys, currently all having `frozen_at IS NULL`).
  - Freeze timestamp `frozen_at` (UTC timestamp).
  - Any subsequent SQL or ORM operation attempting to modify or delete a frozen key (`UPDATE experiment_config ...`, `DELETE FROM experiment_config ...`).
- **Outputs:**
  - Database schema state:
    - `experiment_config` rows have `frozen_at` set to a non-null timestamp.
    - Active SQLite trigger(s) (e.g. `trg_experiment_config_frozen_update` and `trg_experiment_config_frozen_delete`).
  - Error behavior:
    - Attempting an `UPDATE` on any row where `OLD.frozen_at IS NOT NULL` aborts with `sqlite3.IntegrityError` (`RAISE(ABORT, 'experiment_config keys are frozen')`), leaving the row and value unchanged.
    - Attempting a `DELETE` on any row where `OLD.frozen_at IS NOT NULL` aborts with `sqlite3.IntegrityError`.
  - Migration artifacts and test updates:
    - New migration `0012_freeze_config.py` setting `frozen_at` on the target keys and installing the trigger(s).
    - `HEAD` in `test_migrations.py` updated to `"0012_freeze_config"`.
    - Associated integration tests verifying freeze rejection on updates and deletes, clean downgrade behavior, and schema consistency.

## 6. Constraints

- **SQLite Trigger Semantics:**
  - SQLite triggers fire within the active transaction. `SELECT RAISE(ABORT, ...)` raises a `sqlite3.IntegrityError` in Python.
  - Alembic `compare_metadata` does not inspect triggers, avoiding metadata drift in `test_schema.py`.
- **Downgrade Safety:**
  - If a trigger is active on `experiment_config`, running `downgrade()` in migration 0012 must drop the trigger *before* executing any update that resets `frozen_at = None`, otherwise the trigger will abort the downgrade operation.
  - Downgrading to base and re-upgrading to head must continue to succeed cleanly (`test_upgrade_downgrade_upgrade_round_trip`).
- **Append-only / Immutability Principles (GEMINI.md / CLAUDE.md):**
  - "Never change keys in experiment_config after they are frozen."
- **Platform Compatibility:**
  - All migration and database tests must run locally and pass on macOS and Linux (CI) without requiring Apple Silicon or GPU hardware.

## 7. Edge cases

1. **Direct UPDATE of a frozen key's value:**
   - *Example:* `UPDATE experiment_config SET value = '0.15' WHERE key = 'd_min'`
   - *Result:* Triggers `RAISE(ABORT, 'experiment_config keys are frozen')`. SQLite raises `IntegrityError`; `value` remains `0.10`.
2. **Attempting to unfreeze a key by updating `frozen_at` to `NULL`:**
   - *Example:* `UPDATE experiment_config SET frozen_at = NULL WHERE key = 'llm_model_id'`
   - *Result:* Because `OLD.frozen_at IS NOT NULL`, the `BEFORE UPDATE` trigger evaluates to true and aborts the update. A frozen key cannot be unfrozen via SQL `UPDATE`.
3. **Attempting to modify `frozen_at` to another timestamp:**
   - *Example:* `UPDATE experiment_config SET frozen_at = '2026-11-01 00:00:00' WHERE key = 'practice_days'`
   - *Result:* Aborts via the trigger because `OLD.frozen_at IS NOT NULL`.
4. **Attempting to DELETE a frozen key:**
   - *Example:* `DELETE FROM experiment_config WHERE key = 'assignment_seed'`
   - *Result:* If a `BEFORE DELETE` trigger is in place (`WHEN OLD.frozen_at IS NOT NULL`), the deletion is aborted with `IntegrityError`. Unlike `bigram_assignment` (which allows cascading delete when a participant is deleted), `experiment_config` is global and has no valid reason to delete frozen keys.
5. **Inserting and updating an unfrozen key post-freeze:**
   - *Example:* An application test inserts a temporary probe key: `INSERT INTO experiment_config (key, value, frozen_at) VALUES ('test_probe', '"sample"', NULL)`. Subsequently: `UPDATE experiment_config SET value = '"sample2"' WHERE key = 'test_probe'`.
   - *Result:* Succeeds because `OLD.frozen_at` is `NULL`.
6. **Freezing a previously unfrozen key:**
   - *Example:* `UPDATE experiment_config SET frozen_at = '2026-10-29 00:00:00' WHERE key = 'test_probe'` (where `OLD.frozen_at IS NULL`).
   - *Result:* Succeeds. Any subsequent update or delete on `'test_probe'` will then be rejected by the trigger.
7. **Downgrade of migration 0012:**
   - *Example:* `alembic downgrade 0011_calibrate_density`
   - *Result:* Must drop trigger(s) first, then update `frozen_at = None`. If the update is executed before dropping the trigger, the trigger aborts the downgrade.

## 8. Risks

1. **Existing test expectations in `test_schema.py`:**
   `test_schema.py` line 364 explicitly asserts that all keys in `EXPECTED_CONFIG` have `frozen_at is None`. Once migration 0012 is applied, running against a migrated database will fail this assertion unless `test_schema.py` is updated to expect non-null `frozen_at` timestamps.
2. **Existing migration test in `test_migration_0011.py`:**
   `test_migration_0011.py` lines 25–32 assert that `d_min` and `d_max` have `row[0] is None` for `frozen_at` on `migrated_engine`. Because `migrated_engine` runs at HEAD (which will become 0012), this assertion will fail if 0012 freezes `d_min` and `d_max`.
3. **Trigger scope omission (DELETE vs UPDATE):**
   If only a `BEFORE UPDATE` trigger is created, a `DELETE` would completely delete the frozen row, bypassing the freeze protection.
4. **Ordering in migration downgrade:**
   If the trigger is not dropped prior to executing the `UPDATE ... SET frozen_at = NULL` statement in `downgrade()`, the downgrade will fail with `sqlite3.IntegrityError`.

## 10. Owner answers (2026-10-29)

1. **Which keys are frozen in T3.5:**
   - *Answer:* All 33 seeded keys currently in `experiment_config` (from migrations 0001, 0002, 0005, 0006, 0007, 0008, 0009, 0010, 0011) are frozen with `frozen_at` set in migration 0012.
   - *Source:* Design doc §8.1, §16 (M3 "config and analysis plan frozen"), earlier briefs (`T1.1-brief.md` answer 16).
   - *Reasoning:* All 33 keys establish the complete parameter space of the experiment (baseline, assignment, retest, validator, and arms) and must be immutable throughout the randomized trial.

2. **Operations blocked by "Frozen keys reject changes":**
   - *Answer:* Both `UPDATE` and `DELETE` are rejected on any row where `OLD.frozen_at IS NOT NULL` via two dedicated SQLite triggers: `trg_experiment_config_frozen_update` and `trg_experiment_config_frozen_delete`.
   - *Source:* Acceptance criteria §16 ("Frozen keys reject changes") and D08.
   - *Reasoning:* `experiment_config` rows are global; deleting a frozen key is as catastrophic to experimental validity as mutating its value.

3. **Error message and enforcement mechanism:**
   - *Answer:* Use `RAISE(ABORT, 'experiment_config keys are frozen')` in SQLite triggers, which surfaces as a `sqlite3.IntegrityError` in Python.
   - *Source:* Established codebase precedent in migration 0005 (`trg_bigram_assignment_frozen`).
   - *Reasoning:* Database-level triggers guarantee immutability across all access paths (ORM, raw SQL, background workers, or administrative scripts).

4. **`frozen_at` timestamp value:**
   - *Answer:* Set `frozen_at = '2026-10-29 00:00:00'` in migration 0012.
   - *Source:* Codebase migration conventions (fixed deterministic dates in migrations).
   - *Reasoning:* Deterministic timestamps avoid clock drift and allow clean equality assertions across unit, integration, and schema tests.

5. **CLI command vs migration deliverable:**
   - *Answer:* Database migration `0012_freeze_config.py` is the sole deliverable for freezing configuration and installing the triggers.
   - *Source:* Design doc §14, §16.
   - *Reasoning:* The freeze occurs at Milestone 3 completion prior to pre-registering the analysis plan in T3.6; no runtime user-facing CLI command is required to trigger it.
