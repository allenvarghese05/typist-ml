# T2.1 — Analyst brief

## 1. Task

- **ID:** T2.1 (milestone M2 "Loop with heuristic and control", design doc §16).
- **Title (verbatim):** "Tables: bigram_stats, bigram_assignment, drills, generation_jobs,
  generation_attempts".
- **Acceptance criteria (verbatim):** "Migration works".
- **Scope correction (owner-decisions.md #7, T1.9 owner answer 1):** `bigram_stats` already
  exists (created in T1.9, migration `0003_bigram_stats`). **T2.1 adds only the other four
  tables:** `bigram_assignment`, `drills`, `generation_jobs`, `generation_attempts`.

## 2. Why it matters

These four tables are the entire M2 data substrate downstream of raw telemetry:

- **`bigram_assignment`** is the frozen output of T2.2 (assignment.py): the per-participant
  map from weak bigram → set (A–D) → arm, with the baseline snapshot. §3.4/§3.5 analysis and
  D04 ("freeze before practice") depend on these rows being immutable. If the columns or the
  composite PK are wrong, the whole within-person design (D01) has nowhere to record its unit
  of analysis.
- **`drills`** holds every generated practice text with its fairness metrics (density, word
  length, real-word ratio) and reproducibility fields. T2.4/T2.6 (pool selection, marking
  drills used) and T3.x (Markov/LLM) write here; §13's "arms were comparable" write-up reads
  these columns. `drills.used_in_block_id` is the link `session_blocks` already documents
  ("practice drills link back through drills.used_in_block_id; a block holds two drills").
- **`generation_jobs` / `generation_attempts`** are the worker's queue and audit log (D11
  batch worker, §10.2 retry loop). T2.5 (atomic job claim, heartbeat), §13.5 (up to 5 LLM
  attempts logged), and the §15.2 Generation dashboard (acceptance rate, attempts per drill,
  tokens per second) all depend on these columns existing with the right types.

If the migration is wrong (bad column type, missing FK, wrong enum, missing index, broken
up/down) every M2/M3 task that writes these tables is blocked, and because T2.6 links drills to
blocks and §4.2 requires participant deletion, a missing FK or a missing delete path leaves
orphan rows or an un-deletable participant.

## 3. Governing decisions

- **D01 (within-person):** each participant's weak bigrams split into 4 sets, each set one arm
  → `bigram_assignment(participant_id, bigram, set_label, arm)`.
- **D03 (arms):** `control, heuristic, markov, llm` — the arm values for `drills.arm` and
  `generation_jobs.arm`. (`bigram_assignment.arm` is also one of these.)
- **D04 (assignment):** "freeze before practice" → `bigram_assignment.frozen_at`, "Rows are
  immutable after this" (§8.1). T2.1 only creates the table; immutability enforcement is T2.2.
- **D11 (generation timing):** "Batch, via a separate worker process… Keep 3 days of ready
  drills per arm" → `drills.status` (`ready/used/retired`) and `generation_jobs`.
- **D13 (text scope):** lowercase a–z + space, letter-letter bigrams only → `bigram` is two
  lowercase letters (same `length(bigram) = 2` CHECK already used on `bigram_stats`).
- **D16 (fairness gate):** one shared validator → `drills.target_density, mean_word_len,
  real_word_ratio` and `generation_attempts.density, accepted, reject_reasons`.
- **D10/D09 (model/runtime):** `drills.model_id, prompt_version, seed`, and LLM-only attempt
  fields `gen_ms, gen_tokens, tokens_per_sec, peak_memory_mb`.
- **D20/D05:** outcomes read `bigram_assignment` (set membership) — columns must match §3.4.
- **Section 8 intro (binding for every table):** "SQLite with PRAGMA journal_mode=WAL,
  foreign_keys=ON and synchronous=NORMAL. Ids are UUID strings except for the two high-volume
  tables, which use integer ids. Timestamps are UTC ISO-8601. Durations are milliseconds stored
  as REAL. Every schema change is an Alembic migration."

### 4.3 Shared helpers in `services/api/src/typist/models/base.py`

- `NAMING_CONVENTION: Final[dict[str, str]]` with keys `ix, uq, ck, fk, pk` (format strings
  `ix_%(column_0_label)s`, `uq_%(table_name)s_%(column_0_N_name)s`,
  `ck_%(table_name)s_%(constraint_name)s`,
  `fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s`, `pk_%(table_name)s`); set on
  `SQLModel.metadata.naming_convention` at import.
- `class JSONText(TypeDecorator[Any])` — `impl = Text`, `process_bind_param` / `process_result_value`
  do `json.dumps`/`json.loads`; None ↔ SQL NULL. Used for every JSON column.
- `def new_id() -> str:` — 36-char hyphenated UUID4 (OS random, not seeded). Used as
  `Field(default_factory=new_id, primary_key=True)` for TEXT PKs.
- `def sql_in(column: str, values: Sequence[str]) -> str:` — returns `"<column> IN ('a', 'b')"`;
  how every enum CHECK is written (e.g. `sql_in("arm", BLOCK_ARMS)`).

### 4.5 Existing model conventions to copy (exact patterns)

- Enum CHECK via a module-level `Final[tuple[str, ...]]` + `sql_in`, e.g. in `sessions.py`:
  `BLOCK_ARMS: Final[tuple[str, ...]] = ("test", "control", "heuristic", "markov", "llm")` and
  `sa.CheckConstraint(sql_in("arm", BLOCK_ARMS), name="arm")`. **Note:** `BLOCK_ARMS` includes
  `test`; the four generated-drill arms are D03's `control, heuristic, markov, llm` (no `test`).
- TEXT PK: `id: str = Field(default_factory=new_id, primary_key=True)`.
- INTEGER PK (rowid): `id: int | None = Field(default=None, primary_key=True)` (see
  `bigram_stats`, `keystroke_events`).
- FK: `Field(foreign_key="participants.id")`, nullable FK with `default=None`.
- JSON column: `field: <type> = Field(sa_type=JSONText)`.
- `server_default=sa.text("CURRENT_TIMESTAMP")` pattern for DB-filled `created_at`
  (participants); boolean default via `sa_column_kwargs={"server_default": sa.text("0")}`.
- Composite PK: no current model has one. `bigram_assignment` is the first — express as two
  `primary_key=True` fields (SQLModel) and `sa.PrimaryKeyConstraint("participant_id", "bigram",
  name=op.f("pk_bigram_assignment"))` in the migration.

### 4.6 Migration conventions (0001–0003)

- Migration files import **no app code**: plain `sqlalchemy as sa` + `from alembic import op`;
  all names written out with `op.f(...)` so they equal `NAMING_CONVENTION`.
- Header: `revision: str`, `down_revision: str | Sequence[str] | None`, `branch_labels`,
  `depends_on`. New revision id will be `0004_<slug>`; `down_revision = "0003_bigram_stats"`.
- `op.create_table(...)` lists columns, then `CheckConstraint`, `ForeignKeyConstraint`,
  `PrimaryKeyConstraint`, `UniqueConstraint` (all with `op.f(...)` names), then
  `op.create_index(op.f(...), ...)`.
- `downgrade()` drops indexes explicitly then drops tables, **children before parents** (the
  0001 docstring: with `foreign_keys=ON`, DROP TABLE first deletes rows, which fails while child
  rows reference them). `generation_attempts` → `generation_jobs` + `drills` →
  `bigram_assignment` is the child-before-parent order among the new tables.
- `env.py` uses `render_as_batch=True` for both online/offline; `foreign_keys=ON` on every
  connection (T1.1 owner answers 20a/22: batch rebuild of a referenced table with child rows
  fails, and PRAGMA foreign_keys cannot be toggled inside the migration transaction).
- Data seeds are done with `op.bulk_insert` (0001, 0002). **T2.1 seeds no config keys**:
  `assignment_seed` is owned by T2.2; `model_id`, `prompt_version`, `sampler` by T3.x.

### 4.7 Participant deletion — `services/api/src/typist/services/participants.py`

`def delete_participant(session: Session, participant_id: str) -> ParticipantDeletion:` deletes
"children before parents" with **no ON DELETE CASCADE** (T1.1 owner answers 10/18 — this is the
only delete path). Current order: `keystroke_events` → `session_blocks` → `bigram_stats` →

`@dataclass(frozen=True) class ParticipantDeletion` has one int field per table:

**The new FK-bearing tables must be added to this delete path and dataclass** (see §5, §7).

## 6. Constraints

- **Migration-only; up and down must both work** ("Migration works"; §8 "Every schema change is
  an Alembic migration"). Up/down/up round-trip and populated-downgrade are already tested.
- **SQLite + `foreign_keys=ON` on every connection**; WAL; `synchronous=NORMAL`. No ON DELETE
  CASCADE anywhere (T1.1 answer 10) — deletion is manual and ordered.
- **Ids:** UUID TEXT except the two high-volume tables. `drills.id` and all `jobs.*`/`attempts`
  FK ids are TEXT; **`generation_attempts.id` is `INTEGER`** per §8.1 (see Open Question 1).
- **Naming convention is frozen:** every constraint/index name must equal `NAMING_CONVENTION`
  via `op.f(...)`; `compare_metadata` and `EXPECTED_NAMES` enforce parity.
- **Migration files import no app code** (plain SQLAlchemy types; the model classes are the
  source of truth that `test_schema.py` compares against).
- **No frozen-key / experiment-semantics change:** T2.1 adds no `experiment_config` keys and
  does not touch any existing table (it must not re-emit `bigram_stats`).
- **Append-only / immutability are not enforced by DDL here:** `bigram_assignment` immutability
  (D04 "immutable after frozen_at") is T2.2's job; `keystroke_events` append-only is unrelated.
- **Platform:** no mlx-lm involvement; the LLM-only attempt columns are just nullable columns
  on Linux/CI (the table is created and tested off-Mac). No `@pytest.mark.mlx` tests here.
- **Seeded randomness:** not applicable to DDL; `new_id()` uses OS random by design (ids never
  affect results — CLAUDE.md).

## 7. Edge cases

1. **`drills.used_in_block_id` FK to `session_blocks.id` vs delete order.** With
   `foreign_keys=ON`, deleting a `session_blocks` row still referenced by a `drills` row fails.
   So in `delete_participant` the new `drills` delete **must run before** `session_blocks`
   (today's order deletes `session_blocks` second). Example: participant p01 has block B with a
   practice drill D whose `used_in_block_id = B.id`; deleting p01 must remove D before B or the
   FK check aborts the transaction. `generation_attempts.drill_id` FK → `drills` forces
   attempts-before-drills too; `generation_attempts.job_id` FK → `generation_jobs` forces
   attempts-before-jobs. A correct order for the four new tables:
   `generation_attempts` → (`generation_jobs`, `drills`) → `bigram_assignment`, and `drills`
   before `session_blocks`.
2. **`bigram_assignment` composite PK** `(participant_id, bigram)` is the first composite PK in
   the schema; the `pk` naming-convention template is `pk_%(table_name)s` so the name is
   `pk_bigram_assignment` regardless of columns. Example: two rows `(p01,"th")` and `(p01,"he")`
   are distinct; a second `(p01,"th")` violates the PK.
3. **`drills.target_bigrams` empty for control** (§8.1 "Empty for control"). Stored as JSONText;
   the empty case is `[]`, not SQL NULL (JSONText cannot store a JSON null). Example: a control
   drill row has `target_bigrams = []`.
4. **LLM-only attempt columns null for other arms** (§8.1 "LLM only; null for other arms"):
   `gen_ms, gen_tokens, tokens_per_sec, peak_memory_mb` must be nullable. Example: a heuristic
   attempt row has all four NULL but still has `density` and `accepted`.
5. **`generation_attempts.drill_id` NULL until accepted** (§8.1 "drill_id set when accepted").
   A rejected attempt has `drill_id = NULL`; an accepted one points at the drill. FK must be
   nullable.
6. **`attempts.accepted BOOLEAN`** — booleans have no CHECK by default (T1.1 answer: SQLAlchemy
   Boolean emits no CHECK unless asked). Follow the existing `is_builder`/`after_pause` pattern.
7. **`drills.seed INTEGER` and `attempts.gen_tokens INTEGER` vs `drills.model_id`/`prompt_version`
   TEXT:** the §8.1 "TEXT, INTEGER" row packs four columns into two type tokens
   (`generator_version, model_id, prompt_version` = TEXT; `seed` = INTEGER). State explicitly in
   the plan to avoid a wrong column type (see Open Question 2).
8. **`seeded_ids` must build a valid chain for the new rows.** `generation_attempts` needs a
   `job_id` (a seeded `generation_jobs.id`); an accepted attempt needs a `drill_id`; a `drills`
   row with `used_in_block_id` set needs the seeded block id. Simplest seed: one job, one drill
   (status `ready`, `used_in_block_id` = seeded block or NULL), one attempt referencing the job
   (drill_id NULL or the drill). Each must satisfy its CHECKs/enums.
9. **T1.5 restartable-block attempt-identity requirement** (flagged in T1.5 brief open-question
   answer 4&5 / plan: append-only `keystroke_events` + restartable blocks means a later task must
   distinguish a block's final-attempt rows from an abandoned attempt's rows, "likely an attempt
   number becomes part of the block's identity"). **Does any T2.1 table need it? No.** The four
   T2.1 tables are not `session_blocks` or `keystroke_events`; attempt identity lives on the
   block/keystroke side, which T2.1 does not touch. The only contact point is
   `drills.used_in_block_id` pointing at a `session_blocks.id`; if a block is ever
   abandoned/restarted, which block id a drill points to is a T2.6/block-lifecycle concern, not a
   column T2.1 defines (Open Question 5).
10. **Autogenerate parity (`_schema_diff`/`compare_metadata`) is unforgiving:** any column type,
    nullability, default, or constraint that differs between the model class and the migration
    fails `test_migrated_schema_matches_the_models`. JSON columns must be `JSONText` in the model
    and `sa.Text()` (TEXT affinity) in the migration, exactly as 0001 did for the existing JSON
    columns.

## 8. Risks

1. **Delete path not updated** → either an orphaned-row leak or a `FOREIGN KEY constraint failed`
   that aborts participant deletion, and `test_participants_service.py` / `PRAGMA
   foreign_key_check` fail. Highest-likelihood miss (same class of omission T1.8/T1.9 records flag).
2. **Pin constants not updated** (`SEVEN_TABLES`, `APP_TABLES`, `COUNT_QUERIES`, `HEAD`,
   `PROBE_REBUILD_REVISION`, `EXPECTED_NAMES`, `EXPECTED_CHECKS`, `seeded_ids`) → many existing
   tests fail even though the migration itself is correct.
3. **Model/migration drift** → `compare_metadata` non-empty; usually a type mismatch (JSON vs
   Text, INTEGER vs TEXT id, nullable mismatch) or a name not wrapped in `op.f`.
4. **Wrong column types from the packed §8.1 rows** (Open Questions 1, 2) — silent until a later
   task stores a value and gets the wrong affinity.
5. **Over-constraining:** adding CHECKs the design doesn't specify (e.g. enum CHECKs on
   `status`/`arm`/`set_label`) is consistent with existing-table convention but is a design
   choice; if added it must be mirrored in both model and migration and in `EXPECTED_CHECKS`
   (Open Question 3). Under-constraining risks a typo'd `status` later; over-constraining makes a
   future value a batch rebuild (T1.1 answer).
6. **Down-migration order wrong** → `test_downgrade_*` fails under `foreign_keys=ON`.

## 9. Open questions

1. **`generation_attempts.id` is listed `INTEGER` in §8.1, but §8 says "Ids are UUID strings
   except for the two high-volume tables" (keystroke_events, bigram_stats).** Is
   `generation_attempts` intended to be a third integer-id table (treated as high-volume, same as
   `bigram_stats`/`keystroke_events` with `id: int | None = Field(default=None,
   primary_key=True)` as a rowid, no AUTOINCREMENT), or is this a doc inconsistency and should its
   id be UUID TEXT like the other new tables? The §8.1 table clearly prints "attempts.id … INTEGER".

2. **Column type assignment inside the two packed §8.1 rows is inferred, not stated.** Confirm:
   `drills` → `generator_version TEXT`, `model_id TEXT`, `prompt_version TEXT`, `seed INTEGER`;
   `generation_attempts` → `gen_ms REAL`, `gen_tokens INTEGER`, `tokens_per_sec REAL`,
   `peak_memory_mb REAL`. And for `generation_jobs`, the row "jobs.retries, error, created_at,
   started_at, finished_at" gives **no types** — confirm `retries INTEGER`, `error TEXT NULL`,
   `created_at DATETIME`, `started_at DATETIME NULL`, `finished_at DATETIME NULL`.

3. **Enum CHECK constraints are not specified in §8.1 for the new tables, but every existing
   enum column has one (`sql_in`).** Should T2.1 add CHECKs for `bigram_assignment.set_label`
   (A/B/C/D), `bigram_assignment.arm`, `drills.arm`, `drills.status` (ready/used/retired),
   `generation_jobs.arm`, and `generation_jobs.status` (pending/running/done/failed) — and
   `length(bigram) = 2` on `bigram_assignment.bigram` like `bigram_stats` — or leave them
   unconstrained to match the literal §8.1 text? (Note the arm set here is D03's four arms, not
   `session_blocks`' five which include `test`; a shared `BLOCK_ARMS` constant cannot be reused.)

4. **Is `generation_jobs.participant_id` a foreign key to `participants.id`?** §8.1 prints
   "jobs.id, participant_id, arm | TEXT" with no "FK" annotation, unlike `drills.participant_id`
   which is marked "TEXT FK". If it is an FK, it must be added to the delete path; if not, jobs
   for a deleted participant would be left behind. (Same question implicitly for whether
   `bigram_assignment.participant_id` — marked only "composite PK" — carries an explicit FK; it
   should, by parity, reference `participants.id`.)

5. **Which block id should `drills.used_in_block_id` reference once block abandon/restart exists
   (D26 / T1.5 flagged attempt-identity)?** T2.1 only needs a nullable TEXT FK to
   `session_blocks.id`; but confirm no attempt-number column belongs on `drills` now (the T1.5
