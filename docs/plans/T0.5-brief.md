## 2. Why it matters

What T0.5 enables later:
- **Closes M0.** M0 is done only when the "model smoke test prints tokens per second on the
  MacBook". Section 20.3 treats it as the first proof that the project's riskiest dependency runs
  at all on the M1 Pro.
- **Fixes the model runtime version (D09).** The mlx-lm pin in `services/api/uv.lock` that T0.5
  introduces is the version the pilot runs on. Section 5: "Do not upgrade the model runtime or the
  model during the pilot." Section 18: "Library changes mid-project | Behaviour drift | Lockfiles;
  no upgrades between freeze and retest".
- **Validates the section 13.5 wrapper API before T3.2 builds on it.** `load`, `stream_generate`,
  `make_sampler`, `mx.random.seed`, `tokenizer.apply_chat_template` and the response fields
  `text`, `generation_tokens`, `generation_tps`, `peak_memory` are all assumed by 13.5. T3.2's
  acceptance ("attempts logged with tokens per second") and the `generation_attempts` columns
  `gen_tokens, tokens_per_sec, peak_memory_mb` depend on those fields existing.
- **Sets up the dependency mechanism** (the `mlx` optional extra suggested by T0.3 owner answer 10)
  that T2.5 (worker), T3.2 (generator) and T3.3 (bake-off) install from.
- **Gives the first real tokens-per-second number.** Section 13.6 picks a model that "runs at 30
  tokens per second or more"; section 6.2 assumes "several seconds per drill" and "roughly 1 GB of
  memory". T0.5 is the first measurement against those assumptions.

What breaks if it is wrong:
- **CI turns red on Linux.** If mlx-lm lands in the default dependencies, in the `dev` group, or
  without the darwin/arm64 marker, `uv sync --locked` in the `api` job fails. If code under
  pyright's scope imports `mlx` or `mlx_lm` and they are not installed on Linux, `uv run --locked
  pyright` fails. `api` is a required check, so every later PR is blocked.
- **The API or CLI stops starting on Linux (and on a Mac without the extra).** Section 6.1:
  Services "Must not ... Import the model runtime". If `typist.main` or `typist.cli` imports mlx at
  module level, `just dev`'s API line, `typist db migrate` and the existing tests break.
- **Wrong or unrecorded versions.** If the mlx-lm version, the mlx version or the model's revision
  is not recorded, T3.3's bake-off and the pilot cannot be reproduced (13.1: "Determinism | Same
  spec and seed gives the same text (LLM: same seed and pinned versions)"). An unpinned model
  repo can change underneath the pilot.
- **Participant-data or large-file leaks into git.** If the Hugging Face cache is pointed inside the
  repo at a path that is not ignored, ~0.7 GB of weights shows up as untracked files.
- **Privacy claims broken (D19, 4.2).** The README will claim data is "never sent to a third party
  or a cloud AI service". A model runtime that silently contacts the Hugging Face Hub on every load
  weakens the "everything stays local" rule the reviewer checks ("no new network call added
  anywhere (this project makes none, per D19)").

### Design doc section 13.5 wrapper (verbatim)
```python
import mlx.core as mx
from mlx_lm import load, stream_generate
from mlx_lm.sample_utils import make_sampler

class MLXRuntime:
    def __init__(self, model_id: str):
        self.model_id = model_id
        self.model, self.tokenizer = load(model_id)   # once per worker process

    def complete(self, messages, *, max_tokens=160, temp=0.8, top_p=0.9, seed=0):
        mx.random.seed(seed)
        prompt = self.tokenizer.apply_chat_template(
            messages, add_generation_prompt=True, tokenize=False)
        sampler = make_sampler(temp=temp, top_p=top_p)
        text, last = "", None
        for resp in stream_generate(self.model, self.tokenizer, prompt,
                                    max_tokens=max_tokens, sampler=sampler):
            text += resp.text
            last = resp
        return LLMOutput(text=text,
                         tokens=last.generation_tokens,
                         tokens_per_sec=last.generation_tps,
                         peak_memory_gb=last.peak_memory)
```
Facts about the snippet itself:
- `LLMOutput` is used but not defined anywhere in the design doc text.
- `complete`'s parameters are untyped; section 17.1 requires type hints and pyright strict in
  `src/`.
- It returns `peak_memory_gb`, while the `generation_attempts` column is `peak_memory_mb` (8.1).
- `last` is `None` if the stream yields nothing; the snippet would then fail on
  `last.generation_tokens`.
- Sampler settings in 13.5: "temperature 0.8, top_p 0.9, max_tokens 160". Seed: "Derived from
  (participant, arm, drill number, attempt), stored on each attempt".

## 6. Constraints

- **Platform:**

    `sys_platform == 'darwin' and platform_machine == 'arm64'`.
  - CI and cloud sessions run Linux x64 with `uv sync --locked` and no extras. That command must
    still succeed, and must not install mlx.
  - `uv run --locked pyright` on Linux must pass with mlx not installed.
  - `uv run --locked pytest` on Linux must pass; `mlx`-marked tests are skipped there by

  - mlx needs a native arm64 Python. Under Rosetta, `platform.machine()` reports `x86_64`, the
    marker excludes mlx-lm and `conftest.py` skips mlx tests (verify).

    to satisfy it).

  - No network: no `uv lock`, no `uv sync`, no `uv add`, no Hugging Face download.
  - Apple GPU (Metal) access from the sandbox is not verified.
  - Writes outside the worktree (uv cache, `~/.cache/huggingface`) may be blocked.
  - No `git commit` by the builder: pre-commit's stash step fails on the unreadable
    `services/api/.env.example`, so commits are owner-run.
  - `dangerouslyDisableSandbox` is never used. Blocked steps become owner-run resume points
    (T0.3 answer 23, T0.4 answer 25).
  - The builder and reviewer run on the Mac itself, so `conftest.py` does **not** skip `mlx` tests
    for them (edge case 9).
- **Owner-run on the M1 Pro:** `uv lock`, `uv sync --locked` with the extra, the first model
  download, the actual smoke run, and recording its output.
- **Locking:** every API command uses `uv run --locked` (D21 amendment). `pyproject.toml` and
  `uv.lock` must be committed together and consistent, or `check-api` and CI fail.
- **Pins:** exact `==` pins for core libraries (T0.3 answer 14). Section 13.5: "pin that version".
  Section 5: no model-runtime or model upgrades during the pilot.
- **Type checking:** pyright strict for `src/`; standard for `tests/`. mlx-lm's own type coverage

- **Lint and security scans:** ruff lints everything under `services/api` (`ruff check .`).

- **Licensing:** Llama 3.2 is under the Llama 3.2 Community License (verify terms). The weights are

## 7. Edge cases

1. **The extra's marker vs uv's universal lock.** `uv lock` resolves for all platforms at once
   (verify). Adding a darwin/arm64-only requirement makes the lock contain mlx-lm and its tree with
   markers, and may add a `resolution-markers` block that the current lock does not have. A plain
   `uv sync --locked` on Linux must still succeed. Example: if the marker is misspelled
   (`platform_machine == 'aarch64'`, the Linux spelling), the Mac never installs mlx-lm and the
   smoke test fails with `ModuleNotFoundError: No module named 'mlx_lm'`.
2. **Extra vs dependency group.** uv installs the `dev` dependency group by default
   (`uv sync`), but not optional extras (verify for uv 0.12.18). CLAUDE.md says "optional
   dependency group"; T0.3 answer 10 suggests "an optional extra named `mlx`". Putting mlx-lm into
   `dev` would make every `uv sync` on Linux try to install it (skipped by the marker, but still
   locked). `--all-extras` or `--extra mlx` on Linux installs nothing for a marker-guarded extra
   rather than failing (verify; T0.4 brief edge case 37 assumed failure).
3. **Exact sync removes the extra.** `uv sync --locked` without `--extra` removes packages not in
   the requested set (exact sync, verify). Example: the owner runs `uv sync --locked --extra mlx`,
   later follows README step 4 (`uv sync --locked`), and mlx-lm disappears; the next smoke run
   fails on import. `uv run --locked` does an inexact sync and does not remove it (verify).
4. **pyright on Linux sees unresolved imports.** If any file under `include = ["src", "tests",
   "alembic"]` contains `import mlx.core` or `from mlx_lm import ...`, pyright on the Linux runner
   (no mlx installed) reports `reportMissingImports` (an error in standard and strict, verify) and,
   in strict mode, unknown types for every use. Example: `just check-api` passes on the Mac with the
   extra installed but the CI `api` job fails.
5. **pyright on the Mac differs by install state.** The same file type-checks differently on a Mac
   with the extra (imports resolve, strict may flag mlx-lm's partial types) and without it
   (missing imports). `pythonPlatform` is not set in `[tool.pyright]`, so pyright evaluates
   `sys.platform` checks for the host (verify).
6. **mlx-lm typing under strict mode.** `load` returns a `(model, tokenizer)` tuple where the
   tokenizer is a `TokenizerWrapper` that forwards attributes such as `apply_chat_template` to the
   Hugging Face tokenizer via `__getattr__` (verify). In strict mode that yields
   `reportUnknownMemberType` / `reportUnknownVariableType`. Example: `prompt =
   tokenizer.apply_chat_template(...)` is `Unknown`.
7. **Module-level import of mlx in shared entry points.** `typist` is one console script. If a
   module imported by `typist.cli` (or by `typist.main`) imports mlx at module level, then on Linux
   or on a Mac without the extra `typist db migrate` fails with `ModuleNotFoundError`, and the
   existing `tests/integration/test_cli.py` and `test_health.py` fail in CI.
8. **Where "tests use a fake runtime" meets T0.5.** Any non-`mlx` test of smoke-test code must use
   a fake (CLAUDE.md). No fake runtime exists; 13.5 does not define its interface. An `mlx`-marked
   test that really loads the model runs only on the Mac.
9. **`mlx` tests are not skipped on the Mac, whatever the install state.** The conftest decides by
   platform only. On the M1 Pro (including inside the builder's and reviewer's sandbox, which runs
   on the same Mac), an `mlx`-marked test:
   - fails with `ModuleNotFoundError` if the extra is not installed;
   - tries to download ~0.7 GB if the model is not cached (blocked by the sandbox's network rule);
   - needs Metal GPU access (unverified in the sandbox);
   - adds model-load time (seconds) to every `just test`, `just check` and `just check-api` run.
10. **First download vs cached load.** On first run `mlx_lm.load` downloads the weights; later
    runs load from the cache. Even when cached, `huggingface_hub` may send a HEAD/metadata request
    to the Hub to check for a newer revision unless `HF_HUB_OFFLINE=1` is set (verify). Example: an
    offline laptop gets a connection error or a delay from a "cached" load, and a networked one
    makes a request on every load, which the reviewer's D19 check would count as a network call.
11. **Hugging Face telemetry and user agent.** `huggingface_hub` sends a user-agent string with
    library versions on requests, and has a telemetry switch (`HF_HUB_DISABLE_TELEMETRY`) (verify
    what the pinned version sends). CLAUDE.md forbids "telemetry services".
12. **Cache location inside the repo.** If `HF_HOME` or `HF_HUB_CACHE` is pointed at a repo path,
    only `/data/...` is ignored by `.gitignore` and `.semgrepignore`. Example:
    `HF_HOME=services/api/.cache/huggingface` puts ~0.7 GB of untracked files in the worktree, not
    ignored, and semgrep in CI would not see them (not committed) but `git status` would.
    `data/` inside `services/api/` is also not ignored (anchored `/data/`).
13. **Model revision drift.** Without a pinned revision, the `main` head of
    `mlx-community/Llama-3.2-1B-Instruct-4bit` is used. mlx-community repos are sometimes
    re-uploaded (for example to update the tokenizer config or chat template) (verify history).
    Example: T0.5 records outputs from revision X; the bake-off in M3 silently uses revision Y with
    a different chat template.
14. **Gated or unavailable repo.** The original `meta-llama/Llama-3.2-1B-Instruct` is gated. The
    `mlx-community` copy is expected to be ungated (verify). If it is gated, the download needs a
    Hugging Face token (`HF_TOKEN`), which is a secret that must not be committed.
15. **mlx-lm version drift since the design doc.** 13.5 and 19.1 cite "the 0.31.x line". mlx-lm
    releases "every few weeks" (19.1). Known historical renames (verify against the installed
    version):
    - `stream_generate` once yielded plain strings, later `GenerationResponse` objects.
    - `generate`/`stream_generate` once took `temp`/`top_p` keyword arguments directly, later a
      `sampler=` built by `make_sampler`.
    - `make_sampler`'s parameters (`temp`, `top_p`, `min_p`, `top_k`, ...) have changed over time.
    - `peak_memory` was taken from `mx.metal.get_peak_memory()` and later `mx.get_peak_memory()`,
      reported in GB.
    - `GenerationResponse` fields: `text`, `token`, `logprobs`, `prompt_tokens`, `prompt_tps`,
      `generation_tokens`, `generation_tps`, `peak_memory`, `finish_reason` (verify).
    Any difference is exactly what 13.5's "Check at milestone 0" asks T0.5 to find.
16. **pip-audit coverage.** `security-py` exports with `uv export --locked --no-emit-project` and no
    `--extra`, so the mlx extra's packages are probably not audited (verify uv export's default
    for extras). If they were, the export lines carry markers and `pip-audit --no-deps
    --disable-pip` on Linux would have to handle darwin-only requirements (verify). Large
    dependencies such as `transformers` have a history of advisories (verify), which would turn the
    weekly `audit.yml` red if audited.
17. **tokens-per-second meaning and noise.**
    - `generation_tps` excludes prompt processing (`prompt_tps` is separate) (verify).
    - For "one line" (tens of tokens) the figure is noisy; the first call includes Metal kernel
      compilation and weight paging (verify). Example: first run 40 tok/s, second run 150 tok/s on
      the same machine.
    - Other load on the Mac (browser, `just dev`) changes the number. 13.6's threshold is "30
      tokens per second or more".
18. **"One line" is not defined.** The model can emit several lines, stop at `max_tokens`
    mid-word, or emit an end-of-turn token immediately. Llama 3.2 has more than one end token
    (`<|eot_id|>`, `<|eom_id|>`, `<|end_of_text|>`) and mlx-lm takes EOS ids from the tokenizer or
    generation config (verify). Example: output `"Here is a line:\n\nthe quick brown fox..."`.
19. **Chat template and the date.** Llama 3.x chat templates insert "Cutting Knowledge Date" and
    "Today Date" into the system turn, using the current date when the template supports
    `strftime_now` (verify for the mlx-community copy and the pinned transformers/jinja). Example:
    the same seed and messages give a different prompt, and so different text, on different days.
    This affects 13.1's determinism rule for T3.2; for T0.5 it matters only if determinism is
    checked.
20. **Double BOS token.** 13.5 builds the prompt as a string (`tokenize=False`) and passes it to
    `stream_generate`, which tokenizes it again. Depending on the version, the tokenizer may add a
    second `<|begin_of_text|>` (verify whether the pinned mlx-lm guards against it).
21. **Seeding is global.** `mx.random.seed(seed)` sets MLX's global random state; it is not a
    generator object passed in by the caller (CLAUDE.md wording). With `temp=0`, `make_sampler`
    returns greedy argmax and the seed has no effect (verify). With `temp>0`, the output is
    reproducible only for the same seed, same mlx/mlx-lm versions, same model revision and same
    prompt (13.1) (verify whether Metal kernels are bitwise deterministic run to run).
22. **Memory figures.** 6.2 expects "roughly 1 GB of memory"; 13.5 returns GB; 8.1 stores
    `peak_memory_mb`. A printed peak-memory figure (if any) has to state its unit. mlx's wired
    memory limits on macOS can print warnings for large models (verify; not expected for 1B 4-bit).
23. **Version facts to record live in different places.** `uv.lock` pins mlx-lm, mlx and the
    Python dependency tree, but not: the model revision SHA, the macOS version, the chip (`Apple
    M1 Pro`), RAM, or the Metal/mlx backend details. Example: `uv.lock` alone cannot show which
    weights produced the recorded tokens per second.
24. **README table dates.** The "Installed versions" heading already carries a date that does not
    match every row (IMPROVEMENTS item `README.md:31`). New rows recorded on a different date make
    it worse.
25. **Sandbox cannot produce the acceptance evidence.** "Prints text and tokens per second" needs a
    real run on the Mac with the model downloaded. The builder and reviewer can only see pasted
    owner output.
26. **CI caches keyed on `uv.lock`.** The uv cache and pyright cache keys change when the lock
    changes; the first CI run after T0.5 is a cold-cache run (slower, still within
    `timeout-minutes: 10`, verify). Linux does not download mlx wheels because of the marker.
27. **semgrep and bandit on model code.** Code that sets environment variables, spawns processes or
    reads files from the cache may trigger bandit (`src/` only) or semgrep rules (whole repo, no
    skip in CI). Example: a `subprocess` call to `sw_vers` to record the macOS version is a bandit
    B603/B607 finding at low severity (verify severity against `-ll`).
28. **T0.3's lock check expectation is now obsolete.** The T0.3 plan listed `mlx` and `mlx-lm` in the
    lock as "UNEXPECTED". That was a one-off check, not a test, but anyone re-running it after
    T0.5 would see a false alarm.

## 8. Risks

1. **CI breaks on Linux.** The most likely failure: a mlx import reaches pyright's scope (edge
   cases 4 to 6) or a shared import path (edge case 7). The Mac, with the extra installed, hides
   it; the required `api` check shows it only after push.
2. **The sandbox blocks almost everything that proves the task.** Lock, sync, download, Metal
   access and the real run are all owner-run (constraint 6). Resume points must be explicit or the
   builder stalls.
3. **`mlx` tests make `just check` on the Mac slow, networked or red** (edge case 9), including for
   the builder and reviewer, whose sandbox runs on darwin arm64.
4. **13.5's API does not match the installed mlx-lm** (edge case 15). T0.5 is the task that must
   find and record this; if it does not, T3.2 inherits a broken wrapper.
5. **D19 creep through Hugging Face.** Every model load may contact the Hub (edge case 10), and the
   library may send telemetry (edge case 11). No decision covers downloading weights.
6. **Incomplete version record.** `uv.lock` alone omits the model revision, OS and chip (edge case
   23); the model repo can change (edge case 13).
7. **Scope creep into T3.2.** Building `MLXRuntime`, `LLMOutput`, a fake runtime, prompts or
   settings for the sampler now overlaps T3.2's title; not building them conflicts with CLAUDE.md's
   "Code that talks to the model goes through `MLXRuntime`" (open question 2).
8. **Large, advisory-prone dependency tree** (`transformers` and friends) enters `uv.lock`
   (edge case 16), even though it is darwin-only.
9. **Honesty rule conflict.** Writing a tokens-per-second number into the README could be read as a
   "result number before real data exists" (open question 4).
