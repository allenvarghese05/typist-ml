## 2. Why it matters

- **Automates scientific artifact reproduction (§15.3, §16):** Typist-ML is designed as a fully reproducible randomized controlled trial. Task T4.3 delivers the analysis notebook (`notebooks/03_results.ipynb`) and the automated generation pipeline for the figures, tables, and metrics specified in §15.3.
- **Enables downstream task T4.4 (§16):**
  - T4.4 is *"README with numbers, method, limitations, N: Every claim traces to a number in the database"*.
  - T4.4 directly depends on the figures, tables, overhead measurements, and limitations text generated in T4.3.
- **Presents exploratory and primary evidence in an accessible narrative format (§7, §15.1, §15.3):** While the web dashboard (T4.2) provides interactive UI views, the results notebook (`notebooks/03_results.ipynb`) documents the entire analytical chain of custody: loading participant records, evaluating pre-registered exclusions, running Beta posterior sampling and median IKI bootstrapping, comparing generation arms, and evaluating instrumentation overhead.
- **What breaks if it is wrong:**
  - **Broken one-command regeneration:** If figures cannot be rebuilt from live data with a single command without manual intervention, GUI clicks, or interactive Jupyter execution, the primary acceptance criterion fails.
  - **Divergence from pre-registered analysis:** If the results notebook reimplements statistical calculations differently from `services/api/src/typist/services/analysis.py` (e.g. altering the Jeffreys prior, changing the `20261030` seed, misapplying the difference-in-differences sign convention, or aggregating session medians instead of pooling clean IKI samples), published results will contradict the pre-registered analysis plan (`docs/analysis-plan.md`, D20).
  - **Headless CI failure:** If figure generation uses a non-headless matplotlib backend (e.g. attempting to open an X11 or Cocoa window) or introduces unpinned dependencies, `just check` will fail in Linux CI.
  - **Honesty rule violations (D19, §18):** If the figures or notebook assert statistical significance, report p-values, or pool results across participants without clearly flagging the builder's unblinded status, the project honesty rules are violated.
  - **Unsupported claims in T4.4:** If the generated README figures or tables do not exactly match the database numbers, claims in the README will fail verification.

## 5. Inputs and outputs

### 5.1 Inputs

1. **SQLite Database (`data/typist.db` via `typist.db`):**
   - `Participant`: Alias, status (`done`), `is_builder`, `is_blinded`.
   - `BigramAssignment`: Set definitions, mapped arms, baseline rank.
   - `Session` (`TypingSession`): Completed baseline and retest sessions.
   - `SessionBlock`: Completed blocks and text passages.
   - `KeystrokeEvent`: Timestamps, IKI values, dwell, overhead metrics (`handler_ms`, `dispatch_lag_ms`).
   - `BigramStat`: Aggregated attempts and errors per session and bigram.
   - `GenerationJob`, `GenerationAttempt`, `Drill`: Drill counts, attempts, validation metrics, tokens per second, memory.
2. **Analysis Service (`typist.services.analysis`):**
   - `participant_results(...)` returning `ParticipantResults`.
   - `overview_report(...)` returning `Overview`.
3. **Pre-registered Constants (`docs/analysis-plan.md`):**
   - Seed: `20261030`
   - Beta posterior draws: `100,000`
   - Bootstrap resamples: `10,000`
   - Retest attempt cutoff: $\ge 20$

### 5.2 Outputs

Section 15.3 defines four README elements to generate, in addition to the results notebook:

1. **One Chart (§15.3 bullet 1):**
   - Content: Per-set error rate change ($d(s) = p(s, \text{retest}) - p(s, \text{baseline})$) with 95% equal-tailed Jeffreys Beta credible intervals, with the held-out control set explicitly marked.
   - Output file: Deterministic figure file (e.g. `docs/figures/set_error_rate_change.png` or `.svg`).
2. **One Table (§15.3 bullet 2):**
   - Content: Table with columns: `arm`, `drills`, `mean density`, `real-word ratio`, `acceptance rate`.
   - Populated from `overview_report(session).generation.arms`.
3. **One Line (§15.3 bullet 3):**
   - Content: Overhead p95 and LLM tokens per second, measured.
   - Example format: *"Instrumentation overhead: handler p95 = X.X ms (target < 1.0 ms), dispatch lag p95 = Y.Y ms. LLM generation: Z.Z tokens/s on Apple Silicon."*
4. **Limitations Paragraph (§15.3 bullet 4):**
   - Content: States $N$ (number of participants), completed sessions, and total keystrokes.
5. **Results Notebook (`notebooks/03_results.ipynb`, §7):**
   - Valid Jupyter notebook (nbformat v4) that imports `typist` analysis routines, inspects participant records, computes outcomes with intervals, renders the primary and secondary comparisons, checks exclusions, and regenerates the README figures.
6. **One Command Regeneration Interface (§16):**
   - A single command (e.g. `just figures` or `typist figures` / `typist analyze --figures`) that executes the generation pipeline, saves the figure file(s), and emits or updates the README figure artifacts.

## 6. Constraints

- **Pre-registration compliance (D20, `docs/analysis-plan.md`):** All mathematical routines, priors, seeds (`20261030`), and thresholds ($\ge 20$ retest attempts) must strictly match the pre-registered plan.
- **Single source of truth (CLAUDE.md, GEMINI.md):** The notebook and figures must call the verified functions in `services/api/src/typist/services/analysis.py`. No duplicating or rewriting attribution or posterior math.
- **Honesty rules (D19, §18):** Results are descriptive within-person differences. No p-values, hypothesis tests, or significance stars. Claims must trace to numbers in the database.
- **Headless rendering & CI compatibility:** Figure generation must execute cleanly in headless environments (Linux CI without display servers or X11) by configuring `matplotlib.use("Agg")`.
- **Performance in CI:** Full figure regeneration and notebook validation tests must run in seconds and not bottleneck CI.
- **Zero code copied from external projects:** Clean-room implementation per project rules.

## 7. Edge cases

1. **Database has no completed participant (`status != 'done'`):**
   - *Example:* A fresh checkout or newly enrolled participant on day 1.
   - *Behavior:* `participant_results` raises `ParticipantNotDoneError`. The one-command runner must handle this gracefully with a clear message (e.g. *"Participant has not completed study (status: 'baseline')"*) and exit code 1 or skip, without an unhandled traceback.
2. **Participant with dropped bigrams (<20 retest attempts, D23(c)):**
   - *Example:* Bigram `"qu"` has only 15 retest attempts and is dropped from Set A.
   - *Behavior:* Error rate change and intervals for Set A are calculated strictly over the retained bigrams. The figure or notebook notes the dropped bigram in the exclusions summary.
3. **Zero errors or zero attempts in a set:**
   - *Example:* Set B has 120 attempts and 0 errors in retest.
   - *Behavior:* Empirical error rate is 0.0. The Jeffreys posterior $\text{Beta}(0.5, 120.5)$ yields a strictly positive credible interval ($> 0.0$). The plot y-axis must not fail or divide by zero.
4. **Two-set mode contingency (D03, §16):**
   - *Example:* Pilot ran with `arms_enabled = ["control", "heuristic"]`. Sets C and D are unassigned.
   - *Behavior:* The chart and table render Sets A and B (control and heuristic) only, explicitly indicating that Markov and LLM arms were not evaluated.
5. **Multiple participants enrolled ($N = 2$, Builder vs Peer):**
   - *Example:* Database contains builder (`is_builder = True`, `is_blinded = False`) and peer (`is_builder = False`, `is_blinded = True`).
   - *Behavior:* Results are never pooled across participants (D01). The command/notebook must generate separate figures per participant or a clearly separated two-panel figure with the builder flagged as unblinded.
6. **No LLM generation attempts yet:**
   - *Example:* Generation overview run before any LLM drills were generated.
   - *Behavior:* `tokens_per_sec` is `None`. The summary table and overhead line format missing values as `"-"` or `"N/A"` without throwing `TypeError`.
7. **Execution in offline sandbox / CI environment:**
   - *Example:* CI runs `just test` where `data/typist.db` is not populated.
   - *Behavior:* Tests must use a test database fixture (e.g. simulated completed pipeline) to verify that the one-command figure regeneration produces valid image/table artifacts.

## 8. Risks

- **Matplotlib dependency management:**
  - *Risk:* `matplotlib` is currently not in `services/api/pyproject.toml`. Adding `matplotlib` brings in multiple dependencies (pillow, fonttools, contourpy, kiwisolver, cycler). If not pinned properly, it could cause resolution conflicts or inflate lockfile diffs.
- **Headless rendering crashes on Linux CI:**
  - *Risk:* On Linux runners in GitHub Actions, attempting to render a matplotlib plot using an interactive GUI backend (`TkAgg`, `Qt`, `MacOSX`) raises `TclError: no display name and no $DISPLAY environment variable`. Code must explicitly call `matplotlib.use("Agg")` before importing pyplot.
- **Discrepancy between notebook and CLI figure outputs:**
  - *Risk:* If the notebook generates figures using custom plotting cells while the CLI command uses separate script logic, the two artifacts can drift in styling, labels, or bounds. Shared plotting functions must power both.
- **Notebook JSON drift in git:**
  - *Risk:* Interactive Jupyter sessions alter execution counts, kernel metadata, and cell outputs, leading to noisy git diffs. Following the pattern established in T3.3, a unit test should validate notebook structure and consistency without requiring manual Jupyter saves.

## 10. Owner answers (2026-10-31)

1. **README Figure Format and Destination Path:**
   - **Answer:** Save the primary README chart to `docs/figures/set_error_rate_change.png` (high-resolution PNG at 300 DPI, tight bounding box), and also generate `docs/figures/set_error_rate_change.svg` alongside it. Directory is `docs/figures/`.
   - **Source:** Design doc §5.2 ("matplotlib for README figures"), §15.3, standard practice.
   - **Reasoning:** High-res PNG renders consistently across all markdown viewers and mobile GitHub apps, while SVG provides vector fidelity.

2. **One-Command Regeneration Interface:**
   - **Answer:** Implement `typist figures` (and `--figures` flag on `typist analyze`) in `services/api/src/typist/cli.py`, and expose the top-level recipe `just figures` in `justfile`.
   - **Source:** Design doc §5.3, §14.1, §16.
   - **Reasoning:** CLI provides programmatic control and testability, while `just figures` provides the zero-friction one-command developer workflow required by §16.

3. **Matplotlib & Data Stack Dependencies:**
   - **Answer:** Add `matplotlib = ">=3.10.1"` to `dependencies` in `services/api/pyproject.toml`. Configure headless backend `matplotlib.use("Agg")` unconditionally in plotting modules before any pyplot import.
   - **Source:** Design doc §5.2 ("matplotlib for README figures"), D08, D21.
   - **Reasoning:** Satisfies design doc §5.2 explicit technology choice and prevents headless Linux CI crashes without GUI dependencies.

4. **Notebook Structure and Execution Strategy:**
   - **Answer:** `notebooks/03_results.ipynb` imports directly from `typist.services.analysis` (`participant_results`, `overview_report`, and figure generator functions). Pre-populate the notebook with clean reference outputs so it is immediately readable on GitHub, and verify its structure and execution via a unit test (`tests/unit/test_results_notebook.py`) following the T3.3 bake-off pattern.
   - **Source:** T3.3 precedent (`02_model_bakeoff.ipynb`), D20.
   - **Reasoning:** Prevents logic divergence from pre-registered math while maintaining CI verification and instant repository readability.

5. **Handling the Multiple-Participant Case ($N=1$ vs $N=2$):**
   - **Answer:** `typist figures` accepts optional `--pid`. If omitted, it processes all completed participants: if 1 participant is completed, generates `docs/figures/set_error_rate_change.png`.    - **Source:** D01, D18, §15.3.
   - **Reasoning:** Enforces strict non-pooling between participants while transparently displaying all completed study data with honesty blinding tags.

6. **Scope Boundary Between T4.3 and T4.4:**
   - **Answer:** T4.3 delivers the figure generation engine (`just figures` / `typist figures`), `notebooks/03_results.ipynb`, the generated image files (`docs/figures/`), and formats the §15.3 markdown snippets (table, overhead line, limitations text) to stdout and `docs/figures/readme_snippets.md`. T4.4 integrates these into the root `README.md`.
   - **Source:** Design doc §15.3, §16.
   - **Reasoning:** Respects task boundaries while giving T4.4 fully verified figures, tables, and statistics ready for immediate README inclusion.
