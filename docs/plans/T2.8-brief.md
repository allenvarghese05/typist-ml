## 2. Why it matters

T2.8 provides the core state machine that enforces protocol integrity across the entire participant lifecycle:

- **Enforces the experimental protocol and participant lifecycle DAG (§3.2, §9.3, Figure 6).** The experiment requires a strict sequence of phases: enrolment, consent, baseline typing, weak-bigram assignment and freezing, drill pool generation, practice typing across Latin-square rotated arms, post-practice retest typing, and debriefing. If participant state transitions are unconstrained, invalid actions can corrupt the experiment:
  - typing baseline tests before recording consent (§4.2, §11.1),
  - typing practice text before baseline completion and weak-bigram freezing ("starting practice before assignment returns 409", §14),
  - typing practice text when the drill pool is not ready (starving arms or failing mid-session),
  - practicing beyond $N$ practice sessions instead of progressing to retest (§3.2, §9.3),
  - taking retest sessions prematurely before completing the $N$ practice sessions,
  - continuing to record sessions after retest completion (`status == "done"`),
  - recording typing sessions after withdrawal (`status == "withdrawn"`).
- **Connects session completion to participant phase advancement (§10.1, §14).** §14 explicitly specifies for `POST /sessions/{sid}/complete`: *"Compute stats, update phase, enqueue jobs"*. When practice session $N$ completes, the participant must transition from `practice` to `retest`; when retest session 2 completes, the participant must transition from `retest` to `done`. In T1.9 and T2.6, `post_session_complete` deferred this lifecycle transition (`"Participant phase transitions belong to T2.8"`).
- **Unblocks T2.9 (Admin page: participants, pool, jobs, checks) and T2.10 (Dev-only pipeline test).** T2.9 provides the builder UI to monitor participants, view phases, run assignment, and inspect drill pools without raw terminal commands; T2.10 runs a scripted-keystroke test verifying the entire participant flow from `enrolled` to `done` in CI.
- **Provides the missing participant HTTP router and schemas (§14).** Section 14 specifies:
  - `GET /api/v1/participants` and `POST /api/v1/participants`: list or create participants (`alias`, `is_builder`).
  - `POST /api/v1/participants/{pid}/consent`: record consent, transition `enrolled -> baseline`.
  - `POST /api/v1/admin/participants/{pid}/assign`: rank, split, map and freeze ("only in baseline-done state"), transition `baseline -> assigned`.
  - And hardens `POST /api/v1/participants/{pid}/sessions` and `POST /api/v1/sessions/{sid}/complete` to return 409 on invalid transitions.

What breaks if it is wrong:
- **Acceptance criteria failure:** If invalid transitions return 200, 400, 422, or 500 instead of HTTP 409 Conflict, automated checks and API clients cannot distinguish protocol violations from malformed payloads or server crashes.
- **Unconsented data capture:** If an `enrolled` participant can start baseline typing without consent, `consent_at` remains NULL while keystrokes are recorded, violating §4.2 and ethics commitments.
- **Corrupted assignment:** If assignment can be re-run or called from a state other than completed baseline, immutable frozen assignment rows (`bigram_assignment`) could be duplicated or conflict with existing session data.
- **Drill pool starvation:** If a participant transitions to `practice` before the drill pool is ready, sessions will fail with `DrillPoolExhaustedError` mid-study.
- **Protocol drift:** If practice or retest sessions do not advance the participant when reaching their targets ($N$ practice days, 2 retest parts), participants get stuck or over-practice, destroying comparability.

## 3. Governing decisions

- **D01 (Experiment unit — within-person):** Each participant has their own weak bigrams and arm mapping, transitioning independently through the lifecycle.
- **D04 (Assignment freeze before practice):** "Rank weak bigrams, deal into sets in snake order, map sets to arms with a seeded shuffle, freeze before practice. Balances weakness across sets and removes builder choice. Never mid-pilot." Assignment runs only once per participant, strictly in the baseline-done state.
- **D06 (Deployment — local-only on MacBook Pro):** All participants use the local SQLite database; no remote auth/roles needed.
- **D08 (Backend stack):** Python 3.12, uv, FastAPI, SQLModel, Alembic, SQLite in WAL mode, Typer CLI, ruff, pyright, pytest.
- **D11 (Generation timing — batch via worker):** "Batch, via a separate worker process. Keep 3 days of ready drills per arm" (§13.7: 2 drills per block $\times$ 3 days = 6 ready drills per arm). The participant transition `assigned -> practice` requires "drill pool ready" (§9.3 Figure 6).
- **D18 (Blinding):** Blocks are labelled `Block 1` to `Block 4`. The builder is flagged as unblinded (`is_builder = True`, `is_blinded = False`). Participant response schemas must not leak unblinded arm assignments to blinded participants.
- **D19 (No cloud, no WASM):** Local-only, standard FastAPI JSON responses and error shapes.
- **D20 (Pre-registration):** `docs/analysis-plan.md` committed with date before first practice session.
- **D28 (`docs/decisions/D28-assignment-observation-threshold.md`):** Candidate observation threshold is 15.
- **Owner decision (2026-10-21 #1):** "Participants. Only the owner (builder) for the pilot, on the owner's Mac. The owner's participant row is `is_builder = true`, `is_blinded = false`. Second-participant features (blinding, separate reporting) stay in the code but are not exercised."
- **Owner decision (2026-10-21 #2):** "Consent. A basic one-paragraph local consent screen; recording `consent_at` is enough."
- **Owner decision (2026-10-21 #4):** "Pilot. 14 days of daily typing, starting as soon as M3 freezes config." ($N = 10$ practice days, 2 baseline sessions, 2 retest sessions).
- **§14 API specification error rule (verbatim):** "Errors use FastAPI's standard shape with a clear detail. Invalid state transitions (for example starting practice before assignment) return 409."
- **§17.1 Engineering standards:**
  - TypeScript strict, Python type hints everywhere, pyright in strict mode for `src/`.
  - Routers are thin. Business logic lives in services. Table models are never returned from the API; use response schemas.
  - Every experiment parameter lives in config, never as a literal inside logic.

  - Ready `Drill` count per enabled arm in `drills`.

- **HTTP responses:**
  - `ParticipantResponse` (DTO schema, never SQLModel table class): `id: str`, `alias: str`, `is_builder: bool`, `is_blinded: bool`, `status: str`, `keyboard_label: str | None`, `consent_at: datetime | None`, `created_at: datetime`.
  - `list[ParticipantResponse]`.
  - `AssignmentSummary` / `AssignmentResponse` (for assign endpoint).
  - `SessionPlan`: blinded blocks.
  - `SessionSummary`: stats and block counts.
  - Standard FastAPI JSON error responses (`{"detail": "..."}`) with HTTP 404 or HTTP 409.
- **Database updates (committed atomically):**
  - `participants.status`:
    - `enrolled` $\rightarrow$ `baseline` (setting `consent_at = utc_now()`).
    - `baseline` $\rightarrow$ `assigned` (upon successful assignment).
    - `assigned` $\rightarrow$ `practice` (when drill pool is ready / first practice session begins).
    - `practice` $\rightarrow$ `retest` (when practice session $N$ completes).
    - `retest` $\rightarrow$ `done` (when retest session 2 completes).
    - any active status $\rightarrow$ `withdrawn` (if withdrawal is invoked).

## 6. Constraints

- **Platform compatibility:** Python 3.12, SQLModel, FastAPI. No imports of `mlx-lm` in services or routers (runs in Linux CI and macOS).
- **HTTP status code requirement:**
  - HTTP 404 Not Found: when participant, session, or block does not exist.
  - **HTTP 409 Conflict:** on **ANY** invalid state transition or phase mismatch (§14 and acceptance criteria).
- **Schema cleanliness (§17.1):** Table models (`Participant`, `Session`, `SessionBlock`) must never be returned from API endpoints. Always return Pydantic response schemas.
- **Thin routers (§17.1):** All state transition validation and database mutations must live in the services layer (`services/participants.py` or dedicated transition service), not inside route handlers.
- **Config-driven (§17.1):** Thresholds and phase targets ($N=10$, `baseline_parts=2`, `retest_parts=2`) must be loaded from `experiment_config`, never hardcoded as literals.
- **Blinding (D18):** Participant-facing schemas and endpoints must never reveal internal arm mappings.
- **Deterministic assignment:** Admin assign endpoint must use seeded randomness `random.Random(f"{assignment_seed}:{pid}")` as established in T2.2.
- **Atomic transactions:** State transitions and session completions must commit atomically; errors roll back completely.

## 7. Edge cases

1. **Unconsented participant attempts to start a baseline session:**
   - *Scenario:* Participant is in `status="enrolled"`. Client calls `POST /api/v1/participants/{pid}/sessions`.
   - *Behaviour:* Must return HTTP 409 Conflict. Participant must consent first.
2. **Participant submits consent when not in `enrolled` status:**
   - *Scenario:* Participant is already in `status="baseline"`, `practice"`, or `"done"`. Client calls `POST /api/v1/participants/{pid}/consent`.
   - *Behaviour:* Must return HTTP 409 Conflict.
3. **Admin attempts assignment before completing all baseline sessions:**
   - *Scenario:* Participant has completed 1 baseline session, but `baseline_parts = 2`. Admin calls `POST /api/v1/admin/participants/{pid}/assign`.
   - *Behaviour:* Must return HTTP 409 Conflict (`BaselineIncompleteError`).
4. **Admin attempts assignment when participant is in an invalid status:**
   - *Scenario:* Participant has `status="enrolled"` or already has `status="assigned"`/`"practice"`. Admin calls `POST /api/v1/admin/participants/{pid}/assign`.
   - *Behaviour:* Must return HTTP 409 Conflict.
5. **Participant attempts to start practice before assignment:**
   - *Scenario:* Participant is in `status="baseline"` (even with 2 completed baseline sessions), but assignment has not been executed. Client calls `POST /api/v1/participants/{pid}/sessions` with `phase="practice"`.
   - *Behaviour:* Must return HTTP 409 Conflict ("starting practice before assignment returns 409", §14).
6. **Participant attempts to start practice when drill pool is not ready:**
   - *Scenario:* Participant is in `status="assigned"`. The generation worker has not generated ready drills (0 ready drills for one or more arms). Client calls `POST /api/v1/participants/{pid}/sessions`.
   - *Behaviour:* Must return HTTP 409 Conflict (`DrillPoolExhaustedError`). Participant remains in `status="assigned"`.
7. **Transition from `assigned` to `practice` when drill pool is ready:**
   - *Scenario:* Participant is in `status="assigned"`. Sufficient ready drills exist for all enabled arms ($\ge 2$ per arm). Client calls `POST /api/v1/participants/{pid}/sessions`.
   - *Behaviour:* Session is planned, and participant status advances to `"practice"`.
8. **Practice session completes before day $N$:**
   - *Scenario:* Participant is in `status="practice"`. Practice session 5 completes (`POST /api/v1/sessions/{sid}/complete`). Configured `practice_days = 10`.
   - *Behaviour:* Participant status remains `"practice"` ("day below N", Figure 6).
9. **Final practice session completes (day $N$):**
   - *Scenario:* Participant is in `status="practice"`. Practice session 10 completes (`POST /api/v1/sessions/{sid}/complete`).
   - *Behaviour:* Participant status transitions from `"practice"` to `"retest"`.
10. **Abandoned practice session does not count toward $N$:**
    - *Scenario:* Participant starts practice session 3, leaves it idle $> 30$ minutes. It becomes `abandoned`. Next practice session completes.
    - *Behaviour:* Only sessions with `status="completed"` count toward $N$. Abandoned sessions are excluded (§9.3).
11. **Retest session 1 completes (part 1 of 2):**
    - *Scenario:* Participant is in `status="retest"`. Retest session 1 completes (`POST /api/v1/sessions/{sid}/complete`). Configured `retest_parts = 2`.
    - *Behaviour:* Participant status remains `"retest"`.
12. **Final retest session completes (part 2 of 2):**
    - *Scenario:* Participant is in `status="retest"`. Retest session 2 completes (`POST /api/v1/sessions/{sid}/complete`).
    - *Behaviour:* Participant status transitions from `"retest"` to `"done"`.
13. **Attempting to start a session when `status == "done"`:**
    - *Scenario:* Participant has completed retest (`status="done"`). Client calls `POST /api/v1/participants/{pid}/sessions`.
    - *Behaviour:* Must return HTTP 409 Conflict.
14. **Attempting to start a session when `status == "withdrawn"`:**
    - *Scenario:* Participant withdrew (`status="withdrawn"`). Client calls `POST /api/v1/participants/{pid}/sessions`.
    - *Behaviour:* Must return HTTP 409 Conflict.
15. **Participant creation with an existing alias:**
    - *Scenario:* Alias `"builder"` already exists in `participants`. Client calls `POST /api/v1/participants` with `alias="builder"`.
    - *Behaviour:* Must return HTTP 409 Conflict (or clean 400/409 duplicate handling).
16. **Builder unblinded constraint violation:**
    - *Scenario:* Request to create participant with `is_builder=True, is_blinded=True`.
    - *Behaviour:* Database check constraint `is_builder = 0 OR is_blinded = 0` rejects this; API must validate and return 422/400/409.

## 8. Risks

1. **State desynchronisation between session completion and participant status:**
   If `complete_session` marks a session completed but fails to update participant status (e.g. unhandled error during count query), the session is complete but the phase never advances, stranding the participant. The session completion and participant status update must be transactional.
2. **Race condition on concurrent session completion or assignment:**
   If multiple requests hit `/sessions/{sid}/complete` or `/admin/participants/{pid}/assign` concurrently, race conditions could attempt duplicate transitions. Transactions with atomic status checks prevent this.
3. **Regression in existing tests expecting `enrolled` to plan baseline sessions:**
   In T2.6, `resolve_session_phase("enrolled") == "baseline"` was tested in `test_session_planner.py`, and test fixtures created participants with default `status="enrolled"` and immediately called `post_participant_session`. Enforcing that `enrolled` participants must consent before starting baseline could fail existing tests if test helpers are not updated to consent or seed `status="baseline"`.
4. **Coupling between assignment and retest form B composition:**
   In `cli.py`, `assign` calls `assign_participant` and then composes form B passages. If form B composition fails or is slow, does the admin endpoint fail or succeed? Pre-composing form B ensures retest passages exist when retest phase begins.
5. **Drill pool readiness definition:**
   Whether "drill pool ready" requires all enabled arms to have the full 3-day target (6 drills per arm) or merely the minimum drills to start 1 session (2 drills per arm).

A participant may withdraw from any active, uncompleted state (`enrolled`, `baseline`, `assigned`, `practice`, `retest`), which sets `participant.status = "withdrawn"`. Calling withdraw on a participant who is already `done` or `withdrawn` returns HTTP 409 Conflict. Any subsequent attempt to start a session, record a block, or complete a session for a `withdrawn` participant returns HTTP 409 Conflict.

3. **Router layout for `/admin` and `/participants`:**
   - *Source:* (a) Design Doc §7 layout (`api/routers/ # participants, sessions, events, analysis, admin`), §14.
   - *Reasoning:* Add `services/api/src/typist/api/routers/admin.py` (prefix `/admin`, tags `["admin"]`) exposing `POST /api/v1/admin/participants/{pid}/assign`. Add `services/api/src/typist/api/routers/participants.py` (prefix `/participants`, tags `["participants"]`) exposing `GET /api/v1/participants`, `POST /api/v1/participants`, `POST /api/v1/participants/{pid}/consent`, `POST /api/v1/participants/{pid}/withdraw`, and `DELETE /api/v1/participants/{pid}` (calling `delete_participant`). Both are registered in `main.py` under `/api/v1`.

4. **Block lifecycle endpoints in scope (`POST /blocks/{bid}/start` and `POST /blocks/{bid}/complete`):**
   - *Source:* (a) Design Doc §14, §16 title ("Remaining participant, session and block API endpoints; state transitions").
   - *Reasoning:* T2.8 implements `POST /api/v1/blocks/{bid}/start` and `POST /api/v1/blocks/{bid}/complete` in a new router `api/routers/blocks.py` (or on `sessions.py`). `start` sets `SessionBlock.started_at` (returns 409 if already started, 404 if missing, 409 if session not in_progress). `complete` sets `SessionBlock.ended_at` (returns 409 if not started or already completed, 404 if missing, 409 if session not in_progress). Both return a blinded `BlockResponse` (`id`, `session_id`, `block_index`, `label`, `started_at`, `ended_at`).

5. **`enrolled` status rejects session creation until consent is recorded:**
   - *Source:* (a) Design Doc §4.2, §9.3 (Figure 6), §11.1, §14.
   - *Reasoning:* In `session_planner.py`, `resolve_session_phase` must reject `status == "enrolled"` with `InvalidSessionPhaseError("participant must give consent before starting baseline")`, returning HTTP 409 Conflict. Consent (`POST /participants/{pid}/consent`) transitions `enrolled -> baseline` and records `consent_at = utc_now()`. Test fixtures starting baseline sessions must record consent or seed `status = "baseline"`.

6. **Form B composition on `POST /admin/participants/{pid}/assign`:**
   - *Source:* (a) Design Doc §8.1 ("set for retest texts composed after freezing"), (d) `services/api/src/typist/cli.py` (`assign` command).
   - *Reasoning:* When `POST /api/v1/admin/participants/{pid}/assign` runs, it executes `assign_participant`, advances `participant.status` from `"baseline"` to `"assigned"`, and if shared form A passages exist, calls `compose_and_persist_retest(session, pid, index)` (ignoring `BaselinePassagesNotFoundError` if form A is uncomposed in synthetic tests).

7. **Participant status advancement on session completion:**
   - *Source:* (a) Design Doc §9.3 (Figure 6), §10.1, §14 ("Compute stats, update phase, enqueue jobs").
   - *Reasoning:* In `post_session_complete` / `complete_session`:
     - If completed session is `phase == "practice"`, count completed practice sessions for participant. If `completed_count >= config.practice_days` (10), transition `participant.status` from `"practice"` to `"retest"`.
     - If completed session is `phase == "retest"`, count completed retest sessions for participant. If `completed_count >= config.retest_parts` (2), transition `participant.status` from `"retest"` to `"done"`.
     - Both updates commit transactionally with session completion. Attempting to start further sessions once `done` returns 409.
